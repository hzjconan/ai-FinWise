# AI Agent 开发学习路线图

> 面向对象：有多年编程经验、但对 AI 领域不熟悉的工程师。
> 核心思路：以**工程师视角**切入——把 LLM 当成一个不确定性的、按 token 计费的远程函数来集成；学完再学框架，先建立底层直觉。
> 练兵场：本仓库 FinWise（已有 AI 对话 / 智能评估 / 推荐功能），学习与实战绑定。

本文档是 **A. 学习路线图**。配套还有：

- **B. 实战清单**（`01-practice-with-finwise.md`）——每个阶段对应本仓库哪个功能、怎么改。
- **C. 阶段三专题**（`02-tooluse-refactor.md`）——把现有 AI 对话改造成标准 tool-use agent。

## 0. 心智模型的转变（贯穿始终）

传统编程与 LLM 编程的根本差异，先内化这张表，后面每个阶段都在处理它带来的后果：

| 维度 | 传统编程 | LLM 编程 |
|---|---|---|
| 执行 | 确定性逻辑，同输入同输出 | 概率性推理，同输入可能不同输出 |
| 正确性 | 有"正确答案"，单元测试断言相等 | 只有"足够好"，靠 eval 衡量分布 |
| 状态 | 进程/DB 持有状态 | 模型无状态，上下文即内存，每次重新喂 |
| 代码 | 源码是逻辑 | **prompt 也是代码**，要版本管理/测试/review |
| 成本 | CPU/内存，基本免费 | 按 token 计费 + 按 token 限长，成本与延迟是一等公民 |

**验收：** 能用自己的话向别人解释"为什么 AI 功能要写 eval 而不只是单元测试"。

## 阶段一：LLM API 基础（约 1 周）

**目标**：能直接裸调 API，理解每个参数在干什么。**不要用框架**（LangChain 等），框架会掩盖底层机制。

**核心概念**
- token / context window：文本如何被切分、上限意味着什么
- 采样参数：`temperature`、`top_p`、`max_tokens`
- 消息角色：`system` / `user` / `assistant`，多轮如何拼装
- 流式输出（streaming）——本仓库"对话气泡"就依赖它
- 成本与延迟的量级感知（一次调用大概多少 token、多少钱、多少毫秒）

**学习方式**
1. 用 Anthropic SDK（Python 或 TS）写 10 行代码完成第一次调用。
2. 逐个参数做对照实验：把 temperature 从 0 调到 1，观察输出变化。
3. 实现一个命令行多轮对话（自己维护 messages 数组）。
4. 打印每次调用的 token 用量，算出单次成本。

**推荐资源**
- 本仓库内置 `/claude-api` 参考（模型 ID、定价、参数、流式、tool use、缓存）——查这个，别凭记忆。
- Anthropic 官方文档 Messages API。

**验收**
- [ ] 不看示例能写出一次带 system prompt 的流式调用。
- [ ] 能解释 temperature=0 和 =1 的差别及各自适用场景。
- [ ] 能说出一次典型调用的 token/成本量级。

## 阶段二：Prompt Engineering（约 1 周，边做边学）

**目标**：能稳定地让模型产出你想要的东西，尤其是**结构化输出**。

**核心概念**
- 结构化 prompt：角色设定、指令、示例（few-shot）、输出格式约束
- 让模型输出 JSON / 结构化数据（这是 agent 的地基）
- Chain-of-thought：给模型"思考空间"再给答案
- 常见失败模式：幻觉、指令漂移、格式跑偏，以及对应的防御手法

**学习方式**
1. 拿一个真实任务（如：把用户风险问卷答案总结成一句话），写 5 个版本的 prompt 对比效果。
2. 强制模型只输出 JSON，故意用刁钻输入试它破格，再加约束修复。
3. 对比"直接要答案" vs "先分析再给答案"的质量差异。

**验收**
- [ ] 能让模型对 20 条不同输入都稳定输出可解析的 JSON。
- [ ] 有一份自己的 prompt 结构模板（角色/指令/示例/格式）。
- [ ] 能识别一次坏输出属于哪种失败模式。

## 阶段三：Tool Use / Function Calling（约 1–2 周）★ Agent 的核心

**目标**：从"聊天机器人"跨越到"agent"——让模型能调用你的函数、连续行动直到完成任务。这是整个路线的分水岭。

**核心概念**
- 工具调用循环：定义工具 schema → 模型决定调用 → 你执行 → 结果回传 → 模型继续
- **手写 agent loop**：一个 while 循环让模型连续调用多个工具
- ReAct 模式（Reasoning + Acting 交替）
- 并行工具调用、错误处理、终止条件

**学习方式**
1. 定义 1 个工具（如查天气/查数据库），跑通一次完整往返。
2. **亲手写 agent loop**，不用任何框架——一旦写过这个循环，所有 agent 框架都会变透明。
3. 加到 2–3 个工具，让模型自主决定调用顺序完成一个多步任务。
4. 详见配套文档 C：把本仓库 AI 对话改造成 tool-use agent。

**验收**
- [ ] 能不依赖框架，手写一个能连续调用多工具的 agent loop。
- [ ] 能画出 tool-use 一个完整回合的时序（谁调谁、消息怎么流转）。
- [ ] 能处理工具报错并让 agent 恢复。

## 阶段四：RAG / 上下文工程（约 1–2 周）

**目标**：让模型能用它没见过的私有数据/超长数据回答问题。

**核心概念**
- 为什么需要 RAG：模型不知道你的私有数据，或数据太多塞不进 context
- Embedding、向量数据库、语义检索
- Chunking 策略、检索质量、重排（rerank）
- **上下文工程**：什么该进 context、放多少、如何压缩历史（与本仓库多轮对话直接相关）

**学习方式**
1. 把一小批文档（如 FinWise 产品说明）做 embedding 存入向量库。
2. 实现"检索 → 拼进 prompt → 回答"的最小 RAG。
3. 故意用不同 chunk 大小观察检索质量变化。

**验收**
- [ ] 能解释 embedding 检索为什么比关键词匹配强。
- [ ] 跑通一个能引用私有文档作答的最小 RAG。
- [ ] 能说出多轮对话历史过长时你会怎么压缩。

---

## 阶段五：评估与可观测性（约 1 周）★ 生产的分水岭

**目标**：给不确定输出建立可回归的质量防护。这是业余与专业的区别，也直接对应本仓库"每次改动必须有测试"的硬约束——**AI 功能的"测试"就是 eval**。

**核心概念**
- 给不确定输出写测试：LLM-as-judge、规则断言、golden set（黄金样例集）
- Tracing / observability：看清 agent 每一步在想什么（LangSmith、Langfuse 等）
- 回归防护：改了 prompt 会不会让别的 case 变差

**学习方式**
1. 为某个 AI 功能收集 10–20 条 golden 样例（输入 + 期望要点）。
2. 写一个 eval 脚本：规则断言能测的先测，主观质量用 LLM-as-judge。
3. 接一个 tracing 工具，观察一次 agent 运行的完整轨迹。

**验收**
- [ ] 有一套能一键跑的 AI 功能 eval。
- [ ] 改 prompt 后能立刻看到分数升降。
- [ ] 能在 trace 里定位到 agent 哪一步出了问题。

---

## 阶段六：框架与多 Agent（约 2 周）

**目标**：有了底层直觉后，学框架就是"哦原来它帮我封装了这个"。

**核心概念**
- 主流框架深入其一：**Claude Agent SDK**（与本仓库技术栈最契合）、LangGraph、或 OpenAI Agents SDK
- 多 agent 编排：任务分解、agent 间通信、supervisor 模式
- 记忆系统、长期任务、human-in-the-loop

**学习方式**
1. 用框架重写你在阶段三手写的 agent，对比它替你做了什么。
2. 搭一个 2-agent 协作（如"检索 agent + 写作 agent"）。

**验收**
- [ ] 能说清所选框架的核心抽象分别对应你手写过的哪部分。
- [ ] 跑通一个多 agent 协作任务。

---

## 阶段七：生产化（持续）

**目标**：把 demo 变成能上线的东西。

**核心概念**
- 成本优化：prompt caching、模型分级（简单任务用小模型）、缓存
- 延迟优化：流式、并行工具调用
- 安全：prompt injection、越权、输出校验、guardrails
- 可靠性：重试、超时、降级

**验收**
- [ ] 能列出本仓库 AI 功能的三个主要成本/延迟/安全风险及对策。

---

## 学习节奏与三条铁律

**建议节奏**：阶段一~五约 5–7 周（每周投入以你的经验可压缩），阶段六~七随实战推进。

1. **以战养兵**：别学完再动手，拿本仓库现有 AI 功能当练习场（见文档 B）。
2. **裸调优先**：前四阶段坚持不用重框架，建立别人没有的底层直觉。
3. **给 AI 功能建 eval**：符合"改动必须有测试"，最容易被跳过、回报最高。
