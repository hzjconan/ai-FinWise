### 两个值得记的设计点
- **R1 保持 provider 无关**：provider 特有的异常分类留在 client 层（它才认识 Anthropic 异常类），chat_service 只认抽象 `NonRetryableLLMError` 标记。换 provider 只改对应 client，chat_service 一行不动。
- **S2 是纵深防御的完整落地**：软约束（prompt 隔离声明，让模型大概率忽略注入）+ 硬保证（B#7 定级去模型化，等级由代码从维度分算——就算模型被诱导，注入也改不了结论）。一层被绕另一层兜。

## 二、暂不改项（剩哪些 + 为什么）

| # | 类 | 状态 | 为什么不改 |
|---|---|---|---|
| **S1** | 安全 | ⏸ 业务选择 | 客户匿名（`/customer/anonymous`，code 即身份）是**有意业务设计**（匿名理财评估、免注册）。"无认证"不是 bug 是业务约束；`customer_code` 即匿名凭证。根治=引入账户体系，违背业务。缓解建议：code 高熵难猜（凭证要害）+ 防泄露（呼应 S3）。**一课：风险要放业务约束里看，准确定性+上报，而非打补丁掩盖。** |
| **C1** | 成本 | ⏸ 需真 API | prompt caching（system prompt 每轮重复计费）真实降本，但需 `cache_control` + 真 Anthropic API 验证（bridge 不支持缓存）。学习环境无真 key，记录为上线优化项。 |
| **C2** | 成本 | ⏸ 记设计 | 单会话/单用户 token 预算 + 用量监控。生产必要，但需接监控体系（配合 tracing）。设计已在基线记录，本轮不实现。 |
| **R2** | 可靠 | ⏸ 改动较大 | LLM 挂了降级到确定性问卷评估（`risk_calculator` 是现成降级目标）。有价值但改动跨路由+前端交互，超本轮范围。 |
| **L2** | 延迟 | ⏸ 看需求 | 并行工具调用。当前评估流程串行足够；真出现"一轮查多个产品"的并行需求再做。 |

## 四、小结（阶段七收获）

**本轮动手**：R1（重试策略）、L1（超时）、S2（注入隔离）、S3（错误不外泄）——4 项，均带测试，139→140 passed。

**生产化体检的真正一课**（不只是改代码）：
1. **风险放业务约束里看**——S1"越权"在匿名设计里是固有属性，正确处理是准确定性+上报，不是打补丁（若强行加认证反而破坏业务）。
2. **纵深防御**——S2 软约束+硬保证两层；单靠 prompt 不可靠，硬校验兜底才是关键。
3. **provider 无关别破坏**——R1 修复时把 provider 特有分类下沉 client，保持抽象。
4. **"不改"也是决策**——C1/C2/R2/L2 记录设计与理由、暂不实现，比盲目全改更专业（呼应阶段五"数据不足→不改也是结论"）。

对应 roadmap 阶段七验收「列出三个主要成本/延迟/安全风险及对策」：✅ 超额（安全 S1/S2/S3、成本 C1/C2、延迟 L1/L2、可靠 R1/R2 全覆盖，各给对策与取舍）。
