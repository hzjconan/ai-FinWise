## 题 1 · 分布式任务保证只执行一次

> 🔁 **回顾**：L05 第 5 步 **至少一次 + 幂等 = 效果上恰好一次**；第 6 步多实例时进程内的控制只管自己、全局要靠 Redis；L03 幂等键靠**唯一索引**保证原子。

**场景**：每天 02:00 定时"给所有客户结算当日收益"，后端 **3 个实例**都配了这个定时任务：
```
02:00:00  实例 A / B / C 同时触发 → 每个客户收益被加 3 次 ❌
```
根源不在定时任务本身，而在"**多个实例各自都觉得该自己执行**"。

### 1.1 Redis 分布式锁

```
SET lock:settle:2026-10-28  instance-A-7f3c  NX  PX 600000
```
| 部分 | 含义 | 为什么 |
|---|---|---|
| `lock:settle:2026-10-28` | 锁名**带日期** | 今天的锁不能挡住明天 |
| `instance-A-7f3c` | 值 = **持有者唯一标识**（实例名 + 随机串） | 释放时比对用 |
| `NX` | Not eXists：key 不存在才设置成功 | "检查 + 占住"**一条命令原子完成**，同时抢只有一个成功 |
| `PX 600000` | 10 分钟后自动过期 | 持有者崩溃也会自动释放 |
- ⚠️ 不能拆成"先 GET 再 SET"：两个实例可能同时 GET 到"没人占"然后都 SET（同 L03"先查后插"）。

### 1.2 释放锁：原子地比对再删

```
02:00  A 抢到锁（10 分钟），开始结算
02:10  A 没跑完，锁到期自动删除 → B 抢到锁开始结算
02:12  A 跑完 DEL → 删掉的是 B 的锁 → C 又抢到
```
- 先比对再删若是**两条命令**，比对后、删除前锁到期被 B 抢到，照样删掉 B 的 → 用 **Lua 脚本**（执行期间不插入其他命令）：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0      -- 已经不是我的锁，什么都不做
end
```

### 1.3 锁过期但任务没跑完：续期 + 唯一约束

**续期（看门狗 watchdog，Java Redisson 的叫法）**：拿到锁后后台每隔过期时间的 1/3 检查，锁仍是自己的就重设为 10 分钟；结束时停止续期并释放。进程崩溃续期也停 → 照样会过期。
⚠️ 不是 100% 可靠：A **卡住**（长时间垃圾回收暂停、与 Redis 网络中断）无法续期 → 锁过期 B 抢到 → A 恢复后**不知道锁已没了**继续执行 → **单靠锁永远做不到绝对只有一个人执行**。

**唯一约束（写数据层的最后保证）**：
```sql
CREATE TABLE settlement_records (
    customer_id  INT,
    settle_date  DATE,
    amount       DECIMAL,
    UNIQUE (customer_id, settle_date)          -- 同一客户同一天只能一条
);
BEGIN;
INSERT INTO settlement_records (customer_id, settle_date, amount) VALUES (1001, '2026-10-28', 12.34);
    -- 已有 → 违反唯一约束 → 这个客户跳过、不加余额
UPDATE accounts SET balance = balance + 12.34 WHERE customer_id = 1001;
COMMIT;
```
- ⚠️ 插入记录和更新余额**必须同一事务**，否则"记录有、余额没加"或反过来。

| | 分布式锁（+ 续期） | 唯一约束 / 幂等 |
|---|---|---|
| 作用 | **尽量**只让一个实例执行，减少重复劳动 | **保证**结果只生效一次 |
| 失效时 | 偶尔两个实例同时执行 | 不失效（数据库保证） |
| 定位 | **优化** | **正确性底线** |
→ **锁为效率，唯一约束为正确性**，两者一起用。

### 1.4 中途崩溃：状态表 + 心跳 + 重跑

- `task_runs` 表：`pending` → `running`（记心跳时间）→ `done`；
- 一直 `running` 且心跳很久没更新 → 判定执行者已挂，允许别的实例接手；
- 接手者**从头再跑也没关系**：已结算的客户因唯一约束直接跳过 → **至少一次 + 幂等 = 恰好一次**。

### 💬 课堂问答

> 🙋 **问**：3 个实例（不同进程、甚至不同机器），用什么办法只让一个执行？  
> 🧑 **我的回答**：用 Redis 分布式锁，抢到锁的实例才执行  
> 🤖 **点评**：✅ 最常见的第一反应；要点见 1.1（NX 原子、带过期、值存持有者标识、不能拆 GET + SET）。

> 🙋 **问**：02:12 A 的 `DEL` 删掉谁的锁？锁值为什么存持有者标识、释放时怎么用？  
> 🧑 **我的回答**：删的是 B 的锁；释放时先比对值再删  
> 🤖 **点评**：✅ 删掉 B 的 → C 又抢到、B 和 C 同时跑。⚠️ 比对和删除若是两条命令仍有漏洞 → **Lua 脚本原子执行**（1.2）。

> 🙋 **问**：释放写对了，02:10~02:12 A 和 B 仍同时在结算，怎么办？（方向 1：别让锁在任务没跑完时过期；方向 2：写数据层让同一客户同一天只记一次）  
> 🧑 **我的回答**：给锁续期，再加唯一索引保证每天只记一次  
> 🤖 **点评**：✅ 两个方向都答到且组合正确。⚠️ 续期在卡顿 / 网络中断时会失效 → 锁永远不绝对 → 唯一约束是底线（1.3）；➕ 再补崩溃恢复（1.4）。

### 📝 面试版答案

> 核心：**用锁减少重复执行，用幂等保证结果正确**。① **分布式锁**：`SET key 持有者标识 NX PX 过期时间`，NX 原子抢锁，过期防持有者崩溃后不释放；释放用 Lua **原子比对标识再删**，防删别人的锁；执行可能超过过期时间 → **看门狗续期**。② **锁不绝对可靠**：卡顿 / 网络中断无法续期、锁过期，可能两个实例同时执行 → **数据层唯一约束**（同一客户同一天一条结算记录），插记录和改余额同一事务，重复执行只生效一次。③ **崩溃恢复**：任务状态表 + 心跳，超时允许别的实例接手重跑，靠幂等跳过已处理部分 → **至少一次 + 幂等 = 效果上恰好一次**。

## 题 2 · 订单支付时正好超时取消

> 🔁 **回顾**：题 1"先 GET 再 SET"不原子，两个进程可能同时看到"没人占"；L05 第 4 步补偿 = 做相反的业务动作（撤单、退款）。

**场景**：下单后"待支付"，30 分钟不付自动取消。
```
10:00:00  用户下单，订单 #8801 = 待支付
10:29:59  用户在支付宝付款成功 → 支付宝开始发"支付成功"回调
10:30:00  延时任务到点执行"超时取消"；同一时刻支付回调到达
```
```python
# 超时取消任务                          # 支付成功回调
order = db.get(8801)                    order = db.get(8801)
if order.status == "待支付":            if order.status == "待支付":
    order.status = "已取消"                 order.status = "已支付"
    release_stock(order)                    db.commit()
    db.commit()
```

### 2.1 问题：两边都读到"待支付"

| 最后提交的是 | 订单状态 | 问题 |
|---|---|---|
| 取消任务 | 已取消 | **钱扣了、订单没了**，用户投诉 |
| 支付回调 | 已支付 | 看似没事，但额度已被**释放**、可能被别人买走 → **超卖** |
→ 都不一致，且**偶发**（恰好同时才出现），测试很难复现。

### 2.2 状态机 + 条件更新（CAS）

**CAS**（Compare-And-Swap，比较并交换）："状态是预期值才改成新值"，一条语句原子完成。
```python
rows = db.execute(
    "UPDATE orders SET status='已取消' WHERE id=8801 AND status='待支付'"
).rowcount
if rows == 1:
    release_stock(order)          # 只有抢到的一方执行后续动作，与 UPDATE 同一事务
    db.commit()
# rows == 0：已被支付回调抢先改掉，什么都不做
```
- 为什么只有一条成功：UPDATE 给这一行**加锁**，后到的**等前一条提交**后**重新判断 WHERE**，状态已不是"待支付" → 影响行数 0。
- **不需要分布式锁**：单行状态变更数据库行锁就够；面试答案里"或 Redis 分布式锁"也行但多一个组件、还有过期问题 → **能用数据库条件更新的就别上分布式锁**。
- ➕ 本质是**状态机**：只允许"待支付 → 已支付 / 已取消"，每次变更把"从哪个状态来"写进 WHERE，非法变化自然失败。

### 2.3 输掉的一方：补偿 + 回调幂等

- **自动退款 = Saga 补偿**（钱已扣撤不回，做相反动作）：退款请求用**支付流水号作退款请求号**保证幂等；失败重试、多次失败转**人工**；通知用户"已超时取消，款项原路退回"。
- **回调去重**：
```sql
CREATE TABLE payment_callbacks (
    trade_no  VARCHAR PRIMARY KEY,      -- 支付宝流水号，天然唯一
    order_id  INT,
    status    VARCHAR
);
```
  先插记录，重复 → 已处理过，直接返回成功；处理完一定**返回成功响应**支付宝才停止重发（处理失败返回错误则借重发重试）；➕ 回调要**验签**，防伪造"支付成功"。

### 2.4 从源头减少冲突

```
到期 → 先调支付渠道"关闭交易"接口
       ├─ 关闭成功 → 用户再也付不了 → 安全改为已取消
       └─ 失败且原因是"已支付" → 钱已付只是回调没到 → 按已支付处理
```
→ 不再出现"取消了但钱已扣"，退款只是最后兜底；回调可能延迟，取消前**主动查一次支付状态**也常见。

### 💬 课堂问答

> 🙋 **问**：两段"先查再改"同时执行会怎样？最终状态？用户和公司各遇到什么麻烦？  
> 🧑 **我的回答**：两边都读到待支付，订单被取消但钱已扣  
> 🤖 **点评**：✅ 对。➕ 最终状态取决于谁**最后提交**：已取消 → 钱扣了订单没了；已支付 → 额度已释放可能**超卖**；且偶发难复现（2.1）。

> 🙋 **问**：怎么保证只有一方成功？（提示：题 1 的 NX 把检查 + 设置合成一条；UPDATE 也能带条件）  
> 🧑 **我的回答**：UPDATE 加 WHERE status='待支付'，看影响行数是否为 1  
> 🤖 **点评**：✅ 完全正确 = **CAS 条件更新**；行锁 + 重新判断 WHERE 保证只有一条成功；不需要分布式锁；本质是状态机（2.2）。

> 🙋 **问**：取消抢先、回调影响行数 0，但钱已被扣：1）回调该做什么？2）支付宝没收到成功响应会重复回调，什么问题、怎么防？  
> 🧑 **我的回答**：自动退款；用支付流水号做唯一索引去重  
> 🤖 **点评**：✅ 两点都对。➕ 退款就是 Saga 补偿：退款请求幂等、失败重试转人工；去重后**返回成功**才停重发、要验签；➕ 源头上先"关闭交易"再取消（2.3、2.4）。

### 📝 面试版答案

> 根本问题："**先查状态再改状态**"不原子，取消任务和支付回调可能同时读到"待支付"，结果钱扣了订单被取消，或额度已释放又标记已支付（超卖）。① **状态机 + 条件更新**：`UPDATE orders SET status=? WHERE id=? AND status='待支付'`，**影响行数是否为 1** 判断是否抢到；行锁保证只有一方成功，无需分布式锁；成功方才执行后续动作（释放额度、发货），与状态变更同一事务。② **输的一方补偿**：回调发现已取消但钱已扣 → **自动退款**，退款用支付流水号幂等，失败重试转人工。③ **回调幂等**：渠道会重发，**流水号唯一索引**去重，处理完返回成功，回调验签。④ **源头减少冲突**：超时取消前先调渠道"关闭交易"，成功再取消，返回已支付则按已支付处理。

## 题 3 · 验证码系统

> 🔁 **回顾**：L05 第 6 步令牌桶、按用户限流；题 2 比较并修改要**原子**完成。

**场景**：手机号 + 短信验证码登录。最简单版本：
```
发送：输入手机号 → 生成 6 位随机数 → 存 Redis 5 分钟过期 → 调短信服务
校验：提交手机号 + 验证码 → 和 Redis 比对 → 一致就登录
```
能用，但公网上会被攻击 → 分**发送侧**和**校验侧**。

### 3.1 发送侧：防短信轰炸、刷费用

发送接口**不登录就能调**、每条短信都要付费（几分钱）。

| 维度 | 规则举例 | 主要防什么 |
|---|---|---|
| **同一手机号** | 60 秒 1 条、每天最多 10 条 | **短信轰炸**：换再多 IP，受害者手机号也被限住 |
| **同一 IP / 设备** | 每小时最多 20 条 | 一台机器批量换号刷 |
| **全局** | 每天总量 / 总费用上限，超了告警 | **刷费用**：大量 IP + 大量号码绕过前两层时的最后防线 |
| **人机校验**（滑块、图形验证码） | 发送前先过 | 拦自动化脚本，大幅提高攻击成本 |
```
SET sms:interval:13800001111  1  NX  EX 60        ← 设置成功才发，60 秒内再发失败（题 1 的 NX）
INCR sms:daily:13800001111:2026-10-28              ← 当天计数，超过 10 拒绝
EXPIRE sms:daily:13800001111:2026-10-28  86400
```
- ➕ **短信流量欺诈**（SMS pumping）：让系统往攻击者控制的**高价号码**（某些国际号段）发短信，再从运营商分成 → 只面向国内就**只允许国内号段**。

### 3.2 校验侧：防暴力破解、重复使用

- **暴力破解**：6 位 = 100 万种；不限次数、每秒 1000 次约 17 分钟试完；5 分钟内能试 30 万次 → **单个验证码 30% 被猜中**，过期再发新的继续猜 → 几轮就进去。
- **① 限制每个验证码错误次数**：
```
Redis：sms:code:login:13800001111 → {code: "482913", attempts: 0}   5 分钟过期
错误 → attempts + 1；达到 5 次 → 删除验证码，必须重发
```
  猜中概率 5 / 1,000,000（十万分之五），加发送侧每天 10 条 → 一天最多 50 次机会。➕ 再按手机号 / IP 统计一段时间内错误总数（如 1 小时超 20 次）→ 暂时锁定登录，防换验证码持续尝试。
- **② 成功后立即、原子地删除**：用过还留着 → 偷看到 / 日志泄露的验证码 5 分钟内能**重复使用**。⚠️ "先 GET 比对再 DEL"会让两个同时提交正确验证码的请求都通过（同题 2）→ 用 `GETDEL`（Redis 6.2+，取值同时删除）或 Lua，只有真正删掉的那个请求算成功。

| ③ 其他细节 | 原因 |
|---|---|
| key 含**手机号 + 场景**（`login`、`reset_password`） | A 的验证码不能登 B；登录验证码不能拿去重置密码 |
| **安全随机数**：`secrets.randbelow(10**6)`，不用 `random` | `random` 序列可预测，拿到几个样本可能推算下一个 |
| **不写进日志** | 日志很多人能看到 |
| 是否注册都返回"验证码已发送" | 否则可探测哪些手机号是用户 |

### 💬 课堂问答

> 🙋 **问**：发送接口不登录可调、每条要付费，攻击者怎么滥用？怎么防？  
> 🧑 **我的回答**：短信轰炸别人和刷费用，按手机号/IP 限频加人机校验  
> 🤖 **点评**：✅ 都说中。➕ 限频分层（手机号防轰炸、IP / 设备防批量、全局上限防刷费用）、Redis `SET NX EX` + `INCR` 实现、短信流量欺诈 → 限制号段（3.1）。

> 🙋 **问**：1）知道手机号、不知道验证码，怎么登录？怎么防？2）校验成功后验证码还留 5 分钟有什么风险？  
> 🧑 **我的回答**：1.不知道 2.有可能被重复利用  
> 🤖 **点评**：第 2 问 ✅ → 成功后立即删除（一次性）。第 1 问拆小：6 位有多少种？不限次数每秒 1000 次多久试完？该限制什么？  
> 🧑 **我的回答**：100万种，1000秒约17分钟；限制每个验证码的错误尝试次数  
> 🤖 **点评**：✅ 算对、防法是标准做法。➕ 不需要试完：5 分钟 30 万次 = 30% 命中，过期再发继续猜；限 5 次后十万分之五；再加按手机号 / IP 错误总数锁定；删除要原子（`GETDEL` / Lua）（3.2）。

### 📝 面试版答案

> 分发送侧和校验侧。**发送侧**（防轰炸、刷费用）：发送前**人机校验**；**多层限频**——同一手机号 60 秒 1 条、每天最多 10 条，同一 IP / 设备每小时上限，全局短信量和费用上限并告警；只允许业务需要的号段防短信流量欺诈；Redis `SET NX EX` 控间隔、`INCR` 计每天条数。**校验侧**（防暴力破解、重复使用）：**安全随机数**生成，存 Redis、key 含**手机号 + 场景**、5 分钟过期；**每个验证码最多错 5 次**即作废，并按手机号 / IP 统计错误总数超阈值暂时锁定；成功后 `GETDEL` / Lua **原子取出并删除**，保证一次性。验证码不写日志，返回信息不透露手机号是否注册。

## 题 4 · 短链接系统

**场景**：营销短信里放产品页链接 `https://www.finwise.com/products/detail?code=REC-001&channel=sms&campaign=2026-double11&utm_source=...` 太长、不可信 → `https://fw.cn/aZ3kP9` 点击后跳转。核心两件事：**生成**（长链接 → 短码，存对应关系）、**跳转**（短码 → 查长链接 → 让浏览器跳）。

### 4.1 短码生成：哈希 vs 发号

| | A. 哈希截取（如 MD5 前几位） | B. 自增 ID 转 62 进制 |
|---|---|---|
| 冲突 | MD5 128 位截 6 位**很可能冲突** → 每次先查库、被占就加随机内容重算，链接越多冲突越频繁 | 每个 ID 只分配一次，**天然不冲突** |
- **62 进制**：`0-9`（10）+ `a-z`（26）+ `A-Z`（26）= 62；反复除 62 取余：`125 ÷ 62 = 2 余 1 → "1"`，`2 ÷ 62 = 0 余 2 → "2"` → `"21"`。

| 短码长度 | 能表示数量 |
|---|---|
| 6 位 | 62⁶ ≈ **568 亿** |
| 7 位 | 62⁷ ≈ **3.5 万亿** |
- 分布式部署时 ID 用号段 / 雪花算法这类发号器生成。

### 4.2 跳转：301 vs 302

| 状态码 | 含义 | 浏览器行为 |
|---|---|---|
| **301** | Moved Permanently，永久 | **缓存**跳转关系，下次直接去长链接，不再访问短链接服务 |
| **302** | Found，临时 | 每次都先访问短链接服务 |
- 营销要**统计点击**、活动后**失效** → **302**。
- 代价：每次点击都打到服务端，短信一发几十万条点击集中涌来 → 映射放 **Redis 缓存**（**读远多于写**：生成一次、点击成千上万次）。
- 301 适用：永久不变、不需统计（网站换域名，搜索引擎会转移权重）。

### 4.3 安全：自增短码可被枚举

```
张三的链接：https://fw.cn/aZ3kP9 → 下一个 aZ3kPA → 再下一个 aZ3kPB
```
长链接带个人信息（"您的专属理财方案"带客户编号）时，有人能**猜出别人的短链接并访问**（🔁 L03 IDOR）。

- **做法 1：随机短码**：
```python
code = "".join(secrets.choice(ALPHABET_62) for _ in range(8))   # 8 位随机
INSERT INTO short_links (code, long_url) ...                     # code 唯一约束，撞了重新随机
```
  完全无规律。和方案 A 的区别在**空间大小**：62⁸ ≈ 218 万亿，存 1 亿个链接时撞上的概率约**两百万分之一**，偶尔撞上靠唯一约束发现重试；方案 A 是截取的哈希本身易冲突且无法"换一个"。
- **做法 2：保留自增 ID，先打乱再转 62 进制**——一一对应的**乘法取模**：
```
打乱后的数 = (ID × 一个大数) mod 总空间        要求：大数与总空间互质（最大公约数为 1）

小例子（总空间 10、乘数 3）：
ID：        1  2  3  4  5  6  7  8  9
× 3 mod 10：3  6  9  2  5  8  1  4  7      ← 无重复、相邻不再相邻
```
  互质 → **一一对应**、不冲突；实际总空间取 62⁶、乘数选和它互质的大数；现成库 Sqids（前身 Hashids）。⚠️ 只是**混淆不是加密**，样本够多可能反推 → 只提高门槛。

| 防线 | 作用 | 地位 |
|---|---|---|
| 页面后端**鉴权** | 猜到了也看不了 | **必须有** |
| 长链接不放敏感信息（用一次性随机令牌 / 要求登录） | 泄露也没价值 | 应该有 |
| 随机或混淆短码 | 很难猜 | 提高门槛 |
| 限制访问**不存在短码**的频率（🔁 L05 第 6 步限流） | 发现并阻止枚举 | 提高门槛 |

### 💬 课堂问答

> 🙋 **问**：A 哈希截取前几位会有什么问题？B 数字怎么"转换成更短的表示形式"（可用 `0-9a-zA-Z`）？  
> 🧑 **我的回答**：A 会哈希冲突；B 转成 62 进制  
> 🤖 **点评**：✅ 两个都对。➕ A 冲突要查库重试、越多越频繁；B 天然不冲突；62 进制转换方法与容量（4.1）。

> 🙋 **问**：营销要统计点击、活动后失效，跳转用 301 还是 302？  
> 🧑 **我的回答**：选 302，每次点击都经过服务端，能统计和失效  
> 🤖 **点评**：✅ 正是面试答案"302 临时重定向"的原因。➕ 代价是服务端压力 → Redis 缓存（读多写少）；301 适合换域名（4.2）。

> 🙋 **问**：自增短码连续，有人拿到自己的短链接会做什么？怎么防（短码本身 / 长链接里放什么）？  
> 🧑 **我的回答**：可能猜出别人页面的短链接并访问。首先，实际的页面对应的后段要做鉴权，但是我不知道短码本身要怎么处理才能不体现出规律性。  
> 🤖 **点评**：✅ 先说**鉴权**抓住重点——短码再难猜也可能经转发 / 截图 / 日志泄露，后端必须校验"当前登录的人是不是页面主人"（同 L03 IDOR）。➕ 短码去规律两种做法：随机短码（空间大 + 唯一约束重试）、乘法取模打乱自增 ID（互质 → 一一对应）；再加长链接不放敏感信息、限制访问不存在短码（4.3）。

### 📝 面试版答案

> 核心是"短码 → 长链接"映射 + 重定向。① **生成**：**自增 ID 转 62 进制**（`0-9a-zA-Z`），天然不冲突，6 位约 568 亿；哈希截取会冲突、每次查库重试；分布式用号段 / 雪花算法发号。② **跳转用 302**：每次点击经过服务端，能统计、能过期失效；301 被浏览器缓存后看不到后续点击。③ **性能**：读远多于写，映射放 **Redis 缓存**。④ **安全**：自增让短码**可枚举** → **随机短码**（空间足够大 + 唯一约束重试）或乘法取模 / Sqids **打乱 ID**；但只提高门槛，**真正防线是页面后端鉴权**，长链接不放敏感信息，限制访问不存在短码的频率以发现枚举。

## 四题共同的思想

| 思想 | 体现 |
|---|---|
| **原子的检查 + 修改** | 题 1 `SET NX`、Lua 比对删除；题 2 `UPDATE … WHERE status=…`；题 3 `GETDEL` |

| **不信"知道了就能用"** | 题 3 验证码一次性、限错误次数；题 4 后端鉴权 |
