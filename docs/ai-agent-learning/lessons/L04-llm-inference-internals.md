## 第 1 步 · 总览：一个请求在模型里的旅程

### 🔁 回顾
1. **自回归**（05 讲义）：每步只预测下一个 token，写出来后作为输入预测下一个 → 已写的影响后面写的。
2. **Transformer / 注意力 / 多头**（concepts-basics）：很多层叠起来；注意力 = 处理一个词时该多看哪些别的词；多头 = 多角度同时看。
3. **流式输出**（阶段一、04 第七节）：回答一小段一小段推送。

```
"推荐个低风险的产品"
  ① Tokenizer：切成 token、换成编号             → [8732, 1045, 3301, ...]
  ② Embedding：编号查表变向量 + 位置信息          → 每个 token 一个几千维向量
  ③ N 层 Transformer：每层注意力 + 前馈计算        → 向量被一层层"加工"
  ④ 输出层：用最后一个位置的向量算出词表里每个 token 的分数（logits）
  ⑤ 采样：按分数和 temperature 等挑一个 token     → "我"
  ⑥ 接到末尾回到 ②~⑤，直到生成"结束"标记或达到 max_tokens
```

> **💬 课堂问答**
>
> **🙋 问**：prompt 1000 token、生成 200 token。如果每轮都把目前全部 token 完整重算（最后一轮 1199 个），有什么问题？怎么避免？（提示：第 100 轮和第 101 轮输入只多一个 token，前面 1100 个的中间结果一样吗？）  
>
> **🧑 我的回答**：重复计算太浪费，可以把前面算过的结果缓存起来复用  
>
> **🤖 点评**：✅ 对，这就是📛 **KV Cache**（第 6 步细讲）。  
> ➕ 数量级：不缓存 ≈ 200 × 1100 ≈ **22 万**个 token 的计算量；缓存 ≈ 1000 + 200 = **1200**，差近 200 倍。  
> ➕ 为什么能复用：GPT / Claude 这类模型的注意力是"**因果**"的——每个 token **只看前面、不看后面**（第 4 步）→ 第 100 个 token 每层的结果只取决于前 100 个，后面接多少都不变。

由此推理分两阶段（第 5 步细讲）：

| 阶段 | 做什么 | 名字 |
|---|---|---|
| 第 1 轮 | prompt 的 1000 个 token **一次性**算完、存下中间结果、生成第一个 token | 📛 **Prefill**（预填充） |
| 之后每轮 | 只算**新生成的 1 个** token，用存下的结果 | 📛 **Decode**（解码） |

### 📌 要记住的
> Tokenizer → Embedding + 位置信息 → N 层 Transformer → 输出层算分数 → 采样 → 接到末尾再来。每个 token 只看前面 → **算过的结果不变、可缓存（KV Cache）** → 推理分 **Prefill**（一次算完 prompt）和 **Decode**（每轮一个新 token）。

## 第 2 步 · Tokenizer

e5 的 tokenizer 实切（`XLMRobertaTokenizerFast`，词表 250,002）：
```
'我想买低风险的理财产品'（11 字符）
  token：['<s>', '▁', '我想', '买', '低', '风险', '的', '理财', '产品', '</s>']
  input_ids：[0, 6, 23638, 11795, 4814, 23400, 43, 125889, 5889, 2]
'I want to buy a low-risk wealth management product'（50 字符）
  token：['<s>', '▁I', '▁want', '▁to', '▁buy', '▁a', '▁low', '-', 'risk', '▁wealth', '▁management', '▁product', '</s>']
'unbelievably' → ['<s>', '▁un', 'beli', 'eva', 'bly', '</s>']
'稳盈货币A'     → ['<s>', '▁', '稳', '盈', '货币', 'A', '</s>']
'P-TECH'        → ['<s>', '▁P', '-', 'TECH', '</s>']
```
1. 单位是📛 **子词**（subword）：常见词一个 token（风险、理财、management），不常见的拆成几段（unbelievably），有些字单独成 token。
2. **token 数 ≠ 字符数**：中文 11 字符 → 内容 8 个 token；英文 50 字符 → 11 个（约 4.5 字符一个）。**计费和上下文限制按 token 算**（Q30 细比）。
3. 特殊 token：`<s>`（0）/ `</s>`（2）标记开始和结束，tokenizer 自动加；`▁` 表示"这里原来有空格 / 词的开头"（SentencePiece 把空格当文字处理）；🔁 L01 Cross-Encoder 的 `[SEP]`。
4. 输出两样：**`input_ids`**（词表编号，模型真正接收的）；**`attention_mask`**（1 = 真实内容，0 = 补齐空位；多句一起处理时短句补齐，第 8 步会看到）。
   - 面试原题把 `position_ids` 也列为 tokenizer 产物：通常位置编号是**模型内部按顺序生成**的，tokenizer 不一定输出。
5. 🔁 L01 呼应：`稳盈货币A` → 稳 / 盈 / 货币 / A，`P-TECH` → P / - / TECH——**模型自己的 tokenizer 同样会拆散专有名词和代码** → embedding 对它们的"理解"本来就弱（L01 第 2 步"embedding 对代码不敏感"的底层原因之一）。

> **💬 课堂问答**
>
> **🙋 问**：A 按整词 / B 按单个字符 / C 按子词——A、B 各有什么问题？为什么选 C？（提示：词表多大、切成多少 token、训练时没见过的新词）  
>
> **🧑 我的回答**：A词表太大、新词没法表示，B切出来的token太多  
>
> **🤖 点评**：✅ 都对。补细节（下表）。

| 思路 | 问题 |
|---|---|
| A 整词 | 词表几百万（buy / buys / bought、复合词、人名地名）；**新词只能变成"未知"标记 `[UNK]`，意思完全丢失**（新产品名模型只看到"未知"） |
| B 单个字符 | 序列长好几倍 → **计算量随长度增长**（注意力每对 token 都要算）、更快占满上下文；单个字母几乎不带意思，更难学 |
| C 子词 | 折中：词表**固定大小**（几万到几十万），常见词一个 token，**新词都能用片段拼出来**，几乎不出现"未知" |

### 📛 词表（vocabulary）

> **❓ 我的追问**：下面的教学会介绍"词表"的概念吗？不会的话现在介绍下。  

**词表 = token 和编号的固定对照表**：
```
编号      token
0        <s>
2        </s>
6        ▁
43       的
5889     产品
23400    风险
125889   理财
……       （共 250,002 项）
```
**怎么来的**：训练模型**之前**用算法在大量文本上统计。最常见是📛 **BPE**（Byte-Pair Encoding，字节对编码）：
```
① 一开始词表只有所有单个字符：风、险、理、财、产、品……
② 统计哪两个相邻片段一起出现最多（如"风"+"险"出现 100 万次）
③ 合并成新 token"风险"加进词表
④ 重复：理 + 财 → 理财，理财 + 产品 → 理财产品（若足够常见）……
⑤ 达到预定大小（如 25 万）停止
```
→ 越常见的组合越可能合并成一个 token（"稳盈"只在少数产品名里出现 → 被拆开）。

和模型的关系：
1. **第一层和最后一层大小都由词表决定**：Embedding 是"词表大小 × 向量维度"的大表；输出层给词表里每个 token 打分 → logits 长度 = 词表大小。实算 e5：`250,002 × 384 ≈ 9600 万`参数，🔁 e5-small 总共约 1.18 亿 → **约 80% 的参数在 embedding 表上**（多语言模型要覆盖几十种语言，词表必须大）。
2. **换模型就换一张表**：同一句话 token 数、编号都不同，**一个模型的 input_ids 不能给另一个用**；**估算 token 和成本要用目标模型自己的 tokenizer**（Claude API 有专门的计数接口；查 Claude API 资料时看到 Claude 某版本起换了新 tokenizer，同内容 token 数变成约 1~1.35 倍 → 换模型要重算成本）。
3. **训练好后就固定**：新词不加进词表，只能用已有片段拼。

### 📌 要记住的
> Tokenizer 切成**子词**：常见词一个 token、生僻词拆片段、新词都能拼出来；输出 **`input_ids`**（编号）和 **`attention_mask`**（真实内容 vs 补齐）；自动加 `<s>` `</s>` 等特殊 token。**token 数 ≠ 字符数**，计费和上下文按 token。
> **词表**是训练前用 **BPE** 等算法统计出的固定对照表；决定 embedding 表和 logits 的大小（e5 约 80% 参数在 embedding 表）；**不同模型词表不同**，估成本要用目标模型自己的 tokenizer。

## 第 3 步 · 位置信息：为什么需要、RoPE 是什么

### 没有位置信息时，模型看到的是"一袋词"

> **💬 课堂问答**
>
> **🙋 问**：注意力只关心"两个 token 各是什么"，不知道"在第几个位置"。如果模型完全没有位置信息，"客户 推荐 了 产品"和"产品 推荐 了 客户"在它看来有什么区别？  
>
> **🧑 我的回答**：有区别，这两句话，切出来的token一样，但是自然语言里面，同样的两个词，顺序不同表达的意思可能也不同。比如"辣椒"和"矫辣"（假设根据词表每个字被切成了一个token），前者是一种蔬菜，后者没有实际意义。  
>
> **🤖 点评**：✅ 直觉对：顺序不同意思可能完全不同（辣椒 / 椒辣）。⚠️ 但题目问的是另一面：**没有位置信息时模型能不能区分**——**不能，在它看来一模一样**。注意力对每一对 token 算相关程度只看各自是什么，四个 token 怎么排两两组合都相同、结果都相同 → 模型看到的是一袋打乱的词（📛 **词袋**）。→ 所以必须额外告诉模型每个 token 在第几个位置。

### 编号本身没有意思，有意思的是查出来的向量

> **❓ 我的追问**：最终被转换成向量的是 token 对应的 ID（根据词表），是个数字，那怎么能比较语义呢？  

**编号只是数字、本身无含义**——像数据库主键：`id = 5889` 只说明"产品"在第 5889 行，和第 5890 行没关系。编号的作用是去 **embedding 表查出那一行**：`"产品" → 5889 → 第 5889 行 → [0.12, -0.03, 0.88, ……]`。**语义在向量里，不在编号里。**

实查 e5 的 embedding 表：
```
embedding 表形状：(250037, 384)
'风险' 编号 23400；编号相邻：23398 '户'、23399 'xit'、23401 '▁الناس'（阿拉伯语"人们"）、23402 '▁Нова'（俄语）
和相邻编号的向量余弦：'xit' -0.024、'▁الناس' 0.068        ← 编号挨着，意思毫无关系
'风险' vs '▁risk' 0.540 / '收益' 0.312 / '风' 0.216 / '理财' 0.187 / '的' 0.086 / '▁the' 0.038
```
- 编号相邻的 token 向量几乎正交；**意思越近向量越像**，中文"风险"和英文 `risk` 最近 → 多语言模型**跨语言**学到"同一个意思"。
- **字面相似 ≠ 意思相似**："风险"和"风"共享一个字只有 0.216，不如"收益"。🔁 L01"BM25 比字面、embedding 比意思"，只是这次在单个 token 层面。
- **意思是训练出来的**：开始时表里全是随机数，训练"预测下一个 token"时预测错了就微调；经常出现在相似上下文里的 token（"风险"和 risk 后面常跟"等级""承受能力"）被调得越来越像。🔁 句子级 embedding 的对比学习道理相通。
- **这只是第一层的向量**：每个 token **不分语境的固定向量**（"银行"在任何句子里查出来都一样）；**区分语境靠后面 N 层 Transformer**（注意力把周围 token 信息融合进来）。🔁 s4_01 的句子向量 = tokenizer → 查 embedding 表 → 12 层加工 → 所有 token 向量**平均**（池化）→ 384 维 → 算余弦。

> **❓ 我的追问**：embedding 表的 key 是数字、value 是那个 token 转换后的向量；模型拿 token 换成的 id 去查向量，再拿一堆向量做语义分析，对吗？为什么要用 id 做 key，直接用 token 不行吗？  

✅ 流程对，两处更准确：① embedding 表不是字典而是**二维数组（矩阵）**，**编号就是行号**；② value 不是"token 转换出来的"，是**训练学出来的参数**（第 5889 行代表"产品"只因 tokenizer 约定"产品"编号是 5889，训练时遇到"产品"就调这一行）。

**文字 → 编号这一步本来就在 tokenizer 里**（自带真正的字典，key 文字、value 编号）→ 两次查找：
```
"产品" ──① tokenizer 查字典──▶ 5889 ──② 模型取数组第 5889 行──▶ [0.12, -0.03, ……]
       （文字 → 编号，CPU 上做一次）  （编号 → 向量，GPU 上做）
```
为什么分两步、模型不直接拿文字查：
1. **模型只能处理数字**：从头到尾都是数字矩阵运算，GPU 只擅长批量处理数字。
2. **按行号取最快**：起始地址 + 5889 × 每行大小，一步拿到；文字当 key 要算哈希、处理变长字符串，慢得多，也难在 GPU 上一次并行查成千上万个。
3. **输出也用编号**：输出层给每个 token 打分得到长度 250037 的数组，第 i 个分数对应编号 i → **"预测下一个 token" = 选出分数最高的下标**，再交 tokenizer 反查成文字；训练时比较的也是编号 → 输入输出同一套编号才对得上。
4. **有些 token 不是完整文字**：按字节切分（byte-level BPE）时生僻字可能被切成半个字的字节，单独显示不了；编号统一是整数。
- 🔁 数据库类比：订单表存 `customer_id = 1024` 而不是客户姓名（整数比较、索引快，长度固定）；要显示名字再去客户表查。

### 怎么把位置告诉模型

| 做法 | 怎么做 | 谁在用 |
|---|---|---|
| **绝对位置编码** | 再准备一张**位置向量表**（第 0 个位置一个向量、第 1 个一个……），和 token 向量**相加** | BERT、e5 等较早模型；表行数固定 → **能处理的最大长度固定** |
| 📛 **RoPE**（Rotary Position Embedding，旋转位置编码） | 不相加，而是**每一层算注意力时**把向量按位置"**旋转**"一个角度（越靠后转得越多）→ 两个 token 的注意力分数自然**只和相隔多远有关** | Llama、Qwen 等大多数现代大模型 |
- RoPE 好处：表达**相对距离**（"隔了 3 个位置"），语言规律大多和相对距离有关，效果更好；配合技巧更容易**扩展到更长上下文**。
- 面试原题"RoPE 在每一层 Attention 内部生效"= 不是入口加一次，而是**每层算注意力都用到**。

### Decode 时的位置编号

> **💬 课堂问答**
>
> **🙋 问**：prompt 1000 token（位置 0~999），Decode 每轮只处理一个新 token。第一轮那个新 token 的位置编号应该是多少？如果每轮都把它当成 0（"这一轮只输入了一个 token"），会怎样？（提示：RoPE 让分数只和相隔多远有关）  
>
> **🧑 我的回答**：第一个输出的token的位置是0，但如果每一轮都把这轮输出的token位置标成0的话，模型最后就只输出最后一个token了。  
>
> **🤖 点评**：⚠️ 两处都不对。关键混淆：**位置编号是"在整个序列里的位置"，不是"在这一轮输入里的位置"**。  
> ➕ 正确答案 **1000**（第 2 轮 1001、第 50 轮 1049）——前 1000 个 token 的结果在 KV Cache 里，新 token 要和它们一起算注意力，必须知道自己排在它们后面第几个。面试原题："decode 阶段 position_id 必须接续历史序列长度，不能重置为 0"。  
> ➕ 写错成 0 **不会"只输出最后一个 token"**（循环照样每轮产出、接到末尾），出问题的是**质量**（见下）。

```
位置：  0    1    2   ……  999  │ 1000   1001   1002  ……
内容：  推   荐   个  ……  吗？ │ 我     推荐   您
       └────── prompt ──────┘ └── Decode 生成的 ──┘
```
写错成 0 的后果：
1. **新 token 被当成排在最开头**：和 prompt 第 999 个 token 的距离从"紧挨着的前一个"变成"在我后面 999 个"，而因果注意力只看前面，训练中从没见过 → 相对位置完全乱套。
2. **所有生成的 token 挤在同一个位置** → 彼此没有先后顺序（🔁 本步开头的"词袋"）。
→ 越往后越"迷糊"：语句不通、反复重复、答非所问、最后乱码（每步看到的上下文和训练时对不上）。

### 📌 要记住的（第 3 步）
> 注意力本身不知道顺序 → 没有位置信息模型只看到"**词袋**"。两种做法：**绝对位置编码**（位置向量表与 token 向量相加，最大长度固定，BERT / e5）、**RoPE**（每层算注意力时按位置旋转向量，分数只和**相对距离**有关，现代大模型主流）。**位置编号是在整个序列里的位置**：Decode 时接着历史长度往后数，不能重置为 0。
> token **编号本身无含义**（像主键），只用来在 embedding **矩阵**里取行；**语义在训练学出的向量里**（实测"风险"与 risk 0.54、与编号相邻的 token ≈ 0）；先由 tokenizer 字典把文字换成编号，再由模型按行号取向量（模型只处理数字、按行号最快、输出也是编号）。

## 第 4 步 · 三类 Transformer 架构与注意力掩码

🔁 第 1 步：Claude、GPT 是**因果**注意力（每个 token 只看前面）→ KV Cache 成立。但不是所有 Transformer 都这样：L01 用过的 **e5** 和 **bge-reranker** 就不是。

> **💬 课堂问答**
>
> **🙋 问**：Cross-Encoder 把 `[query] 想给爸妈存养老钱 [SEP] [文档] 养老目标日期基金，为退休储备而设计` 拼在一起。如果它也用因果注意力，query 里的"爸妈"还能注意到后面文档里的"退休"吗？由此推：e5 / bge-reranker 这类理解型模型和 Claude 这类生成型模型，在"能看哪些 token"上应有什么不同？  
>
> **🧑 我的回答**：看不到后面的，理解型模型应该能双向看  
>
> **🤖 点评**：✅ 完全正确：因果下"爸妈"看不到"退休"，Cross-Encoder 失去最大优势（只能由文档单向看 query）→ 理解型模型都是**双向**的：每个 token 都能看全部 token。

📛 **attention mask**（注意力掩码）矩阵控制"谁能看谁"（✅ = 这一行能看这一列）：
```
双向（e5、bge-reranker）          因果（Claude、GPT）
       想  给  爸妈  存                  想  给  爸妈  存
想     ✅  ✅  ✅   ✅           想     ✅  ❌  ❌   ❌
给     ✅  ✅  ✅   ✅           给     ✅  ✅  ❌   ❌
爸妈   ✅  ✅  ✅   ✅           爸妈   ✅  ✅  ✅   ❌
存     ✅  ✅  ✅   ✅           存     ✅  ✅  ✅   ✅
       全部都能看                       只能看自己和前面（下三角）
```
- 🔁 第 2 步 tokenizer 的 `attention_mask` 标的是"补齐的空位别看"；这里的因果掩码是"别看后面"，两者**叠加**使用。

| 架构 | 注意力 | 训练方式 | 擅长 | 代表 |
|---|---|---|---|---|
| **Encoder-only** | **双向** | 📛 **掩码语言模型**（MLM）：随机遮住一些词，根据前后文猜（完形填空） | **理解**：句子向量、分类、重排 | BERT、**e5**、**bge-reranker** |
| **Decoder-only** | **因果** | **预测下一个 token** | **生成**：对话、写作、agent | GPT、**Claude**、Llama、Qwen |
| **Encoder-Decoder** | 编码器双向读完输入；解码器因果生成、每步可**回头看编码器结果** | 输入一段、输出另一段 | **转换**：翻译、摘要 | T5、BART、最早的 Transformer 翻译论文 |
- **更正面试题说法**（差距分析标过）："Encoder 读取所有词元生成向量表，Decoder 根据 encoder 生成下一个词"只描述了**第三种**。**Decoder-only 根本没有 encoder**，输入输出在同一个解码器里用因果注意力一路处理。
- 生成型为什么必须因果：① **训练时不能偷看答案**（能看后面就直接看一眼下一个 token，什么也学不到）；② **推理时后面还不存在**，训练和推理条件要一致。
- Decoder-only 成主流：**一个模型做所有事**（理解任务也能改写成"生成答案"）、最容易扩大规模、能用 KV Cache 加速。

> **💬 课堂问答**
>
> **🙋 问**：拿一个**双向**模型硬要它像 Claude 一样逐 token 生成（每次把新 token 接到末尾），前面 token 的计算结果还能缓存复用吗？（提示：双向下第 100 个 token 能不能看到新接上的第 1001 个？）  
>
> **🧑 我的回答**：不能复用，第100个token会看到新接的token，结果会变  
>
> **🤖 点评**：✅ 完全正确。双向下每接一个新 token，**所有**旧 token 的结果都会变 → 每轮都要从头全算（第 1 步的 22 万 vs 1200）→ **KV Cache 只对因果注意力成立**，这也是生成型模型都是 Decoder-only 的原因之一。

### 追问 1：KV Cache 的 KV 是什么

> **❓ 我的追问**：KV cache 的 KV 是什么意思？  

**K = Key、V = Value**，和 **Q（Query）** 一起是注意力计算的三样东西（concepts-basics 只讲了直觉，这里补具体算法）。每个 token 的向量在每一层都被**分别乘以三个训练好的矩阵**，变成：

| 向量 | 名字 | 直观含义 |
|---|---|---|
| **Q** | Query（查询） | "我想找什么样的信息" |
| **K** | Key（键） | "我这里有什么，用来被别人匹配"（标签） |
| **V** | Value（值） | "你决定关注我时，我提供的内容" |

🔁 和 L01 检索几乎一样：

| 检索（L01） | 注意力 |
|---|---|
| 用户的 query 向量 | 当前 token 的 **Q** |
| 每篇文档的向量（算相似度用） | 每个 token 的 **K** |
| 每篇文档的正文（找到后真正用的） | 每个 token 的 **V** |
| query 和文档算点积 / 余弦 | Q 和每个 K 算**点积** → 注意力分数 |
| 取最相似的几篇拼进 prompt | 按分数**加权求和所有 V** → 这个 token 的新向量 |
→ 区别：检索"选出前几篇"，注意力"按比例混合所有的"。

```
注意力输出 = softmax( Q · Kᵀ / √d ) · V
```

| 符号 | 含义 | 例子 |
|---|---|---|
| Q | 当前 token 的查询向量 | "爸妈"的 Q |
| K | 每个可被看的 token 的键向量，排成矩阵 | 想 / 给 / 爸妈 / 存 各自的 K |
| Kᵀ | K 的转置，让 Q 和每个 K 都做一次点积 | — |
| Q · Kᵀ | Q 和每个 K 的点积 = 相关分数 | 🔁 L01 Q27 的 a·b |
| √d | 向量维度的平方根，**缩小分数**，避免 softmax 过于极端 | 维度 64 除以 8 |
| softmax | 把一组分数变成**加起来为 1 的比例** | [2.0, 1.0, 0.1] → [0.66, 0.24, 0.10]（第 7 步还会用） |
| 乘 V | 按比例把所有 V 加权求和 | 0.66 × V₁ + 0.24 × V₂ + 0.10 × V₃ |

**为什么缓存 K、V 不缓存 Q**：Decode 每轮只有**新 token**在"提问"，只需要它自己的 Q；它要和**所有旧 token** 的 K 做点积、用它们的 V 加权求和。因果下旧 token 的 K、V 不再变 → 存下来复用；**旧 token 的 Q 以后用不到**（它们不再提问）→ 不存。= **缓存每一层、每个旧 token 的 K 和 V**。

### 追问 2：encoder 和 decoder 在"编码""解码"什么

> **❓ 我的追问**：Encoder-only 和 Decoder-only 架构，encoder 和 decoder 分别是对什么东西编码、解码？  

名字来自**最早的翻译模型**（Encoder-Decoder）：
```
"我爱你" ──encoder（编码）──▶ 一组向量（模型内部对这句话的理解） ──decoder（解码）──▶ "I love you"
```
- **编码** = 把输入文字转换成模型内部的表示（一组向量）；**解码** = 把这个表示逐个 token 转换回输出文字。

| | 拿了哪一半 | 实际在做什么 |
|---|---|---|
| Encoder-only | 只有"编码" | 把输入**编码成向量就到此为止**，不生成文字。🔁 e5 的 384 维句子向量就是编码结果；bge-reranker 在编码结果上加一层输出相关度分数 |
| Decoder-only | 只有"解码"（因果、逐个生成） | **没有单独的编码器**，prompt 和输出在同一个因果结构里处理；"decode"已不是"把编码结果解码"，理解为"**逐个 token 生成**" |
- 容易忽略的对应：Decoder-only 里 **Prefill 在功能上相当于"编码"**——把整个 prompt 读一遍、算出每层的 K、V 存进 KV Cache，后面生成的每个 token 都去"查看"它们；只是用的是**因果**，真正的 encoder 是**双向**。

### 追问 3：Encoder-Decoder 的注意力（示例）

> **❓ 我的追问**：再详细解释下 Encoder-Decoder 架构的注意力，最好能给个简单的示例。  

三种注意力，用"把 `我 爱 你` 翻译成 `I love you`"演示：
```
① 编码器自注意力（双向）：输入 token 之间互相看
② 解码器自注意力（因果）：已生成的输出 token 之间互相看，只看前面
③ 交叉注意力（cross-attention）：解码器的 token 去看编码器的全部结果   ← Encoder-Decoder 独有
```
**第一步：编码器读完整个输入（只做一次）**
```
        我   爱   你
  我    ✅   ✅   ✅
  爱    ✅   ✅   ✅
  你    ✅   ✅   ✅
→ 3 个向量：我'、爱'、你'（每个都融合了整句话的信息）
```
**第二步：解码器从 `<s>` 出发逐个生成，每步做两次注意力**
```
第 1 个词：自注意力 <s> 只看自己；交叉注意力 <s> 的 Q vs 我'、爱'、你' 的 K
          → [我' 0.8, 爱' 0.1, 你' 0.1]（主要看"我"）→ "I"
第 2 个词：自注意力（因果）
                <s>   I
          <s>   ✅    ❌
          I     ✅    ✅
          交叉注意力 I 的 Q vs 我'、爱'、你' → [我' 0.1, 爱' 0.8, 你' 0.1]（主要看"爱"）→ "love"
第 3 个词：自注意力 <s>、I、love 只看前面；交叉注意力主要看"你" → "you"，然后 </s>
```

| 注意力 | Q 来自 | K、V 来自 | 能看哪些 | 作用 |
|---|---|---|---|---|
| ① 编码器自注意力 | 输入 token | 输入 token | 全部输入（双向） | 理解输入：每个词结合整句意思 |
| ② 解码器自注意力 | 输出 token | 输出 token | 已生成的输出（因果） | 保持输出通顺（"love"后接"you"） |
| ③ **交叉注意力** | **输出 token** | **编码器结果** | 全部输入 | **决定"现在该翻译输入的哪部分"** |
- ③ 是核心：**输入输出分开处理**，输入只用编码器**双向**读一次、理解更充分；解码器每步都能**完整回看**整个输入。
- 交叉注意力也能缓存：编码器结果整个生成过程不变 → 它们的 K、V **只算一次**。
- 🔁 和 L01 **Cross-Encoder** 不是一回事：Cross-Encoder 是两段文字**拼成一段**双向读（属 Encoder-only）；Encoder-Decoder 的交叉注意力是**解码器看编码器**结果。

### 📌 要记住的（第 4 步）
> 注意力掩码决定"谁能看谁"：**双向**（全看）vs **因果**（只看前面，下三角）。**Encoder-only**（双向、完形填空训练、擅长理解：e5、bge-reranker）/ **Decoder-only**（因果、预测下一个 token、擅长生成：Claude、GPT，主流）/ **Encoder-Decoder**（编码器双向 + 解码器因果并回看编码器、擅长翻译摘要：T5）。生成必须因果（训练不能偷看、推理时后面不存在）；**KV Cache 只对因果成立**（双向下新 token 会改变所有旧 token 的结果）。Decoder-only **没有 encoder**。  
> **Q / K / V**：Q（我想找什么）· K（我有什么）点积 → softmax 成比例 → 按比例混合 V（≈ 检索，但按比例混合而非选前几个）；Decode 只有新 token 需要 Q、旧 token 的 K / V 不变 → 缓存 **K、V** = **KV Cache**。名字来自翻译模型：encoder 把输入编码成内部向量、decoder 把它逐个解码成输出；Decoder-only 里 Prefill 功能上相当于编码。Encoder-Decoder 三种注意力：编码器双向自注意力（只做一次）、解码器因果自注意力、**交叉注意力**（Q 来自解码器、K / V 来自编码器，决定现在处理输入的哪部分）。

## 第 5 步 · Prefill vs Decode：两个阶段为什么性能特征不同

> 🔁 **回顾（第 1 步）**：**Prefill** 一次读完整个 prompt，算出每层每个 token 的 K、V 存进 KV Cache，并生成第 1 个 token；**Decode** 每轮只处理 1 个新 token：用它的 Q 查看缓存里的全部 K、V → 生成下一个 → 把自己的 K、V 追加进缓存 → 循环。

### 缩写

| 缩写 | 全称 | 含义 |
|---|---|---|
| **TTFT** | Time To First Token | 发请求到**收到第 1 个 token** 的等待时间，主要由 Prefill 决定 |
| **TPOT** | Time Per Output Token | 之后**每多生成 1 个 token** 的耗时，由 Decode 决定 |
| **HBM** | High Bandwidth Memory | GPU 显存，权重和 KV Cache 都在这里，计算前要读进计算单元 |
| **FLOPs** | Floating-point Operations | 浮点运算次数，衡量计算量 |

### 核心：每一步的时间要么花在"算"，要么花在"搬"

每生成一步，GPU 都要把**全部权重**从显存读一遍（7B 模型 fp16 ≈ 14 GB）。

| | Prefill | Decode |
|---|---|---|
| 一次处理多少 token | **整个 prompt**（如 4000 个），并行 | **1 个** |
| 读一遍权重能算多少 | 4000 个 token 共用一次读取，**算得多、搬得少** | 只算 1 个，**搬 14 GB 只为算一点点** |
| 瓶颈 | **计算密集**（compute-bound）：算力跑满 | **访存密集**（memory-bound）：算力闲着等数据 |
| 决定的指标 | **TTFT**：prompt 越长越久 | **TPOT**：基本固定（KV Cache 越长略慢） |

- 粗算：H100 显存带宽 ≈ 3.35 TB/s，14 GB ÷ 3.35 TB/s ≈ **4 ms / token** → 单请求上限约每秒 250 个 token。
- 所以推理服务要**把多个请求打包一起 Decode（batching）**：读一次权重给 32 个请求各算 1 个 token，分摊搬运成本（vLLM，L10）。

### 总耗时

```
总耗时 ≈ TTFT + (输出 token 数 − 1) × TPOT
```

| 符号 | 含义 | 取值来源 | 例子代入 |
|---|---|---|---|
| TTFT | 首 token 等待时间 | 随 **prompt 长度**增长 | 4000 token prompt ≈ 0.4 s |
| 输出 token 数 | 这次回答多长 | 回答长度 | 300 |
| TPOT | 每个输出 token 耗时 | 模型大小、显存带宽、批大小；**和 prompt 长度关系不大** | 20 ms |

代入：0.4 + 299 × 0.02 ≈ **6.4 s**

**对 agent 工程的意义**：
- **流式输出**（streaming）：TTFT 后用户就看到字，体感快，但总耗时不变；
- **输出比输入贵**（Claude 输出单价一般是输入的 5 倍），原因之一：Decode 每个 token 都独占一轮"搬全部权重"；
- prompt 很长 → TTFT 明显变长 → 第 6 步 **prompt caching** 跳过重复的 Prefill。

### 💬 课堂问答

> 🙋 **问**：FinWise 顾问 agent：prompt 4000 token、回答 300 token（TTFT 0.4 s、TPOT 20 ms）。A：prompt 降到 2000（TTFT 减半到 0.2 s）；B：要求简洁，输出降到 150。哪个省时间更多？  
> 🧑 **我的回答**：选B。方案A快0.2秒，方案B快150 * 20 = 3000ms，快3秒  
> 🤖 **点评**：✅ 完全正确，B 省的是 A 的 15 倍。  
> ➕ **延时主要花在输出上**：6.4 s 里 Prefill 只占 0.4 s。想让 agent 更快，先砍输出长度（要求简洁、结构化输出只要必要字段、别让模型复述输入），再考虑缩 prompt。  
> ➕ A 并非没用：它省的是**钱**（输入按 token 计费）和**上下文空间**；在多轮 agent 循环里，prompt 每轮都在变长（工具结果不断追加），积累下来 Prefill 也会变重——这正是第 6 步 prompt caching 要解决的。  
> ⚠️ 实际 TTFT 还包含排队、网络时间，不只是 Prefill 计算。

### 📌 要记住的（第 5 步）
> **Prefill** 并行处理整个 prompt、**计算密集**、决定 **TTFT**；**Decode** 每轮 1 个 token、每轮都要读一遍全部权重和 KV Cache、**访存密集**、决定 **TPOT**。总耗时 ≈ TTFT + (输出数 − 1) × TPOT，**通常输出长度主导延时**。Decode 靠 **batching** 分摊权重读取提吞吐；输出 token 比输入贵；流式输出改善体感、不缩短总耗时。

## 第 6 步 · KV Cache：存什么、为什么省、和 prompt caching 的关系

> 🔁 **回顾**：第 1 步——不缓存时每生成一个新 token 都要把前面全部重算（例子约 22 万），缓存后每轮只算新 token（约 1200）。第 4 步——因果下旧 token 的 K、V 不变，新 token 只需自己的 Q → 只缓存 **K、V**。

### 6.1 存什么、多大

**每一层、每个 token、每个头**一份 K 和 V。**多头注意力**（Multi-Head Attention）：每层把向量切成若干"头"，各自独立做注意力（有的偏语法、有的偏指代），所以 K、V 也按头各存一份。

```
每个 token 的 KV 大小 = 2 × 层数 × KV 头数 × 每个头的维度 × 字节数
```

| 符号 | 含义 | 取值来源 | 代入 Llama-2-7B |
|---|---|---|---|
| 2 | K 和 V 各一份 | 固定 | 2 |
| 层数 | Transformer 层数 | 模型结构 | 32 |
| KV 头数 | 存 K、V 的头数 | 模型结构 | 32 |
| 每个头的维度 | 每个头的向量长度 | 隐藏维度 ÷ 头数 = 4096 ÷ 32 | 128 |
| 字节数 | 每个数几字节 | fp16 = 2 | 2 |

代入：2 × 32 × 32 × 128 × 2 ≈ **0.5 MB / token** → 4000 token 请求约 **2 GB**；32 个并发约 **64 GB**，远超权重 14 GB。
➡️ **KV Cache 是并发数和上下文长度的主要瓶颈**（也是第 5 步 Decode 访存密集的原因之一：每轮还要读整份 KV Cache）。

优化（知道名字即可）：
- **GQA**（Grouped-Query Attention，分组查询注意力）：多个 Q 头**共用**一组 K、V 头。Llama-3-8B：32 个 Q 头、8 个 KV 头 → 约 128 KB / token，缩到 1/4。
- **PagedAttention**：像操作系统内存分页一样按小块分配 KV Cache，减少显存浪费（vLLM 核心，L10）。

### 6.2 为什么省：用显存换计算

| | 不缓存 | 有 KV Cache |
|---|---|---|
| 生成第 n 个 token 要算多少 | 前面 n 个全部重算 | 只算 1 个新 token |
| 总计算量 | 1 + 2 + … + n ≈ n²/2（约 22 万） | ≈ n（约 1200） |
| 代价 | — | 占显存（6.1） |

### 6.3 生命周期：只活在一个请求里

**请求结束 KV Cache 就释放。** 但多轮对话 / agent 循环每次都把**完整历史**重发：
```
第 1 轮：[system 3000][用户问题]                          → Prefill 3000+
第 2 轮：[system 3000][用户问题][回答][工具结果][追问]     → 前面完全一样，却又 Prefill 一遍
第 3 轮：……越来越长，每轮从头 Prefill
```
➡️ 重复 Prefill 既费钱又拖慢 TTFT（第 5 步）。

### 6.4 Prompt caching：把 KV Cache 跨请求保留

服务端把某个 **prompt 前缀**的 KV Cache **保存一段时间**；下一个请求以**完全相同的前缀**开头 → 直接复用，跳过这部分 Prefill。

**为什么必须完全相同的前缀**（由第 4 步因果性推出）：一个 token 的 K、V 取决于**它自己和前面所有 token**；第 N 位改一个字 → 第 N 位**及之后**的 K、V 全变，**之前**的不变 → 只有"从开头起完全一致"的部分能复用。

**Claude API**（claude-api 文档，截至 2026-10）：

| 要点 | 说明 |
|---|---|
| 开启 | 内容块加 `cache_control: {"type": "ephemeral"}` 作断点；或请求顶层加，自动放在最后一个块；每请求最多 4 个断点 |
| 拼接顺序 | `tools` → `system` → `messages`；工具列表变了后面全失效 |
| TTL | 默认 **5 分钟**，可选 `"ttl": "1h"`；每次命中重新计时 |
| 价格 | **读 ≈ 0.1 倍**输入单价（Opus 5.5 为 0.05 倍）；**写 1.25 倍**（5 分钟档）/ 2 倍（1 小时档） |
| 最短长度 | 太短不缓存且**不报错**；因模型而异，最新模型 512 token |
| 确认命中 | `usage.cache_read_input_tokens > 0`；`cache_creation_input_tokens` 是本次写入量 |

**值不值**（5 分钟档，前缀用 2 次）：不缓存 1 + 1 = **2 倍**；缓存 1.25 + 0.1 = **1.35 倍** → 复用 2 次就开始省；agent 循环一次十几轮，省更多，TTFT 也降。

**原则：不变的放前面，常变的放后面**：工具定义 → 固定 system → 对话历史（只追加不修改）→ 本轮新内容。

### 追问 1：Transformer 的"层"是什么

> **❓ 我的追问**：transformer的层是什么？  

> 🔁 第 1 步流程：Tokenizer → Embedding + 位置 → **N 层 Transformer** → logits → 采样。这里打开中间那段黑盒。

**一层 = 一个"加工工位"**：每个 token 的向量进去，出来还是同样长度（n 个 token × d 维，Llama-2-7B d = 4096），但更"懂上下文"。几十个**结构相同、参数不同**的层串联，前一层输出就是后一层输入：
```
Embedding（只知道"我是哪个词、在第几位"）→ 第 1 层 → … → 第 32 层 → 最终向量（融合整段上下文）
→ 取最后一个 token 的向量 → logits → 预测下一个 token（第 7 步）
```

| 子步骤 | 做什么 | 比方 |
|---|---|---|
| ① **注意力** | token 之间**交换信息**（Q / K / V，第 4 步） | 开会：听别人发言 |
| ② **FFN**（Feed-Forward Network，前馈网络，也叫 MLP 多层感知机） | **每个 token 各自**加工：放大到约 4 倍维度 → 非线性变换 → 压回原维度；token 之间不交流 | 散会后各自消化、结合已有知识 |

- 例："爸妈"进第 1 层前只是"爸妈这个词，第 4 位" → ① 融入"给""存"→"作为受益人的爸妈" → ② 结合知识"给老人理财偏稳健"。经验上**底层**偏词法语法、**中间层**偏语义、**顶层**偏"下一个词说什么"（大致规律）。
- **残差连接**（Residual Connection）：`输出 = 输入 + 子步骤(输入)`——子步骤只算**修改量**加回原向量，叠几十层原始信息也不被冲掉、训练更稳。
- **LayerNorm**（Layer Normalization，层归一化）：每个子步骤前把向量数值拉回统一范围，防止越滚越大或越小。

| 之前学的 | 和"层"的关系 |
|---|---|
| 第 6 步 KV 公式里的"**层数**" | **每层有自己的 Q / K / V 矩阵** → 每层的 K、V 都不同、都要缓存 |
| 第 5 步"每个 token 要读一遍全部权重" | 权重主要在层里：Llama-2-7B 每层约 2 亿 × 32 ≈ 65 亿，FFN 约 2/3、注意力约 1/3 |
| 第 2 步 e5 embedding 表占 80% | e5 是**小模型配大词表**（12 层、每层小）；大模型反过来，层占绝大部分 |
| 第 4 步双向 vs 因果 | 区别只在**注意力**子步骤的掩码；FFN 各算各的，不涉及"能看谁" |

|---|---|---|

### 📌 要记住的（第 6 步）
> **KV Cache** 存每层、每 token、每头的 K 和 V（约 0.5 MB / token @ 7B），是**用显存换计算**（n² → n），也是并发和长上下文的瓶颈（GQA 共用 KV 头、PagedAttention 分页缓解）。它**只活在一个请求里**；**prompt caching** 把**前缀**的 KV Cache 跨请求保留，必须**字节级完全相同的前缀**（因果性：改第 N 位 → N 之后全变）。Claude：`cache_control` 断点、5 分钟 / 1 小时 TTL、读约 0.1 倍、写 1.25 倍，复用 2 次即回本；看 `cache_read_input_tokens` 确认命中。设计：**不变在前、常变在后**，时间戳 / 用户 ID 这类变量别放 system 开头。  
> **层** = 注意力（token 间交换信息）+ FFN（各自加工）+ 残差 + LayerNorm；几十个结构相同、参数不同的层串联；每层有自己的 K、V（KV Cache 按层存），大模型参数主要在层里。

## 第 7 步 · 采样：logits → softmax、temperature、top-k、top-p

> 🔁 **回顾**：第 1 步——每轮最后输出 **logits** 再**采样**出下一个 token。"层"的追问——最后一层、最后一个 token 的向量乘以"词表大小 × d"的矩阵 → **长度 = 词表大小**的分数列表 = logits。

### 7.1 logits → 概率：softmax

**logits** = 未归一化的分数（可正可负、加起来不为 1）。例："我想给爸妈存一笔___"（真实词表几万到几十万项，这里取 4 个）：

| 候选 | 钱 | 养老 | 定期 | 股票 |
|---|---|---|---|---|
| logit | 2.0 | 1.0 | 0.5 | −1.0 |

```
P(候选 i) = e^(zᵢ / T) ÷ Σⱼ e^(zⱼ / T)
```

| 符号 | 含义 | 取值来源 | 例子（T = 1） |
|---|---|---|---|
| zᵢ | 候选 i 的 logit | 模型算出 | "钱" 2.0 |
| T | **temperature（温度）** | 调用方设置，默认 1 | 1 |
| e^(…) | 以 e ≈ 2.718 为底的指数：变正数并拉大差距 | 计算 | e² = 7.39、e¹ = 2.72、e^0.5 = 1.65、e^−1 = 0.37 |
| Σⱼ | 所有候选求和，归一化 | 计算 | 12.13 |

T = 1：钱 **0.61**、养老 **0.22**、定期 **0.14**、股票 **0.03**。
- **贪心解码**（greedy）：总选最大 → 确定，但易重复、呆板；**采样**（sampling）：按概率掷骰子。

### 7.2 Temperature：变尖或变平

| T | 钱 | 养老 | 定期 | 股票 | 效果 |
|---|---|---|---|---|---|
| **0.5** | **0.84** | 0.11 | 0.04 | 0.002 | **变尖**：更稳定保守 |
| **1** | 0.61 | 0.22 | 0.14 | 0.03 | 模型原始分布 |
| **2** | 0.43 | 0.26 | 0.21 | **0.10** | **变平**：更多样，也更易胡说 |
| → 0 | 1 | 0 | 0 | 0 | 等同**贪心** |

原因：T < 1 放大 logits 差距（2.0 / 1.0 → 4.0 / 2.0），指数后更悬殊；T > 1 相反。

### 7.3 Top-k / Top-p：先截长尾再采样

几万个冷门候选概率加起来不小，抽中就胡言乱语 → 先**截断**，再**重新归一化**，再采样。

| 方法 | 规则 |
|---|---|
| **Top-k** | 只留概率**最高的 k 个**（k = 2 → {钱, 养老}） |
| **Top-p**（nucleus sampling，核采样） | 从高到低**累加**，到 **≥ p** 就停，保留到这里为止 |

- Top-k 的 k 固定：模型确定时放进垃圾、犹豫时砍太多；**Top-p 自适应**。
- 完整流程：`logits → ÷T → softmax → top-k / top-p 截断 → 重新归一化 → 采样`

### 7.4 Claude API 现状：采样参数已收回（claude-api 文档，截至 2026-10）

| 情况 | 带 `temperature` / `top_p` / `top_k` |
|---|---|
| API 版本 **`2026-10-21`** | **所有模型都 400**，哪怕传默认值 `temperature: 1` |
| 旧版本 `2023-06-01` | 看模型：Opus 4.7 起已移除；Sonnet 5 拒绝非默认值；更早的 Claude 4.x 最多传 `temperature` / `top_p` 之一 |

- 想要稳定确定：写清 prompt + **结构化输出**约束格式 + `effort` / 思考模式控制推理深度，而不是调温度。
- FinWise：`backend/app` 没发 `temperature`，不受影响；scratch 走 bridge，本来就忽略。
- 自部署开源模型（vLLM 跑 Llama 等）仍可用 → 原理照样要懂、面试照样问。

### 追问：attention_mask 到底怎么起作用

> **❓ 我的追问**：解释下这里attention_mask  

- `<pad>` 也是正常 token（有 embedding、会算出 K / V）→ 必须明确告诉模型"别看"。
- **在注意力里**：mask 为 0 的位置，分数在 softmax **之前**换成 **−∞** → e^(−∞) = 0 → 权重为 0。

```
"养老"的分数：  <s> 1.2   ▁ 0.3   养老 2.0   </s> 0.5   <pad> 0.8 × 7
不用 mask：4 个真实 e^分数 13.71，7 个 pad 15.6 → pad 抢走 53% 注意力，且同一句话和不同长度的句子打包结果会不同
用 mask：  pad → −∞ → softmax [0.24, 0.10, 0.54, 0.12, 0 …] = 单独编码、不补齐时的结果
```

| | 因果掩码（第 4 步） | attention_mask（padding 掩码） |
|---|---|---|
| 屏蔽 | **后面的** token | **补齐的** `<pad>` |
| 理由 | 生成不能偷看未来 | 填充无意义 |
| 由谁决定 | 架构固定（Decoder-only） | 每批数据不同，tokenizer 算出 |
| e5 用吗 | 不用（双向） | **用** |
- Decoder-only 批量推理时两者**叠加**：在前面 **且** 不是 pad 才能看。
- **e5 求句子向量**（mean pooling，平均池化）也用它：`Σ(token 向量 × mask) ÷ Σ mask`，只对真实 token 平均（sentence-transformers 内部自动做）。
- 线上 LLM 服务尽量不补齐（白算）：vLLM 把请求首尾相接 + 掩码隔开，或 continuous batching（连续批处理）随到随加，L10 展开。

### 追问：exp / exp.sum() 有精度问题吗

> **❓ 我的追问**：exp / exp.sum()，这个除法会有精度问题吗？能保证这个向量里面每个数字最后加起来=1吗？  

**不保证恰好 = 1**（二进制浮点数有舍入误差，经典例子 `0.1 + 0.2 = 0.30000000000000004`），但通常可忽略。实测 5 万个候选 × 1000 次：

| 精度 | 字节 | 最大误差 | 恰好 = 1 |
|---|---|---|---|
| float64（numpy 默认） | 8 | 3 × 10⁻¹⁶ | 517 / 1000 |
| float32（GPU 常用） | 4 | 1.7 × 10⁻⁷ | 0 / 1000 |
| float16 | 2 | **1.1 × 10⁻³** | 0 / 1000 |

- 测试用 `pytest.approx` / `assert_allclose`，**不用 `==` 比浮点**；
- `rng.choice(p=...)` 自带容差（约 10⁻⁸），差太多报 `ValueError: probabilities do not sum to 1`；
- 推理框架即使权重 fp16，**softmax 也转 float32 算**；`torch.multinomial` 不要求和为 1，内部自己归一化。
- 和"减最大值"同属**数值稳定性**：那个防**溢出**，这个是**舍入**。

> 🙋 **问**（顺着精度追问发现的 bug）：`probs = np.full(10, 0.1)`、p = 1.0，期望全部保留，实际只保留 1 个。为什么？  
> 🧑 **我的回答**：（直接改好了代码）  
> ```python
> # 用 np.where 而不是 np.argmax：避免浮点数误差导致 cumulative[-1] 略小于 p 时
> # np.argmax(cumulative >= p) 全 False 返回 0（只保留 1 个）的边界问题
> crossings = np.where(cumulative >= p)[0]
> keep_count = crossings[0] + 1 if len(crossings) > 0 else len(probs)
> ```  
> 🤖 **点评**：✅ 原因找得准：累加末项 0.9999999999999999 < 1.0 → 布尔数组**全 False** → `np.argmax` 返回 **0** → 只留 1 个，p = 1 反而变成贪心。修复后 10 个测试全过。  
> ➕ 用 mask 相乘而非删除元素，和 `attention_mask` 同一思路：形状、顺序不变。  
> ➕ 另一种常见写法（Hugging Face 类似）：保留"**之前累加 < p**"的候选，`keep = (cumulative - probs[order]) < p`，天然至少留 1 个、p = 1 时全留，不用特判。  
> ⚠️ 教训：**`np.argmax` 对全 False 返回 0 而不报错**；"找第一个满足条件的位置"要考虑"一个都没有"。

### 📌 要记住的（第 8 步）
> `attention_mask`：1 = 真实、0 = 补齐；softmax 前把 0 位置设 **−∞** → 权重 0 → 补齐结果 = 单独编码；与因果掩码原理同、目的不同、可叠加；e5 平均池化也只算 mask = 1。token 数取决于具体 tokenizer（**频率**决定词表），估成本用目标模型的 tokenizer。浮点：减最大值防溢出；求和不保证恰好 1（fp64 可忽略、fp16 约 10⁻³ → softmax 用 fp32）；比较用近似；`np.argmax` 全 False 返回 0 是边界陷阱。

### Q28 🟡 temperature 在数学上改了什么？T → 0 / T → ∞？`temperature=0.7, top_p=0.9` 的执行顺序？

> 🙋 **问**：temperature 在数学上改了什么？
> 🧑 **我的回答**：在 softmax 之前把每个 logit 除以 T
> 🤖 **点评**：✅ 正确。➕ 等于把 logits 间的**差值**缩放 1/T 倍（softmax 只看差值，第 8 步）。

> 🙋 **问**：T → 0 和 T → ∞ 分布各变成什么？
> 🧑 **我的回答**：T=0的时候，等于"贪心"解码，T无穷大时，logit/T接近0,导致候选概率也接近0
> 🤖 **点评**：T → 0 ✅。T → ∞ 前半对、最后一步 ⚠️ 错：zᵢ/T → 0 时 e^(zᵢ/T) → **e⁰ = 1**，不是 0；且 softmax 结果加起来永远是 1，不可能都趋近 0。
> 🧑 **重答**：都趋近 1，归一化后每个 1/4，是均匀分布
> 🤖 ✅ 正确。

| T | 分布 | 效果 |
|---|---|---|
| → 0 | 最大的为 1，其余 0 | **贪心**：完全确定 |
| = 1 | 模型原始分布 | — |
| → ∞ | 每个 1 / 词表大小 | **均匀**：完全随机（乱码） |

> 🙋 **问**：同时设 `temperature=0.7, top_p=0.9`，先做哪个？为什么？
> 🧑 **我的回答**：先除以 T 再做 top-p，因为 top-p 按调温后的概率累加
> 🤖 **点评**：✅ 正确。用课上例子：T = 1 时 0.61 / 0.22 / 0.14 / 0.03，累加 0.61 → 0.83 → 0.97，top-p 0.9 保留 **3 个**；T = 0.7 时 0.73 / 0.18 / 0.09 / 0.01，累加 0.73 → 0.90，只保留 **2 个**。
> ➕ 降温让头部集中 → top-p 保留更少，两者**叠加生效**。主流框架（Hugging Face、vLLM）先温度、后截断；同时有 top-k 时一般先 top-k 再 top-p。

**📝 面试版答案**：temperature 是在 softmax **之前**把每个 logit **除以 T**，相当于把候选间差距缩放 1/T 倍：T < 1 变尖更确定、T > 1 变平更多样；**T → 0 退化为贪心**，**T → ∞ 变成均匀分布**（zᵢ/T → 0，e⁰ = 1，每个 1 / 词表大小）。同时设 `temperature=0.7, top_p=0.9`：**先除以 T、softmax，再按调温后的概率累加到 0.9 截断**，重新归一化后采样；降温会让 top-p 保留的候选变少。补充现状：截至 2026-10，Claude API `2026-10-21` 版对所有模型拒绝采样参数，稳定性改用 prompt、结构化输出和 effort；自部署开源模型仍可调。

### Q29 🟡 为什么 embedding 模型大多 encoder-only、对话模型 decoder-only？反过来用会怎样？

> 🙋 **问**：e5 用平均池化求句子向量。如果用因果注意力，第一个 token "我想"的向量能包含后面"爸妈""养老"吗？对平均结果有什么影响？
> 🧑 **我的回答**：不能，因果下"我想"只看到自己（只能看自己和之前的），平均后前面的向量信息不全
> 🤖 **点评**：✅ 正确：越靠后看到越多，**只有最后一个 token 看到全句**，平均被前半句拉偏。
> ➕ 新趋势：e5-mistral、Qwen3-Embedding 等 decoder 做 embedding（MTEB 排名靠前），改用 **last-token pooling（末位池化）**，或微调时改成双向 → 准确说法是"**传统上**以 encoder-only 为主"。

> 🙋 **问**：用双向 encoder 逐个生成，每生成一个新 token，旧 token 的 K、V 会怎样？对速度有什么影响？
> 🧑 **我的回答**：双向模型不能缓存KV，因为每一个token能看到后面的token，所以每次内容都在变。不能用KV缓存的话，每处理一个token都要把模型读到显存里，处理速度就慢了
> 🤖 **点评**：前半 ✅。后半 ⚠️ 不准确：权重**一直在显存里**，不会反复加载；有没有 KV Cache，Decode 每步都要读一遍权重（第 5 步固定成本）。真正多出来的是**计算量**：每步把前面所有 token 每层的 K、V 全部重算，总量 n → n²/2（约 1200 → 约 22 万）。
> ➕ 另一原因：**完形填空**训练的是"已知两边猜中间"，没练过"只凭前文往下写"，生成时右边不存在 → 训练和使用不匹配。

| 反过来用 | 问题 |
|---|---|
| decoder 做 embedding | 前面 token 看不到后文，平均被拉偏 → 末位池化 / 微调改双向 |
| encoder 做生成 | ① 训练方式不匹配；② 新 token 改变所有旧 token 的 K、V → **无 KV Cache**，计算 n → n² |

**📝 面试版答案**：关键在**注意力方向**。embedding 要把整句压成一个向量，**每个 token 都应看到全句** → **双向**，encoder-only 用完形填空训练正好学到，再平均池化得句子向量。对话要**从左到右逐个生成**，训练不能偷看、推理时后文不存在 → **因果**，旧 token 的 K、V 不变可缓存，Decode 每轮只算一个新 token。反过来：**decoder 做 embedding**，前面 token 看不到后文、平均会偏，所以 e5-mistral、Qwen3-Embedding 改用**最后一个 token 的向量**或微调成双向；**encoder 做生成**，训练方式不匹配，且每加一个 token 所有旧表示都变、**KV Cache 失效**，计算 n → n²。

### Q37 🔴 "你们 system prompt 每轮重复计费，为什么不开缓存？"——量化取舍

FinWise 实际数据：

| 项目 | 情况 |
|---|---|
| 模型 | `claude-haiku-4-5-20251001`（`app/config.py:17`） |
| system prompt | `prompts/risk_assessment_system.md`，1881 字符（962 汉字），无时间戳等变量 ✅ |
| 工具 | 4 个，序列化约 988 字符 |
| 前缀（tools + system） | **估计 2000~2500 token**（无 key，按字符估） |

最低缓存长度（claude-api 文档）：最新模型（Opus 5.5、Sonnet 5.5、Haiku 5.5 等）512；Sonnet 4.5 / 4.6、Opus 4.8 等 1024；Opus 4.7 2048；**Opus 4.5 / 4.6、Haiku 4.5 为 4096**（不随代际单调变化）。

> 🙋 **问**：现在在 system 末尾加 `cache_control`，第一轮能缓存吗？
> 🧑 **我的回答**：不能，前缀约 2500 token，低于 Haiku 4.5 的 4096
> 🤖 **点评**：✅ 且**不报错**（`cache_creation_input_tokens` 为 0），也不收写入溢价 → 只缓存 tools + system 在 Haiku 4.5 上**无效**。

> 🙋 **问**：一次评估约 15 次 LLM 调用、每次追加约 150 token、初始 2500，用顶层自动缓存，从第几次开始能缓存？几次受益？
> 🧑 **我的回答**：第 11 次开始，15 次里有 5 次能缓存
> 🤖 **点评**：✅（4096 − 2500）÷ 150 ≈ 10.6。⚠️ 细分：第 11 次是**写入**，第 12~15 次才**读取**（4 次）。TTL：agent 循环内几秒、用户回答 1~2 分钟，都在 5 分钟内且命中重新计时 → 不需要 1 小时档（写入 2 倍）。

> 🙋 **问**：第 11~15 次前缀近似 4100，不开 / 开缓存各花多少？占整场 55,500 的百分之几？
> 🧑 **我的回答**：不开 20500，开 6765，省约 13700，占 25% 左右。但有个问题，12-15次的写入成本怎么算？
> 🤖 **点评**：✅ 算对。追问很好——简化掉了：**自动断点每次后移**，第 12 次起每次 = 读上次缓存的前缀（0.1 倍）+ **写新追加的约 150 token（1.25 倍）**。新追加部分不开缓存也要付 1 倍，只多 0.25 × 150 ≈ 38 / 次，可忽略（文档：多轮时 `cache_creation_input_tokens` ≈ 上一轮输出 + 新追加输入，相对整段对话很小）。
> 精确重算（第 i 次输入 = 2500 + 150 × i）：第 11~15 次不开 22,250 / 开 7,688（全量写 5,188 + 读 1,750 + 新增写 750）→ 省约 14,560，**约 26%**。
> ➕ 对比：换成最低 512 的模型（如 Haiku 5.5）第 1 次就能缓存，整场约 11,000，**省约 80%**（单价不同只比比例；换模型要重评效果、用新 tokenizer 重数）。

> 🙋 **问**：用自己的话回答面试官"为什么不开缓存"。
> 🧑 **我的回答**：首先看对应的模型最小缓存长度是多少个token，如果在整个会话过程中，消耗的总token小于这个数，那开了也没用。如果在会话过程中，等到最后几次和LLM的交互消耗的token数才达到最低标准，那开了反而可能成本更高。比如在最后一次LLM交互中触发了缓存，这一次的写入成本提高，但后续没有机会再去读了。
> 🤖 **点评**：✅ 思路清楚，"最后一次才写入、后面没机会读"很敏锐。⚠️ 缺**数字和结论**：前缀始终不够长 → **零代价**（没写入就不收溢价）；只在最后一次写入、之后没读 → 白付一次溢价 0.25 × 约 4800 ≈ 1,200，约整场 **2%**；FinWise 实际（第 11 次写、12~15 次读）→ 省约 14,560，**26%**。只要后面还有 1 次读取就回本（1.25 + 0.1 < 2）→ **应该开**。
> ⚠️ 当初"暂不改"是**环境限制**（无 key、无法验证），不是技术不划算——面试时环境限制和技术取舍要分开说。

**📝 面试版答案**：**结论：应该开，但要清楚能省多少、何时生效。** ① 先看最低缓存长度：Haiku 4.5 是 **4096**，tools + system 只有约 2500 → 只缓存 system **完全无效且不报错**。② 多轮会变长：用**顶层自动缓存**，断点随对话后移；约 15 次调用、每次 +150，**第 11 次**超过 4096 写入，之后每次读取（0.1 倍）、只有新增部分按写入价 → 整场输入省**约 26%**。③ TTL：循环内几秒、用户回答 1~2 分钟，都在 **5 分钟**内且命中续期，不需要 1 小时档（写入 2 倍）。④ 风险：最坏只在最后一次写入后无读取，白付约 2%；前缀不够长零代价 → 期望收益远大于风险。⑤ 当初没开：无真实 key、bridge 不支持，**没法验证**；缓存失效不报错只是账单变高，上线要在集成测试断言第二次请求 `cache_read_input_tokens > 0` 并监控 usage。⑥ 更大杠杆是模型选型：换最低 512 的新模型从第 1 次就缓存，约省 **80%**（需重评效果、重数前缀）。

### 追问：cache 是不是可以无脑开？

> **❓ 我的追问**：所以其实在真实项目里，cache可以无脑开？因为最坏场景，最后一次交互触发了缓存但是之后没有用上，多出来的成本也很少？

**多轮 / agent 循环基本可默认开，但不能无脑开**：FinWise 最坏只多 2% 是因为**15 次里只白写 1 次**；换一种请求结构，可能**每次都白写**。

```
成本比 = (1.25 + 0.1 × r) ÷ (1 + r)
```

| 符号 | 含义 | 取值来源 |
|---|---|---|
| 1.25 | 写入一次（5 分钟档） | 定价 |
| 0.1 | 每次读取 | 定价（Opus 5.5 为 0.05） |
| r | 这份缓存过期前**被读几次** | 请求结构和流量（FinWise 第 11 次写入后 r = 4） |
| 1 + r | 不开缓存时这段前缀被全价算几次 | 写 1 次 + 读 r 次 |

r = 0 → 1.25（**多 25%**）；r = 1 → 0.68；r = 4 → 0.33；r = 10 → 0.21。**只要 r ≥ 1 就省；每个请求都 r = 0 就整体多付 25%。**

| r 长期为 0 的场景 | 原因 | 例子 |
|---|---|---|
| ① 每个请求从开头就不同 | 无可复用前缀 | system 开头放时间戳 |
| ② 共享部分短、独有部分长，又用自动缓存 | 自动断点落在**独有内容之后**，每次写、永远读不到 | **Q30 的 2000 份摘要**：每次把整份说明按 1.25 倍写入 → 输入多 25% |
| ③ 流量稀疏 | 间隔超过 TTL，没读就过期 | 每小时一次的定时任务用 5 分钟档 |
| ④ 并发 | 缓存要等第一个请求**开始返回**才可读，同时发的 N 个各写一遍 | 并发 50 个摘要 |
| ⑤ 隐形失效 | 前缀里有东西在变 | 工具顺序不固定、`json.dumps` 没 `sort_keys` |

⚠️ ⑤ 最危险：以为在省钱，实际每次多付 25%，不报错、可能几个月没人发现。

| 场景 | 做法 |
|---|---|
| 多轮对话、agent 循环（FinWise） | **默认开顶层自动缓存**（文档："Automatic is the right default for multi-turn conversations"）+ 固定 system 加显式断点 |
| 共享指令 + 每次不同内容（Q30） | 不用自动缓存，**只在共享指令末尾放显式断点**；指令低于最低长度就不开 |
| 批量并发 | 先发 1 个写好缓存，开始返回后再并发其余 |
| **任何场景** | **开了必须验证** `cache_read_input_tokens > 0`，测试 / 监控长期盯 |

### 追问：2000 份摘要是不是应该每份一个独立会话？

> **❓ 我的追问**：你说的那"那 2000 份摘要"的场景，处理这种任务，是不是就不应该在一个会话里处理2000份文档？是不是应该做成每个文档是一个独立的会话？（提示词里只包含一个文档的内容）

✅ 对，**每份一个独立请求**（"摘要指令 + 这一份文档"），Q30 估算也是按这个结构算的。

- **API 在服务端没有会话**：每个请求独立，"多轮"= 客户端每次重发完整历史（🔁 第 6 步 6.3）。"一个会话处理 2000 份" = 第 k 次带上前面 k−1 份和摘要。

| 放一个会话的问题 | 说明 |
|---|---|
| 成本平方级 | 总输入约 2000²/2 份，独立请求的约 **1000 倍**；缓存读 0.1 倍也还约 100 倍 |
| 上下文装不下 | 2000 × 1500 ≈ 300 万 token > 1M |
| 质量下降 | 注意力被旧文档分散，还会**串台**（上一份的信息写进这一份） |
| 失败无法隔离 | 一份出错后面全受影响；独立请求只重试失败那份 |
| 无法并行 | 只能串行；独立请求可并发或交给 **Batch API**（半价） |

➡️ 原则：**任务间没有依赖就不共享上下文**，每个请求只放当前任务**需要的**内容（L06 上下文工程核心）。

- 回到缓存（场景 ②）：`[摘要指令（都一样）][这一份说明（每次不同）]` → 自动缓存每次白写；正确做法：**指令在前、文档在后，只在指令末尾放显式断点**；指令低于最低长度就**不开**，省钱靠 Batch API 半价。

### 📌 要记住的（第 9 步）
> **Q28**：T 在 softmax 前除 logits（缩放差值），T → 0 贪心、T → ∞ 均匀；先温度后 top-p，降温让 top-p 保留更少。
> **Q29**：embedding 要每个 token 看全句 → 双向；生成要逐个写、可缓存 → 因果；反用：decoder 平均被拉偏（改末位池化），encoder 训练不匹配 + 无 KV Cache（n → n²，多的是计算不是加载）。
> **Q30**：中文通常更贵但看 tokenizer（语料比例）；`max_tokens` 是硬上限，查 `stop_reason`；用目标模型自己的 tokenizer 数（Claude `count_tokens`，免费），输出抽样实测。
> **Q37**：先看最低缓存长度（Haiku 4.5 = 4096），多轮自动缓存约省 26%、最坏约多 2% → 应该开；环境限制 ≠ 技术取舍。**缓存划算条件 = 过期前被读 r ≥ 1 次**；每次都不同 / 稀疏 / 并发 / 隐形失效时 r = 0 多付 25%；独立批量任务只在共享指令末尾放显式断点。**API 无服务端会话**，互不依赖的任务每份独立请求。
