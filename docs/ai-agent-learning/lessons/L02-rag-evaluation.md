## 第 1 步 · 为什么只有检索指标不够

### 🔁 回顾
- **Hit@K**：正确答案有没有进前 K；**MRR**（Mean Reciprocal Rank，平均倒数排名）：正确答案排第几（1、0.5、0.33…，没进记 0，取平均）。两者**只看检索**。
- **RAG = 检索 + 生成**（s4_02）：用户看到的是 LLM 的回答，不是检索结果。
- L01 Q31：排查"答非所问"第一刀就是分"检索的锅 / 生成的锅"。

> **💬 课堂问答**
>
> **🙋 问**：检索在 golden set 上满分（Hit@5 = 1.00），正确产品都交给了 LLM，用户还可能拿到糟糕回答吗？有哪些情况？  
>
> **🧑 我的回答**：1. 题目里的面查询文本太过于理想，和实际用户口语化的输入相去甚远 2. 给模型的提示词有问题  
>
> **🤖 点评**：① ✅ 这是对 eval 本身的质疑（🔁 s5_01"结论取决于题"），但偏离了本题前提（检索确实做对了）——记作"检索指标本身可能不可信"，另一类问题。  
> ② ✅ 方向对，⚠️ 太笼统：面试官会追问"具体出什么样的坏回答"，要能说出具体失败模式（下表）。

### 检索全对，生成仍可能出的五种问题（FinWise 例：用户问"随时要用、别亏本"，资料里有 P-MMF）

| 失败模式 | 例子 | 🔁 之前在哪见过 |
|---|---|---|
| ① 编造 | "稳盈货币A 年化约 **2.5%**"（资料没写收益率） | s4_02 grounding |
| ② 张冠李戴 | "科技创新股票**几乎无波动**"（货币基金的特点） | s4_02b 硬校验 |
| ③ 答非所问 | 问"能不能随时取"，答"收益有多高" | L01 Q31 |
| ④ 挑错 / 漏掉 | 推荐"短债 30 天持有"（取钱要等 30 天） | lost in the middle |
| ⑤ 拒答失当 | 资料不够硬编；资料够却说"暂无合适产品" | s4_02"房贷"题 |

### 检索 × 生成 四格表

| | 生成好 | 生成坏 |
|---|---|---|
| **检索好** | ✅ 正常 | ❌ 上表 ①~⑤（**检索指标完全看不到**） |
| **检索坏** | 老实说"没有合适的"（算好表现） | ❌ 拿错资料硬答 |

Hit@K / MRR 只能看"检索好不好"这一行，**右上角那格测不到** → 必须加**生成侧指标**（第 3 步 RAGAS）。

### 📌 要记住的
> 检索满分，回答仍可能坏：**编造、张冠李戴、答非所问、挑错漏掉、拒答失当**。检索指标只看"资料找没找对"，必须加**生成侧指标**（忠实度、答案相关性）。

## 第 2 步 · 检索侧补全：Hit@K → Recall@K / Precision@K → nDCG

🔁 s5_01 的 golden set 是 `(query, 期望 code)`，**每题只有一个正确答案**；Hit@K 问"这一个对的进没进前 K"。

### 多个相关文档时，Hit@K 会掩盖问题

> **💬 课堂问答**
>
> **🙋 问**："有哪些低风险、不怎么亏的产品？"相关的有 3 个（P-MMF、P-BOND、P-SHORTBOND），前 5 名只命中 P-MMF。Hit@5 是多少？准确吗？怎么改进？  
>
> **🧑 我的回答**：Hit@5 是 1，不准确，3 个只找到 1 个，但是因为goldenset里只写了一个期望结果，所以误认为hit rate很高，应该改进golden set  
>
> **🤖 点评**：✅ 都对，golden set 要**列全**相关文档。  
> ➕ 但光改 golden set 不够：Hit@K 的**定义**是"至少一个进了前 K"，写全 3 个后这题 Hit@5 **仍是 1** → 指标也要换成 Recall@K。

| 指标 | 问的问题 | 公式 | 这道题 |
|---|---|---|---|
| Hit@K | 有没有**至少一个**相关的进前 K | 有 1 / 无 0 | 1 |
| **Recall@K**（召回率） | 相关的**找到了几成** | 前 K 里相关数 ÷ **全部相关数** | 1 ÷ 3 = **0.33** |
| **Precision@K**（精确率） | 前 K 里**几成是相关的** | 前 K 里相关数 ÷ **K** | 1 ÷ 5 = **0.20** |

符号：K = 看前几名（5）；前 K 里相关数 = 前 5 名中出现在 golden set 相关列表里的个数（1）；全部相关数 = golden set 里这题写的相关产品数（3）。
🔁 召回 = "别漏"，精确 = "别错"（concepts-basics「Eval」），"@K" = 只看前 K 名。每题只有一个正确答案时 **Recall@K = Hit@K**。

### 名次也要算进去：MRR 的盲点 → nDCG

> **💬 课堂问答**
>
> **🙋 问**：A = ✅✅✅❌❌，B = ❌❌✅✅✅。Recall@5 各是多少？能区分吗？MRR 呢？  
>
> **🧑 我的回答**：都是 1，Recall 区分不了，A 更好  
>
> **🤖 点评**：✅ 对。  
> ➕ MRR（没答）：A = 1，B = 1/3，能区分；但 MRR **只看第一个相关文档**——C = ✅❌❌✅✅ 的 MRR 也是 1，和 A 分不开 → 需要把每个相关文档的名次都算进去：nDCG。

📛 **nDCG = Normalized Discounted Cumulative Gain**（归一化折损累计增益），从后往前拆：
- **Gain**：每个文档的得分（相关 1、不相关 0；可分级如 3/2/1）
- **Cumulative**：前 K 名得分相加
- **Discounted**：越靠后打折越多（除以 log₂(名次 + 1)）
- **Normalized**：除以理想排序下的得分 → 0~1

```
          K     rel_i
DCG@K =   Σ   ───────────          nDCG@K = DCG@K ÷ IDCG@K
         i=1   log₂(i + 1)
```

| 符号 | 含义 | 值从哪来 | 例子 |
|---|---|---|---|
| i | 名次，从 1 开始 | 检索结果顺序 | 1~5 |
| rel_i | 第 i 名的相关度 | **golden set 标注** | ✅ = 1，❌ = 0 |
| log₂(i + 1) | 折损分母，名次越后越大 | 公式固定 | 见下表 |
| DCG@K | 实际排序的累计得分 | 计算 | — |
| IDCG@K | **I**deal DCG：相关文档全排最前时的 DCG | 按理想顺序算 | A 就是理想排序 |

| 名次 i | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 折扣 1/log₂(i+1) | 1.000 | 0.631 | 0.500 | 0.431 | 0.387 |

```
A：✅ ✅ ✅ ❌ ❌    DCG = 1 + 0.631 + 0.5     = 2.131    nDCG = 1.000
B：❌ ❌ ✅ ✅ ✅    DCG = 0.5 + 0.431 + 0.387 = 1.318    nDCG = 0.618
```
- 为什么归一化：不同题相关数不同（3 个相关最高 2.131，1 个相关最高 1），除以 IDCG 才能跨题平均。
- MTEB 检索榜主要指标就是 **nDCG@10**（第 6 步）。

> **💬 课堂问答**
>
> **🙋 问**：算 C = ✅❌❌✅✅ 的 nDCG@5（IDCG = 2.131）。和 A 比，nDCG 能区分吗？  
>
> **🧑 我的回答**：C 的 DCG = 1.818，nDCG ≈ 0.853，能区分，A 更好  
>
> **🤖 点评**：✅ 完全正确：1 + 0.431 + 0.387 = 1.818，÷ 2.131 ≈ 0.853。A 和 C 的 MRR 都是 1，nDCG 分得开。

### 检索侧指标总表

| 指标 | 问的问题 | 看几个相关 | 在乎名次 | A / B / C |
|---|---|---|---|---|
| Hit@K | 至少一个进前 K | 至少一个 | ❌ | 1 / 1 / 1 |
| Recall@K | 找到了几成 | 全部 | ❌ | 1 / 1 / 1 |
| Precision@K | 前 K 里几成相关 | 全部 | ❌ | 0.6 / 0.6 / 0.6 |
| MRR | 第一个相关排第几 | 只看第一个 | ✅ | 1 / 0.33 / 1 |
| **nDCG@K** | 整体排得好不好 | 全部 | ✅ | **1 / 0.618 / 0.853** |

### 📌 要记住的
> 单一正确答案：**Hit@K + MRR** 够用（s5_01）。多个相关文档：golden set **列全**，用 **Recall@K**（找全没）+ **nDCG@K**（排得好不好，越靠后折扣越多、支持分级相关度）。Precision@K 看混进了多少噪声。MTEB 检索榜主指标是 nDCG@10。

## 第 3 步 · RAGAS 四指标（进入生成侧）

📛 **RAGAS = Retrieval-Augmented Generation Assessment**（RAG 评估），2023 年的开源评估框架（Python 库 `ragas`）。核心思路：**一次 RAG 请求有三样东西，两两比较得到不同指标**。

```
                 ① question（用户问题）
                 ╱                    ╲
   Context      ╱                      ╲    Answer Relevancy
   Precision   ╱                        ╲   （答案有没有回答问题）
   （检索资料   ╱                          ╲
   相不相关）
  ② contexts（检索到的资料）───────────── ③ answer（LLM 的回答）
                      Faithfulness
              （回答里说的，资料里有没有依据）

  另加 ④ reference（标准答案）→ Context Recall：资料是否覆盖标准答案需要的全部信息
```

| 指标 | 比较的是 | 问的问题 | 属于 |
|---|---|---|---|
| **Context Precision** | question ↔ contexts | 检索资料相不相关、相关的排得靠不靠前 | 检索侧 |
| **Context Recall** | reference ↔ contexts | 标准答案里的信息，资料覆盖了多少 | 检索侧 |
| **Faithfulness**（忠实度） | answer ↔ contexts | 回答里每句话，资料里有没有依据 | 生成侧 |
| **Answer Relevancy**（答案相关性） | answer ↔ question | 回答有没有针对问题、有没有跑题 | 生成侧 |

和 Hit@K 最大的区别：**不依赖文档 id 标注**，而是让 **LLM 当评审**读文字、做判断（第 5 步）→ 能评主观的东西，代价是评审本身也会错。

> **💬 课堂问答**
>
> **🙋 问**：第 1 步那五种问题（① 编造 ② 张冠李戴 ③ 答非所问 ④ 挑错 ⑤ 拒答失当），分别被 RAGAS 哪个指标抓到？  
>
> **🧑 我的回答**：①② ⑤是 Faithfulness，③ ④是 Answer Relevancy  
>
> **🤖 点评**：✅ ①②（没依据 / 和资料矛盾）→ Faithfulness；③ → Answer Relevancy。  
> ⚠️ ④ 挑错（随时要用却推荐 30 天持有的短债）**两个都很可能抓不到**：回答里每句资料都有（忠实度满分），也没跑题（相关性高）——问题是"选错了"，四个指标都不判断"对不对"。  
> ⚠️ ⑤ "资料够却说暂无合适产品"应是 **Answer Relevancy**：这句话没有事实可核对，Faithfulness 抓不到；Answer Relevancy 专门惩罚**敷衍回答**（noncommittal）。反过来"资料不够却硬编"才是 Faithfulness 抓的。

| 问题 | 谁能抓 |
|---|---|
| ① 编造 | Faithfulness |
| ② 张冠李戴 | Faithfulness |
| ③ 答非所问 | Answer Relevancy |
| ④ 挑错 | ❌ 四个都抓不到 → **Answer Correctness**（和 reference 标准答案比）或**业务规则硬校验**（"随时要用"→ 不能有最短持有期；🔁 B#7 / s4_02b"用代码核对"） |
| ⑤ 该答却拒答 | Answer Relevancy（noncommittal 惩罚）；该拒答却硬编 → Faithfulness |

### 📌 要记住的
> RAGAS 四指标 = 三样东西（question / contexts / answer）+ reference **两两比较**：Context Precision、Context Recall（检索侧），Faithfulness、Answer Relevancy（生成侧）。
> **盲区**：只判断"有没有依据""有没有跑题"，**不判断"答得对不对"** → 选错产品要靠 **Answer Correctness** 或**业务规则硬校验**。

## 第 4 步 · 忠实度怎么算；幻觉率、引用准确率

### Faithfulness 的计算
```
① 拆陈述：让 LLM 把回答拆成一条条独立、可核对的陈述（claim）
② 逐条核对：让 LLM 判断每条能不能从资料（contexts）推出

Faithfulness = 有依据的陈述数 ÷ 全部陈述数
```

| 符号 | 含义 | 值从哪来 |
|---|---|---|
| 陈述（claim） | 回答里一条独立的事实性说法 | LLM 拆 |
| 有依据 | 能从检索资料推出 | LLM 逐条判 |
| Faithfulness | 0~1，1 = 每句都有依据 | 计算 |

> **💬 课堂问答**
>
> **🙋 问**：问"随时要用，别让我亏本"；资料"稳盈货币A：货币市场基金，随时申购赎回，几乎无波动，适合放随时可能用到的活钱和应急备用金。"；回答"推荐稳盈货币A。它是货币市场基金，可以随时申购赎回，几乎没有波动，年化收益约2.5%，非常适合存放应急备用金。"拆成陈述、逐条判断、算 Faithfulness。  
>
> **🧑 我的回答**：6 条陈述，年化 2.5% 那条没依据，Faithfulness = 5/6 = 0.83  
>
> **🤖 点评**：✅ 判断对：只有"年化 2.5%"没依据。  
> ➕ 我拆是 5 条（货币基金 / 随时申赎 / 几乎无波动 / 年化 2.5% ❌ / 适合应急备用金）→ 0.80。**拆的粒度不同分数就不同**（RAGAS 由 LLM 拆，每次可能不同 = 噪声）；**判得松严也不同**（资料"适合"、回答"**非常**适合"算不算夸大？）。  
> → Faithfulness **适合看趋势、做对比**（同一评审、同一套题），不宜当精确绝对值。

### 幻觉率、引用准确率

- **幻觉率（Hallucination Rate）**：含**至少一条**无依据陈述的回答 ÷ 全部回答。**按回答**统计。
- 对比：Faithfulness **按陈述**统计。10 个回答都是"5 句错 1 句" → 平均 Faithfulness 0.80，**幻觉率 100%**。
- **引用准确率（Citation Accuracy）**：回答标注了出处（如"[来源：P-MMF]"）时，检查每个引用是否真的支持它所在的那句话。🔁 s4_02b 的 `recommended_code ∈ 检索候选集` 就是**用代码做的引用校验**（确定性，不需要 LLM 评审）。

> **💬 课堂问答**
>
> **🙋 问**：FinWise 理财推荐，上线看板只能选一个监控"幻觉"：Faithfulness（平均 0.80）还是幻觉率（100%）？  
>
> **🧑 我的回答**：幻觉率，金融场景一句编错的收益率就可能误导用户  
>
> **🤖 点评**：✅ 对：金融看"有没有错"，不看"平均对几成"，平均分会把风险平均掉。  
> ➕ 两者不是二选一：**幻觉率当红线**（看板），**Faithfulness 用来诊断和比较**（幻觉率没变但 Faithfulness 0.80 → 0.90，说明在改善）。  
> ➕ 陈述重要程度不同："年化 2.5%"错 ≠ 多了个"非常"。**关键字段**（收益率、风险等级、持有期）用**代码硬校验**：正则抽出数字和等级，检查是否原样出现在资料里，没有就拦。🔁 L01 第 6 步代码硬校验、B#7 关键值去模型化。

### 📌 要记住的
> **Faithfulness = 有依据陈述 ÷ 全部陈述**，受"怎么拆""判多严"影响，适合同一评审方式下做比较。
> 高风险场景看**按回答统计的幻觉率**（一句错就算错）。**关键字段用代码硬校验**，LLM 评审覆盖其余难写成规则的部分。引用准确率 = 每个出处是否真支持那句话，能用代码核对就用代码。

## 第 5 步 · LLM-as-judge：怎么用、有哪些偏差、怎么校准

RAGAS 的 Faithfulness / Answer Relevancy 背后都是 **LLM-as-judge**（让一个 LLM 评判另一个 LLM 的输出）。🔁 阶段五路线图：规则能断言的先用规则，主观质量交给 LLM 评审（当时没动手，第 8 步写一个）。

```
评审 prompt（评分标准）+ 被评的东西（问题、资料、回答）→ LLM 评审 → 结构化输出 {理由, 判定}
```

### 四种常见偏差及对策

| 偏差 | 表现 | 对策 |
|---|---|---|
| 位置偏差（position bias） | 比较 A、B 时偏向排前面的（也有偏后的） | **交换顺序再评一次**，两次一致才算 |
| 长度偏差（verbosity bias） | 偏爱更长更详细的回答 | 标准写明"长度不加分"；用"有没有依据"这类**二元问题** |
| 自我偏好（self-preference） | 偏爱同一模型 / 同家族生成的 | 评审用**不同家族**或更强的模型 |
| 宽松偏差 | 普遍偏高，区分不出好坏 | **二元判断**或少量档位（别用 1~10 分）；每档给**具体例子** |

> **❓ 我的追问**：关于"自我偏好"，评审的 LLM 怎么知道喂给它的内容是自家模型产出的？  

**它不需要"知道"**——输入里没有"这是 Claude 生成的"标签，偏好来自**文字本身的特征**：
1. **自家的文字在它看来"更顺"**：🔁 LLM 本质是算下一个 token 的概率（自回归），自己生成的文字用词、句式都是它认为概率最高的写法 → 读起来"很顺"，而"顺"容易被当成"好"。（类比：人更容易觉得和自己文风相近的文章写得好。）
2. **同家族模型的"审美"相同**：训练数据和偏好调教相似，对"好回答长什么样"偏好一致（分点列、某种谨慎措辞）→ 用同一把有偏差的尺子量自己。
- 研究发现 LLM 能以高于随机的准确率认出自己的文字，且认得越准自我偏好往往越强——但靠的也是**文风**，不是标签。
- 对策：**去掉来源信息没用**；**换不同家族模型**当评审；或让评审只做**二元事实判断**（"这句资料里有没有"），受"顺不顺"影响小。
- ⚠️ **本课已知局限**：第 8 步生成和评审都经 bridge 用 Claude（自己评自己），学习环境换不了模型；评的是"有没有依据"这类二元事实判断，影响相对小。

> 📌 自我偏好不靠认出标签，而来自文字特征（自家文字概率高更顺、同家族审美一致）→ 去掉来源没用，要**换家族**或只做**二元事实判断**。

### 评审输出的字段顺序

> **💬 课堂问答**
>
> **🙋 问**：评审的结构化输出有 `verdict`（判定）和 `reason`（理由），schema 里哪个放前面？为什么？  
>
> **🧑 我的回答**：reason 放前面，先写理由再下判定，之前学过，LLM输出的时候，已经输出的内容会影响后面要输出的内容，所以把reason放在前面，反过来的话，LLM就有可能是对着结果硬编一个reason  
>
> **🤖 点评**：✅ 完全正确，原理也对。  
> ➕ 用 05 的术语：**自回归生成**；reason 在前 = 先推理再结论（CoT）；verdict 在前 = **事后找补**。生效的是 `properties` 顺序，`required` 顺序无效。  
> ➕ reason 还是给**人**看的审计线索，复查评审时比只看判定有用得多。

### 怎么知道评审本身靠不靠谱

> **💬 课堂问答**
>
> **🙋 问**：怎么验证"这个 LLM 评审判得准不准"？（提示：s5_01 的 golden set 是你亲手标的）  
>
> **🧑 我的回答**：人工标一批样本，和评审的判定对比一致率  
>
> **🤖 点评**：✅ 对，这就是 **eval 的 eval**。➕ 细节决定靠不靠谱（下表）。

| 细节 | 怎么做 | 原因 |
|---|---|---|
| 样本量 | 起步 30~100 条 | 🔁 s5_02：太少则一致率本身不可信 |
| 样本构成 | 两类都要有，**刻意放难判的**（"非常适合"式夸大、只差一个数字） | 全是简单题一致率虚高（🔁 L01 天花板效应） |
| 看什么数 | 除总一致率，**重点看"无依据"那类被抓到多少**（对幻觉的召回） | 90% 样本有依据时，评审全判"有依据"也有 90% 一致率 |
| 迭代 | 看判错样本 → 改评审 prompt → 再测；**留一部分不参与调 prompt**，最后单独测 | 否则是"针对考题调参" |
| 重新校准 | 评审模型或 prompt 一变就重测 | 校准只对当时那个评审有效 |

📛 **Cohen's Kappa**（科恩 Kappa 系数）：**扣除碰巧一致之后**的一致率，正好处理"全判有依据也有 90%"的问题。知道名字和用途即可。

### 📌 要记住的
> LLM-as-judge 有**位置、长度、自我偏好、宽松**四种偏差 → 交换顺序、二元判断、换家族模型、给档位例子。输出 **reason 在前、verdict 在后**。
> **验证评审 = 人工标 30~100 条（含难判的）算一致率**，重点看幻觉有没有被抓到；按判错样本迭代，留一部分做最终测试；换模型就重新校准。

|---|---|

## 第 7 步 · 从 RAG 到 agent，再到线上

面试原题："怎么判断 agent 的实际能力已经达标？" agent 要多步决策（调哪个工具、填什么参数、何时停），评估要分层：

| 层 | 问的问题 | 指标举例 |
|---|---|---|
| **结果** | 任务最终做成没有 | 任务完成率；FinWise **定级准确率**（🔁 s5_02） |
| **过程**（轨迹） | 中间每步对不对 | 工具选择正确率、参数正确率、步数、有没有死循环 |
| **安全与鲁棒** | 刁钻输入会不会出事 | 负向测试（该拒绝的拒绝没）、prompt 注入测试、边界输入 |
| **线上** | 真实用户用得怎样 | 用户干预率（转人工、重问、👎）、投诉 |

> **💬 课堂问答**
>
> **🙋 问**：风险评估 agent 定级准确率 100%，但 trace 显示正常 5 题能评完，它平均问 15 题，还会重复问。只看结果层会漏什么？上线后果？  
>
> **🧑 我的回答**：漏了过程指标，效率低、成本高，用户会烦  
>
> **🤖 点评**：✅ 三点都对。➕ 两个更隐蔽的风险：  
> ① **重复提问是 bug 信号**：没记住用户答过的内容（🔁 上下文即内存：历史拼装或 State 漏存），结果对可能只是"问到最后碰巧评对"。  
> ② **离线结果虚高**：模拟用户会耐心答完 15 题，真实用户第 8 题就可能关页面 → 线上完成率明显低于离线；平均 15 步意味着有人 20+ 步，接近 `MAX_AGENT_STEPS` 会被兜底截断。

过程层要补的指标：

| 指标 | 能发现什么 |
|---|---|
| 平均 / P95 步数 | 效率；有没有用户接近步数上限 |
| 重复调用次数（同问题 / 同参数工具） | 记忆或状态 bug、死循环苗头 |
| 每任务 token 数 / 成本 | 15 步约是 5 步的 3 倍 |
| 每任务耗时 | 用户要等多久 |

### 8a · 评审输出的 schema ✅
```python
"claim": {"type": "string"},
"reason": {"type": "string"},
"verdict": {"type": "string", "enum": ["有依据", "无依据"]},
```
- 顺序 claim → reason → verdict（先写判的是哪句，再推理，再判定）。
- `enum` 把取值限死，避免"基本有依据""部分有"这种没法统计的答案（🔁 风险等级只能 C1~C5 同理）。
- 可选：给字段加 `description`（🔁 05 schema 即 prompt，description 也是指令）。

| 先写 reason 再下 verdict | 第 5 步 |

### 8c · `score()` ✅
```python
if not claims:                      # 没有事实陈述可核对（如正确拒答）→ 不算幻觉
    return 1.0, False
supported = sum(1 for c in claims if c.get("verdict") == "有依据")
return supported / len(claims), supported < len(claims)
```
- `supported < len(claims)` = 至少一条无依据，复用已算好的数。
- `c.get()` 而非 `c[]`（🔁 03 别信模型的结构）。顺带形成好的默认：verdict 缺失、拼错、其他值**都算无依据** → 评审输出出问题时偏向"判有幻觉"。📛 **fail-closed**（出错时关闭 = 默认拒绝），相对 fail-open（出错时放行）。金融场景要 fail-closed。

### 8d · `unsupported_numbers()` ✅（修过一次）

初版：`[n for n in re.findall(r"\d+(?:\.\d+)?", answer) if n not in context]`
正则：`\d+` 一个或多个数字；`(?:\.\d+)?` 可选的小数部分，`(?:...)` 是**不捕获分组**（否则 findall 只返回括号里那段）。

| 做法 | 怎么实现 | 特点 |
|---|---|---|
| 业务规则硬校验 | 推荐产品风险等级 C4/C5 时，回答**必须含**风险提示词（"亏损""波动大""风险"），否则拦 | 确定、不漏判；风险等级来自数据库不来自模型（🔁 B#7） |
| 单独的评审问题 | "回答是否完整传达了资料里的风险提示？" | 能处理换说法，但有评审偏差 |

> **💬 课堂问答**
>
> **🙋 问**：answer = "最短持有3天就能取出来"，context 含"最短持有30天"，你的函数返回什么？对吗？  
>
> **🧑 我的回答**：返回空列表，"3" 也算在资料里了，漏判  
>
> **🤖 点评**：✅ 对：`"3" in "…30天…"` 是子串匹配，误导性的"3 天"被放行。同类："5"被"2.5"骗、"20"被"2040"骗。  
> ➕ 修法：资料也先抽成数字 **set**，比较**元素完全相等**（🔁 set 的 `in` 不做子串匹配）。

修复后（加了测试 `test_numbers_not_fooled_by_substring`，12/12 通过）：
```python
context_numbers = set(re.findall(r"\d+(?:\.\d+)?", context))
return [n for n in re.findall(r"\d+(?:\.\d+)?", answer) if n not in context_numbers]
```

| 情况 | 例子 | 为什么漏 |

> **🙋 问**：评审与人工 8/8 一致、幻觉 4/4 全抓到。能下结论"评审很可靠、可以上线"吗？

> **🧑 我的回答**：目前还不能，因为样本太少

> **🤖 点评**：✅ 最主要的问题。➕ 对照第 5 步的表还缺这些：

| 第 5 步的要求 | 这次的情况 | 缺什么 |
|---|---|---|
| 样本量 30~100 | 只有 8 条 | 你答到的这点 |
| 刻意放难判样本 | 都是手写的、界线分明；难判的只有 S2"非常适合" | 更多边界情况，最好用**线上真实 bad case**（🔁 第 7 步闭环） |
| 留一部分不参与调 prompt | 写 prompt 时已知道 8 条考什么，规则基本对着写 | 需要**写 prompt 时没见过的**样本单独测，否则是对着考题调参 |

### 📌 要记住的
> 评审 schema：**claim → reason → verdict**，verdict 用 enum 限死；评审输出异常时 **fail-closed**（按无依据算）。
> **Faithfulness 衡量"有没有根据"，不是"对不对"**：资料外的内容哪怕是事实也判无依据。
> **"说错"和"漏说"是两类问题**：遗漏风险提示 Faithfulness 抓不到，要**单独检查**（业务规则硬校验 + 专门评审问题）。
> **硬校验与评审互补**：硬校验确定但覆盖窄（只管数字），要做**精确匹配**（两边都抽成集合）；评审覆盖广但有偏差和随机性。

## 第 9 步 · 穿插复习题

### Q32 · 如何降低幻觉：三层可落地方案 ✅

> 原题：如何降低 hallucination？给出三层可落地方案，并说清每层在 FinWise 里对应哪段代码或机制。

🔁 回顾：concepts-basics「Grounding 与分层防御」（prompt 是软约束，**越往下越硬**）；s4_02b 开头的四层（prompt grounding → 结构化 + 引用约束 → 服务端硬校验 → 兜底话术）；mock-interview Q9。

> **💬 课堂问答**
>
> **🙋 问**：按 RAG 管线（检索 → 生成 → 返回给用户），三个阶段分别怎么防幻觉？  
>
> **🧑 我的回答**：检索 -> 通过query重写，RRF多路检索，重排得到尽量理想的检索结果；生成 -> 把答案拆分成若干claims，LLM根据RAG的返回结果，给出评审（哪些claim是有依据的，哪些是没依据的）；返回给用户 -> 做校验，比如检查返回的产品code，名字是否真实存在  
>
> **🤖 点评**：✅ 检索：正是 L01。➕ 再加**相关性闸门**（top-1 相似度低于阈值 → 当作没有资料，让模型说不知道）。  
> ⚠️ 生成：拆 claim + 评审是**生成之后的检查**，属于第 3 层。生成层问的是"**怎么让模型从一开始就少编**"= 限制自由度（下表）。  
> ✅ 返回：正是 s4_02b 硬校验。➕ LLM 评审也放这层；拦下后要有**兜底话术**。

生成层 = 限制模型自由度：

| 手段 | FinWise 里在哪 |
|---|---|
| grounding prompt："只用资料，没有就说没有" | s4_02 `SYSTEM_PROMPT` |
| 结构化输出 + 强制引用 | s4_02b `recommended_code` |
| 关键值不让模型生成，由代码算 | B#7 风险等级由代码计算 |
| 降低 temperature | 输出更保守（🔁 阶段一） |
| 允许拒答 | s4_02"房贷"题 |

完整三层：
```
第 1 层 · 检索：给模型对的资料
  query 改写、混合检索 + RRF、重排（L01）、相关性闸门
                ↓
第 2 层 · 生成：让模型少编
  grounding prompt（s4_02）、结构化 + 强制引用（s4_02b）、关键值由代码算（B#7）、低 temperature、允许拒答
                ↓
第 3 层 · 验证 + 兜底：编了也拦住
  code 必须在候选集里（s4_02b）、数字硬校验（s5_03）、LLM 评审（s5_03）、风险提示完整性检查
  → 拦下后返回安全话术（fail-closed）
```

> **💬 课堂问答**
>
> **🙋 问**：把 LLM 评审放到线上、每个回答返回前同步跑一次，有什么代价？哪些场景值得同步，哪些可以换方式？  
>
> **🧑 我的回答**：延迟会增加一倍，高风险场景同步跑，其他抽样异步跑, 不直接作用到给用户的输出，可以存下来，作为后期优化的依据  
>
> **🤖 点评**：✅ 三点都对，"存下来作为优化依据"正好接上第 7 步闭环。  
> ➕ 代价不止延迟翻倍：评审输出常比原回答还长（可能不止一倍）；**成本** token 至少翻倍；**流式体验**没了（要等评审完才能给用户看；🔁 04 第七节 FinWise 本就缓冲结构化输出，影响较小）。  
> ➕ 中间还有一档：**便宜的代码硬校验永远同步跑**（下表）。

| 手段 | 耗时 | 怎么跑 |
|---|---|---|
| 代码硬校验（code ∈ 候选集、数字精确匹配、高风险必带风险提示词） | 毫秒 | **全量同步** |
| LLM 评审 | 秒级 | **只对高风险回答同步**（推荐 C4/C5、带收益率数字） |
| LLM 评审（抽样） | 不影响用户 | **其余抽样异步** → 看板（幻觉率趋势）+ bad case 池（人工复核后进 golden set） |

### 📌 要记住的
> **降低幻觉三层**：① **检索**给对资料（改写、混合检索、重排、相关性闸门）② **生成**限制自由度（grounding、强制引用、关键值由代码算、低温度、允许拒答）③ **验证 + 兜底**编了也拦住（硬校验、LLM 评审，拦下返回安全话术）。越往下越硬。
> **线上评审分层跑**：代码硬校验全量同步；LLM 评审只对高风险同步；其余抽样异步进看板和 bad case 池。代价是延迟、成本、流式体验。
