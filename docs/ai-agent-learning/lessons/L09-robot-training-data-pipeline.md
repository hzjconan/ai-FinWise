## 第 1 步 · 从视频到 batch

假设一个行为克隆训练样本包含时刻 t 的多路相机最近几帧、本体状态 / 指令，以及对齐的示范动作片段作为监督目标。具体输入与动作窗口由模型设计决定，不是所有模型都相同。

```text
对象存储 / 本地数据
  → 按样本定位视频片段与对应状态 / 动作
  → 读取文件 / 字节
  → 解码成帧
  → 帧采样与预处理（缩放、归一化、按需增强）
  → 组装样本并拼成 batch
  → 送到计算设备
  → 前向、反向、更新参数
```

这是概念链路，实际系统会将部分处理离线化、缓存或放到 GPU 上。重点是模型不能直接把压缩视频文件的全部字节当作普通图像张量使用；需要匹配其输入格式的加载 / 解码 / 预处理与多模态对齐。

### 本课的核心区分

- **资源等待**：Job 尚未获准、Pod Pending 等，L08 已学。
- **数据等待**：Pod 已 Running、GPU 已分配，但下一批数据尚未准备好，计算无法持续进行。原因可能是读取、视频解码、预处理、batch 组装或传输，需要测量，不靠 GPU 已分配量判断。

假设单 worker、单 batch 流程无重叠、忽略其他开销：准备一批数据需 200 ms，设备计算需 50 ms，则每批总计 250 ms，其中计算时间比例为 50/250=20%。这是教学时间比例，不是 DCGM GPU utilization 的精确预测，也不是 MFU。

启发：如果瓶颈是准备数据，增加 GPU 不会自动提高数据供应速度；先定位耗时环节，再讨论并行、预取、缓存或数据布局。优化同时要保持样本内容、时间对齐和评估标准，不能以错配动作或丢难样本换吞吐。

## 第 2 步 · Dataset / DataLoader 与 batch（进行中）

用户确认第 1 步无疑问，进入数据组织概念。本段先用可按索引访问的 map-style Dataset 解释；流式 IterableDataset 后面按需引入。

### 2A：一个样本与一批样本

- **Dataset**：规定数据集包含哪些样本，以及如何根据索引取出一个样本。典型实现包含 `__len__` 与 `__getitem__`。机器人样本可以包含同一时段的相机帧、本体状态、指令及示范动作目标，并非必然等于一个完整视频文件。解码 / 预处理常在取样路径中完成，也可提前离线处理。
- **Sampler**：决定本轮取哪些样本、按什么顺序，例如索引 7、2、9、1；默认顺序 / 随机采样可以由 DataLoader 按参数选择，无需一开始自定义。
- **DataLoader**：组织取样与 batch 输出，并可协调多进程加载等。`batch_size: 4` 的意思是一次输出一组 4 个样本，不是 4 个 worker 或 4 张 GPU。
- **collate_fn**：把样本列表拼成一个 batch 的函数。默认对等形状张量增加 batch 维并堆叠；不等长视频 / 动作窗口可能要自定义补齐、裁剪和 mask，不能假设默认能拼所有数据。

```text
Sampler 给出索引：7、2、9、1
  → Dataset 分别取 4 个对齐样本
  → collate_fn 组装这 4 个样本
  → DataLoader 输出一个 batch
  → 训练循环将相应张量送到设备并计算
```

普通用法中 DataLoader 不会仅因创建出来就自动把数据送进 GPU；设备传输由训练循环或相应框架负责。组 batch 也不是把 4 段视频接成长视频，而是使输入具有共同的 batch 维，同时保持每个样本自己的输入 / 目标配对。

`batch_size=4`、10 个样本、完整遍历一次且不打乱 / 不丢尾批（drop_last=False），将输出大小为 4、4、2 的三个 batch。drop_last=True 才会丢掉末尾不完整的一批；影响样本覆盖，不能只为吞吐忽略其正确性影响。

### 追问：batch 是什么，大和小有什么影响？

先用单卡、不使用梯度累积的常见训练循环说明：一次取 B 个样本，分别计算误差，通常按均值形成 batch loss，反向传播计算汇总梯度，优化器更新一次参数。batch 是这一组样本，batch_size 是其数量。每个样本仍是自己的输入 / 动作目标配对，batch 不是整轮数据，也不是 GPU 数量。

假设 1024 个样本、完整遍历一轮：batch_size=16 时有 64 次参数更新；batch_size=64 时有 16 次。两者均看过 1024 个样本，但更新次数不同，所以不能仅按同样 epoch 认定训练过程等价。

| 影响 | 较小 batch | 较大 batch |
|---|---|---|
| 训练显存 | 保存的中间激活通常更少 | 激活通常更多，可能 OOM；模型与优化器状态不会因此全部同比增加 |
| 硬件效率 | 过小可能不能有效利用 GPU，单样本摊销开销高 | 在一定范围内常提高 samples/s，达到瓶颈后收益递减，不保证越大越快 |
| 单次更新 | 样本少，梯度估计一般更有噪声 | 更多样本汇总，通常更平稳，但受样本相关性影响 |
| 学习过程 | 固定样本数下更新更频繁 | 固定样本数下更新更少，需结合学习率 / 训练预算评估效果 |
| 数据管线 | 每批需求小，但批次数更多 | 每批需准备更多数据，批处理可能提高效率，也可能受读取 / 解码供应限制 |

机器人视频中单样本可能含多相机多帧，因此相同 batch_size 下的内存和计算量也受相机数、帧数、分辨率和模型影响。相邻视频样本高度相关时，batch 更大不一定带来相应的信息增量。更稳定的梯度不等于最终质量必然更好，应按目标评估指标看达到所需质量的总时长和资源成本。

多卡数据并行要区分本地 batch 与全局有效 batch：各 rank 等量且正确汇总梯度时，全局有效 batch = 每卡 micro-batch × 数据并行 rank 数 × 梯度累积次数。例如 4 卡 × 每卡 8 × 累积 2 = 64，注意不是把所有训练并行方式的卡数都直接相乘。梯度累积是多次小批计算后才更新一次，能降低单次激活内存需求，但不保证运行速度或带 batch 相关层时与一次大批完全一致。本段只点明区别，按需再深入。

选择原则：在质量标准不变的前提下，测显存、samples/s、数据等待时间和达到目标质量的成本；不能只因大 batch 不 OOM 就选最大值，也不能为了性能随意改变全局 batch。

### 2B：样本内按时间对齐，样本间可以 shuffle

用户确认 batch 大小无疑问。用根据观测预测动作片段的行为克隆举例，假设锚点时刻 t=10.0 秒，样本输入包含同一 episode 的画面 9.8 / 9.9 / 10.0 秒、本体状态 10.0 秒和任务指令；监督目标为 10.0 / 10.1 / 10.2 秒对应的示范动作。这只是窗口约定示例，实际相机 / 控制频率与动作延迟需按任务定义，不要求所有模型使用这些偏移。

**对齐不等于所有字段都取同一个时间戳**，而是按任务规定的相对时序关联观测与动作。输入只能使用部署决策时可获得的信息；预测未来动作时，不可把未来相机画面作为部署时不存在的输入。多路相机、状态与动作要明确时钟、采样频率和容忍误差，不能只按文件行号或分别随机读取来拼。

map-style Dataset 的一个索引对应一个完整样本 / 时间窗口。`shuffle=True` 通常改变样本索引访问顺序：可先取 t=20 的完整样本，再取 t=5 的完整样本，batch 中每个输入仍匹配其自己的动作目标。不会自动打乱样本内部的帧 / 动作时间顺序，也不应把图像和动作列表分别 shuffle。LeRobot 的 delta_timestamps 就提供了相对样本锚点取窗口的接口。

```text
正确：样本 C（输入 C、目标 C）→ 样本 A（输入 A、目标 A）→ 样本 B（输入 B、目标 B）
错误：输入 C 配目标 A，或把一个窗口的动作顺序任意打乱
```

动机：相邻视频窗口往往高度相关，打乱完整样本的访问顺序可减少连续批次只看到同一局部场景的情况；具体采样仍需考虑 episode / 场景平衡、存储局部性与模型要求。上述“可打乱样本间顺序”针对样本自包含、样本间不保留隐状态的训练；跨样本延续 RNN 隐状态等情形需额外保证序列边界和状态管理。

### 2C：按相关组切分，避免相邻窗口污染验证

用户确认样本内部时间对齐与 shuffle 无疑问。训练集用于计算梯度、更新参数；验证集用于比较模型 / 配置效果，评估时不拿这些样本做参数更新。切分要服务于要测的泛化目标，而不是只看比例。

同一 episode 按滑动窗口生成样本时，锚点 10.0 秒的窗口可能包含 9.8 / 9.9 / 10.0 秒帧，10.1 秒窗口包含 9.9 / 10.0 / 10.1 秒帧，二者共享两帧，动作目标也可能重叠。先生成窗口再随机按样本 80/20 切分，可能让高度相似甚至部分相同的输入 / 目标分别进入训练和验证，得到过于乐观的泛化估计。这与训练集内部 shuffle 不是同一操作。

常用基础做法是先按 episode 等相关组划分，再分别生成 / 读取各组样本：例如 100 个 episode 中 80 个用于训练、20 个用于验证；同一 episode 的窗口不跨集合。80/20 只是示例，组数比例不保证样本数恰好同样比例。若想测新房间 / 新场景 / 新物体 / 新机器人，应按对应层级留出完整组；仅按 episode 切分不保证未见过同场景或近重复演示。

```text
先切分 episode / 场景等组
  → 训练侧生成窗口，训练中可 shuffle 完整样本
  → 验证侧生成窗口，固定评估集合与统计口径
```

同一长时间流也可按时间切，但边界需考虑输入和动作目标的完整窗口，留出必要间隔，避免跨边界重叠。归一化等需要从数据拟合的统计一般只用训练集计算，再应用到验证集。具体如何分组 / 留出取决于评估目标，不能将任何随机切分都一概判为错误。

### 数据与代码结构

- `make_fixture()`：临时目录生成 4 个 episode 的 PNG，每段 16 个三帧滑动窗口，先按 episode 划分，前三段训练 48 样本，最后一段验证 16 样本。相邻窗口共享帧，但训练 / 验证不共享 episode 或帧文件。动作 `[episode_id, anchor_frame]` 是核对配对的标记，不是真实控制指令。
- `RobotWindowDataset.__getitem__()`：一次返回一个窗口和动作标记。`read` 计时覆盖三个文件 read_bytes；`decode` 计时覆盖 Pillow 真实像素解码与 RGB 转换（调用 load 避免延迟解码遗漏）；`preprocess` 计时覆盖双线性缩放、数组堆叠、张量维度排列和像素除以 255，以及动作张量构造。

- `timed_collate()`：复用 default_collate，将对应字段沿 batch 维组装，额外计时，不修改输入 / 目标关联。
- `measure()`：DataLoader 固定 num_workers=0、shuffle=False、drop_last=False，输出每个 batch 大小、完整样本覆盖、各阶段累计毫秒、整轮耗时与 samples/s。脚本固定 PyTorch CPU 线程数 1；尚未研究并行或预取。

### 4A：num_workers / prefetch_factor / persistent_workers

- `num_workers=0`：在调用 DataLoader 的主进程里取样 / 解码 / 预处理 / 组 batch。
- `num_workers=4`：用 4 个子进程做数据加载。本实验是 CPU 进程，不是 4 个训练 Pod 或新增 4 张 GPU。对 map-style 自动 batching，主进程安排批索引，worker 按分配任务读取数据并组批。
- `prefetch_factor=2`（num_workers>0）：每个 worker 预先安排 2 批，总量级为 4×2=8 个批任务；它们可能处于排队、处理中或已准备好，不保证此刻有 8 个完整 batch 就绪。当前 epoch 的剩余 batch 数也限制实际数量。单位是 batch，不是样本。
- `persistent_workers=True`：同一 DataLoader 多轮迭代时保留 worker，减少每轮启动成本；会保留内存和 Dataset 实例状态，不会让首次启动免费，也不是缓存全部样本。

并行让不同批的准备可以同时进行，预取使数据准备可与训练计算重叠。预取主要缓冲和减少等待，不能单独提高磁盘 / CPU 的供给上限；如果平均供给持续跟不上计算，缓冲仍会耗尽。

增加 worker 可能因进程启动、跨进程数据传输、CPU / 解码线程争用、存储饱和和更多内存占用而变慢。当前只有 48 个小样本、加载全轮约几十毫秒，Mac spawn 启动和导入开销可能更大；需实测冷启动及复用 worker 后的表现，不能预设并行一定加速。主入口 guard 与可序列化顶层 Dataset / collate 定义也是 Mac 多进程实验的前提。

后续计时还要区分：各 worker 累计阶段耗时之和是工作量，不是端到端墙钟时间；并发后不能将各阶段相加当总耗时，基线的统计说明需随代码一起更新。

### 4C：预取深度、内存与平均供给速度

用户确认并行对照结果无疑问。本段先讲原理与内存估算，不修改代码，不将未运行的 prefetch_factor 对照当实测结果。

预取像缓冲备货：加载进程提前准备后面的 batch，在训练消费当前 batch 时并行工作。增加预取深度可覆盖短时读取 / 解码波动，但不提高底层磁盘带宽或 CPU 解码算力。如果所有加载进程合计平均每秒只供给 5 批，计算设备每秒能消费 20 批，即使一开始缓冲充足，长时间仍会耗尽并等待；要提升平均供给速度，需要针对实际瓶颈优化，而非只扩大缓冲。

本脚本一批 images 的 shape=[8,3,3,112,112]，float32 每元素 4 字节：8×3×3×112×112=903168 个元素，图像张量 3612672 字节，约 3.45 MiB。用 torch.empty / numel / element_size 已实际核对这个尺寸，不是内存峰值实测。

选择预取深度应结合训练端等待、读取 / 解码波动、整体吞吐与内存峰值：短时供给抖动可能从更深缓冲获益；持续供给不足则仍要修数据生产能力，过大还可能导致内存压力和反向减速。当前无真实模型 / GPU 消费，尚未用本实验验证重叠收益。

## 第 5 步 · 小文件、分片与缓存（进行中）

### 5A：先区分文件访问、字节传输和解码

读取一个小图像文件可能包含路径 / 元数据查找、打开 / 关闭、读取字节，以及 PNG 解码。远程对象存储还有请求延迟和服务端成本；不是每次读取慢都意味着链路带宽不足。大量小文件可能将元数据 / 请求固定开销放大，具体取决于文件系统、缓存及访问模式。

本脚本每个样本读三帧，两个相邻窗口例如 [0,1,2] 和 [1,2,3]：共发起六次文件读取和解码，但只涉及四个不同帧文件。默认训练 48 窗口一轮发起 144 次帧读取 / 解码，实际仅对应 54 个不同 PNG（3 episode×18帧）。OS 文件缓存可能减轻磁盘访问，但不代表脚本已缓存解码后的像素。

**分片（sharding）**：把大量样本 / 文件组织成多个较大的数据块。例如将一百万个小文件放到多个 tar shard，读取器在每个 shard 内顺序扫描，减少频繁打开单独文件或远程发起小请求。不是把所有东西塞成一个无限大文件，也不是简单改后缀。要配合适合的读取方式；仍在每次取样时重新打开归档、无索引扫描，可能没有收益。WebDataset 使用 tar shards，样本相关文件按命名约定关联，并支持顺序 I/O。

**缓存（caching）**：复用已经读取 / 解码 / 确定性处理过的结果。缓存原始 PNG 字节主要减轻读取，缓存解码图像才可能避免重复 PNG 解码；缓存 float32 张量可能再省确定性预处理，但空间更大，并须考虑随机增强、版本与一致性。后续再细讲缓存层次与边界。

两者可组合，但不等同：分片改变数据组织和访问模式，缓存改变重复访问时是否重做某些工作。将 PNG 原字节放进未改变编码的 tar 不会自动把 PNG 变成像素，也不会自动消除 PNG 解码，更不能保证总体提速。本段仅讲原理与现有代码读取次数，没有新增分片 / 缓存实验或作真实吞吐结论。

### 5B：缓存位置决定省什么，缓存也有空间与语义成本

用户确认分片与解码区别无疑问。用相邻窗口复用帧的现有脚本说明缓存：

| 缓存层 | 命中后省什么 | 仍需做什么 |
|---|---|---|
| 原始 PNG bytes | 从原存储重复读文件 / 请求 | PNG 解码、预处理 |
| 解码 RGB 像素（uint8） | 上述读取和图像解码 | 缩放、归一化、按需增强 |
| 确定性处理后的张量 | 读取、解码及已缓存的确定性预处理 | 未缓存的变换、按需随机增强、组 batch |

这是应用内存缓存命中路径的概念比较；若缓存在本地 SSD 上，仍要读取本地缓存文件。OS 文件页缓存可能减轻底层存储访问，但不等于应用已缓存解码图像。persistent_workers 只保留进程 / Dataset 实例，不会自动添加图像缓存；普通 Python 字典缓存通常每 worker 一份，也不自动跨进程共享。

单帧载荷估算 / 实际核对：96×96 RGB uint8 为 27648 Byte（27 KiB）；同一帧经本例 resize 到112×112后 float32 为 150528 Byte（147 KiB）。单纯同形状 uint8 转 float32 是 4 倍载荷，本例还放大尺寸，因此约 5.44 倍。临时生成的一张随机噪声 PNG 为 27812 Byte，甚至略大于原像素；压缩字节大小依内容而定，不能总说 PNG 必然远小于解码图像。这些均非完整缓存 RSS 实测。

缓存深并不必然更优：要看瓶颈、命中率、条目大小和容量。按帧缓存可复用重叠窗口的共同帧；按整个窗口缓存会重复存相同帧。容量应有上限与淘汰策略；缓存 key 应包含足以区分数据版本 / episode / frame 的标识，若缓存预处理结果，还应区分输出尺寸和处理版本，避免用错旧结果。

随机性边界：若训练要求每次重新随机裁剪 / 增强，缓存第一次随机处理后的最终张量并一直复用，会冻结该样本的随机视图，改变训练过程。可缓存随机操作前的解码像素或确定性处理结果，再在每次访问时执行要求的随机增强。具体增强仍须与机器人观测 / 动作语义匹配，不能把任何图像增强都当作标签不变。

本段只做载荷计算及原理讲解，未在 Dataset 添加缓存，未声称实测缓存加速。参考：[PyTorch 数据变换与随机裁剪示例](https://docs.pytorch.org/tutorials/beginner/data_loading_tutorial.html)。

### 5D：多进程缓存并不自动共享

用户确认 5C 无疑问。当前并行脚本显式使用 spawn；若在 Dataset 实例中增加普通 Python 字典缓存，每个 worker 进程通常有各自独立的缓存。worker 0 解码并缓存某帧，不代表 worker 1 能直接命中它的字典。同一帧分发到不同 worker 时可能重复读取 / 解码，缓存载荷也可能重复占内存。因此不能将单进程的 54 次解码推算直接当作多进程结果。

persistent_workers=True 可以保留 worker 及其 Dataset 实例，从而让自行实现的实例缓存有机会跨轮复用；它不会自动实现缓存，也不保证后续访问分配到相同 worker。关闭 persistent_workers 后，轮次结束退出的 worker 内存缓存也随进程消失。

此处的普通应用字典与操作系统文件页缓存有区别：即使命中文件页缓存，仍可能重复执行 PNG 解码。多进程共享解码结果需要另外设计共享存储、同步与生命周期，不能仅凭设置 num_workers 获得。

### 5E：有限缓存、访问局部性与 shuffle

用户确认 5D 无疑问。缓存无法无限增长，通常设置容量上限并淘汰条目；LRU（Least Recently Used，最近最少使用）优先淘汰最久未访问的条目。以单进程、空缓存、容量 3 帧为例，顺序访问窗口 [0,1,2] 后再访问 [1,2,3]，第二个窗口的 1、2 命中，只需解码 3，插入时淘汰最久未访问的 0。顺序前移形成访问局部性，小缓存即可复用相邻窗口。

全局随机打乱可能让相邻访问落到不同 episode 或很远的时间段；缓存有限时，潜在复用帧可能已被淘汰，命中率可能下降。这不是取消 shuffle 的充分理由：连续高度相关样本集中在一起也会影响训练，需结合模型和评估验证。可考虑随机排列 shard / episode、在局部缓冲中打乱完整样本等折中；这种打乱不等价于全局均匀随机，不保证同等质量，且仍须保持样本内部时序和动作对应，不改变训练 / 验证隔离。
