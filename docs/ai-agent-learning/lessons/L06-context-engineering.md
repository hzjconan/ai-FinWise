## 第 1 步 · 总览：上下文为什么会"坏"，上下文工程管什么

> 🔁 **回顾**：L04 Q37 追问——API 服务端**没有会话**，每次重发完整历史，模型**每次只看到这次发过去的内容**。L04 第 5、6 步——prompt 越长 Prefill 越久（TTFT）、越贵。mock-interview Q12——State 别塞大段内容、历史要 trim / summarize（当时没成体系）。

**上下文**（context）= 模型**这一次调用能看到的全部内容**：system prompt、工具定义、对话历史、工具结果、检索文档……**上下文之外的东西对模型都不存在**。

| # | 变长后的问题 | 说明 |
|---|---|---|
| ① | **装不下** | 窗口硬上限，超了报错 |
| ② | **又贵又慢** | 🔁 L04：按 token 计费、Prefill 随长度增长、多轮每轮重发 |
| ③ | **注意力被稀释** | 🔁 L04 第 4 步：注意力对**所有** token softmax 分比例，无关内容越多关键内容分得越少，越易被带偏 |
| ④ | **中间内容被忽略** | **lost in the middle**：放在长上下文中间的信息利用效果明显差于开头和结尾（第 3 步） |
| ⑤ | **新旧信息打架** | 第 2 轮"能接受 C4"、第 8 轮"还是 C2 吧"都在上下文里，模型可能用旧的 |
- ① ② 是**硬成本**易量化；③ ④ ⑤ 是**质量问题**更隐蔽（不报错，只是越答越差）。

**上下文工程**（context engineering）= 每次调用前决定**放什么、放多少、以什么形式、放在哪**：

| 动作 | 含义 | 对应 |
|---|---|---|
| **选** | 只放这一步**需要**的 | 第 2 步分层、第 6 步意图识别（先搞清要干什么才知道放什么） |
| **压** | 太多时压成摘要 / 结构化信息 | 第 4、5 步 |
| **排** | 重要的放在最容易被注意的位置 | 第 3 步 |
| **隔** | 不同任务用各自独立的上下文 | 🔁 L04 Q30 追问"每份一个独立请求"；L07 多 agent |
- 跨会话维度：这次学到的下次还能用 → 第 7 步**长期记忆**。
- ➕ vs **prompt 工程**：prompt 工程关心"**指令怎么写**"；上下文工程关心"**这一次看到的全部信息怎么组织**"，指令只是其中一部分。

### 💬 课堂问答

> 🙋 **问**：窗口已到 100 万 token，"什么都塞得下，上下文工程没必要了"，同意吗？用五个问题说明。  
> 🧑 **我的回答**：不同意，理由 1. token要花钱的 2. 太长了模型容易晕，得不到好的结果  
> 🤖 **点评**：✅ 对。"花钱"= ②（还要加"**慢**"：100 万 token 的 Prefill 要几十秒）；"容易晕"= ③ 注意力稀释 + ④ lost in the middle。➕ 漏了 **⑤ 新旧打架**：窗口越大塞的旧信息越多、冲突越多。→ **大窗口只解决 ①**，其余反而因"反正装得下"更严重。  
> ➕ prompt caching 只缓解 ②（重复前缀 0.1 倍、跳过 Prefill），对 ③ ④ ⑤ **完全没用**——省的是计算，模型"看到"的一点没少。  
> ➕ **窗口大小是上限，不是目标**：只放这一步需要的、最相关的，哪怕还剩很多空间。

### 📌 要记住的（第 1 步）
> 上下文 = 模型一次调用能看到的全部。变长五问题：装不下、又贵又慢、注意力稀释、中间被忽略、新旧打架。大窗口只解决"装不下"，caching 只缓解"贵慢"，**质量问题只能靠上下文工程**：选、压、排、隔 + 跨会话长期记忆。

## 第 2 步 · 上下文分层：Task / Working / Knowledge / Runtime / Historical

> 🔁 **回顾**：第 1 步"选"——只放这一步需要的。L04 第 6 步——prompt caching 要"**不变在前、常变在后**"。FinWise 现状——`build_api_messages` 把会话**全部历史**从库里取出塞进 messages；一轮内的工具往返只在内存。

**为什么分层**：上下文里各块内容的**来源、变化频率、生命周期**都不同。混在一起只能"全留 / 全删"；分开管，每层用最适合它的方式处理。

| 层 | 放什么 | FinWise 对应 | 变化频率 | 怎么管 |
|---|---|---|---|---|
| **指令层**（面试答案没单列） | 角色、规则、输出格式、工具定义 | system prompt（风险评估助手 + 5 维评分锚点）、4 个工具 | 几乎不变 | 放**最前**，加缓存 |
| **Task** 任务 | 用户**当前**要做什么 | 本轮用户输入："想给爸妈存笔养老钱" | 每轮变 | 放**最后**，离生成位置最近（第 3 步） |
| **Working** 工作状态 | 进度、计划、已确定的中间结论 | 5 维度问到哪些、各自取值、还缺哪几个 | 每步可能变 | **结构化**保存，**覆盖更新**，不追加 |
| **Knowledge** 知识 | RAG 文档、Skill | 产品说明书、合规条款 | 按需 | 检索 top-K（🔁 L01），用完可丢 |
| **Runtime** 运行时 | 工具返回的**实时**数据 | `search_products` 结果、当前净值 | 每次调用不同 | **只留必要字段**，注意时效 |
| **Historical** 历史 | 之前的对话、长期记忆 | 前几轮问答 | 不断累积 | 近几轮留原文、更早的压摘要（第 4、5 步）；跨会话进长期记忆（第 7 步） |

- ✅ FinWise Runtime 层已做对一件事：`_execute_tool` 只回喂产品代码 / 名称 / 类型 / 预期收益，不回喂整行记录（注释"只回喂精简字段，控制 token"）。
- ⚠️ FinWise **缺 Working 层**："5 维问到哪了"藏在对话历史里，模型每轮都要从头读历史**自己推断**进度。

### 💬 课堂问答

> 🙋 **问**：第 2 轮"亏 30% 也没事"，第 8 轮"还是保守点，最多亏 5%"，两句都在历史里，第 10 轮下结论可能用旧的。用 Working 层怎么解决？和"两句都留在历史里让模型自己判断"有什么不同？  
> 🧑 **我的回答**：Working 层只存最新值，改口时直接覆盖旧的  
> 🤖 **点评**：✅ 核心就是这个。不同在于：留在历史里 = **把"哪句最新"的判断交给模型**，长上下文里它可能判断错（③ 稀释、④ 中间被忽略）；Working 层 = **由代码保证只有一个值**，模型根本看不到冲突。  
> ➕ **谁来写**：让模型调工具上报，如 `record_answer(dimension="loss_tolerance", value=...)`，**代码**按维度 key 覆盖存进库（🔁 L05 / 定价类 agent：关键值由服务端掌控）。不是让模型自由文本里"记一下"。  
> ➕ **放哪**：每次调用把 Working 状态渲染成一小块结构化文本（如"已收集：经验=3 年；承受亏损=5%（第 8 轮更新）；待问：期限、收入"）放在**靠后**位置（常变，不能放缓存前缀里）。  
> ⚠️ **旧句还在历史里**：仅覆盖 Working 层不够彻底——system prompt 要写明"**维度取值以【当前进度】为准**"，或者把早期历史压成摘要（第 4、5 步），冲突才真正消失。

### ❓ 我的追问

- Working 层和 Historical 层会不会重复占 token？→ 会有一点，但 Working 层很小（几十 token），换来的是模型不用从长历史里推断进度；而且有了 Working 层，早期历史就**更敢压缩**——关键结论已经结构化保存，不怕摘要丢掉。

### 📌 要记住的（第 2 步）
> 按"来源 / 变化频率 / 生命周期"分层：指令（最前、缓存）→ Knowledge / Runtime（按需、精简）→ Historical（近留原文、远压摘要）→ Working（结构化、覆盖更新）→ Task（最后）。**Working 层由代码覆盖更新**，把"哪个值最新"从模型的判断题变成代码的保证——专治"新旧打架"。

## 第 3 步 · lost in the middle：现象与对策

> 🔁 **回顾**：第 1 步问题④。L01——RAG 漏斗"召回 → 重排（reranker 打相关度分）→ Top-K"。L04 第 4 步——注意力对所有 token softmax 分权重。

**现象**（Liu 等 2023，*Lost in the Middle: How Language Models Use Long Contexts*）：给 20 篇文档、只有 1 篇含答案，改变它的位置测准确率 → **U 形曲线**。
- **开头效应**（开头记得牢）+ **结尾效应**（离生成位置最近）；**中间最差**，部分设置下甚至低于**不给文档**。
- ⚠️ 新模型在"大海捞针"（长文本里藏一句话让模型找）上好很多，但真实任务（综合多处、推理）仍受位置影响 → 面试说"**有缓解，仍需设计**"，别说"已解决"。

| 对策 | 做法 | 为什么有效 |
|---|---|---|
| ① 减少上下文 | 只放 Top-K，K 取小；无关的不放 | 中间段直接变短 |
| ② 重排序 | 最相关放**两头**，最不相关放**中间** | 顺着 U 形摆 |
| ③ 压缩 | 长文档先压摘要 / 要点 | 同①，总长变短 |
| ④ reranker | 重排模型挑最相关 | 给①②提供分数 |
| ⑤ 问题放最后 | 长文档在前，问题和指令在**最后** | 结尾效应；Anthropic 长上下文建议同此 |
| ⑥ 结构化 + 先引用 | `<document index="1">` 标签包裹；先让模型**摘出相关原文**再回答 | 标签便于定位；先引用逼它每篇都看 |

- 与第 2 步合起来：**指令最前、Task 最后**——既缓存友好（不变在前），又顺 U 形（最重要的在两头）。

### 💬 课堂问答

> 🙋 **问**：reranker 打分 A=0.9 B=0.8 C=0.7 D=0.6 E=0.5，加上用户问题一起放进 prompt，从上到下怎么排？问题放哪？  
> 🧑 **我的回答**：A C E D B，问题放在最后  
> 🤖 **点评**：✅ 完全正确。A、B 占两头，C、D 次之，最弱的 E 在正中间；问题放最后吃结尾效应。  
> ➕ 问题放最后时，**B 紧挨着问题**，其实是"离问题最近"的位置。所以也有人把 A 放最后（`… C A + 问题`），两种都说得通——关键是**最弱的在中间**、**问题在最后**。拿不准时用自己的评测集比一比。  
> ➕ 5 篇短文档时位置影响很小；文档**又多又长**时（几十篇、几万 token）才明显。先做①减少，再做②重排。

### 📌 要记住的（第 3 步）
> lost in the middle：长上下文 U 形曲线，两头强中间弱。对策 = **少放**（Top-K / 压缩）+ **排好**（最相关放两头、最弱放中间）+ **问题放最后** + 标签结构化、先引用再回答。新模型有缓解，不等于解决。

## 第 4 步 · 压缩的触发策略（含 Claude 服务端压缩与上下文编辑）

> 🔁 **回顾**：第 2 步——Historical 层"近留原文、远压摘要"。L04 第 6 步——缓存要求前缀**字节级一致**，前面改一个字后面全作废。L05——预算。

**压缩** = 用一次 LLM 调用把一段长历史压成摘要、替换原文。本步讲**何时压**，第 5 步讲**怎么压不丢**。

| | 压得太勤 | 压得太晚 |
|---|---|---|
| 成本 | 每次多一次 LLM 调用 | 每轮重发长历史，贵且慢 |
| 缓存 | 每压一次前缀变，**缓存作废** | 前缀稳定，命中率高 |
| 质量 | 摘要的摘要，**逐层丢信息** | 压之前已在变差（③④），还有超窗风险 |
- 原则：**次数少、每次压得多**。

| 策略 | 触发时机 | 优点 | 缺点 |
|---|---|---|---|
| ① 固定 token 阈值 | 输入 > N（如 100K） | 最简单、可预测 | 可能在任务做到一半时压掉进行中的细节 |
| ② 语义边界 | 子任务 / 话题**结束时** | 内容"完整"，摘要质量高 | 要识别边界；边界不来仍会超长 → 配①兜底 |
| ③ 按占比分级 | 60% 清旧工具结果（轻）→ 80% 压旧历史（中）→ 95% 截断（重） | 能用便宜手段就不用贵的 | 参数多 |
| ④ ACM 主动上下文管理（Active Context Management） | **agent 自己**调"整理 / 压缩"工具 | 模型最清楚什么没用了 | 可能忘调或调太勤 |
- ⚠️ 硬规则：**不在一次工具往返中间压缩**（tool_use 还在等 tool_result 时会把一对拆开）。
- ➕ Claude Code = ③ 自动压缩 + ④ 手动 `/compact`。

**Claude API 的两个服务端功能**：

| | 服务端压缩（compaction） | 上下文编辑（context editing） |
|---|---|---|
| 做什么 | 早期历史**总结成摘要** | 旧工具结果 / thinking 块**直接清掉**，不总结 |
| 配置 | beta `compact-2026-01-12`；`context_management={"edits":[{"type":"compact_20260112","trigger":{"type":"input_tokens","value":100_000}}]}` | beta `context-management-2025-06-27`；`clear_tool_uses_20250919` / `clear_thinking_20251015` |
| 对应策略 | ① 固定阈值 | ③ 的"轻"档 |
| 注意 | 返回 `compaction` 块，要把 `response.content` **整个**追加回 messages；`instructions` 会**替换**默认摘要 prompt | **腾窗口的工具，不是省钱手段**：每清一次缓存作废；用 `clear_at_least` 避免频繁小清理 |
- ⚠️ 支持服务端压缩的是较新模型（Opus 4.6+、Sonnet 4.6+、Haiku 5.5 等，以 Models API 的 `capabilities["context_management"]["compact_20260112"]["supported"]` 为准）；**FinWise 用的 Haiku 4.5 不支持**。

### 💬 课堂问答

> 🙋 **问**：① FinWise 一次评估约 10 轮、几千 token，现在需要压缩吗？② 若以后同一会话"评估完继续聊产品、过几天回来再聊"，只能选一种触发时机，选哪种？具体在哪一刻？  
> 🧑 **我的回答**：1.现在不需要，token加起来也不多 2.我会优先选服务端压缩（从Haiku换成其他支持的模型比如opus）, 如果模型不能换，那选择在agent里面根据"按占比分级"的策略自己压缩，压缩完后把要发给模型的提示词里把原先被压缩的内容替换成压缩后的摘要  
> 🤖 **点评**：① ✅。➕ 不只是"不多"：硬上压缩反而**更亏**——多一次 LLM 调用 + 缓存作废，几千 token 根本省不回来。  
> ② ⚠️ 答的是"**用什么压**"（服务端 / 客户端），题目问的是"**什么时候压**"。服务端压缩本身就是 ① 固定阈值。  
> ⚠️ 为一个功能**换到 Opus 不划算**：Opus 5.5 是 $4 / $20 每百万 token，Haiku 4.5 约 $1 / $5，单价贵约 4 倍。同档升级 **Haiku 5.5** 就支持压缩，单价反而更低（$0.10 / $0.50，≤100K prompt；注意新 tokenizer 同样文字约多 30% token）。原则：**按任务选模型，别让一个功能绑架模型选择**。  
> ✅ 客户端做法描述对了：把被压缩的那段替换成摘要。➕ 官方推荐的客户端形状是 **simple compaction**：摘要 + 新一轮用户输入，更早的原文一概不再重发。  
> ➕ **最佳答案：② 语义边界**——FinWise 最明显的边界是 **`conclude_assessment` 成功那一刻**：评估结论（等级 + 5 维取值）已经结构化落库，前面 10 轮问答可以整体压成一句"已完成评估：C3，经验 3 年……"。再配 ① 阈值兜底（防止聊产品聊很久）。

### 📌 要记住的（第 4 步）
> 压缩"次数少、每次多"：太勤贵且毁缓存、逐层丢信息；太晚质量先坏。四种触发：固定阈值（简单）/ 语义边界（质量最好，配阈值兜底）/ 按占比分级（先轻后重）/ ACM（agent 自己压）。不在工具往返中间压。Claude 服务端压缩 = 阈值触发的摘要；上下文编辑 = 直接清旧工具结果，是腾窗口不是省钱。FinWise 的天然边界 = `conclude_assessment` 成功。

## 第 5 步 · 压缩时怎么不丢关键信息

> 🔁 **回顾**：第 2 步——Working 层结构化、代码覆盖更新。第 4 步——"摘要的摘要"逐层丢信息；服务端压缩的 `instructions` 替换默认摘要 prompt。阶段三 B#7——tool_use schema 强制按字段输出。

**为什么会丢**：让 LLM "总结一下"，它按**自己的判断**取舍。最易丢：

| 易丢 | 例子 | 原因 |
|---|---|---|
| 具体数字和 ID | "最多亏 5%"、产品代码 | 摘要爱写"用户偏保守"式概括 |
| 约束和否定 | "**不要**股票类"、"3 年内要用钱" | 一句带过就没了 |
| 改口 | 30% → 5% | 只留旧的或混在一起 |
| 未解决的问题 | "手续费还没回答" | 摘要只写做了什么，不写还欠什么 |

| 对策 | 做法 | 解决什么 |
|---|---|---|
| ① 结构化抽取 | 给 **schema**，tool_use 强制按字段填（画像 / 约束 / 决定 / 待办…） | 字段固定 → **不会整类漏掉**；数字 / ID 有专门字段 |
| ② 分层存储 | **原文和摘要分开存**，原文不删，摘要标"来自第 3~10 轮" | 压缩**可回退**，可给 agent "查原文"工具 |
| ③ 校验反馈 | **代码查**（原文里的数字 / 代码在摘要里还在吗）+ **LLM 查**（原文 + 摘要对比，问漏了什么） | 发现遗漏 → 补上或重压 |
| ④ 关键内容钉住不压 | system prompt、Working 层、用户明确约束**不进压缩**，每次原样带 | 不经过摘要就**不可能被摘要弄丢** |
| ⑤ 最近 N 轮留原文 | 只压较早部分 | 进行中的细节都在 |
- ➕ ④ = 第 2 步分层的回报：**各层压缩方式不同**，指令层、Working 层从不压，只压 Historical。
- ➕ 防"摘要的摘要"：有②就**从原文重新生成**；或按①的 schema **增量更新**（新信息只覆盖对应字段）。

### 💬 课堂问答

> 🙋 **问**：`conclude_assessment` 成功后把 10 轮问答压成结构化摘要供后续聊产品用。① schema 要哪些字段（4~6 个）？② 哪些可以直接从代码 / 数据库取，不用 LLM 抽？  
> 🧑 **我的回答**：1.应该有用户各纬度的评分，推荐的产品编号 2.从维度分数算风险等级，产品的具体信息  
> 🤖 **点评**：① ✅ 维度评分、推荐产品编号都该有。⚠️ 漏了"易丢"表里最要命的几类——它们恰恰**不在**结构化的评分里：**投资目标与约束**（"给爸妈养老"、"3 年内要用"、"不要股票"）、**用户对产品的态度**（看中哪个、拒了哪个及原因）、**未解决的问题**。  
> ② ✅ 风险等级由分数**代码算**（🔁 B#7 确定性定级）；✅ 产品详情从库取。➕ 更进一步：产品详情**根本不进摘要**，只存产品代码，用时实时查（净值会变，是 Runtime 层）。➕ 再进一步：**维度评分本身也在库里**（conclude_assessment 的入参已落库），同样不用 LLM 抽。  
> ➕ **关键原则：能从代码 / 库取的，绝不让 LLM 抽**——LLM 只负责抽**没被结构化过的**内容（目标、约束、态度、待办）。参考 schema：

```
来自代码 / 数据库（不经 LLM）       由 LLM 抽取（schema 强制）
- risk_level: C3                    - goals: ["给父母存养老钱"]
- dimension_scores: {...}           - constraints: ["3 年内可能用钱", "不要股票类"]
- recommended_codes: [...]          - product_feedback: [{code, 态度, 原因}]
- source_turns: 3~10（指向原文）    - open_questions: ["手续费怎么收"]
```

### 📌 要记住的（第 5 步）
> 摘要易丢：数字 / ID、约束否定、改口、未解决问题。对策：schema 结构化抽取、原文与摘要分开存（可回退）、代码 + LLM 双重校验、关键层钉住不压、最近 N 轮留原文。**能从代码取的绝不让 LLM 抽**，LLM 只抽没结构化过的（目标、约束、态度、待办）。

## 第 6 步 · 意图识别与低置信度兜底

> 🔁 **回顾**：第 1 步——先搞清要干什么才知道"选"什么。L01——漏斗，便宜的先上。L05——HITL 高风险先确认。

**意图识别**（intent recognition）= 把用户的话归到**预定义意图**，并抽出执行所需参数（**槽位** slot）。例："帮我看看 C3 的产品" → 意图 = 查产品，槽位 = {risk_level: C3}。识别后才知道走哪个流程、加载哪些上下文 / 工具、风险多大。

| 层 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| ① 规则 | 关键词 / 正则（"转人工"直接转） | 快、免费、确定 | 换说法就漏 |
| ② 向量相似度 / 小分类器 | 每意图备例句，找最像的（🔁 L01 embedding） | 接得住同义说法；**相似度可当置信度** | 要备例句，复杂句分不清 |
| ③ LLM 分类 | 结构化输出 `{intent, confidence, slots, missing_slots}` | 懂复杂、带上下文的表达 | 慢、花钱 |
- 漏斗组合：**能用规则确定的不交给模型**，匹配不上再往下。
- ➕ agent 里常是**隐式**的：模型选哪个工具本身就是意图识别（FinWise 现状）。

**置信度别全信模型自报**：LLM 说 0.9 常过度自信，只作参考。更可靠的信号：**规则是否命中**、**top1 与 top2 的差距**（0.82 vs 0.80 = 分不开）、**槽位是否齐全**（意图明确但缺参数照样不能执行）。

**风险 × 置信度**（风险等级由**代码按意图类型查表**，不让模型评）：

| | 置信度高 | 置信度低 |
|---|---|---|
| **低风险**（查询、问概念） | 直接执行 | 按最可能的执行 + **方便用户纠正** |
| **高风险**（购买、删除、下线） | 执行前**确认**（HITL） | **追问澄清，绝不执行** |
- 追问设计：**给选项**不要开放式；**限轮数**（如 2 次）不清楚就转人工。
- bad case `"帮我处理一下 node，node 下线"`：① "处理"是重启 / 下线 / 排查？② "node 下线"是陈述（告警说已下线）还是命令？③ 哪个 node（槽位缺）？+ 下线是高风险 → 右下格：给选项追问。

### 💬 课堂问答

> 🙋 **问**：用户做完评估看完推荐后说"那个稳一点的帮我买了吧"。① 意图？风险高低？② 置信度高低，依据？③ agent 怎么回应（用"给选项"）？  
> 🧑 **我的回答**：1.意图是买某个比较稳健低风险的产品。执行的风险是高，因为并没有明确要买哪个产品 2.置信度低，如上所说，当有多个合适的产品的时候，模型并不清楚要买哪个 3.列出可能比配的几个产品，让用户明确回答，或者让用户重新输入  
> 🤖 **点评**：① ✅ 意图 = 购买，风险高。⚠️ 但理由放错了轴：风险高是因为**购买动钱**（意图类型决定，查表），和"没说买哪个"无关——就算说清了买哪个，风险照样高。"没说清"属于置信度那根轴。**两根轴要分开判断**。  
> ② ✅ 更精确地说：**意图置信度其实高**（明确想买），低的是**槽位**——买哪个（"稳一点"是相对的，可能对上多个）、**买多少**（金额完全没提）。即"意图明确、槽位缺失"。  
> ③ ✅ 列选项。➕ 选项比"重新输入"好：用户点一下就行，也不会再说出新的模糊话。➕ 要同时问**金额**。➕ 用户选完后进入"高风险 + 高置信度"格，**还要再确认一次**（澄清 → 确认，两道关）。➕ 候选产品由代码按用户风险等级筛（适当性），不让模型自己挑。  
> ➕ 现实约束：FinWise 的 4 个工具里**没有购买工具**——agent 不能假装买了，应引导到购买页面。

参考回应：

```
你说的"稳一点"，在刚才推荐里有两款：
  A. FP001 稳盈 90 天（R2，预期 2.8%）
  B. FP003 安享月月盈（R1，预期 2.3%）
请问是哪一款？打算买多少？
（确认后我会把下单页发给你，由你在页面上最终确认。）
```

### 📌 要记住的（第 6 步）
> 意图识别 = 意图 + 槽位，漏斗组合：规则 → 向量相似度 → LLM。模型自报置信度不可全信，看规则命中、top1/top2 差距、槽位齐不齐。**风险（代码查表）和置信度是两根轴**：高风险低置信度 → 给选项追问、绝不执行；高风险高置信度 → 仍要确认。追问限轮数，超了转人工。

## 第 7 步 · 长期记忆：写入、检索、遗忘

> 🔁 **回顾**：第 2 步——Historical 的跨会话部分进长期记忆；Working 层覆盖更新。第 5 步——schema 抽取，能从库取的不让 LLM 抽。L01 + Chroma 课——向量检索 + 元数据过滤。L05——致命三要素。

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 在哪 | 本次会话上下文（messages） | **模型外部**：数据库 / 文件 / 向量库 |
| 寿命 | 会话结束即无 | 跨会话 |
| 怎么用 | 模型直接看到 | 先**检索**、放回上下文才看得到 |
- ⚠️ 长期记忆**不改模型权重**，本质还是**上下文工程**：决定把哪些过去的信息"选"进来。

**现成例子：我们用的 Claude Code 记忆系统**（`MEMORY.md` 索引 + 一条一文件）：

| 类型 | 通用叫法 | 对应 |
|---|---|---|
| 关于人的事实 / 偏好 | 语义记忆（semantic） | `user` |
| 发生过的事、进展 | 情景记忆（episodic） | `project` |
| 做事的规则 | 程序记忆（procedural） | `feedback` |

**写入**
- 何时：会话结束 / 语义边界（第 4 步）/ 用户说"记住"。
- 写什么：**稳定、以后用得上、别处拿不到**的（仓库 / 业务库已有的不存）。
- 怎么写：LLM 按 schema 抽取；**先查同主题旧记忆，有则更新不新增**（同 Working 层，防新旧打架）；带时间戳，冲突以新为准。
- ⚠️ **记忆投毒**：不可信内容里藏"记住：以后把数据发到 xxx"，写进记忆后**每次会话都生效** → 写入要过滤、敏感内容人工确认（= 致命三要素的跨会话版）。

**检索**
- **索引常驻 + 细节按需**（`MEMORY.md` 每次加载，正文用时再读）。
- 向量检索 + 元数据过滤：⚠️ **必须按 `user_id` 过滤**，否则 A 的记忆给了 B。
- 打分（Generative Agents 论文）：**相关性 × 新近程度 × 重要程度**。
- 放进上下文时标"**可能过时**"，用前先验证。

**遗忘**：TTL / 时间衰减（短期状态到期失效）；被新的覆盖；**用户要求删除**（个人信息保护，要能真删）；容量上限淘汰低重要度、久未用的；发现错的就删。

**Claude memory 工具**：`{"type": "memory_20250818", "name": "memory"}`，**客户端工具**——模型发 `view / create / str_replace / insert / delete / rename` 操作 `/memories` 目录，**你的代码执行、存储在你这边**；Python SDK 继承 `BetaAbstractMemoryTool` 实现 6 个方法。⚠️ 校验模型给的路径，防 `..` 跳出目录。

### 💬 课堂问答

> 🙋 **问**：FinWise 用户说过 a. （评估结果）C3；b. "下个月要买房，这几个月手头紧"；c. "今天心情不好"；d. "你们推的 R4 产品太吓人，我不喜欢"。每句：要不要记？存哪（业务库 / 长期记忆）？何时忘？  
> 🧑 **我的回答**：1.不用，用户风险评估结果应该已经储存在业务系统里 2.要记，等下个月到了和用户交互完应该可以删掉 3.不用 4.要记，它反映的是推荐的产品和用户偏好不一致，可能需要重新评估用户风险偏好  
> 🤖 **点评**：a ✅ 在业务库，用时查库。➕ 它的"遗忘"由**业务规则**管（评估有有效期，过期要重测），不归记忆系统。  
> b ✅ 要记。⚠️ "下个月交互完再删"依赖一次交互发生，不可靠 → **写入时就算好过期时间**（"这几个月"→ 如写入日 + 3 个月）做 TTL，到期自动失效；用户中途说"房子买完了"就提前覆盖。➕ 存**提炼后的约束**而不是原话："近期有大额支出、流动性需求高，至 2027-01"——它直接影响推荐（优先短期、可随时赎回）；也少存敏感细节。  
> c ✅ 不记：一时情绪，无复用价值；➕ 情绪 / 健康类属敏感信息，**本会话内**可调整语气（短期记忆），不写长期。  
> d ✅ 要记，长期偏好，无 TTL，变了就覆盖。⚠️ 两点：① C3 用户按适当性**本就不该被推 R4**——真推了是合规 bug，先查推荐逻辑；"不喜欢 R4"和 C3 其实**一致**，不是矛盾。② 记忆可以**触发"建议重新评估"**，但**不能直接改风险等级**——等级只能由正式评估得出（🔁 关键值由服务端掌控）。**记忆是参考，不是权威。**

### ❓ 我的追问

- `"type": "memory_20250818"` 的前缀是固定的吗？→ **整个字符串都固定**，照文档原样抄：`工具名_版本日期(YYYYMMDD)`。这类是 **Anthropic 定义的工具**：要写 `type`，`name` 基本固定（memory 工具叫 `"memory"`），**不用写 description / input_schema**（用法训练在模型里）；memory、bash 由你的代码执行，web_search 由 Anthropic 执行。升级 = 发新日期的新版本，旧版不变（如 `web_search_20250305` → `web_search_20260209`），换前确认模型支持。本课的 `compact_20260112`、`clear_tool_uses_20250919` 同格式。⚠️ 别和 beta 请求头（`context-management-2025-06-27`，短横线分隔）搞混。

- 代码怎么知道哪句该记、记了怎么维护？→ **分工：LLM 判断"记什么"（语义），代码管"怎么记、怎么维护"（规则）**。  
  - **判断**：标准写进 prompt（记什么类型、什么不记），让 LLM 按 schema 输出 `{should_save, type, key, content, ttl_hint, importance}`。两种时机：**会话中**由 agent 调 memory 工具自己记（如 Claude memory 工具）；或**会话后**跑一个独立的抽取任务读整段记录（不在主流程上、可用便宜模型）。  
  - **代码把关**：类型白名单；敏感信息过滤（身份证号 / 手机号正则、情绪健康类拒收）；按 `(user_id, key)` **upsert**（有就覆盖）；`ttl_hint` → 绝对时间 `expires_at`；单用户条数上限。  
  - **维护**：检索时过滤 `expires_at > now`（懒删除）+ 定时任务真删；同 key 覆盖；定期让 LLM **合并**重复 / 矛盾的记忆；给用户"查看 / 删除我的记忆"入口（向量库里的也要删）；用时发现错了就删。  
  - 例：我们的 Claude Code 记忆系统里，"记什么"是 Claude 按 system prompt 的规则判断的，harness 代码只提供目录、每次加载 `MEMORY.md`。

- "记住以后要做某事"这种，不是到时间就能删，要等事做完，怎么处理？→ 它不是"事实"而是**待办**：按**状态**管（`status: open / done` + 完成条件），不按时间管。  
  - **谁发现做完了**：① agent 自己——待办每次随记忆加载进上下文，做完时调工具标 done（Claude memory 工具的 `str_replace` / `delete`）；② 代码——完成条件能写成查询时（"评估过期提醒" → 库里出现新评估记录即完成），代码自动关；③ 用户说"那件事不用了"→ LLM 匹配到这条后关掉。  
  - **兜底**：完成信号可能漏掉 → 仍设 `review_after`（如 30 天未关就问用户"这件事还要做吗？"），而不是直接删。  
  - **做完先标 done 不立刻删**：留痕、防重复做，归档后再定期清理。  
  - 例：我们的记忆里 "向量数据库补课 ✅已完成" 就是做完后**改状态**；"补课完成后做总 cheat sheet"、"面试差距分析临时文档（补完后删）" 是还开着的待办，完成条件写在内容里，由我在做完时更新。

### 📌 要记住的（第 7 步）
> 长期记忆 = 模型外部存储 + 检索回上下文，不改权重。写：稳定 / 可复用 / 别处没有的，先查后更新、带时间戳、防投毒；查：索引常驻 + 细节按需、**按 user_id 过滤**、相关 × 新近 × 重要；忘：TTL、覆盖、用户删除、容量淘汰。业务数据在业务库，**记忆是参考不是权威**，不能用记忆改关键值。

## 第 8 步 · 穿插复习题：Q36

> **Q36**：标准生产 system prompt 由哪几块组成？为什么"什么时候**不要**调工具"必须写明？拿 FinWise 的 `search_products` 举例。

> 🔁 **回顾**：第 2 步——指令层最前加缓存、Task 最后。第 6 步——先搞清要干什么。L05——步数预算，FinWise `MAX_AGENT_STEPS = 5`。

| 块 | 写什么 | FinWise `risk_assessment_system.md` |
|---|---|---|
| Role 角色 | 你是谁、语气 | ✅ 风险评估助手，专业、亲和 |
| Goal 目标 | 达成什么、何时算完成 | ✅ 唯一目标，输出 C1–C5 |
| Context 背景知识 | 领域知识 | ✅ 5 维锚点 `{DIMENSIONS}`、映射参考 |
| Rules 规则 | 必须 / 禁止 / 边界情况 | ✅ 对话节奏、约束（含防注入） |
| Tools 工具 | 每个工具**何时用、何时不用** | ⚠️ 只写了 2 个 |
| Output format | 输出结构 | ✅ 工具 schema 约束 |
| Examples 示例 | 正例 / 反例 | 🟡 少量 |
| Current task | 本轮要做什么 | 不在 system 里，= messages 最新用户消息 |
- ➕ 前 7 块几乎不变 → system 里加缓存；Current task 每轮变 → 最后（第 2、3 步）。

**为什么必须写"何时不调"**：① 工具摆着就是暗示，只写"能做什么" = "随时可用"；② 每次调用有代价（往返、token、延迟、**吃步数预算**）；③ 可能有风险 / 副作用（写库、花钱、把流程带偏）；④ description 只说能力，"本业务何时不该用"只有你知道。

### 💬 课堂问答

> 🙋 **问**：system prompt 写"每轮**必须**调 ask_next_question / conclude_assessment 之一"+"不推荐具体产品"，但 `TOOLS_SCHEMA` 实际给了 4 个工具，其中 `search_products` 描述为"（可选）按风险等级查询当前在售产品，供评估参考"。① 有什么问题，评估中途模型可能做什么？② 给 `search_products` 写一条"何时不要调用"的规则。  
> 🧑 **我的回答**：1.可能会选错工具 2.写清楚"只在xxx情况下调用此工具，其他场景不要调用"  
> 🤖 **点评**：① 🟡 方向对但太笼统，面试要说出**具体后果**：  
> - **指令冲突**：prompt 说"只能调这两个"，工具列表却有 4 个，描述还说"供评估参考"——两处打架，模型行为不可预测；  
> - **风险等级还没定**：评估中途调用只能**猜**一个等级传进去；  
> - **诱导作答**：把产品摆给客户会影响他后面的回答（锚定），评估就不客观了，也违反"不推荐具体产品"；  
> - **吃步数预算**：一轮只有 5 步，查产品占掉的步数本该用来问问题。  
> ② 🟡 句式对（"只在…时调用"），⚠️ 但关键在把 **xxx 填具体**。好的"不要调用"规则 = **条件 + 原因 + 替代动作**：

```
- `search_products` / `get_product_detail`：评估阶段（conclude_assessment 成功之前）**不要调用**。
  原因：此时风险等级未定，任何产品信息都会影响客户作答，且违反"不推荐具体产品"。
  客户在评估中主动问产品时：用 ask_next_question 回应"评估完成后为您匹配合适的产品"，然后继续评估。
```
> ➕ **更彻底：最好的"不要调用"是不给它**——按阶段动态传工具：评估阶段只传 ask / conclude，评估完成后再加 search / detail（= 第 1 步"选"用在工具上）。prompt 规则是软约束，**工具列表是硬约束**。  
> ➕ 工具自己的 description 也要写何时不用（如"仅在已完成风险评估后使用"），而不是"（可选）供评估参考"这种会**鼓励**调用的措辞。

### 📌 要记住的（第 8 步）
> system prompt 八块：Role、Goal、Context、Rules、Tools、Output format、Examples（+ messages 末尾的 Current task）。必须写"何时不调"：工具在场即暗示、调用有成本、有副作用、业务边界模型推不出。好规则 = 条件 + 原因 + 替代动作；最硬的约束是**按阶段只传需要的工具**。
