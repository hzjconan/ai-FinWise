## 第 1 步 · 数据飞轮全景：一条链 + 每段产出

> 🔁 **回顾**：L06 第 1 步"**选**"——只放需要的。这里同理：**不需要的数据，不传、不存、不训。**

**数据单位 episode**（一段完整任务演示，如"把杯子放进水槽"）：多路视频（头部 + 双腕，30fps）+ **本体状态**（proprioception：关节角、夹爪开合）+ **动作**（发给电机的指令，模型要学会输出的）+ 语言指令与元数据（成功 / 失败、机器人、场景）。来源：**遥操作**（teleoperation，人远程操控示范）为主，自主运行日志、仿真为辅。

| 段 | 做什么 | 产出 |
|---|---|---|
| ① 采集 | 录视频 + 传感器，**各路按时间对齐** | 原始 episode |
| ② 端侧处理 + 上传 | 机器人上先压缩、过滤再传 | 压缩后 episode |
| ③ 存储 | 对象存储（S3 / MinIO / Ceph）+ 元数据库 | 数据湖 + 索引 |
| ④ 清洗 / 筛选 / 标注 | 去坏数据（掉帧、模糊、传感器异常）、去重；VLM 自动标注 + 人工抽检 | 干净带标签数据集 |
| ⑤ 预处理 / 打包 | 解码、缩放、抽帧、与动作对齐、切分片 | 训练分片 |
| ⑥ 训练 | k8s GPU 集群分布式训练 | checkpoint |
| ⑦ 评估 | 由便宜到贵：离线指标 → 仿真成功率 → **真机成功率** | 能否上线 |
| ⑧ 部署 | 导出、量化 / 蒸馏，端侧芯片或云端推理 | 新版本模型 |
| ⑨ 回流 | 分析失败场景，决定**下一轮采什么** | 新采集需求 → ① |
- ⑨ → ① 的闭环 = **飞轮**：每轮都知道该补什么数据。

**规模感**（粗估）：1 路 1080p30 H.264 ≈ 几 Mbps ≈ 每小时 2~3 GB；100 台 × 3 路 × 8 小时 × 3 GB ≈ **每天约 7 TB**，且只增不减。

| 问题 | 主要在哪段 |
|---|---|
| 带宽 | ② |
| 存储 | ③（及 ④⑤ 的中间数据） |
| 训练开销 / 时间 | ⑤⑥ |
| 质量 | ④ 数据质量 + ⑦ 评估 |

### 💬 课堂问答

> 🙋 **问**：只能在一个环节优化，且要同时降带宽、存储、训练三项成本，选哪段？为什么？  
> 🧑 **我的回答**：选②端侧处理，越早丢掉的数据后面越不花钱  
> 🤖 **点评**：✅ 完全正确，"**越早丢越省**"是这个岗位最核心的一句话。  
> ⚠️ 但 ② 也是**风险最大**的一段：端侧丢掉的数据**永远找不回来**；机器人上的算力和电量也有限，复杂的过滤跑不动。所以要分层处理：  
> - **确定没用的才在端侧丢**：文件损坏、机器人静止不动的空闲片段、明显重复；  
> - **拿不准的先传"轻量版"**：元数据 + 低分辨率缩略视频，云端判断有价值后**再按需拉全量**；  
> - ⚠️ **失败的演示不是坏数据**：机器人没抓住杯子的那段视频，恰恰是飞轮 ⑨ 最需要的输入，不能当垃圾丢。"坏数据"指的是**数据本身有问题**（损坏、不同步），不是**任务结果**不好。

### 📌 要记住的（第 1 步）
> 数据单位 episode = 多路视频 + 本体状态 + 动作 + 指令 / 元数据。九段链：采集 → 端侧处理上传 → 存储 → 清洗标注 → 预处理打包 → 训练 → 评估（离线 → 仿真 → 真机）→ 部署 → 回流（飞轮）。**越早丢越省，但越早丢越不可逆**：端侧只丢确定没用的，拿不准的先传轻量版；失败演示是宝不是垃圾。

## 第 2 步 · 视频模型 vs 文字模型

> 🔁 **回顾**（L04）：文字 token = 词表里的离散 ID，几个字节；注意力计算量约随 **n²** 增长；对话模型 decoder-only 逐 token 生成。

| | 文字生成模型 | 机器人视频模型 |
|---|---|---|
| 输入变 token | BPE → **离散 ID** | 图片切 **patch**（如 16×16 像素），每块映射成向量，**无词表**；视频再加时间维 |
| 一次多少 token | 一句几十个 | **非常多**（见下方计算） |
| 输出 | 下一个文字 token | **动作**（关节角、夹爪等**连续值**），常一次预测一小段（**action chunk**） |
| 训练方式 | 海量网页文本预测下一个 token（自监督） | **模仿学习**（behavior cloning）：示范里学"看到 → 做"；**数据稀缺且贵**（要人遥操作） |
| 训练瓶颈 | 主要在 GPU 计算 | 常卡在**数据**：视频解码耗 CPU，文件大 I/O 重 |
| 部署 | 晚几秒可接受 | **实时控制**（每秒几次到几十次）、端侧芯片（如 Jetson），需量化 / 蒸馏 |

| 模型类型 | 做什么 | 例子 |
|---|---|---|
| 视觉编码器 | 图像 / 视频 → 特征向量（"看懂"） | ViT、SigLIP、DINOv2 |
| **VLA**（Vision-Language-Action） | 画面 + 指令 + 本体状态 → **动作**；视觉编码器 + 语言模型主干 + 动作头 | RT-2、OpenVLA、π0 |
| 世界模型 / 视频生成 | 预测"做了这个动作后画面会怎样" | 仿真、扩充数据 |
- ⚠️ 策略模型每步通常**只看最近几帧** + 当前状态；长视频是**训练素材**，切成大量（观测, 动作）小样本。
- 与岗位的关系：数据贵 → 质量决定模型；token 爆炸 → 分辨率 / fps / 路数**同时**影响带宽、存储、计算；训练常卡数据加载 → 贵 GPU 在空等。

### 💬 课堂问答

> 🙋 **问**：3 路 × 10 秒 × 30fps × 每帧 196 patch（224×224 按 16×16 切），总 token 数？两种降 token 的办法？  
> 🧑 **我的回答**：1. token有176400个 2.降低fps，降低分辨率  
> 🤖 **点评**：✅ 都对。17.6 万 vs 一句话几十个，差了几千倍。量化一下两个办法：  
> - fps 30 → 5：×1/6 → 29,400；  
> - 分辨率 224 → 112：每帧 (112÷16)² = 49 块，×1/4；两者叠加 ≈ 7,350，**降到 1/24**。  
> - 注意力约 n²：token 降到 1/6，注意力那部分计算约降到 1/36。  
> ➕ 公式里还有能调的：**摄像头路数**（按任务选需要的视角）；**时间维合并**（tubelet：相邻 2 帧合成一个 token，再减半）；**token 压缩**（池化 / 合并相似 token）。➕ 另一类是"不重复算"：视觉编码器冻结时**预先算好特征存起来**，每轮训练不用再解码视频、再过编码器（第 4 步）。  
> ⚠️ 代价：精细操作（插孔、拧螺丝）需要手腕摄像头的高分辨率；动作快的任务需要较高 fps。降多少**要用评估结果说话**（第 6 步），不能拍脑袋。

### 📌 要记住的（第 2 步）
> 视频模型：patch 向量（无词表）、token 量大几千倍、输出连续动作（action chunk）、模仿学习数据贵、训练常卡数据加载、部署要实时。三类：视觉编码器 / VLA / 世界模型。token ≈ 路数 × 秒 × fps × (分辨率÷patch)² → **降 fps、降分辨率、少路数、时间合并、token 压缩、预计算特征**，降多少看评估。

## 第 3 步 · 带宽与存储：在质量不变的前提下降成本

> 🔁 **回顾**：第 1 步——越早丢越省，端侧只丢确定没用的，拿不准的先传轻量版；规模约每天 7 TB、只增不减。
> ⚠️ 前提：**视频质量不变**。第 2 步的降 fps / 分辨率是**算法侧的建模选择**，不是本岗位的省钱手段。

**怎么证明"质量不变"**：**数学无损**（像素完全一致，体积巨大，少用）vs **视觉无损**（人眼和模型都察觉不到差异，实际所说的"无损"）。指标：**VMAF**（Netflix 感知质量分，0~100）、SSIM、PSNR。话术：先定**质量红线**（如 VMAF ≥ 95）→ 样本集验证不越线 → 最好再用训练效果验证。

| 带宽 | 说明 |
|---|---|
| ① 更高效编码 | 同画质 H.265 约比 H.264 小 30~50%，AV1 更小；编码更耗算力 → 看机器人芯片有无**硬件编码器** |
| ② 编码参数 | **CRF 固定质量**代替固定码率：静止画面自动少用码率 |
| ③ 不传没用的片段 | 空闲、重复的不传，留下的**画质不变** |
| ④ 传输策略 | 断点续传；充电 / Wi-Fi 好 / 闲时上传；**有价值的先传**（失败案例）；元数据 + 缩略图先行，按需拉全量 |

| 存储 | 说明 |
|---|---|
| ① 冷热分层 | 近期训练用的放热存储（SSD），旧的按**生命周期策略**自动降到冷存储（HDD / 归档） |
| ② 副本 → 纠删码 | Ceph 默认**三副本**（占 3 倍）；**纠删码**（erasure coding）k 块数据 + m 块校验，坏任意 m 块可恢复，占 (k+m)/k 倍 |
| ③ 去重 | 重复上传、多个数据集复制同一份 → 存一份、其余引用 |
| ④ 管好派生数据 | 训练分片、预计算特征等中间数据常比原始还大 → 定期清理；逐类判断"**存着划算还是用时重算划算**" |

### 💬 课堂问答

> 🙋 **问**：每天 7 TB，三副本 vs 纠删码 4+2（1.5 倍）每天各占多少？一年差多少？为什么不全用纠删码，它适合热数据还是冷数据？  
> 🧑 **我的回答**：1.三副本21TB，纠删码10.5TB，一年差约3800TB 2.纠删码适合冷数据  
> 🤖 **点评**：① ✅ 10.5 TB × 365 ≈ 3,830 TB ≈ **3.8 PB / 年**——光这一项就是大量硬盘和机柜。  
> ② ✅ 结论对，➕ 面试要把**原因**说出来：  
> - **写入**：要先计算校验块，耗 CPU、延迟高；  
> - **读取**：三副本可以从任意一份读、多份并行读；纠删码一块坏了要读其余 k 块**现场算回来**（降级读），慢；  
> - **恢复**：坏盘重建要通过网络读大量数据块，恢复流量大、时间长；  
> - 小文件、随机读写尤其吃亏。  
> → 热数据（刚上传、正在反复被训练读取）用**三副本**保性能；冷数据（旧的、偶尔才读）用**纠删码**省空间，甚至用更大的 k（如 8+3 ≈ 1.375 倍）。这正好和冷热分层配套。  
> ➕ 细节：视频是大文件、多为顺序读，纠删码对它的影响比小文件小，所以不少团队对"温"数据也用纠删码——具体要压测。

### 📌 要记住的（第 3 步）
> 质量不变 = 视觉无损，用 **VMAF 红线 + 训练效果**证明。带宽：更高效编码（H.265 / AV1，看硬件编码器）、CRF、不传无用片段、传输策略（续传、闲时、价值优先、轻量先行）。存储：冷热分层 + 生命周期、**热数据三副本 / 冷数据纠删码**、去重、管好派生数据（存 vs 重算）。

## 第 4 步 · 训练：成本与效率（别让 GPU 闲着）

> 🔁 **回顾**：第 2 步——训练常卡数据（解码耗 CPU、I/O 重）。第 3 步——派生数据"存 vs 重算"。L05——checkpoint / 断点恢复。

```
训练成本 = GPU 卡数 × 训练小时数 × 每卡每小时单价
训练小时数 ≈ 总计算量 ÷ 实际有效算力
```
- 质量不变 → **总计算量固定**；能优化的是**实际有效算力**。三个方向：A 少闲着、B 算得快、C 少白算。
- ⚠️ `nvidia-smi` 的 **GPU util** 只表示"有没有任务在跑"，100% 也可能只用了一小部分算力。更准：**MFU**（Model FLOPs Utilization）= 实际有用计算速度 ÷ 理论峰值，大模型训练约 40% 已不错。

| A. 在等什么 | 现象 | 不影响质量的办法 |
|---|---|---|
| ① 等数据（最常见） | GPU util 忽高忽低、CPU 打满、取数据耗时长 | 加 worker + 预取；**GPU 解码**（NVDEC / DALI）；离线预处理一次；**分片格式**（WebDataset tar 顺序读）代替海量小文件；GPU 节点**本地 NVMe / 分布式缓存**（Alluxio、JuiceFS） |
| ② 等通信 | 多卡每步同步梯度 | 计算与通信重叠；NVLink / InfiniBand / RoCE；**同一任务的 worker 调度到网络相近的节点**（第 5 步） |
| ③ 等别的 | 周期性停顿 | **异步 checkpoint**；评估放单独任务；处理慢节点 |

| B. 算得快 | 对质量 |
|---|---|
| **预计算冻结编码器的特征** | **完全一样** |
| 混合精度 BF16（吞吐约翻倍、显存减半） | 一般无影响，**要验证** |
| 算子融合、`torch.compile` | 基本无影响 |
| 加大 batch size | ⚠️ **改变训练过程**（学习率要调），不是质量中立 |

- C. 少白算：checkpoint + 断点恢复；小规模实验先行；**及早停掉没希望的实验**；实验追踪（MLflow / W&B）防重复跑。

### 💬 课堂问答

> 🙋 **问**：8 卡训练，GPU util 30%~90% 忽高忽低，CPU 一直 100%，每步一大半时间在等数据。瓶颈在哪？两个不影响质量的办法？  
> 🧑 **我的回答**：1.瓶颈是视频解码耗CPU 2.GPU解码，离线预处理  
> 🤖 **点评**：✅ 都对。➕ 面试再补每个办法的**代价**：  
> - **GPU 解码**：NVDEC 是 GPU 上**独立的硬件解码单元**，不占计算核心，但要占显存和 PCIe 带宽，单卡解码路数也有上限；  
> - **离线预处理**：⚠️ 解码后的原始帧**比压缩视频大很多倍**（压缩率常在十倍以上），等于**拿存储换 CPU**（🔁 第 3 步"存 vs 重算"）。如果编码器冻结，存**预计算特征**通常比存原始帧划算。  
> ➕ **CPU 已经 100%，单纯加 DataLoader worker 没用**——worker 也要 CPU。要么把活挪出 CPU（GPU 解码、离线做），要么给更多 CPU。  
> ➕ 和 k8s 相关的一个坑：先检查训练 Pod 的 **CPU limit** 是不是设得太低。超过 limit 会被**限流**（throttling），看起来像"CPU 不够"，其实是配置问题。GPU 节点的 **CPU : GPU 配比**也要够（视频任务每卡常需要不少 CPU 核）。

### ❓ 我的追问

- **梯度是什么？为什么多卡每步都要同步？** → 训练 = 不断微调参数让 **loss**（预测动作和示范动作差多远）变小。**梯度** = 对每个参数算出"它往上调一点，loss 会变大还是变小、变化多快"——像大雾里下山，脚下感觉到的**坡度和方向**。更新：`新参数 = 旧参数 − 学习率 × 梯度`（顺着坡往下走一小步）。  
  例：参数 w = 2.0，梯度 = +0.5（w 变大 loss 变大），学习率 0.1 → 新 w = 2.0 − 0.1 × 0.5 = 1.95。  
  **数据并行**：8 张卡各有一份完整模型，各吃不同的一批数据、各算出一份梯度 → 必须**求平均**（all-reduce）后再更新，否则 8 份模型越走越不一样。梯度个数 = 参数个数：7B 参数（如 OpenVLA）× 2 字节（BF16）≈ **每步要同步约 14 GB** → 所以通信会成为瓶颈。

- **参数量就是模型内向量的维度吗？** → 不是。**维度**（hidden size，如 e5-small 的 384、7B 模型的 4096）= 每个 token 的向量有多"宽"，是**流过模型的数据**的形状；**参数** = 模型里所有**权重矩阵**中数字的总数，是**模型本身**。关系：一个线性层的权重矩阵是 `输入维度 × 输出维度`，维度 4096 → 一个 4096 × 4096 矩阵就有约 1,677 万参数。Transformer 每层（🔁 L04：注意力 + FFN）约 `12 × d²` 个参数（注意力 4d² + FFN 8d²），总量 `≈ 12 × 层数 × d² + 词表大小 × d`。验算：d = 4096、32 层 → 12 × 32 × 4096² ≈ 64 亿，加词表 32000 × 4096 ≈ 1.3 亿 → **约 7B** ✅；e5-small：d = 384、12 层 → 约 2,100 万 + 词表 30522 × 384 ≈ 1,200 万 → **约 33M** ✅。**维度翻倍 → 参数约变 4 倍**（d²）。

- **梯度最终在模型文件里吗？** → 不在。梯度是**每一步的临时值**：算出 → 同步 → 更新参数 → 清零，下一步重新算。（注：64 亿只是各层部分，加词表总共约 70 亿参数。）三种"文件 / 内存"要分清：  
  - **部署用的模型文件**（如 safetensors）：**只有参数**。7B × 2 字节（BF16）≈ 14 GB；量化到 4 bit ≈ 3.5 GB。  
  - **训练 checkpoint**（断点恢复用）：参数 + **优化器状态**（Adam 为每个参数存两个 FP32 值：动量 m、方差 v）+ 常见还有 FP32 主权重 + 步数 / 学习率进度 / 数据读到哪。**一般不存梯度**（恢复后重算）。7B 约 7B × (4 + 4 + 4) ≈ **84 GB 起** → 写盘慢（用异步 checkpoint）、存储贵（只留最近 N 个 + 最好的那个）。  
  - **训练时显存**：混合精度 + Adam 每参数约 **16 字节**（BF16 参数 2 + 梯度 2 + FP32 主权重 4 + m 4 + v 4）→ 7B ≈ 112 GB，**一张 80 GB 的卡放不下** → 用 FSDP / ZeRO 把参数、梯度、优化器状态**切分到多张卡**。

- **batch 是什么？**（第 6 步后补问）→ 训练**每一步拿一组样本一起算**，这一组就是 batch，组里的样本个数 = **batch size**。机器人场景一个样本 =（最近几帧 + 本体状态）→ 一段示范动作。一步：batch 里每个样本算 loss → 梯度**求平均** → 更新**一次**参数。为什么不一次一个：单样本梯度**噪声大**（像只问一个路人指路），GPU 也吃不满；为什么不一次全部：**显存放不下**、一轮只更新一次太慢。  
  - 术语：**step** = 一次参数更新；**epoch** = 全部数据过一遍。例：10,000 样本、batch 32 → 每 epoch 约 313 步。  
  - **全局 batch = 每卡 batch × 卡数 × 梯度累积步数**（梯度累积：显存不够时连跑几个小 batch、把梯度加起来再更新，效果等同大 batch）。例：每卡 24 × 4 卡 × 1 = 96。  
  - **为什么改 batch 会影响质量**：batch 大 → 梯度平均得更准、但同样数据下**更新次数变少** → 学习率要跟着调（常用经验：batch 翻倍、学习率约翻倍，需验证）；过大还可能泛化变差。所以加卡时**固定全局 batch** 才质量中立。

### 📌 要记住的（第 4 步）
> 训练成本 = 卡数 × 小时 × 单价；质量不变时总计算量固定，优化**有效算力**。看 **MFU** 别只看 GPU util。A 别闲着：数据（GPU 解码、离线预处理、分片格式、本地缓存）、通信（重叠、高速网络、就近调度）、其他（异步 checkpoint）。B 算得快：预计算冻结特征（完全等价）、BF16（要验证）；加 batch 不是质量中立。C 少白算：断点恢复、小实验先行、早停、实验追踪。CPU 打满先查 Pod 的 CPU limit 和 CPU : GPU 配比。

## 第 5 步 · k8s 训练集群：扩展性与成本

> 🔁 **回顾**：第 4 步——worker 就近放、查 Pod 的 CPU limit、checkpoint 断点恢复。L05——队列与限并发。前提：机器可加但花钱。

**① gang scheduling（成组调度）**：k8s 默认**逐个 Pod** 调度，但分布式训练 N 个 worker **必须同时启动**（每步都要一起同步梯度）→ 要么全给要么全不给。工具：**Volcano**、**Kueue**（排队，配额够了才放整个任务进来）。

| ② 组件 | 做什么 |
|---|---|
| GPU device plugin | 让 k8s 认识 GPU：`nvidia.com/gpu: 8` |
| 按型号分节点池 | label + taint 隔离，普通任务不占 GPU 节点 |
| 训练 Operator | Kubeflow PyTorchJob：一个 YAML 描述 N worker 任务，负责创建 / 重启 / 清理 |
| 队列 + 配额 | 每团队一份配额，**闲置可借出、需要时收回** |
| 优先级 + 抢占 | 生产 > 实验；被抢占的**从 checkpoint 恢复** |
| 拓扑感知调度 | 同任务的 worker 放同机 / 同机架，少等通信 |

| ③ 扩容 | 要点 |
|---|---|
| 自动扩缩容 | Pod Pending → 加节点（Cluster Autoscaler、Karpenter）；空闲 → 缩 |
| GPU 节点扩容慢 | 开机、驱动、拉十几 GB 镜像，可能要几分钟以上 → **镜像预拉** |
| 基线 + 弹性 | 常态负载 = 固定容量（自有 / 长期预留，最便宜）；高峰 = 按需（贵）；可中断任务 = **抢占式实例 spot**（最便宜、随时收回，必须有 checkpoint） |
| 何时加机器 | 比较**等待成本**（人在等、交付期限）vs **加机器成本**；常见：**高优先级等待超阈值才扩**，低优先级排队 |

| ④ 先用好现有的 | 办法 |
|---|---|
| 分配了 ≠ 用上了 | **DCGM exporter** 采集每 Pod 的 GPU 实际使用，找"占卡不干活" |
| 碎片化 | 单卡任务散在各机器，凑不出 8 张空卡 → **bin packing 装箱**集中放 |
| 小任务独占整卡 | **MIG** 切卡或时间片共享（调试、评估、推理） |
| 闲置占用 | 空闲 notebook 自动回收 |
| 弹性训练 | torchrun elastic：worker 数可变、不用重启 |
- ⚠️ 加 GPU 时**存储和网络带宽也要跟着加**，否则多的卡只是在等数据。

### 💬 课堂问答

> 🙋 **问**：① 正好 8 张空卡，A、B 两个任务各要 8 个单卡 worker，默认调度器会怎样？② 集群满载都是低优先级实验，来了个明天要结果的高优先级生产训练——扩容还是抢占？前提是什么？  
> 🧑 **我的回答**：1.两个任务各拿4张卡互相卡死 2.抢占，前提是有checkpoint  
> 🤖 **点评**：① ✅ 这就是**部分分配死锁**（不一定正好 4 / 4，任何拆分都一样）：卡 **100% 已分配、0% 在算**，而且永远等下去。gang scheduling 下 A 整体进入、B 整体排队，A 跑完 B 再跑。  
> ② ✅ 抢占 + checkpoint 是对的默认选择：**快**（扩 GPU 节点要几分钟以上，有时还没货）、**不花钱**。➕ 前提再补几条：被抢占任务能**自动恢复**（Operator 重启 + 读最近 checkpoint）、**PriorityClass 配好**且只允许高抢低、通知任务负责人。➕ 抢占的代价 = 被抢任务**从上次 checkpoint 到现在的进度白做** + 它被推迟——checkpoint 越勤损失越小。  
> ➕ 不是二选一：**先抢占，不够再扩容**。抢完低优先级还凑不够卡，或者按现有卡数算**赶不上明天**（如需 20 小时），就为这个任务临时加机器——这时"等待成本"（错过交付）明显大于机器成本。

### ❓ 我的追问

- **一张 GPU 能同时跑 2 个以上训练任务吗？** → 能，但**只对小任务划算**。k8s 默认 `nvidia.com/gpu` 只能申请整数张，要共享得靠下面三种机制：

| 方式 | 原理 | 隔离 | 适合 |
|---|---|---|---|
| **时间片**（time-slicing） | device plugin 把 1 张卡报成 N 份，各进程**轮流**用 | ⚠️ **显存不隔离**（一个吃满别人 OOM）、故障不隔离、有切换开销 | 调试、notebook 等轻负载 |
| **MPS**（Multi-Process Service） | 多个进程的计算**真正同时**在卡上跑 | 较弱（可限显存 / 算力比例），一个出错可能牵连别人 | 多个都用不满卡的小任务（小模型超参搜索） |
| **MIG**（Multi-Instance GPU，A100 / H100 等） | **硬件**切成最多 7 个独立小卡，各有自己的显存和计算单元 | **强** | 推理、评估、多租户；切分规格固定，改切法要先清空卡 |
- ⚠️ **大训练任务不该共享**：本来就能把算力和显存吃满（7B 训练要约 112 GB，一张卡都不够），两个挤一张只会**都变慢**、显存也不够。
- 判断标准：**单个任务用不满这张卡**（MFU 低是因为任务小，不是因为等数据）时，共享才能提高利用率。➕ 开源方案 HAMi 可在 k8s 里做 GPU 虚拟化（按显存 / 算力比例申请）。

- **8 台 × 4 卡共享集群，训练 A 初始 4 卡：① `nvidia.com/gpu` 和 Pod 数怎么设？② 跑满了想 4 → 5、最多 6（留 2 张给别人），怎么配？**  
  - ① **1 个 Pod × 4 卡**（`limits: nvidia.com/gpu: 4`，`torchrun --nproc_per_node=4`）优于 4 个 Pod × 1 卡：同机 4 卡走 NVLink / PCIe，快；4 个单卡 Pod 可能被散到 4 台机器，通信走网络、还制造碎片。每台正好 4 卡 → 整机放下。➕ 配好 CPU / 内存，`/dev/shm` 挂内存盘（DataLoader 多进程靠共享内存，默认 64 MB 会报错）。  
  - ② ⚠️ 先纠正前提：**"4 卡跑满"是好事**（不在等数据），不是扩容理由；扩容理由是**赶时间**。⚠️ 加卡 = 全局 batch 变大 → 学习率要调，**不是质量中立**（第 4 步）——要保持质量就固定全局 batch（每卡 batch 变小 / 梯度累积调整）。  
  - ⚠️ **5、6 卡跨机**：4 + 1 / 4 + 2 分在两台机器，all-reduce 被**最慢的那条链路**（机间网络）拖住，6 卡可能远不到 1.5 倍、甚至不如 4 卡。训练扩容按**整机**（4 → 8）最划算；必须 4 → 6 要先实测。  
  - 配置思路（字段以所用 Training Operator 版本文档为准）：**弹性训练** → 改成单卡粒度的 Worker（`nvidia.com/gpu: 1`）+ `elasticPolicy: {minReplicas: 4, maxReplicas: 6, rdzvBackend: c10d}`，`torchrun --nnodes=4:6`；加 Pod 亲和性尽量挤在少数机器上。⚠️ 成员变化时 torchrun 会让**所有 worker 重启、从最近状态恢复**，并非无缝。  
  - **"最多 6、留 2 张给别人"是配额问题，不是任务参数**：命名空间 ResourceQuota `requests.nvidia.com/gpu: "6"`，或 Kueue ClusterQueue 的 `nominalQuota` / `borrowingLimit`；别人的保底由他们的配额保证。高优先级用 `priorityClassName`。  
  - 现实中更常见的简单做法：**存 checkpoint → 停掉 → 用 6 卡重新提交 → 从 checkpoint 恢复**（损失几分钟），比弹性训练省心。

- **只有 4 张空卡且分散在 4 台机器上，1 Pod × 4 卡怎么办？** → 这个 Pod 会一直 **Pending**（没有一台机器能放下）。四个选择：  
  - **等**：排队到某台机器空出整机。代价 = 等待时间。  
  - **拆成 4 Pod × 1 卡**马上跑：跨机通信慢；只有模型小（梯度少）或有 RDMA 高速网时才可接受，要实测。  
  - **腾出一整台（碎片整理）**：A 是高优先级 → kube-scheduler 的**抢占**会找一台"踢掉低优先级 Pod 就能放下"的机器，把那上面的小任务驱逐（它们从 checkpoint 恢复、挪到别处）。Volcano / Kueue 也支持。高优先级时通常选这个。  
  - 决策：比较 **预计等待时间 vs 拆开跑变慢多少 vs 被抢任务的损失**。  
  - **根治 = 别让碎片发生**：调度打分用 **MostAllocated**（装箱，优先填满已用的机器）；**分池**（多卡整机任务一个池、单卡小任务另一个池）；用 descheduler 定期把小任务挪到一起。

- **4 卡的 checkpoint 改 6 卡恢复，之前的训练结果还有用吗？** → **完全有用**。⚠️ 先纠正：checkpoint **不带梯度**（🔁 第 4 步追问）；梯度本来**每一步都重新算**，和卡数无关。checkpoint 里的东西都与卡数无关：**参数** = 学到的结果本身（下山比喻里"你站在哪"）；**优化器状态**（Adam 的 m、v）也是每个参数一份；步数、学习率进度照旧。加卡只改变"**每一步的梯度由几张卡分摊算、再求平均**"，不改变已经走到的位置。要注意三点工程细节：  
  - **分片 checkpoint**：FSDP / ZeRO 按卡切分存（4 份），6 卡加载要**重新切分** → 用 PyTorch 的分布式 checkpoint（DCP，支持换卡数加载）或先合并成整份；  
  - **数据进度**：每张卡读到哪是按 4 卡划分的 → 记录"**全局**读到第几个样本"，6 卡重新划分剩下的数据，避免重复或漏读；  
  - **全局 batch 保持不变**：如 4 × 24 = 96 → 6 × 16 = 96，训练动态不变（第 4 步：batch 变了不是质量中立）。

### 📌 要记住的（第 5 步）
> 分布式训练要 **gang scheduling**（Volcano / Kueue），否则部分分配死锁：卡全分配、零计算。组件：device plugin、节点池、训练 Operator、队列配额（可借）、优先级抢占（靠 checkpoint）、拓扑感知。扩容：基线固定 + 高峰按需 + 可中断用 spot；**等待成本 vs 机器成本**，高优先级超阈值才扩；镜像预拉。先用好现有：DCGM 看真实使用、装箱防碎片、MIG 切小卡、回收闲置、弹性训练。加卡要同步加存储 / 网络带宽。紧急任务：**先抢占，不够再扩**。

## 第 6 步 · 质量 vs 成本 + 面试口述框架

> 🔁 **回顾**：第 3 步——VMAF 红线 + 训练效果证明质量不变。第 4 步——"完全一样 / 要验证 / 会改变训练"。L02——评估驱动决策。

| ① 三类优化 | 例子 | 怎么决定 |
|---|---|---|
| **等价**（结果完全一样） | 缓存、数据加载、预计算冻结特征、去重、冷数据纠删码、异步 checkpoint、调度、碎片整理 | 放手做，验证功能正确 |
| **近似等价**（要验证） | 换编码（H.265 / AV1）、BF16、分片格式转换 | 质量红线 + 小规模 A/B |
| **有损取舍** | 降分辨率 / 帧率、丢数据、小模型、少训练步数 | **不是你一个人定**，和算法 / 业务看评估结果 |
- 质量不变前提下，主战场是前两类，**按顺序**：先等价、再近似等价；第三类拿数据交大家决定。

| ② 验证层次 | 看什么 | 成本 |
|---|---|---|
| 数据质量 | VMAF、掉帧率、同步误差 | 低 |
| 离线指标 | loss、动作误差 | 低 |
| 仿真 | 仿真成功率 | 中 |
| 真机 | 真机成功率 | **高** |
- A/B：只差一项、**多随机种子**看是否在正常波动内、做成流水线**固定关卡**。

**③ 单位成本**：每有效训练小时成本、每 TB 有效数据成本、MFU、**每提升 1% 成功率的成本**。➕ **数据质量 > 数量**：多样 / 困难 / 失败场景比堆量更提质、更省钱（飞轮回流的价值）。

**④ 口述五步**：
```
1. 量化现状：拆账（带宽 / 存储 / 计算各占多少）+ 关键指标（MFU、存储增速、上传量）
2. 找最大头：二八原则，花钱最多 / 瓶颈在哪
3. 按顺序出方案：等价 → 近似等价 → 有损（交大家决定）
4. 定质量红线和验证方法：VMAF、离线、仿真、真机，A/B
5. 试点 → 逐步扩大 → 全量，成本看板持续监控、可回滚
```
- 关键是第 1 步：**先测量再动手**。

### 💬 课堂问答

> 🙋 **问**：模拟面试——"我们每月 GPU 账单很高，你入职第一个月会怎么做？"用五步框架口述。  
> 🧑 **我的回答**：1. 先拿到账单明细，看看钱都花在哪些环节了，比如传输视频的带宽费用，存储费用，计算时的机器/GPU费用等 2. 看看当前哪里花钱最多，从大到小看有没有优化的空间，比如，传输和存储视频的开销大的话，可以考虑用低分辨率或者更高压缩率编码的视频。但这有可能降低最终训练的质量，这个可以拿已有数据降低分辨率重新训练后做对比测试。 3. 如果有不影响质量的优化方式，建议优先执行，比如去除原是视频素材内无效的部分（机器人没有动作/白屏等） 4. 先不改变现在的质量衡量标准，用相同标准来比较优化前后的效果 5. 优化方案验证通过后，先小范围实机部署，在实际环境中验证通过后，再大规模铺开  
> 🤖 **点评**：结构完整，五步都在 ✅。三处要改：  
> ⚠️ **答题要贴题**：问的是 **GPU 账单**，第 2、3 步举的却是带宽 / 存储的例子。应聚焦计算：GPU 分配了多少、实际用了多少（DCGM、MFU）、哪些团队 / 任务最花钱、有没有闲置的 notebook、失败后从头重跑的任务、重复实验、排不上队的碎片。  
> ⚠️ **第 1 步只看账单不够**：账单告诉你**钱花在哪**，**利用率指标**才告诉你**浪费在哪**。  
> ⚠️ **降分辨率违反"质量不变"前提**，是"有损取舍"，不该放在第一个例子；"更高压缩率的编码"是近似等价 ✅。另外"降分辨率后**重新训练**做对比"很贵 → 用小规模实验。  
> ✅ 第 3 步"不影响质量的优先"顺序对，但应提到第 2 步之前；✅ 第 4 步"**不改质量标准**"很好（防止"改标准让结果好看"）。  
> ➕ 第 5 步"实机部署"适用于**模型**改动；**基础设施**改动（调度、缓存）的灰度是"先在部分队列 / 部分任务上开启"，并准备好**回滚**。参考回答见 `robot-data-interview-notes.md` 题 1。

### 📌 要记住的（第 6 步）
> 优化分三类：**等价**（放手做）→ **近似等价**（红线 + A/B）→ **有损**（交大家用评估决定），按顺序来。验证分层：数据质量 → 离线 → 仿真 → 真机，多种子、做成流水线关卡、不改质量标准。看单位成本（MFU、每有效训练小时、每 1% 成功率的成本）；数据质量 > 数量。口述五步：**量化 → 找最大头 → 按类出方案 → 红线验证 → 灰度上线 + 看板**，先测量再动手，答题贴题。
