## 第 1 步 · BM25 = 修好了的 TF-IDF

### 🔁 回顾：TF-IDF（s4_03）
- 切词：中文用连续两字（bigram），"养老储备" → 养老 / 老储 / 储备。
- **TF**（term frequency，词频）：词在这篇文档里出现几次。
- **IDF**（inverse document frequency，逆文档频率）：`log(总文档数 / 含该词的文档数)`，越稀有越高。
- 每篇文档 → 词表那么长的稀疏向量（每位 = TF × IDF），和 query 向量算**余弦**。

### 📛 名字
> **❓ 我的追问**：BM25 完整的名字是啥意思？（同时提出：以后碰到缩写术语，先介绍下概念）

- **BM25 = Best Matching 25**，也叫 **Okapi BM25**。
- 1990 年代伦敦城市大学 Robertson 等人在 **Okapi** 检索系统里试了一系列权重公式（BM1、BM11、BM15……），**第 25 号**效果最好，一直沿用下来。"25"只是编号。
- 关键词检索的**事实标准**：Elasticsearch / OpenSearch / Lucene 的默认打分算法。

### BM25 修了 TF-IDF 的三个毛病

| 毛病 | TF-IDF | BM25 |
|---|---|---|
| ① TF 线性 | 出现 10 次 = 1 次的 10 倍，容易被关键词堆砌钻空子 | **TF 饱和**，封顶 k1 + 1 |
| ② 不管长短 | 长文档天然词多，占便宜 | **长度归一化**：比平均长就打折 |
| ③ IDF 会变 0 | 每篇都有的词，log(N/N) = 0 | 平滑版 `ln((N − df + 0.5)/(df + 0.5) + 1)`，永远 > 0（了解即可） |

另外**打分方式不同**：TF-IDF 建向量算余弦；BM25 不建向量，**把 query 里每个词的得分直接相加**。

### 完整公式

```
                         IDF(t) × tf × (k1 + 1)
score(q, d) =   Σ    ──────────────────────────────────────
              t ∈ q   tf + k1 × (1 − b + b × |d| / avgdl)
                                 └──── 长度惩罚因子 ────┘
```

| 符号 | 含义 | 值从哪来 | 例子里代入的值 |
|---|---|---|---|
| **q** | query，用户查询 | 用户输入 | — |
| **d** | 正在打分的文档 | 文档库里的一篇 | A 或 B |
| **t ∈ q**、**Σ** | 对 query 里**每个词**分别算分再相加 | query 切词 | 只有"养老" |
| **tf** | 词 t 在**这篇文档**里出现的次数 | 数当前文档 | 1 |
| **IDF(t)** | 词 t 的稀有度 | 建库时**全库**统计 | A、B 相同，比较时约掉 |
| **\|d\|** | 这篇文档的长度（词数） | 数当前文档 | A = 20，B = 2000 |
| **avgdl** | average document length，全库平均文档长度 = 所有文档长度之和 / 文档数 | 建库时**全库**统计 | 假设 200 |
| **k1** | TF 饱和速度旋钮 | **人工常数**（超参数） | 1.2（默认，常用 1.2~2.0） |
| **b** | 长度惩罚力度，0~1 | **人工常数**（超参数） | 0.75（默认） |

> 值的三种来源：**当前文档**（tf、|d|）、**全库统计**（IDF、avgdl，和 s4_03 的 vocab/idf 一样，建库时学出来、query 时复用）、**人工常数**（k1、b）。
> "长度"实际按**词（token）数**算，例子用字数只为直观。

### k1：词频饱和速度
> **❓ 我的追问**：k1 是什么？（同时提出：以后碰到公式，把每一项的意思、用了什么值都说明下）

- 名字：k 是常数的惯用字母，1 是编号（早期还有 k2、k3，现基本不用）。
- 固定 tf = 5、文档长度 = 平均长度（排除 b 的影响），TF 部分 = `5 × (k1+1) / (5 + k1)`：

| k1 | TF 部分 | 含义 |
|---|---|---|
| 0 | 1.0 | 只看出现没出现 |
| 0.5 | 1.36 | 很快饱和 |
| **1.2（默认）** | **1.77** | 适中 |
| 2.0 | 2.14 | 饱和更慢 |
| → ∞ | 5 | 不饱和，退化成 TF-IDF 的线性 TF |

- k1 = 1.2 时随 tf 变化：tf = 1 → 1.0，2 → 1.38，5 → 1.77，10 → 1.96，∞ → 2.2（= k1+1）。
- 小巧合：tf = 1 且长度 = 平均时，TF 部分 = (k1+1)/(1+k1) = 1，与 k1 无关。**k1 只影响"重复出现"那部分加分。**

### b：长度惩罚
例子：两篇都只提到"养老" 1 次——A 是 20 字简介，B 是 2000 字合同。**A 更可能专门讲养老**，所以要惩罚长文档里的词频。

> **💬 课堂问答**
>
> **🙋 问**：两篇都只提到"养老" 1 次，A 是 20 字简介、B 是 2000 字合同。哪篇更可能专门讲养老？BM25 应该奖励还是惩罚长文档里的词频？
>
> **🧑 我的回答**：A 更可能
>
> **🤖 点评**：✅ 对。由此推出：BM25 要**惩罚**长文档里的词频，参数 b 控制惩罚力度。

> **❓ 我的追问**："长度 / 平均"，A 是 0.1，怎么计算的？

逐步算（k1 = 1.2，b = 0.75，tf = 1，avgdl = 200）：

```
               A（20 字）                    B（2000 字）
① 长度比       20/200 = 0.1                  2000/200 = 10
② 惩罚因子     1 − 0.75 + 0.75×0.1 = 0.325    1 − 0.75 + 0.75×10 = 7.75
③ 分母         1 + 1.2×0.325 = 1.39           1 + 1.2×7.75 = 10.3
④ 分子         1 × 2.2 = 2.2                  2.2
⑤ TF 部分      2.2/1.39 ≈ 1.58               2.2/10.3 ≈ 0.21
```

同样出现 1 次，A 得分约是 B 的 **7.5 倍**。
直觉：比平均短 → 惩罚因子 < 1 → 得分放大；比平均长 → 惩罚因子 > 1 → 打折；等于平均 → 不加不减。b = 0 不管长短，b = 1 完全按比例罚。

### 📌 要记住的
> BM25 = TF-IDF 改良版：① **TF 饱和**（k1）② **长度归一化**（b）③ **IDF 平滑**。打分是 query 每个词得分**相加**，不算余弦。默认 **k1 = 1.2、b = 0.75**，要调就用 eval 在自己数据上调。

### 补充：BM25 索引怎么建——倒排索引（用户追问，Q31 时补）

> **❓ 我的追问**：建 BM25 索引这步怎么做？

📛 **倒排索引（Inverted Index）**：
- **正排索引（Forward Index）**：文档 → 它包含哪些词。s4_06 的 `BM25Index.docs_tf` 就是正排：每篇一个 `{词: 次数}`。
- **倒排索引**：反过来，**词 → 哪些文档包含它（以及出现几次）**。"倒排"就是把正排倒过来。类比**书末的索引页**：查"养老"直接翻到第 12、37 页，不用从头读整本书。
- 每个词对应的那串 `[(文档, tf), …]` 叫 **posting list（倒排列表）**。

FinWise 7 个产品建出来的倒排索引（共 232 个 bigram 词条），截取几条：
```
养老 → [(P-PENSION, 2)]
本金 → [(P-BOND, 1)]
20   → [(P-PENSION, 1)]
货币 → [(P-MMF, 2), (P-SHORTBOND, 1)]
基金 → [(P-MMF,1), (P-PENSION,1), (P-TECH,1), (P-BOND,1), (P-SHORTBOND,2), (P-MIX,1)]
```

**建索引四步（离线，一次性）**：

| 步 | 做什么 | 存下来给打分用 |
|---|---|---|
| ① 分词 | 每篇文档切词（这里是 bigram；生产用 jieba / Elasticsearch IK 分词插件，代码当整体） | — |
| ② 统计每篇 | 每个词的 tf、文档长度 \|d\| | tf（写进 posting）、\|d\| |
| ③ 写倒排表 | 每个词追加 `(文档 id, tf)` 到它的 posting list | posting list |
| ④ 全库统计 | 文档总数 N、平均长度 avgdl；**df = posting list 的长度**（不用另外存） | N、avgdl → 算 IDF |

**查询时（在线）**：query 切词 → **只取这几个词的 posting list** → 只给出现在这些列表里的文档打分、相加 → 排序。
- 例："本金一分都不能少" → 只有"本金"有 posting → **只碰 P-BOND 一篇**。
- 对比 s4_06 的练习版：对 7 篇**全部**打分（O(N) 全表扫，和 s4_01 for 循环算余弦一样）。百万级时倒排只碰"含 query 词"的几十~几千篇。
- **"基金"这种词 posting 很长、IDF 很低** → 既拖慢查询又几乎不贡献分数 → 生产常当**停用词**（stop word）过滤。

**增量更新**：新文档 → 分词 → 追加进相关 posting list，更新 N / avgdl；删除通常先**打删除标记**、后台再合并清理（Lucene 的做法）。

**谁在用**：Elasticsearch / OpenSearch / Lucene 的核心就是倒排索引 + BM25 打分。

**追问：增删文档时，N / avgdl / df 变了，之前算好的数据要重算吗？**

> **❓ 我的追问**：文档总数 N 变化的时候，新增或者删除文档，会影响之前算好的数据吗？比如 avgdl

关键是**存原始计数，不存派生值**：

| 数据 | 归属 | 新增一篇文档时 |
|---|---|---|
| posting 里的 `(文档, tf)` | 每篇自己的 | **不变**（只给新文档的词追加条目） |
| 每篇的长度 \|d\| | 每篇自己的 | **不变**（新文档记一个） |
| N | 全库计数器 | N + 1 |
| 总长度 | 全库计数器 | + 新文档长度 → **avgdl = 总长度 / N 现算** |
| df | = posting list 长度 | 新文档包含的词各自 + 1（追加时自动变） |
| IDF | **派生值** | **不存，查询时用当前 N、df 现算** |

- 所以增删只是**改几个计数器 + 追加/标记 posting**，旧数据不用重写。
- 副作用：同一篇老文档、同一个 query，今天和明天的 BM25 **分数会略有不同**（IDF、avgdl 变了）。没关系——🔁 分数只在同一 query 内比相对排名。
- 删除通常先打标记、后台合并时才真正移除，所以 df 在合并前会**略微偏大**——Lucene 接受这点误差换取速度。
- 🔁 **反例对照**：s4_03 的 `TfidfEncoder` 把 `tf × idf` **乘好存成向量**（派生值被"烤"进去了）→ 新增一篇导致 IDF 变化，**所有文档的向量都要重算**。s4_06 的练习版 `BM25Index` 在 `__init__` 里也预先算好了 `self.idf` 和 `self.avgdl`，增删后同样会过时，只能整体重建。
- 🔁 **embedding 没有这个问题**：每篇文档的向量只取决于它自己的文本，和库里有没有别的文档无关 → 新增只编码新文档。这是向量检索在增量更新上的一个优势。

> 📌 倒排索引**存原始计数**（tf、|d|、N、总长度，df = 列表长度），**IDF / avgdl 查询时现算** → 增删文档只改计数器，不重算旧数据。代价是老文档的分数会随库变化轻微漂移（不影响同一 query 内的排名）。

> 📌 **向量检索靠 ANN 索引（HNSW）避免全表扫；关键词检索靠倒排索引（词 → 文档列表）避免全表扫。** 建 BM25 索引 = 分词 → 统计 tf/长度 → 写倒排表 → 全库统计 N/avgdl（df = 倒排列表长度）。

## 第 2 步 · 有了 embedding，为什么还要 BM25

### 🔁 回顾：s4_03 / s5_01 结论
- embedding（e5，384 维）比**意思**："养老"能找到"退休储备"。
- TF-IDF 比**字面**：没有共同词就是 0 分。
- s5_01 B 套（口语化）题：embedding Hit@3 = 1.00，TF-IDF = 0.67。

### 问题
用户这样搜时会怎样？"**P-TECH** 还能买吗"、"那个 **2040** 的养老基金"、"最短持有 **30 天**的"。

共同点：**都是精确的代码、编号、数字**。embedding 在这里容易误判、召回不准；关键词检索（**BM25**，不是 TF-IDF）反而最好。

> **💬 课堂问答**
>
> **🙋 问**："P-TECH 还能买吗""那个 2040 的养老基金""最短持有 30 天的"——这三个 query 有什么共同点？embedding 可能在哪里吃亏？
>
> **🧑 我的回答**：都是精确的代码或数字，embedding 可能误判或者召回度不高。这时候用TF-IDF匹配到的结果是最好的。
>
> **🤖 点评**：✅ 共同点答对了。  
> ⚠️ 关键词检索要说 **BM25**（TF-IDF 的改良版，生产都用它），不是 TF-IDF。  
> ➕ 面试会追问"embedding **为什么**吃亏"：编号没有语义、相近数字区分度低、训练时没见过（见下表）。

### 为什么 embedding 吃亏
🔁 embedding 是**对比学习**训练的（意思近的拉近、不同的推远），学会的是"**意思像不像**"。

| 原因 | 解释 | 例子 |
|---|---|---|
| ① 编号没有"意思" | 标识符没有语义可学 | "P-TECH" 和 "P-MIX" 向量可能很近（都像编号） |
| ② 相近数字区分度低 | 模型觉得 2040 和 2035 很像 | 搜 2040，2035 的基金分数只比它低一点点（7d 实测只差 0.015），干扰项一多就容易被翻 |
| ③ 训练时没见过 | 新产品名、内部术语 | 新上线的"安心盈 Pro" |

BM25 逐字比对：只有含"2040"的文档能得这项分；而且这类词很**稀有**（df 小 → IDF 高），命中就高分。

### 📌 要记住的
> **两路互补**：embedding 擅长"**意思近、字面不同**"；BM25 擅长"**字面精确、意思难懂**"（代码、编号、数字、专有名词、新词）。线上两路都召回 = **Hybrid Retrieval（混合检索）**。
> 动手时会加一套"精确匹配题"（C 套）亲眼验证。  
> ⚠️ 更正（7d 实测）：e5 对数字**不是完全"盲"**，加了 2035 干扰项后 2040 仍排第一，但**只险胜 0.015**；准确说法是"**区分度很低**"，不是"会排错"。

## 第 3 步 · 两路分数为什么不能直接相加

```
向量检索：  [P-PENSION 0.89,  P-MIX 0.86,     P-BOND 0.84]
BM25：     [P-PENSION 7.3,   P-SHORTBOND 2.1, P-MMF 0.9]
```

### 🔁 回顾：embedding 分数压缩（concepts-basics）
e5 的余弦分数挤在 **0.7 ~ 0.95** 窄带里，绝对值没意义，**只有同一 query 内部的相对排名有意义**。

> **💬 课堂问答**
>
> **🙋 问**：结合 embedding 分数压缩（0.7~0.95），直接把余弦分和 BM25 分相加会出什么问题？
>
> **🧑 我的回答**：BM25 分数范围远大于余弦，简单相加的话，BM25占的比重太大，余弦其实就不重要了。
>
> **🤖 点评**：✅ 对，就是**量纲不同**。  
> ➕ 更麻烦的是 BM25 **没有固定上限**，连"乘个系数缩小"都不好定 → 干脆不用分数、只用排名（RRF）。

### 结论
- **量纲不同**：BM25 范围远大于余弦，直接相加 BM25 主导，余弦几乎不起作用。
- 更麻烦：BM25 **没有固定上限**（query 越长、词越稀有分越高，可能 2 也可能 30），连"乘个固定系数缩小"都不好定。
- 解法：**不用分数，只用排名** → RRF。

### 📌 要记住的
> 两路分数**量纲不同、BM25 无上界** → 不能直接相加。要么只用**排名**融合（RRF），要么先**归一化**再加权。

## 第 4 步 · RRF 倒数排名融合

### 📛 名字
- **RRF = Reciprocal Rank Fusion**，倒数排名融合。Reciprocal = 倒数，Rank = 排名，Fusion = 融合：把每一路的**名次取倒数**再合并。
- 出处：Cormack 等，2009。简单稳定，混合检索的**默认融合方法**（Elasticsearch、Weaviate、Milvus 内置）。

### 🔁 回顾：倒数排名（s5_01）
`reciprocal_rank`：第 1 名 → 1.0，第 2 → 0.5，第 3 → 0.33，即 1/名次，是 MRR 的基础。**RRF 用同一个思路**：MRR 用它**评估**，RRF 用它**合并排序**。

### 公式

```
                    1
RRF(d) =   Σ    ─────────────
         r ∈ R   k + rank_r(d)
```

| 符号 | 含义 | 值从哪来 | 例子里代入的值 |
|---|---|---|---|
| **d** | 某篇文档 | 任一路召回到的文档 | P-PENSION 等 |
| **R** | 所有参与融合的检索器 | 系统设计决定 | {向量检索, BM25} |
| **Σ r ∈ R** | 每个检索器算一项再相加 | — | 两项 |
| **rank_r(d)** | d 在检索器 r 结果里的名次，从 1 开始；**没召回 → 这项记 0** | 各路结果 | 1、2、3 |
| **k** | 平滑常数，防止第 1 名权重太突出 | **人工常数**，默认 **60**（论文实验得出） | 60 |

### 例子（k = 60）

| 文档 | 向量名次 | BM25 名次 | RRF | 最终 |
|---|---|---|---|---|
| P-PENSION | 1 | 1 | 1/61 + 1/61 = **0.0328** | 1 |
| P-MIX | 2 | — | 1/62 = 0.0161 | 2（并列） |
| P-SHORTBOND | — | 2 | 1/62 = 0.0161 | 2（并列） |
| P-BOND | 3 | — | 1/63 = 0.0159 | 4（并列） |
| P-MMF | — | 3 | 1/63 = 0.0159 | 4（并列） |

原始分数（0.89、7.3）完全没用到 → 量纲问题自然消失。

### 另一种融合：归一化 + 加权
先把两路分数各自 **min-max 归一化**到 0~1：`(分数 − 最小值) / (最大值 − 最小值)`，再加权求和。保留了"分差大小"信息，但对异常值敏感、权重要调参。**默认先用 RRF**（无需调参）。面试原题"归一化 → 去重 → 融合排序（RRF）"说的就是这两种思路。

### 小问题：X 和 Y 谁高（k = 60）
- **X**：向量排第 1，BM25 没召回 → 1/61 = **0.0164**
- **Y**：向量排第 3，BM25 也排第 3 → 1/63 + 1/63 = **0.0317**（约为 X 的 2 倍）

**Y 更高**：BM25 没召回 X，这一路就是 0。→ **RRF 偏好"两路都认可"的文档**（共识优先）。

> **💬 课堂问答**
>
> **🙋 问**：k = 60，X 向量第 1、BM25 没召回；Y 两路都排第 3。谁的 RRF 分数更高？说明 RRF 偏好什么样的文档？
>
> **🧑 我的回答**：Y 更高，因为BM25没召回的话，这一路的分数就是0了。说明 RRF 偏好两路都认可的文档
>
> **🤖 点评**：✅ 完全正确。X = 0.0164，Y = 0.0317，约 2 倍。  
> ➕ k 决定"看重共识"还是"看重单路第一"：k = 0 时 X 反而赢（见下表）。

### k 的作用：调节"单路第一" vs "多路共识"

| k | X（单路第 1） | Y（两路第 3） | 谁赢 |
|---|---|---|---|
| 0 | 1/1 = 1.0 | 1/3 + 1/3 = 0.67 | **X** |
| 60（默认） | 1/61 = 0.0164 | 2/63 = 0.0317 | **Y** |

- k 小 → 名次差距被放大（第 1 名和第 3 名差很多）→ 偏向**单路排名靠前**。
- k 大 → 名次差距被拉平（1/61 和 1/63 差不多）→ 偏向**被多路召回**。
- k = 60 是论文在多个数据集上实验出来的稳妥值，一般不用调。

### 📌 要记住的
> **RRF = Σ 1/(k + 名次)**，只用名次、不用分数 → 天然解决量纲问题、无需调参。没召回记 0 → **偏好多路共识**。k（默认 60）越大越看重共识，越小越看重单路第一。

## 第 5 步 · 重排：Bi-Encoder vs Cross-Encoder，Top-K 漏斗

### 先问：重排的目的是什么？

> **❓ 我的追问**：重排的目的是什么？（当时直接讲了"怎么重排"，跳过了"为什么"）

🔁 回顾：
- **召回（Recall）** = 该找到的找到多少（别漏）；**精确（Precision）** = 找到的有多少对（别错、别乱排）。两者互相拉扯。
- **K 太大的三个代价**（mock-interview 第二轮）：① 噪声带偏模型 ② lost in the middle（长 context 中间信息被忽略）③ 又贵又慢。

矛盾：
```
召回阶段：想"别漏"   → 多取，比如 50 篇（正确答案多半在里面，但排第几不一定）
给 LLM 时：想"少而准" → 只能放 5 篇左右
```
**重排 = 连接两头**：对候选用更准但更慢的模型重新打分，把真正相关的挑到最前。**召回负责"找全"，重排负责"排准"。**

s5_01 的证据：B 套题 embedding **Hit@3 = 1.00**（全召回到了），但 **MRR = 0.722**（不总排第 1）。只取第 1 篇就会拿错 → 正是重排要解决的。
🔁 呼应 mock-interview Q4：**重排只能调整已召回到的**；正确文档没进候选，重排救不回，要改召回（换 embedding / 改 chunk / 加 BM25）。

### 📛 两种编码器
- **Encoder（编码器）**：把文本变成数字表示的模型（e5 就是）。
- **Bi-Encoder**（Bi = 两个，"双塔"）：query、文档**各自单独**编码成向量，再算余弦。你一直用的 e5 就是。
- **Cross-Encoder**（Cross = 交叉）：把 query 和文档**拼成一段**一起送进模型，直接输出**相关度分数**。例：bge-reranker、Cohere Rerank。

```
Bi-Encoder（e5）                         Cross-Encoder（如 bge-reranker）
query ──▶ [模型] ──▶ 向量 q ┐            "query [SEP] 文档" ──▶ [模型] ──▶ 0.93
doc   ──▶ [模型] ──▶ 向量 d ┘─ 余弦       （[SEP] 是分隔符，标出两段分界）
       各编码各的，互不相见                  拼在一起，每个词都能看到对方
```

🔁 **注意力**：模型处理一个词时会"看"其他词。Cross-Encoder 里 query 的词能直接注意到文档的词（"爸妈"看"退休"）→ **更准**；Bi-Encoder 各自压缩成一个向量，细节在压缩时丢了。

| | Bi-Encoder | Cross-Encoder |
|---|---|---|
| 输入 | 分开编码 | 拼一起 |
| 输出 | 两个向量 → 余弦 | 直接一个相关度分数 |
| 精度 | 中 | **高** |
| 速度 | **快** | 慢 |
| 用在哪 | **召回**（海量里找候选） | **重排**（少量候选精排） |

### 小问题：为什么不直接用 Cross-Encoder 给全部文档打分？
**文档向量可以提前算好**；Cross-Encoder 必须等 query 来了，**对每个 (query, 文档) 对现跑一次模型**，文档多了性能太差。

> **💬 课堂问答**
>
> **🙋 问**：Cross-Encoder 更准，为什么不直接用它给全部 100 万篇打分，非要先用 Bi-Encoder 召回？
>
> **🧑 我的回答**：文档向量可以提前算好，Cross-Encoder 要等 query 来了才能算，文档多的话，性能太差
>
> **🤖 点评**：✅ 对，关键就是"**能不能提前算**"。  
> ➕ 用数字感受差距：全库 Cross-Encoder 约 2.8 小时 vs Bi-Encoder 召回几十毫秒 vs 只重排 50 篇 ≤ 0.5 秒（见下表）。

量级感（粗略：小型 cross-encoder 在 CPU 上约 10ms / 对）：

| 方式 | 用户提问后要做的计算 | 耗时 |
|---|---|---|
| Cross-Encoder 打 100 万篇 | 100 万次模型推理 | 100 万 × 10ms ≈ **2.8 小时** |
| Bi-Encoder 召回 | 编码 query 1 次 + ANN 索引搜索 | **几十毫秒** |
| Cross-Encoder 只重排 50 篇候选 | 50 次推理（可批量） | **≤ 0.5 秒** |

🔁 **ANN**（Approximate Nearest Neighbor，近似最近邻）：chroma-primer 讲的 **HNSW** 索引，不用和每个向量都比，百万级也是毫秒返回。

### Top-K 漏斗

```
全库（百万）──Bi-Encoder + BM25 召回、RRF 融合──▶ 30~50 篇
            ──Cross-Encoder 重排────────────────▶ 10~20 篇
            ──取最前面────────────────────────▶ 5~10 篇给 LLM
```

这些数字是**经验起点，不是常数**。重排数量依据（面试原题）：
- **召回质量**：召回准（MRR 高）→ 可少取；召回不准 → 要多取给重排更大空间。
- **延迟预算**：重排篇数 × 单篇耗时 要塞进 P95（P95 = 95% 的请求都不超过的耗时）。
- **token 成本**：最终给 LLM 的篇数直接决定 token。
- **任务难度**：简单事实问答取少；需要综合多份资料的问题取多。
- 最终用 eval（Hit@K / MRR）在自己数据上定。

### 📌 要记住的
> **召回用 Bi-Encoder（快，文档向量可预算）找全；重排用 Cross-Encoder（准，query 与文档一起过模型）排准。** Cross-Encoder 每对都要现算，只能用在少量候选上。
> 漏斗经验值：召回 **30~50** → 重排 **10~20** → 给 LLM **5~10**，按召回质量、延迟、token、任务难度用 eval 调。
> 信号：**Hit@K 高、MRR 低 → 加重排；Hit@K 低 → 改召回。**

## 第 6 步 · Query 改写

用户原话**本身可能就不适合检索**。

### 小问题：多轮里的"那风险低一点的呢？"
```
用户：推荐个养老的基金
AI：  推荐「安心养老目标2040」……
用户：那风险低一点的呢？
```
直接拿第三句检索 → **丢了上下文**，不知道问的是养老基金。向量检索只能按"风险低"找（可能排出货币、纯债，偏离主题）；BM25 能匹配的字更少。

> **💬 课堂问答**
>
> **🙋 问**：多轮对话"推荐个养老的基金 → … → 那风险低一点的呢？"，直接拿第三句去检索会出什么问题？
>
> **🧑 我的回答**：丢了上下文，检索不知道问的是养老基金
>
> **🤖 点评**：✅ 对。向量只能按"风险低"找（会偏到货币、纯债），BM25 能对上的字更少 → 需要 query 改写。

### 四种改写

| 做法 | 做什么 | 例子 | 解决什么 |
|---|---|---|---|
| ① 补全成独立问题 | LLM 结合历史补全代词和省略 | "那风险低一点的呢？" → "风险较低的养老基金" | 多轮丢上下文 |
| ② 多 query 扩展（Multi-Query） | 生成几种说法，**各检索一次再 RRF 合并** | "给爸妈存养老钱" + "退休储备基金" + "长期养老理财产品" | 用户措辞 ≠ 文档措辞 |
| ③ HyDE | 先让 LLM 写一段**假想答案文档**，拿它去检索 | 生成"养老目标日期基金，适合长期持有……"再检索 | 问句短口语 vs 文档长书面 |
| ④ 拆分（Decomposition） | 复杂问题拆成子问题分别检索 | "养老基金和纯债哪个风险低" → 两个子查询 | 一问涉及多篇文档 |

📛 **HyDE = Hypothetical Document Embeddings**（假想文档嵌入）：**一种 query 改写**——把问句改写成一段"像文档的假想答案"，**用它代替 query 去检索**。依据是**文档与文档比问句与文档更像**。假想文档**不加进知识库**、用完就丢；内容可能是编的也没关系，只用来检索，不给用户看。

#### HyDE 到底起什么作用（7e 时追问）

> **❓ 我的追问**：HyDE 具体起到什么作用？它让模型根据用户输入假想一个答案，又不给用户看，那这个过程起到了什么作用？  

**一句话：假想文档不是答案，是一把更好的"搜索钥匙"。** 它把用户的口语问句，**翻译成和库里文档同一种"说话方式"**，再拿去检索。

**为什么需要翻译**：用户问句和产品说明是**两种文体**。
```
用户问句：我年轻能扛，想搏一个翻倍的机会
真实文档：股票型基金，重仓科技成长企业，波动大、回撤深，适合能承受大幅亏损、追求高收益的进取投资者。
```
两句**几乎没有共同的词**，长度、语气也不同：BM25 完全对不上；向量能靠语义勉强对上，但问句向量和文档向量**不在同一片区域**。
- 🔁 e5 要求查询加 `query:`、文档加 `passage:` 前缀，正是因为**问句和文档天生长得不一样**。前缀是在**模型那一侧**弥补这个差距，HyDE 是在**输入这一侧**弥补。

**HyDE 怎么翻译**：LLM 读懂"搏翻倍、年轻能扛"后，写出类似
```
本基金为股票型基金，投资高成长行业，净值波动较大，适合风险承受能力强、追求高收益的进取型投资者。
```
- 它用了**真实文档里会出现的词**：股票型、波动、进取型投资者 → BM25 也能对上了；
- 文体、长度都像产品说明 → 向量落到了"股票类产品说明"那片区域。
- 本质：借用 **LLM 的世界知识**，把"用户怎么说"转换成"文档怎么写"。

**为什么编错了也没关系**：假想文档只负责"把检索带到对的区域"。哪怕它编的收益率是错的、甚至产品类型写偏了一点，**最终给用户的答案来自检索到的真实文档**：
```
用户问句 ─▶ LLM 写假想文档 ─▶ 编码 ─▶ 向量检索 ─▶ 真实文档 top-K
                                                   │
        原问题 + 真实文档 ─▶ LLM 生成回答 ◀────────┘     （假想文档到此丢弃）
```

**代价和风险**：多一次 LLM 调用（延迟、成本）；LLM 若**理解错意图**，会把检索带到错的区域 → 所以要**原 query 一起检索、RRF 合并**（第 6 步的防法）。

> **💬 课堂问答**
>
> **🙋 问**（我的追问）：所以 HyDE 其实也是一种 query 重写的方式吧？我一开始看讲义，以为它是新增了一个假想的文档  
>
> **🧑 我的理解**：HyDE 是 query 改写的一种；一开始误以为是往库里新增文档  
>
> **🤖 点评**：✅ 对，它就是四种改写里的第 ③ 种。  
> ⚠️ 误解来自名字里的 "Document"：假想文档**不进库**（库里还是那 7 个产品），而是**代替 query 去检索**，用完就丢。  
> ➕ 和"补全成独立问题"的区别只在改写后的形状：补全后仍是问句，HyDE 改写成"答案的形状"。

| | 误解 | 实际 |
|---|---|---|
| 假想文档放在哪 | 新增进知识库 | **不进库** |
| 扮演什么角色 | 被检索的对象 | **代替 query 去检索** |
| 用完之后 | 留在库里 | **丢掉** |

> 📌 **HyDE 的作用 = 把问句翻译成"文档的样子"再检索**（用词、文体、长度都向文档靠拢），弥补"问句 vs 文档"的文体差距。假想文档只当检索钥匙，内容对错不重要，答案仍来自真实文档。

🔁 **你已经用过 ①**：FinWise chat_service 是 agent loop，`search_products` 的参数是模型**看完整个对话历史后自己填的** → concepts-basics「检索即工具（Agentic RAG）」天然带了 query 改写。

代价：**多一次 LLM 调用**（延迟 + 成本）；**语义漂移**（改掉原意）。

### 小问题：改写丢了精确词
"**P-TECH** 还能买吗？" → 改写成 "科技类股票基金现在是否适合购买？"
- 丢了：**P-TECH 代码** → **BM25 匹配不上**（第 2 步：精确代码正是 BM25 的强项）。
> **💬 课堂问答**
>
> **🙋 问**："P-TECH 还能买吗？"被改写成"科技类股票基金现在是否适合购买？"，丢了什么？后果？怎么防？
>
> **🧑 我的回答**：丢了 P-TECH 代码，BM25 匹配不上；保留原 query 一起检索,就是用多query扩展
>
> **🤖 点评**：✅ 两点都对：丢代码 → BM25 失效；最稳的防法就是原 query 也一起检索、RRF 合并。  
> ➕ 再加几道防线：代码硬校验（正则抽代码，改写后不在就退回原 query）、prompt 要求原样保留、相似度检查（阈值要自己定）、该跳过就跳过（见下表）。

- 防法：

| 防法 | 说明 |
|---|---|
| **保留原 query 一起检索** | 原 query + 改写 query 各召回、RRF 合并（就是 ② 多 query 扩展）。最简单可靠 |
| prompt 要求原样保留 | "代码、编号、数字、产品名必须原样保留"——软约束 |
| **代码硬校验** | 用正则从原 query 抽出代码/数字，检查改写后还在不在，不在就退回原 query。🔁 B#7「别信模型、关键值硬校验」 |
| 相似度检查 | 原句与改写句的余弦低于阈值就弃用。面试原题说"≥ 0.8"，但 🔁 e5 分数挤在 0.7~0.95，**阈值要用自己的模型和 eval 定，不是常数** |
| 该跳过就跳过 | query 已经完整、或就是一个精确代码 → 不改写，省一次 LLM 调用 |

### 追问："原 query 一起检索"= 2 个 query × 2 个检索器 = 4 次查询？

> **❓ 我的追问**：之前提到的"② 双路召回：向量（ANN）+ BM25"，准确来说是指让 2 个检索器针对原始 query 和改写后的 query 各做一次，所以一共是 4 次查询是吗？

**是的，完整做法就是 4 路**，RRF 对任意多路都适用：
```
原 query   ─┬─ 向量 ─▶ 列表 1 ┐
            └─ BM25 ─▶ 列表 2 │
改写 query ─┬─ 向量 ─▶ 列表 3 ├─▶ RRF（4 个列表）─▶ 重排
            └─ BM25 ─▶ 列表 4 ┘
```
- 多 query 扩展生成 n 个改写时：(n + 1) 个 query × 2 个检索器 = 2(n + 1) 路。
- **成本不在这里**：每次检索是毫秒级、可**并行**；向量那路每个 query 多编码一次（也是毫秒级）。贵的是**改写那一次 LLM 调用**，只调一次。
- 4 路下，一篇文档被"两种说法 × 两种检索"都找到，会拿到 4 份 RRF 分 → **共识效应更强**。
- 变体：**不对称**（BM25 用原 query 保精确词、向量用改写 query 补语义）只有 2 路，更省；但多轮场景下原 query"那风险低一点的呢"对 BM25 没用，所以不是通用解。也可以**加权 RRF**（给某一路乘个权重，如多轮时降低原 query 的权重）。
- 先用完整 4 路 + 普通 RRF，有 eval 证据再精简或加权。

### 📌 要记住的
> 改写四招：**补全（多轮）、多 query 扩展、HyDE（假答案去检索）、拆分**。agent 调检索工具时自己填参数 = 天然改写。
> 风险：**语义漂移、丢精确词**。最稳的防法是**原 query 也一起检索、RRF 合并**；再加代码硬校验。

## 第 7 步 · 动手：s4_06 混合检索 + RRF + 重排

- 脚本：`backend/scratch/s4_06_hybrid_rerank.py`（复用 s4_01 产品库、s4_03 切词、s5_01 指标）
- 测试：`backend/scratch/test_s4_06_hybrid_rerank.py`（12 个，数字取自本讲义的手算例子）
- 4 种检索器（纯向量 / 纯 BM25 / 混合 RRF / 混合 + 重排）× 3 套题（A 字面近、B 口语、**C 精确匹配**）
- 检索文本 = 产品名 + 描述（C 套题的"2040""30天"只在产品名里），所以纯向量的分数和 s5_01 略有不同
- 预期：库只有 7 篇，重排提升可能不明显——"数据规模小，重排价值有限"本身也是结论

### 7a · `bm25_term_score` ✅

```python
return idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * doc_len / avgdl))
```

- 易错点：`k1 *` 要乘整个长度惩罚因子 `(1 - b + b * doc_len / avgdl)`，不是只乘 `1 - b`。
- 6 个测试对应：A ≈ 1.58 / B ≈ 0.21（长度归一化）、tf 再大封顶 2.2（饱和）、tf = 0 得 0、IDF 线性放大、精确数字只召回一篇。

真实产品库上的表现（avgdl = 39.4 个 bigram）：
```
"2040那只还能买吗" → 只有 P-PENSION 4.89，命中 20 / 04 / 40（全库独有 → IDF 高）
"给爸妈存养老钱"    → 只有 P-PENSION 2.26，命中"养老"（碰巧有字面重合）
```
换成"想给爸妈存钱，放十年八年的"，一个 bigram 都对不上 → BM25 返回空 → 这正是 embedding 的强项，所以要混合。

### 7b · `rrf_fuse` ✅

```python
scores: dict[int, float] = {}
for ranking in rankings:
    for rank, doc in enumerate(ranking, start=1):
        scores[doc] = scores.get(doc, 0) + 1 / (k + rank)
return sorted(scores, key=lambda d: scores[d], reverse=True)
```

- `enumerate(..., start=1)`：名次从 1 开始，对应公式里的 rank。
- `scores.get(doc, 0)`：第一次见到这篇文档时从 0 开始累加；某一路没出现的文档，那一路自然不加分（= 公式里"记 0"）。
- `sorted(scores, ...)`：对 dict 排序时遍历的是 **key**（文档下标），所以直接返回下标列表。
- **并列时谁在前？** Python 的 `sorted` 是**稳定排序**（分数相同时保持原有顺序），dict 又按**插入顺序**遍历 → 并列时**先出现的那一路**（这里是向量那一路）的文档排前面。也就是说并列时，`rankings` 里各路的**先后顺序**会影响结果。
- 4 个测试对应：两路共识胜过单路第一（X / Y）、k = 0 时反过来、合并后不重复、某一路为空时退化成另一路。

### 7c · `rerank` ✅

```python
pairs = [(query, texts[c]) for c in candidates]
scores = model.predict(pairs)
return [c for c, _ in sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)]
```

- **拼 pairs → 一次 predict 批量打分 → zip 配对 → 按分数降序 → 只返回下标。**
- 一次批量 predict（不是每篇调一次）：模型可以并行算一批，这正是"重排 50 篇也只要零点几秒"的原因。测试专门检查只调用一次。
- `zip(candidates, scores)`：把两个等长列表逐个配成 `(下标, 分数)` 对。

#### ⚠️ 生产注意：为什么不该传全库 `texts`（用户追问）

> **❓ 我的追问**：为什么要传"texts"所有的文档的文本？这样不会很大吗？100 万个文本的话

> 决定：练习接口先不改，但在 `rerank` 的 docstring 里写明"⚠️ 练习简化，不是生产设计"。

- **传参本身不贵**：Python 传的是引用（地址），不复制列表；函数里也只用 `texts[i]` 取候选那几篇。
- **问题在前提**：要能传 texts，就得先把**全库文本整体加载进内存**——百万级不可行。
- **生产做法：重排只需要候选的文本，按 ID 取**：
  ```
  召回 → 候选 ID + 文本 → 重排
          ├─ 方式一：召回时一起返回文本（🔁 chroma-primer：query(..., include=["documents"])）
          └─ 方式二：只拿 ID，再去数据库 / KV 批量取（SELECT text FROM chunks WHERE id IN (...)）
  ```
  接口相应地直接收候选文本：`rerank(query, candidates: list[tuple[doc_id, text]], model)`。
- 练习里保留"下标 + 全库列表"只因库仅 7 篇、本就在内存，且能和 rrf_fuse 的下标直接接上。代码注释里也标明了这是练习简化。

> 📌 重排只需要**候选**的文本：要么**召回时一起返回**，要么**按 ID 批量取**，不把全库加载进内存。

> **🙋 问**：假想文档该用 `encode_docs`（passage:）还是 `encode_query`（query:）编码？  
>
> **🧑 我的回答**：用query前缀，因为前面讨论过了，这本质上就是query重写  
>
> **🤖 点评**：⚠️ 应该用 **`encode_docs`（passage:）**。从**角色**看它确实是 query，但要看的是"希望它的向量落在哪"：库里文档都按 passage 编码，同前缀才是"文档对文档"；用 query: 会把 HyDE 要消除的"问句 vs 文档"差异加回来。  
> ➕ 前缀表示"**这段文字长什么样**"，不是"它在流程里扮演什么角色"。e5 官方也说对称比较可两边都用 query:，所以严格说是可以实验的问题。

> **❓ 我的追问**：刚才不是确认过 HyDE 是改写 query、假想文档不进库吗？  
> → "角色"和"编码方式"是两个独立问题：**角色是 query**（不进库、用完就丢），**编码方式按文档**（passage: 前缀）——"用文档的编码方式，编码一个 query"。`encode_docs` 只做"加前缀 + 算向量 + 返回"，**不存任何东西**；"进库"是赋给 `doc_vecs` / Chroma `upsert`。函数名更准确应叫 `encode_as_passage`。

> **❓ 我的追问**：我之前理解 passage 前缀 = 被检索的数据、query 前缀 = 查询语句；所以一条 passage 前缀的文本，也可以和已有的 passage 向量做匹配？  
> → **可以**。向量就是向量，同一个模型的任意两个向量都能算余弦；前缀只影响"怎么编码"，不限制"能和谁比"。"找相似产品"就是 passage 对 passage。
> 小实验：P-BOND 和其他 6 篇（都按 passage）的余弦全挤在 0.92~0.96，且股票基金（0.945）排在短债（0.938）前面——7 条说明**写法几乎一样**（"××基金，……，适合……投资者"），文档对文档时**文体相似占比很大**。这正是 HyDE 有效的原因（先拿到文体这一块），最终排对还要靠内容用词。

> **🙋 问**："胆子小，本金一分都不能少"——假想文档把类型写成了"货币市场型基金"（应是纯债），为什么还能把 P-BOND 排第 1？  
>
> **🧑 我的回答**：风险低、本金安全、保守型投资者这些描述和 P-BOND 一样  
>
> **🤖 点评**：✅ 对。"波动很小 / 波动很小""本金安全 / 本金损失""保守型投资者 / 保守投资者"几乎一字不差；而 P-MMF 讲的是"活钱、应急备用金"。  
> ➕ 决定成败的是**整段描述的用词整体上靠近哪篇**，不是某一个词对不对——"编错了也没关系"是指编错一部分，整体偏了就会带错路。

> **💬 课堂问答**
>
> **🙋 问**：开课前我用另一版 prompt 跑过，② 是 1.00 / 0.917；你这次是 0.83 / 0.722。现在能下"HyDE 有没有用"的结论吗？怎么下？  
>
> **🧑 我的回答**：不能，噪声这层：LLM 每次生成都不同，要多跑几次取平均  
>
> **🤖 点评**：✅ 对，这是 L01 前面没有、这次新出现的一层：**LLM 生成有随机性**。  
> ⚠️ 还有一个问题：两次运行**同时变了两个东西**（prompt 和随机生成），分不清差异来自哪个。要**一次只变一个**：固定 prompt，跑 N 次（如 5~10 次），看平均值和波动范围。  
> ➕ 样本量（6 题）和题的问题依然在。bridge 会忽略 temperature；而且即使 temperature = 0，LLM 也不保证完全确定。  
> ➕ 两次运行里 **④ RRF 4 路都是满分** → 相对稳的信号：**单用 HyDE 不稳，和原 query 一起融合更稳**（样本仍小，只能算方向）。

> 📌 **7e 结论**：HyDE 是一次**押注**——LLM 写的描述和正确文档用词重合就有帮助，整体写偏就带错路；单用不稳。**和原 query 一起做 RRF** 才稳。评估含 LLM 生成的环节，要**固定其他变量、多跑几次看平均和波动**。

## 第 8 步 · 穿插复习题

### Q27 · 余弦 / 点积 / 欧氏距离 / L2 归一化 ✅

> 原题：两个 embedding 已做 L2 归一化，点积、余弦、欧氏距离三者什么关系？Chroma 用 `l2` 和 `cosine` 时 top-K 一样吗？

🔁 回顾：**点积** a·b = 逐位相乘再相加；**模长** ‖a‖ = √(a·a)；**余弦** cos = a·b / (‖a‖ × ‖b‖)，只看方向。

📛 **L2 范数** = 模长（欧几里得长度，先平方再开方，故名 L2；L1 是各分量绝对值之和）。**L2 归一化** = 向量除以自己的模长 → 长度变 1、方向不变。例：(3,4) ÷ 5 = (0.6, 0.8)。
📛 **欧氏距离**（Euclidean distance）= 两点直线距离 = ‖a − b‖。

**三小步推导**（‖a‖ = ‖b‖ = 1）：

| 步 | 推导 | 结论 |
|---|---|---|
| ① 余弦 | cos = a·b / (1 × 1) | **cos = a·b**（所以很多库归一化后直接用点积，省两次模长和一次除法） |
| ② 欧氏距离 | ‖a−b‖² = (a−b)·(a−b) = a·a − 2(a·b) + b·b = 1 − 2cos + 1 | **‖a−b‖² = 2 − 2cos** |
| ③ 排名 | cos 越大 → 距离越小，单调关系 | **三者排名完全一致** |

> **💬 课堂问答（三小步）**
>
> **🙋 问 ①**：‖a‖ = ‖b‖ = 1 时，cos = a·b / (‖a‖ × ‖b‖) 变成什么？  
> **🧑 我的回答**：余弦等于点积，cos = a·b  
> **🤖 点评**：✅ 对。➕ 所以很多库归一化后直接用点积，省计算。
>
> **🙋 问 ②**：把 (a−b)·(a−b) = a·a − 2(a·b) + b·b 继续算下去，‖a − b‖² 等于什么？  
> **🧑 我的回答**：‖a − b‖² = 2 − 2cos(a,b)  
> **🤖 点评**：✅ 完全正确。
>
> **🙋 问 ③**：向量已归一化时，Chroma 用 `l2` 和 `cosine`，top-K 一样吗？  
> **🧑 我的回答**：一样，cos 越大距离越小，排名顺序不变  
> **🤖 点评**：✅ 对。➕ 更具体：`l2` 距离正好是 `cosine` 距离的 2 倍。⚠️ 前提是归一化——核对时发现 e5 自带归一化层，顺带更正了 chroma-primer 里"会翻车"的说法。

**Chroma**：`l2` 返回 ‖a−b‖²、`cosine` 返回 1 − cos → `l2 = 2 × (1 − cos) = 2 × cosine 距离`，每个文档都乘同一个 2 → **top-K 一样**。**前提是归一化**；没归一化时 l2 把长度差异也算进去，可能不同。

**实测发现**：s4_01 写的是 `normalize_embeddings=False`，但 e5 输出的 7 个向量模长全是 1.0000——e5 **自带归一化层**（`modules.json` 第 3 层 `Normalize`）。所以本项目里 `l2` 和 `cosine` 排名一致；chroma-primer 里"不设 cosine 会翻车"说重了，已更正。仍建议显式设 `cosine`（换模型也安全、距离 0~2 直观）。

> 📌 归一化后：**cos = 点积**，**欧氏距离² = 2 − 2cos**，排名完全一致；Chroma `l2` = 2 × `cosine` 距离。前提是归一化——要知道自己的模型输出是否已归一化（e5 自带）。

### Q31 · RAG"答非所问"怎么逐层排查 ✅

> 原题：FinWise 产品问答 RAG 上线后用户反馈"答非所问"。给一套逐层隔离的排查步骤：每一步固定什么、换掉什么、看哪个指标。

**核心思路：固定一层、只换一层；从下游往上游，每一刀把范围砍半。**

#### 第 1 小步：先画管线
```
【离线】 原始文档 → ⓪ 切 chunk → encode 存向量库 / 建 BM25 倒排索引
【在线】 用户提问
          → ① query 改写（原 query 保留，两路之前统一做）
          → ② 双路召回：向量（ANN）+ BM25，各取 30~50 篇（原 query + 改写 query 各查一次 → 共 4 个列表）
          → ③ RRF 融合（之后可能截断，如取前 20 送重排）
          → ④ Cross-Encoder 重排，取 top-K（5~10 篇）
          → ⑤ prompt 组装（system 指令 + 检索片段 + 用户问题）
          → ⑥ LLM 生成
```
> **💬 课堂问答**
>
> **🙋 问**：从用户提问到 LLM 回答，一次 RAG 请求依次经过哪几个环节？
>
> **🧑 我的回答**：
> ```
> 用户提问 -
>   向量（余弦相似度）检索器：
>     query -> query改写 -> encode -> 改写后的query向量 -> 和每个文档的向量做余弦相似度 -> 按分数降序
>   BM25检索器：
>     query -> 和每个文档算BM25分数 -> 按分数降序
>   RRF:
>     针对每个任一路检索器召回的文档 -> 计算这个文档的RFF -> 文档按照分数降序排列
>   重排：
>     query -> RRF返回的所有文档 -> 做一次批量cross encoder打分 -> 按分数降序 -> 取top-K
> ```
>
> **🤖 点评**：✅ 检索四段拆得很细，"重排一次批量打分"也记住了。  
> ⚠️ 缺了**离线入库**（切 chunk、建索引）和最后的 **prompt 组装 + LLM 生成**。  
> ⚠️ query 改写应在**两路之前**统一做（并保留原 query），否则 BM25 那路仍丢上下文。  
> ➕ 生产里不会"和每个文档算余弦"，而是 ANN 索引（HNSW）。

易漏：**离线那段**（chunk 是最常见的问题来源）；**⑤⑥**（"答非所问"生成端也可能出错）；**改写要在两路之前**，否则 BM25 那路仍丢上下文。

#### 第 2 小步 · 第一刀：检索 or 生成？
- **看日志 / trace 里实际拼进 prompt 的检索结果**（🔁 lg_06 LangSmith、FinWise 的 `tool_result`）。
- ❌ 别让模型复述它拿到的资料：① 复述可能改写、漏掉、编造（🔁 别信模型）；② 改了 prompt 就改了被测系统。
> **💬 课堂问答**
>
> **🙋 问**：怎么用一个简单的检查，判断"答非所问"是检索的锅还是生成的锅？
>
> **🧑 我的回答**：在原始的promt后面，追加一句，让模型输出它拿到的数据 - 也就是RAG的输出结果，这样可以判断是数据额不对（检索问题），还是模型问题（生成）
>
> **🤖 点评**：✅ 方向对：先看 LLM 拿到的检索结果。  
> ⚠️ 但别让模型复述：① 复述可能改写、漏掉、编造（别信模型）；② 改 prompt 就改了被测系统。  
> ➕ 直接看**日志 / trace** 里实际拼进 prompt 的资料——数据本来就在你自己的程序里。

- 正确 chunk **在** → 生成问题：**固定检索结果**（把记录的 prompt 原样重放），只换 prompt 写法 / 模型。
- 正确 chunk **不在** → 检索问题，往上游查。

#### 第 3 小步 · 第二刀：召回没找到 or 被重排挤掉？
- 日志**分层记录**：向量 top-50 / BM25 top-50 → RRF 融合（截断前后）→ 重排后 top-5。
- **正确 chunk 最后出现在哪一层，问题就在下一层。**
- RRF 本身不丢文档（取并集），但**融合后的截断**可能切掉只被一路召回、排得靠后的文档。
> **💬 课堂问答**
>
> **🙋 问**：正确 chunk 不在最终 top-5 里。怎么判断是"召回根本没找到"，还是"召回找到了、被重排挤出 top-5"？
>
> **🧑 我的回答**：通过日志看召回阶段（RRF，重排前）的候选里有没有正确的 chunk，如果没有，那就是原始召回的问题，如果有，那应该就是最后重排的时候被踢出了top-5(RRF应该不会有问题)
>
> **🤖 点评**：✅ 对，看重排前的候选。  
> ⚠️ "RRF 应该不会有问题"要加前提：RRF 本身不丢文档，但很多系统在 RRF 之后会**截断**（如取前 20 送重排），只被一路召回、排得靠后的文档可能被切掉 → 日志要分层记录。

- 批量判断（是否系统性问题）：golden set 算 **候选 Hit@50 vs 最终 Hit@5**。差得多 → 重排在丢；Hit@50 本身低 → 召回问题。

#### 第 4 小步 · 第三刀：是不是 chunk 切坏了？
**直接读包含答案的 chunk 原文**（不用跑模型），看它是否**完整、能自己读懂**：

| 问题 | 原文的样子 | 类型 |
|---|---|---|
| 截断 | "最短持有"在上一块末尾、"30 天"在下一块开头 | 碎 |
| 丢主语 | "**该产品**最短持有 30 天"，产品名被切走 | 碎 |
| 太大 | 一块塞五六个产品，向量被"平均"稀释 | 糊 |
| 结构丢失 | 表格只剩数字，表头在别的块 | 碎 |

> **💬 课堂问答**
>
> **🙋 问**：怎么检查是不是 chunk 切分的问题？（提示：不用跑模型，直接看一样东西）
>
> **🧑 我的回答**：直接看那个 chunk 的原文，看有没有句子或者单词在语义上被截断了
>
> **🤖 点评**：✅ 对，直接读原文。  
> ➕ 不止截断：还要看**丢主语**（"该产品…"产品名被切走）、**太大被稀释**、**表格丢表头**（见上表）。标准是"答案在 chunk 里是否完整、能自己读懂"。

🔁 chunk **太大 = 糊、太小 = 碎**（症状相反，别说反）。修法：按标题 / 语义切、加 overlap、给 chunk 补标题和产品名前缀、表格保留表头、跨页表先合并再切（L 课 N9 细讲）。

#### 第 5 小步 · 第四刀：query 不好 or embedding 不行？
**手动造一个"理想 query"**（固定 chunk 和模型，只换 query）：
- 例：用户说"希望 70 岁以后还能有收益"（没有"养老"字眼）→ 手动改成"养老目标基金"，甚至直接**照抄 chunk 里的措辞**（最强的测试）。
- **理想 query 能找到** → **query 问题** → 修 query 改写（第 6 步：补全 / 多 query / HyDE）。
- **理想 query 也找不到** → 先排除两个"非模型"原因，再怪 embedding：
  - **chunk 根本不在索引里**（增量入库失败、被删）——拿 chunk id 直接查库；
  - **元数据过滤把它挡掉了**（风险等级、权限过滤条件错了）——去掉 where 条件再搜一次。
  - 都排除了 → **embedding 问题**：换模型在 golden set 上比 Recall@20 / Hit@K；领域词多可考虑微调；或靠 BM25 那一路兜底。

> **💬 课堂问答**
>
> **🙋 问**：chunk 没问题但召回找不到，是 query 不好还是 embedding 不行？（提示：固定一层只换一层，手动造一个"理想 query"）
>
> **🧑 我的回答**：先手动造一个语义上绝对能匹配的查询，比如用户的意图是查询"养老"类产品，但查询文字里压根没"养老"这样的字眼，只是很模糊的一些描述，比如说希望"70岁以后还能有收益"，这时候我们主动构造一个带"养老"字眼的查询，如果找到了，那就是query问题（或者是query改写问题），反之，则是embedding问题
>
> **🤖 点评**：✅ 思路完全正确：固定 chunk 和模型，只换 query。  
> ➕ 理想 query 可以更狠：**直接照抄 chunk 原话**。  
> ⚠️ 照抄也找不到时先别怪 embedding：先查 chunk **在不在索引里**、有没有被**元数据过滤**挡掉。

#### 完整答案骨架（面试用）
```
① 看 trace 里拼进 prompt 的资料  → 在：生成问题（固定检索结果，换 prompt / 模型）
                                  → 不在 ↓
② 看漏斗每层候选                 → 候选有、top-5 没有：重排 / 截断问题
                                  → 候选也没有 ↓
③ 读 chunk 原文                  → 截断 / 丢主语 / 太大 / 表格：chunk 问题
                                  → chunk 完好 ↓
④ 手造理想 query                 → 能找到：query / 改写问题
                                  → 找不到：查索引、查过滤 → 都没问题才是 embedding
批量版：golden set + 分层指标（候选 Hit@50、最终 Hit@5、MRR）判断是不是系统性问题
```

> ⚠️ 面试原题答案里"60% 是 chunk、20% recall、10% rerank、10% prompt"是编出来的比例，别报数字。说"经验上 chunk 和召回问题最常见，所以先看检索侧"即可。
