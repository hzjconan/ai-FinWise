补充：原始图像帧 → 视频编码器生成压缩视频流 → 封装器将视频流、可选音频流及时间 / 索引等组织为容器文件。播放 / 训练读取时先解封装取得对应编码数据及时间信息，再解码为像素。H.264 / H.265 是编码标准，MP4 / MKV / MOV 等为容器格式；容器有支持与兼容性约束，并非任意组合都能在任意播放器运行。无声视频也可使用 MP4，音频不是必需。

重新封装（remux）在目标容器支持时复制已有编码数据，通常无需解码重编码，不自动提升压缩率；重编码需解码并再次编码，可保持同编码标准而改变参数，也可换编码标准，消耗计算且有损处理可能改变质量。单纯修改文件后缀既不重封装也不重编码。当前是概念讲解，未执行视频转换。确认有无问题后继续工具准备。

### 3B：相对无损源的 PSNR（已实测）

运行前说明 PSNR 是对应像素误差的对数表达，在同一参考与相同条件下通常越高表示像素误差越小；单位 dB，不是百分数，不是模型成功率。读取本机 `-h filter=psnr` 确认参数，随后对 crf18 / crf28 分别与 source.mkv 比较。

两路都是 640×360、yuv420p、240 帧。因本实验预先验证为相同 30 fps 连续帧，统一 settb=AVTB 并 setpts=N/(30*TB)，按相同帧序列构造比较时间戳，防止 MKV / MP4 时间基准差影响配对。这不是对真实视频任意覆盖原时间戳的通用方案；实际素材需核验同步与帧对应。psnr 配置 shortest=1:repeatlast=0，不延长末帧来补缺失。

示例完整命令（把 crf18 替换为 crf28 即另一个对照）：

```bash
"$VIDEO_FFMPEG" -hide_banner -nostdin \
  -i backend/scratch/robot-video-lab/crf18.mp4 \
  -i backend/scratch/robot-video-lab/source.mkv \
  -filter_complex '[0:v]settb=AVTB,setpts=N/(30*TB)[dist];[1:v]settb=AVTB,setpts=N/(30*TB)[ref];[dist][ref]psnr=shortest=1:repeatlast=0[out]' \
  -map '[out]' -progress pipe:1 -nostats -f null -
```

滤镜的两路分别是待比较视频与参考；map 选比较结果；null 输出不生成媒体文件。脚本式临时调用检查子进程成功、progress=end、实际输出 240 帧，取 FFmpeg PSNR 汇总的 average 字段。该字段为滤镜按误差汇总得到的值，不声称是逐帧 dB 的简单算术均值。

| 输出 | 文件大小（MB） | 相对 source 的汇总 PSNR（dB） |
|---|---:|---:|
| CRF 18 | 1.166283 | 49.118780 |
| CRF 28 | 0.423107 | 39.337538 |

本素材上 CRF 18 更接近无损源的像素，CRF 28 更小但像素误差更大。不能将约 10 dB 差解释为模型成功率相差 10%，也不能从平均指标推定所有局部 / 短暂事件都保留完好。无机器人训练评估，不确定哪个达到真实任务质量底线。未新增 Python 模块或运行新 pytest。

参考：[FFmpeg PSNR 滤镜](https://ffmpeg.org/ffmpeg-filters.html#psnr)。

### 3F：编码链路与完整解码的墙钟时间（已实测）

运行前说明用 time.perf_counter 包住 FFmpeg 子进程，先预热一次、再记录 3 次并取中位数；编码写 TemporaryDirectory 的独立输出，不覆盖已有媒体，结束自动清理。每次先编码再解码，四种设置顺序固定，没有随机化，也没有声称测 CPU 利用率或纯编码器算子时间。

本次编码输入都是 source.mkv，解码线程在输入前固定 threads=1，编码线程在输出前固定 threads=1，filter_threads=1；输出 libx264 / medium / yuv420p / 无音频，CRF 和滤镜按前述各条件配置。解码计时则读取对应已生成 MP4、threads=1，完整输出 null，并检查每次 progress=end、out_time_us=8000000、帧数 240 或 120。两组计时边界不同，编码包括读 / 解码无损源、可选滤镜、编码和写容器；解码包括读 MP4、解码、null 输出和 progress 文本收集。都含启动与调度开销，文件可能命中系统缓存，无磁盘落盘同步保证。

| 设置 | 编码链路 3 次（ms） | 编码中位数（ms） | 解码 3 次（ms） | 解码中位数（ms） |
|---|---|---:|---|---:|
| 640×360 / 30fps / CRF18 | 1105.97,1094.15,1094.58 | 1094.58 | 140.87,142.55,143.82 | 142.55 |
| 640×360 / 30fps / CRF28 | 915.53,900.21,907.23 | 907.23 | 93.30,93.88,92.92 | 93.30 |
| 320×180 / 30fps / CRF18 | 375.88,378.90,373.41 | 375.88 | 47.45,47.16,47.15 | 47.16 |
| 640×360 / 15fps / CRF18 | 665.35,656.39,685.54 | 665.35 | 94.04,93.35,97.85 | 94.04 |

本机这段短素材上缩小空间 / 时间采样以及提高 CRF 均有不同耗时结果，不是编码标准或任意内容的通用加速比。固定 preset，不涉及 H.264 与 H.265 速度比较。fps 滤镜在此链路位于源解码之后，所以输出 120 帧不意味着只解码了源的 120 帧；也不能把计时变化简单当纯编码工作量等比变化。真实机器人端若额外解码重编码，会增加端侧计算，需要与上传 / 存储收益共同核算。

## 第 4 步 · 端侧过滤

### 4A：平均变化小不代表没有关键事件

先明确按完整片段 / episode 等单位筛选，保留选中单位内部时序、动作对应与上下文；不要直接删掉变化小的单帧后继续按旧索引训练。低变化分数可提供候选筛选信号，不能直接等同“无效数据”。

实测小例子（仅 NumPy 图像，不是假装真实视频实验）：两张 100×100 RGB uint8 图像，第一张全黑，第二张只有 2×2 区域变白。用 float32 相减取绝对值再平均，避免 uint8 无符号减法溢出。变化仅 4 像素 / 10000 像素；全图平均绝对变化为 4×255÷10000=0.102（按 0～255 尺度），NumPy 实测约 0.101999998。若阈值设 1，判为低变化。这里阈值仅教学设定，不是生产推荐。

即使这个区域对应重要信号，算法也不会知道其业务意义。玩具例子不表示任意 2×2 变化都可用于实际识别，只用于展示全局平均可掩盖局部变化。实际还须考虑光照 / 相机抖动假变化、静止目标的价值、外部任务事件信号及失败 / 长尾保留规则。后续构建可复现视频片段与真实编码 / 解码过滤对照，并给新代码配测试。
