### 本题后续采用的教学假设

用户确认需求澄清点评无疑问。下列为面试场景补充假设，不是实际公司的既有事实：

- 目标为基于示范的机器人动作策略训练，采集视频以及时间对齐的动作、本体状态和任务指令；有数据质量检查与固定质量评估标准，不能仅凭训练 loss 批准部署。

- 按每日采集批次的截止点计，该批次应在随后 8 小时内上传完整；数据就绪后训练应在 10 小时内完成。时间窗口不自动等同全天采集时长，实际调度可有重叠，评估发布另计且须通过质量门槛。

### 第二问回答与点评

用户方案：采集 → 数据清理 → 上传 / 存储 → 训练 → 部署端侧 → 评估，失败样本回流。端侧采集视频与传感器数据，压缩、过滤、时间对齐后上传私有云，GPU 训练并部署，再评估真机效果。

端侧可轻量筛选、记录统一时间信息并校验基本完整性；云端补充校验 / 对齐检查、切 episode / 样本、生成可追溯且不可变的数据集版本及训练 / 验证划分。准确时间对齐依赖采集时间戳与同步，不保证事后清理总能修复；模型输入要求和质量约束下再决定重编码，不默认所有视频都需再次压缩。原始与清理 / 派生数据分别记录，不能将变更后的派生数据无条件当作原始记录。

产物关联：采集记录含 robot / episode / 时间 / 当时模型版本；数据集版本引用选定片段、对齐标注与处理版本；训练记录关联数据集版本、代码 / 配置和 checkpoint，产出候选模型版本；发布记录关联评估结果、模型版本与目标机器人。失败样本与上下文、当时运行模型版本回流到数据接入 / 筛选流程，参与新数据集与再训练，而非仅“重新采集”或自动立即上线训练。

### 第三问：不稳定网络下的上传与数据就绪

用户确认主链路点评无疑问，展开上传部分。场景假设：机器人网络会断开；一个 episode 包含多个相机视频文件，以及动作 / 状态和时间信息文件。上传中断后需继续，客户端也可能超时重试。训练端只能消费已完整上传并通过约定校验的 episode，不能把单个视频上传成功当作整个 episode 就绪。

请说明上传设计如何处理三件事：中断后避免大文件从头重传；超时重试避免逻辑重复；确认同一 episode 所需文件完整后再发布为训练可用数据。先听用户方案，再根据回答讲解分块续传、幂等标识、清单 / 校验与完成状态等概念；不提前给出完整实现，不要求编写代码。

### 第三问回答与点评

用户回答：支持断点续传；上传前查文件 hash，服务端已存在则不上传；服务端校验整套 episode，合格才进入下一步。

点评：总体方向正确。断点续传可按分块 / multipart 管理 upload session、已成功分块与完成合并，客户端保留进度，重连查询服务端确认后仅补未完成部分；进程重启也需恢复进度，不能只靠当前内存。

hash 查重针对内容去重和避免重复传输，不完全替代业务幂等。服务端已存字节仍需建立正确的 episode / 文件角色关联；预检查与正式提交间可能有并发重试。使用稳定 episode_id、文件角色 / 标识或幂等键，服务端唯一约束与幂等创建 / 完成操作，使重复请求指向同一逻辑记录 / 返回已有结果。hash 应基于受控已校验内容，不能只相信客户端声明。不同 episode 可能引用相同内容但仍是不同业务记录，不因内容一致合并掉来源关系。

episode manifest 声明必需文件、角色、大小、校验值和时间等必要元信息；服务端确认实际对象 / 完成状态及校验，再执行所需格式 / 时间对齐等质量检查，满足约定就绪条件才将状态由 uploading / validating 改为 ready，并让下游仅消费 ready 数据。就绪状态与通知需考虑可靠发布和重复消费；后续按需要展开，不假定多对象存储自动原子提交。

### 第四问回答与点评

用户回答：按时间范围固定数据；同一 episode 切出的数据一部分训练、一部分验证，确保验证不包含训练已有数据。

## 第 3 步 · 集群治理与恢复（进行中）

### 第五问：训练任务提交与恢复

沿用 4 节点×4 GPU，甲乙两团队各名义 8 GPU，允许在策略范围内借空闲份额。甲现在提交固定规模的 3 个 worker、每 worker 4 GPU 的任务；数据集版本已生成，使用具备持久化 checkpoint / 恢复能力的训练程序，后续可能被紧急任务抢占。

请串联三方面：训练记录 / 启动配置应绑定哪些关键版本和恢复信息；怎样表示任务整体 12 GPU 的准入与团队队列归属；重建 Pod 后如何恢复进度。先听用户作答，再补配额准入不等于实际节点可放下、Kueue 不自动恢复业务等边界。不要求编写 YAML。

### 第五问回答与点评

用户回答：程序支持 checkpoint，有则加载、无则从头；甲在 Kueue 配 4 GPU，等 3 worker 各有 4 空闲 GPU 再创建 Pod；借入借出需 Cohort / ClusterQueue / LocalQueue；恢复由训练代码检查和执行。

正确点：checkpoint 的保存 / 加载属于训练程序，Kueue 不负责恢复业务进度；也识别出跨队列资源借用相关对象。恢复应选择完整且与本次 run / 配置兼容的持久 checkpoint，首次启动无 checkpoint 可从头；要求续训却找不到依赖时不能无声当新训练，需按任务策略报错或显式确认重启语义。

需补：训练记录绑定 dataset_version、代码 / 容器版本、模型与训练配置、run_id 和持久 checkpoint 位置。不能不区分任务而加载任意“上一个 checkpoint”。完整分布式恢复需保存协议一致。

资源职责纠正：3 个训练 worker 在本例是 3 个 Pod，不等同 3 个 Kubernetes 节点；每 Pod 的 nvidia.com/gpu 请求为 4，整体需求 12。Kueue 按整体需求及队列策略准入，在本课已学基础配置下不保证物理节点已有合适布局 / Pod 同时开始；准入后解除 Job suspend，由 Job 控制器建 Pod，scheduler 分别选择合适节点。每节点总共 4 GPU，所以本例实际需要三台各有 4 卡可分配的节点。没有配置拓扑感知等额外能力，不声称 Kueue 提前保证该布局。

团队链路：甲 namespace 内 LocalQueue → 甲 ClusterQueue（名义 8，借入上限至少 4）；乙 LocalQueue → 乙 ClusterQueue（名义 8，允许借出至少 4）；两个 ClusterQueue 加入同一 Cohort，并满足匹配资源 / flavor 和其他准入条件。乙有可借份额时甲才可能准入 12 卡；8 是队列份额，4 是每 Pod 请求，12 是整体任务需求，不能混用。

当前停在第五问点评，先确认有无疑问，不继续新题。

用户追问“配额够也可能因 GPU 碎片 Pending”。解释采用一致场景：乙已有 4 个单卡 Pod，恰好每节点各 1 个；4 节点每节点总 4 卡，所以各空闲 3 卡，总空闲 12。假设乙名义 8、允许借出 4，甲名义 8、可借 4，其他条件满足，则甲 3 Pod×4 GPU 的 12 卡需求可获得配额准入。但任意一个甲 Pod 都需单节点 4 卡，没有节点具备，故 scheduler 无法绑定，Pod Pending。配额准入是允许使用多少，节点放置是单 Pod 能在哪里装下；基础配额账本不等同节点布局检查。即使物理空闲总数也为 12，仍不足以说明可调度。本段答疑后先确认是否仍有问题。

用户进一步问是否只看整体空闲 GPU 数。纠正：本课基础配置主要依据任务整体资源请求与 ClusterQueue / Cohort 的可用配额、借用和策略，而非直接统计物理空闲卡；已获配额但尚 Pending 的 Workload 也可能占配额。并非只支持 GPU，还可管理配置的 CPU / 内存等资源及 ResourceFlavor，遵循优先级等调度策略；额外拓扑感知等配置可纳入更多放置约束。因此不能将基础示例泛化成 Kueue 的全部能力。参考官方 ClusterQueue 概念文档。

用户确认配额区别后询问 scheduler 是否要自己写，并要求复习原配置。已读取 step6/scheduler-config.yaml、scheduler.yaml、auto-small.yaml 和 L08 实验记录，按三部分回顾：组件配置定义 l08-binpack profile、仅保留 NodeResourcesFit GPU MostAllocated 评分且默认过滤仍保留；独立 Deployment 运行原生 kube-scheduler，通过 ConfigMap 挂载并 --config 读取，配 ServiceAccount / RBAC，单副本关闭选主；目标 Pod 模板写 schedulerName=l08-binpack 使用该实例。默认调度器未替换，独立调度器自身由默认调度器放置。评分按资源请求 / allocatable 而非实际 GPU 计算利用率，不迁移已有 Pod，无法自动修复既有碎片；历史实验四个单卡 Pod 自动集中到 worker4，此次只读复习未重新执行或变更集群。停在答疑，确认无问题后回到系统设计。

用户确认 scheduler 三部分关系清楚，返回系统设计。

### 第六问：任务运行后的瓶颈与扩容

场景：需要的训练 Pod 已全部 Running，但训练不能在数据就绪后 10 小时内完成。算法团队建议把单任务 GPU 数翻倍，暂不改变模型与质量目标。

请说明先观察哪些信号区分数据准备、设备计算和分布式同步；若确认主要是 CPU 解码且窗口复用帧，如何优化；什么证据支持额外增加 GPU，并怎样验证扩容的完成时间与资源成本收益。先听用户分析，不根据 Running 或低利用率直接断定瓶颈。此题完成并确认无疑问后进入最后发布 / 回流与指标收束。

### 第六问回答与点评

用户回答：先看 GPU 使用率判断等数据还是算得慢；确认 CPU 解码瓶颈则用帧缓存；扩卡后比较完成时间与合计 GPU 时间，也注意 batch size 变化，最好无任务运行时操作。

点评：缓存、完成时间和 GPU 总时间方向正确，也注意到了训练语义变化。GPU 利用率只能作线索，不能单独区分数据等待、设备传输、通信或慢 worker；结合端到端吞吐、取 batch 等待、CPU 解码 / 读取耗时以及 GPU 计算 / 传输 / 通信时间线判断。

缓存应考虑容量与命中率、多 worker 独立缓存、随机增强边界。扩卡前测供给能否支持新增消费，避免供给瓶颈不变却新增资源占用。

“无任务运行时做”可避免直接扰动现有固定规模训练，但不能消除新训练 batch 变化。数据并行有效全局 batch=每进程微批大小×数据并行进程数×梯度累积步数；例 8 进程×8 样本×累积 1=64，扩到 16 进程且其他不变则 128，即使旧任务早已结束仍会改变更新行为。保持可比时可在资源允许情况下调整每进程 batch / 累积，或显式重调学习率等并验证质量；也要比较达到同等质量的总时间和成本。本课固定规模作业优先用独立新任务对照，不将热扩容能力视为默认支持。

### 第七问：灰度、回滚与失败证据

场景：新模型已通过离线与约定的受控验证，准备部署到 100 台机器人。需要控制现场风险并保留改进证据，不把测试通过当作所有真实场景都可靠的保证。

### 第七问回答与点评

用户回答：先部署 10 台；既然已通过评估但真机失败，考虑更新评估项目并重新学习；记录机器人 ID、模型版本、失败视频与传感器数据。

点评：灰度和版本化失败证据方向正确。选择覆盖有代表性场景的小批机器人，不只随意取 10 台；对照相近任务 / 场景下旧模型，观察任务成功 / 失败、关键事件、推理延迟与运行稳定性，通过门槛再扩大。机器人数仅为示例，不保证 10 台就一定充分。

现场显著退化时先暂停扩大发布，按既定策略回滚到已验证且配置兼容的版本 / 执行约定处置，确认机器人实际生效版本并保留证据；不能只等重新训练。随后定位根因，可能是评估场景覆盖不足，也可能是输入预处理、动作接口、模型文件 / 配置版本或机器人运行环境问题，不一律归因模型缺数据。重训前明确修复方案。

失败记录补充 episode / 任务 ID、时间、指令与目标、对齐的动作 / 状态、失败结果与场景信息，以及模型 / 预处理配置版本、发布批次和必要运行日志。由模型版本追溯训练 run 和数据集版本，才能复现与归因。失败并不自动带来正确示范动作标签；需要质检、标注 / 补采示范后再按目标构建样本。回流再训练并重新评估，作为训练输入的失败案例不能同时冒充未见的独立测试样本；维护独立验证 / 测试与版本，避免泄漏。
