## 0. 30 秒自我定位

> 机器人数据平台的成本主要在三块：**把视频传上来（带宽）、存下来（存储）、拿去训练（GPU）**。我的思路是**越早丢越省**（但只丢确定没用的）、**别让 GPU 等数据**、**调度上不让卡闲着也不让大任务排不上**；所有优化先分清是**等价、近似等价还是有损**，前两类用指标证明质量不变后灰度上线，有损的拿数据和算法团队一起决定。

## 1. 数据飞轮全景

**episode**（一段完整任务演示）= 多路视频（头部 + 双腕，30fps）+ **本体状态**（关节角、夹爪）+ **动作**（发给电机的指令，模型要学会输出的）+ 语言指令 / 元数据（成功失败、机器人、场景）。来源：**遥操作**为主，自主运行日志、仿真为辅。

```
① 采集 → ② 端侧处理+上传 → ③ 存储 → ④ 清洗/筛选/标注 → ⑤ 预处理/打包
   ↑                                                              ↓
⑨ 回流（失败场景 → 下一轮采什么） ← ⑧ 部署 ← ⑦ 评估 ← ⑥ 训练（k8s GPU）
```

| 段 | 要点 |
|---|---|
| ① 采集 | 多路数据**按时间对齐** |
| ② 端侧 | 压缩、过滤；算力 / 电量有限 |
| ③ 存储 | 对象存储（S3 / MinIO / Ceph）+ 元数据库 |
| ④ 清洗 | 去坏数据（损坏、掉帧、不同步）、去重、VLM 自动标注 + 人工抽检 |
| ⑤ 预处理 | 解码、对齐、切分片；产生大量**派生数据** |
| ⑥ 训练 | 分布式 GPU 训练 |
| ⑦ 评估 | 由便宜到贵：离线指标 → 仿真成功率 → **真机成功率** |
| ⑧ 部署 | 量化 / 蒸馏，端侧芯片（如 Jetson）实时控制 |
| ⑨ 回流 | 失败案例决定下一轮采集 → **飞轮** |

**成本落点**：带宽 ②；存储 ③（+ ④⑤ 中间数据）；训练 ⑤⑥；质量 ④ + ⑦。

**核心一句**：**越早丢越省，但越早丢越不可逆** → 端侧只丢确定没用的（损坏、空闲静止、重复）；拿不准的先传元数据 + 缩略视频，云端判断后按需拉全量。⚠️ **失败的演示不是坏数据**——是回流最需要的输入。

## 2. 视频模型 vs 文字模型

| | 文字生成模型 | 机器人视频模型 |
|---|---|---|
| 输入 | BPE → 离散 token ID（词表） | 图片切 **patch**（16×16 像素）映射成向量，无词表；视频加时间维 |
| token 量 | 一句几十个 | 大几千倍（见下） |
| 输出 | 下一个文字 token | **连续动作**，常一次预测一段（action chunk） |
| 训练 | 海量文本自监督 | **模仿学习**（behavior cloning），示范数据**稀缺且贵** |
| 瓶颈 | GPU 计算 | 常卡**数据**：解码耗 CPU、I/O 重 |
| 部署 | 晚几秒可接受 | **实时控制**，端侧芯片，需量化 / 蒸馏 |

| 模型类型 | 做什么 | 例子 |
|---|---|---|
| 视觉编码器 | 图像 → 特征向量 | ViT、SigLIP、DINOv2 |
| **VLA**（视觉-语言-动作） | 画面 + 指令 + 状态 → 动作 | RT-2、OpenVLA、π0 |
| 世界模型 | 预测动作后的未来画面 | 仿真、扩充数据 |

- 策略模型每步只看**最近几帧** + 当前状态；长视频是训练素材，切成大量（观测, 动作）样本。

```
token 数 = 摄像头路数 × 秒数 × fps × (分辨率 ÷ patch 边长)²
例：3 × 10 × 30 × (224 ÷ 16)² = 3 × 10 × 30 × 196 = 176,400
```
- 降 token 的办法（降 fps / 分辨率 / 路数、时间合并、token 压缩）属于**算法侧的建模选择**，不是本岗位的省钱手段；本岗位能做的是**预计算冻结编码器特征**（结果完全一样）。

## 3. 训练基础概念速查

| 概念 | 一句话 |
|---|---|
| **loss** | 预测和示范差多远，训练就是让它变小 |
| **参数** | 模型里所有权重矩阵中数字的总数，是模型本身 |
| **维度**（hidden size） | 每个 token 向量的宽度，是流过模型的数据的形状。**参数 ≈ 12 × 层数 × d² + 词表 × d**，维度翻倍参数约 4 倍 |
| **梯度** | 每个参数一个：它变大时 loss 怎么变。`新参数 = 旧参数 − 学习率 × 梯度`（大雾下山摸坡度） |
| **batch** | 每一步一起算的一组样本；梯度取平均、更新一次 |
| **step / epoch** | 一次更新 / 全部数据过一遍 |
| **全局 batch** | 每卡 batch × 卡数 × 梯度累积步数 |
| **数据并行** | 每卡一份完整模型、吃不同数据，梯度 **all-reduce 求平均**后一起更新 |
| **FSDP / ZeRO** | 把参数、梯度、优化器状态**切分到多卡**（单卡放不下时） |

**三种"存的东西"别混**：

| | 内容 | 7B 模型大小 |
|---|---|---|
| 部署模型文件 | **只有参数** | BF16 ≈ 14 GB；4 bit ≈ 3.5 GB |
| 训练 checkpoint | 参数 + **优化器状态**（Adam 的 m、v）+ FP32 主权重 + 进度；**一般不存梯度** | ≈ 84 GB 起 |
| 训练时显存 | 每参数约 16 字节（参数 2 + 梯度 2 + 主权重 4 + m 4 + v 4） | ≈ 112 GB，单张 80 GB 卡放不下 |

- 梯度是**每步的临时值**，算完同步、更新后就清零。
- **换卡数恢复**：checkpoint 里的东西都与卡数无关，结果**完全可用**；注意分片 checkpoint 重新切分（PyTorch DCP）、数据进度按**全局**样本号重分、**全局 batch 保持不变**。

## 4. 带宽与存储（质量不变）

**证明质量不变**：数学无损（像素一致，巨大）vs **视觉无损**（察觉不到差异，实际所说的"无损"）。指标 **VMAF**（0~100）/ SSIM / PSNR。话术："先定红线（如 VMAF ≥ 95）→ 样本集验证 → 最好再用训练效果验证。"

| 带宽 | 做法 |
|---|---|
| 更高效编码 | 同画质 H.265 约比 H.264 小 30~50%，AV1 更小；看端侧有无**硬件编码器** |
| 编码参数 | **CRF 固定质量**代替固定码率 |
| 不传没用的 | 空闲、重复片段不传，保留的画质不变 |
| 传输策略 | 断点续传；充电 / Wi-Fi 好 / 闲时传；**有价值的先传**；元数据 + 缩略图先行，按需拉全量 |

| 存储 | 做法 |
|---|---|
| 冷热分层 | 热 SSD → 冷 HDD / 归档，**生命周期策略**自动迁移 |
| 副本 vs 纠删码 | 三副本占 3 倍；纠删码 k+m 占 (k+m)/k 倍（4+2 = 1.5 倍）。**热数据三副本**（写快、可多副本并行读、恢复快），**冷数据纠删码**（省空间；写要算校验、坏块要现场重算、恢复流量大） |
| 去重 | 重复上传、多数据集复制 → 存一份、其余引用 |
| 派生数据 | 分片、预计算特征常比原始还大 → 定期清理，逐类判断**存 vs 重算** |
| checkpoint 保留 | 只留最近 N 个 + 最好的那个 |

## 5. 训练效率：别让 GPU 闲着

```
训练成本 = GPU 卡数 × 训练小时数 × 每卡每小时单价
训练小时数 ≈ 总计算量 ÷ 实际有效算力     （质量不变 → 总计算量固定）
```
- ⚠️ `nvidia-smi` 的 GPU util 只表示"有没有任务在跑"；看 **MFU**（实际有用计算 ÷ 理论峰值，大模型约 40% 已不错）。

| GPU 在等什么 | 现象 | 等价的解决办法 |
|---|---|---|
| **等数据**（最常见） | util 忽高忽低、CPU 打满、取数据慢 | **GPU 解码**（NVDEC / DALI，独立硬件单元，占显存和 PCIe）；**离线预处理**（拿存储换 CPU，解码后的帧比压缩视频大十倍以上）；预计算冻结特征；**分片格式**（WebDataset）代替海量小文件；本地 NVMe / 分布式缓存（Alluxio、JuiceFS） |
| 等通信 | 多卡每步同步梯度（7B ≈ 每步 14 GB） | 计算通信重叠；NVLink / InfiniBand / RoCE；**同任务 worker 就近调度** |
| 等别的 | 周期性停顿 | **异步 checkpoint**；评估单独跑；处理慢节点 |

| 算得快 | 对质量 |
|---|---|
| 预计算冻结编码器特征 | **完全一样** |
| BF16 混合精度（吞吐约翻倍） | 一般无影响，要验证 |
| 算子融合、`torch.compile` | 基本无影响 |
| 加大 batch | ⚠️ 改变训练过程（学习率要调），**不是质量中立** |

- **少白算**：checkpoint + 断点恢复、小实验先行、早停没希望的实验、实验追踪（MLflow / W&B）防重复。
- ⚠️ CPU 已 100% 时加 DataLoader worker 没用；先查 Pod 的 **CPU limit**（超了被 throttling）和 **CPU : GPU 配比**；`/dev/shm` 要挂内存盘。

## 6. k8s 训练集群

**gang scheduling**：默认调度器逐个 Pod 调度，分布式训练要求 N 个 worker **同时启动** → 否则**部分分配死锁**（8 张空卡、两个 8 卡任务各拿一部分：卡 100% 分配、0% 计算）。工具：**Volcano**、**Kueue**。

| 组件 | 做什么 |
|---|---|
| GPU device plugin | `nvidia.com/gpu: N`（只能整数） |
| 节点池 | 按 GPU 型号用 label / taint 隔离 |
| 训练 Operator | Kubeflow PyTorchJob：创建 / 重启 / 清理 |
| 队列 + 配额 | 每团队配额，闲置可借出（Kueue `nominalQuota` / `borrowingLimit`） |
| 优先级 + 抢占 | PriorityClass；被抢的从 checkpoint 恢复 |
| 拓扑感知 | 同任务 worker 同机 / 同机架 |

| 扩容 | 要点 |
|---|---|
| 自动扩缩容 | Pending → 加节点（Cluster Autoscaler、Karpenter）；空闲 → 缩 |
| GPU 节点慢 | 开机、驱动、十几 GB 镜像 → **镜像预拉** |
| 容量规划 | **基线固定**（最便宜）+ **高峰按需**（贵）+ **可中断用 spot**（最便宜，必须有 checkpoint） |
| 何时加 | **等待成本 vs 机器成本**；高优先级等待超阈值才扩 |
| 带宽配套 | 加 GPU 时存储 / 网络带宽也要加，否则卡只是在等数据 |

| 先用好现有的 | 办法 |
|---|---|
| 分配 ≠ 使用 | **DCGM exporter** 看每 Pod 真实使用 |
| 碎片 | **装箱**（调度打分 MostAllocated）、**分池**（整机任务池 / 小任务池）、descheduler 定期整理 |
| 小任务独占整卡 | 共享（下表） |
| 闲置 | 空闲 notebook 自动回收 |
| 弹性训练 | torchrun elastic（成员变化时全体重启恢复，非无缝） |

**一张卡跑多个任务**（只对**用不满卡的小任务**划算；大训练任务不该共享；"等数据导致的空闲"共享解决不了）：

| 方式 | 隔离 | 适合 |
|---|---|---|
| 时间片 | 显存不隔离 | 调试、notebook |
| MPS | 较弱 | 多个小任务（小模型超参搜索） |
| **MIG**（A100 / H100） | **硬件强隔离**，最多 7 份 | 推理、评估、多租户 |
| HAMi（开源） | 按显存 / 算力比例申请 | k8s 内 GPU 虚拟化 |

**场景速答**（8 台 × 4 卡共享集群）：
- **4 卡任务怎么申请**：**1 Pod × 4 卡**（同机 NVLink 快、整机放下、不制造碎片），`torchrun --nproc_per_node=4`。
- **跑满了想 4 → 6**：⚠️ 跑满是好事不是扩容理由，扩容是为赶时间；加卡要**固定全局 batch**；5、6 卡会**跨机**，被机间网络拖住，可能远不到 1.5 倍 → **按整机扩（4 → 8）最划算**，否则先实测。"最多 6、留 2 张给别人"用**配额**管（ResourceQuota / Kueue），不是任务参数。实际常用：**checkpoint → 停 → 改卡数重提 → 恢复**。
- **只有 4 张空卡且分散**：Pod 会 Pending → 等 / 拆成单卡跨机跑（慢）/ **抢占腾出整机**（高优先级通常选这个）；根治靠装箱 + 分池。
- **满载来了明天要结果的高优先级任务**：**先抢占**（快、不花钱，前提：checkpoint + 自动恢复 + PriorityClass 只许高抢低 + 通知负责人），**不够或赶不上再扩容**。

## 7. 质量 vs 成本

| 类别 | 例子 | 怎么决定 |
|---|---|---|
| **等价** | 缓存、数据加载、预计算冻结特征、去重、冷数据纠删码、异步 checkpoint、调度、碎片整理 | 放手做 |
| **近似等价** | 换编码、BF16、分片格式转换 | 红线 + 小规模 A/B |
| **有损** | 降分辨率 / 帧率、丢数据、小模型、少训练步数 | 和算法 / 业务用评估结果一起定 |

- 验证分层：数据质量（VMAF、掉帧、同步误差）→ 离线（loss、动作误差）→ 仿真成功率 → 真机成功率（最贵）。
- A/B：只差一项、**多随机种子**、做成流水线**固定关卡**、**不改质量标准**。
- 单位成本：每有效训练小时成本、每 TB 有效数据成本、MFU、**每提升 1% 成功率的成本**。
- **数据质量 > 数量**：多样 / 困难 / 失败场景比堆量更提质、更省钱。

## 8. 面试答题框架与高频问答

**开放题五步**：
```
1. 量化现状：拆账（带宽 / 存储 / 计算）+ 利用率指标（账单说钱花在哪，指标说浪费在哪）
2. 找最大头：二八原则
3. 按顺序出方案：等价 → 近似等价 → 有损（交大家决定）
4. 定质量红线和验证方法
5. 试点 → 逐步扩大 → 全量；成本看板、可回滚
```
- **答题贴题**：问 GPU 就聚焦计算，问带宽就聚焦传输。先测量再动手。

| 可能被问 | 一句话要点 |
|---|---|
| 视频模型和 ChatGPT 这类模型有何不同？ | patch 无词表、token 量大几千倍、输出连续动作、模仿学习数据贵、常卡数据加载、部署要实时 |
| 完整流程是什么？ | 九段飞轮：采集 → 端侧 → 存储 → 清洗标注 → 预处理 → 训练 → 评估（离线 → 仿真 → 真机）→ 部署 → 回流 |
| 带宽怎么降？ | 端侧只丢确定没用的 + 高效编码（看硬件编码器）+ CRF + 价值优先 / 闲时 / 续传 / 轻量先行 |
| 存储怎么降？ | 冷热分层 + 热三副本冷纠删码 + 去重 + 管派生数据 + checkpoint 保留策略 |
| 训练怎么又快又省？ | 先看 MFU；等数据 → GPU 解码 / 预处理 / 预计算特征 / 分片 / 缓存；等通信 → 就近调度；少白算 → 断点恢复、早停 |
| 训练密集时集群怎么扩？ | gang + 队列配额 + 优先级抢占；基线 + 按需 + spot；等待成本 vs 机器成本；先治碎片和闲置再加机器；加卡配套加带宽 |
| 质量和成本怎么平衡？ | 三类优化按顺序；红线 + 分层验证 + 多种子 A/B；单位成本；数据质量 > 数量 |
| 每月 GPU 账单很高，第一个月做什么？ | 见 `robot-data-interview-notes.md` 题 1 |

## 9. 关键数字速记

| 数字 | 含义 |
|---|---|
| 1080p30 H.264 ≈ 几 Mbps ≈ 2~3 GB / 小时 / 路 | 单路视频量级 |
| 100 台 × 3 路 × 8 小时 ≈ 7 TB / 天 | 机队规模感 |
| 三副本 3× vs 纠删码 4+2 1.5×（8+3 ≈ 1.375×） | 7 TB / 天时一年差约 3.8 PB |

## 11. K8s 调度实战速查（L08）

讲义：[L08](lessons/L08-k8s-training-scheduling.md)；配置：仓库根目录 `robot-k8s-lab/`。实验为 kind 4 台 worker × 4 张模拟 GPU，能验证资源计数与调度，不能证明真实训练吞吐、通信效率或模型质量。

### 对象和组件各管什么

```text
Job 的 queue-name 标签 → 同 namespace 的 LocalQueue
                         → ClusterQueue（资源额度与准入规则）
                           → Cohort（可选，共享空闲配额）

Kueue 创建关联 Workload，按整体需求决定准入
  → 解除 Job 的 suspend
  → Kubernetes Job 控制器创建 Pod（使用 Job 的 spec.template）
  → kube-scheduler 为 Pod 选择节点
  → kubelet / 容器运行时启动容器
```

Workload 是 Kueue 自定义资源，ownerReferences 关联原 Job。控制器通过 watch / 工作队列 / reconcile 协作，不直接读取本地 YAML。Deployment 则经 ReplicaSet 管理 Pod；标签选择器用于匹配，ownerReferences 表示实际控制归属。

LocalQueue 的价值是提供 namespace 内的提交入口，ClusterQueue 统一管集群级份额。例如一个团队有 dev / eval 两个 namespace，各自 LocalQueue 都指向同一个 8 卡 ClusterQueue，则合计共享 8 卡；不是每个入口各获得 8 卡。入口与账本不必一对一。Job 不直接用 queue-name 引用 ClusterQueue；LocalQueue 的权限与可用范围还需 RBAC / namespaceSelector 配套。对象要存在，不要求单独一个 YAML 文件，同文件可用 --- 定义多个对象。

### 本课实验结论

| 问题 | 实验与结论 | 对策 / 边界 |
|---|---|---|
| 部分分配 | 默认逐 Pod 调度，A/B 各需 12 卡、交替提交，可能各占一部分但都无法训练 | Kueue 按固定规模 Job 整体准入：16 卡下先准入一个 12 卡任务，另一个保持暂停、没有 Pod |
| 团队额度与闲置 | 两队各 8 卡，允许借入 / 借出 4，甲可运行 12 卡任务 | 相同资源 / flavor 的队列加入 Cohort；甲 total=12、borrowed=4，total 已包含借入量 |
| 借出后回收 | 甲用 12 时乙申请自身 8，禁用回收则乙等待；开启乙 reclaimWithinCohort=Any 后甲整体暂停、乙运行 | 配额份额不等于随时立即可用；Any 回收不要求请求方优先级更高，但仍受份额回收条件限制 |
| 优先级抢占 | 独立 8 卡队列，普通任务 10 先运行，紧急任务 100 到来后驱逐普通任务 | withinClusterQueue=LowerPriority；优先级高不绕过 Never 策略 |
| 自动重新运行 | 紧急任务退出，普通 Job / Workload 保留并重新准入，创建新 Pod | 调度恢复不等于业务进度恢复，需要程序加载 checkpoint |
| GPU 碎片 | 每台 4 卡、各占 1：全局空闲 12，但 1 Pod × 4 卡仍 Pending | 单 Pod 资源须在同一节点满足；单看总量不够 |
| 装箱 | 四个单卡 Pod 用 MostAllocated 自动集中在一台，后续 4 卡 Pod 可放其他完整节点 | 按请求量评分，不看实际 GPU 利用率；影响新 Pod，不会自动迁移已有 Pod |

### 关键字段与常见误区

- `limits.nvidia.com/gpu: 4`：本实验中是固定申请 4 个整卡资源单位；只写 limits 自动补同值 requests，同时写时须相等。资源可计数不代表有真实设备。
- `capacity` 是节点资源总量，`allocatable` 是可供 Pod 分配的总额度；已有 Pod 申请 1 卡后，allocatable=4 通常仍为 4，调度器结合已有请求算剩余 3。
- `parallelism` 决定并发 Pod 数；`completions` 是需成功完成的数量，不表示必须同时运行。固定 3 worker × 4 卡实验使用 parallelism=3。
- `nominalQuota` 是名义份额，`borrowingLimit` 是额外借入上限，`lendingLimit` 是名义份额中允许借出的上限；它们不把物理卡固定划给某团队。
- Kueue 总配额准入不保证所有 Pod 原子地一起启动，也不保证实际节点有合适空间；需结合拓扑 / 节点容量 / 就绪检测等机制。
- `WorkloadPriorityClass` 与 Job 的 `kueue.x-k8s.io/priority-class` 管 Kueue 优先级，不自动改变 Pod 的 Kubernetes PriorityClass。
- `KubeSchedulerConfiguration` 是调度器进程配置；要通过 --config 读取。目标 Deployment / Job 写 `spec.template.spec.schedulerName: l08-binpack`，只读配置文件或只写名字都不足以运行新调度器。
- 容器在原 Pod 内重启不重新调度；控制器新建替代 Pod 才按其 schedulerName 调度。

### Checkpoint 与抢占成本

定期保存为基础，SIGTERM 时在安全训练边界争取补存。Pod 的 terminationGracePeriodSeconds 是退出时间预算；强杀、OOM、节点故障可能没有补存机会。

完整续训通常保存模型参数 / 持久 buffer、优化器、更新步数 / 学习率调度、必要的数据读取和随机数状态；使用 FP16 GradScaler、EMA 等时也保存其状态，并记录模型 / 数据 / 代码配置。常见完整更新边界不用保存梯度；梯度累积中途精确恢复则需额外处理尚未应用的梯度与累积进度。

checkpoint 放 PVC / 对象存储等持久位置，保留完整版本，新进程启动时主动加载。多 worker / 分片训练需要一致的分布式保存协议，不能直接套单进程信号处理。保存优化器状态是为了延续更新行为：Adam 的 m、v 为每个参数维护梯度和梯度平方的滑动统计，只有权重而没有优化器状态时，学到的结果保留，后续更新行为可能改变。

成本取舍：更频繁保存减少被抢占后的重复计算，但增加 I/O 与存储开销；资源交接还要计入优雅退出、Pod 启动和 checkpoint 加载时间。当前 pause 实验未验证真实保存恢复。

### 排障命令

```bash
kubectl --context kind-robot-train -n default get jobs,pods,workloads
kubectl --context kind-robot-train get clusterqueues
kubectl --context kind-robot-train -n default describe workload <workload名称>
kubectl --context kind-robot-train -n default describe pod <pod名称>
kubectl --context kind-robot-train -n default get pod <pod名称> -o yaml
```

先辨环节：Workload WaitingForQuota → 配额 / 借用规则；PodScheduled=False / FailedScheduling → 节点资源、碎片、污点等；已选节点但 ImagePullBackOff → 镜像拉取。describe 末尾的 Events 是关联事件，Event 独立于 Pod，get pod -o yaml 不附带事件列表；ownerReferences 位于 Pod 的 metadata 中。

### 当前实验边界

独立 l08-binpack 调度器只处理明确选择它的新 Pod，默认调度器继续工作，二者共享物理资源。本次为隔离评分因素，只保留 NodeResourcesFit 的 GPU MostAllocated 评分，生产须评估其他评分目标。自动装箱不是实时 GPU 利用率优化，也不能替代训练数据加载、存储吞吐和网络通信优化。

### 验证优化是否有效

| 目标 | 观察指标 |
|---|---|
| 少占卡不算 | GPU 已分配比例对比实际计算利用率；worker 等同伴时长 |
| 更快交付 | 按团队 / 优先级统计提交到准入、准入到全 worker 就绪、端到端完成时间的 P50/P95，以及任务吞吐 |
| 少碎片 | 因资源不足 Pending 的持续时间、具有完整空闲 GPU 容量的节点数；不能只看全局空闲量 |
| 少重算 | 每次抢占后重复计算步数 / GPU 小时、checkpoint 成功率和保存 / 加载耗时 |
| 成本与质量 | 相同任务 / 数据 / 质量标准下的单位有效训练成本，灰度对比并考虑优先级让位的代价 |

Kueue 等待任务可能尚无 Pod，需看 Workload，不能仅看 Pending Pod。checkpoint 次数不能代表避免了多少重算；例如 8 卡任务丢失 6 分钟进度，对应约 48 GPU 分钟（0.8 GPU 小时）的重复计算，另加启动 / 加载成本。完整口述参考见面试笔记题 2。L08 已完成，其他第二阶段专题待继续。

## 12. 训练数据管线速查（L09）

### 输入与正确性

典型链路：定位视频 / 状态 / 动作 → 读字节 → 解码 → 帧采样与预处理 → 组 batch → 搬到 GPU → 前向 / 反向 / 参数更新。具体窗口按模型定义，不是所有视频模型都输出动作。

Dataset 定义单样本，Sampler 决定样本取用顺序，DataLoader 组织加载与批次，collate 拼 batch。打乱完整样本不能打乱样本内帧的时序与动作对应。先按 episode 等独立组划分训练 / 验证，再切窗口，避免重叠内容泄漏；分组边界还要匹配希望泛化的场景。

教学脚本 4 episode 各 18 张图，共 72 张，三帧窗口各 16 个。前三个 episode 训练，共 48 样本；最后一个验证，共 16 样本。单样本 images 为 [3 帧,3 通道,112 高,112 宽]，batch=8 后为 [8,3,3,112,112]。float32 每元素 4 字节，一批图像约 3.45 MiB。动作标签只是合成的对齐标记，没有真实机器人语义或训练模型。

### 并行与预取

- num_workers 增加加载进程，收益受任务规模、启动、CPU、存储和内存限制，不能越多越好。
- persistent_workers 保留 worker / Dataset 实例，不自动缓存图像。单轮小任务可能启动成本占主导，跨轮复用才有机会摊薄。
- 4 worker × prefetch_factor 2 表示最多预先安排 8 个 batch 任务，不代表已有 8 批就绪；数据集还须有足够批次。
- 预取吸收短时抖动，不能把持续供给 5 batch/s 变成 20 batch/s。缓存、预取与当前 batch 的内存都要计入，不能仅按图像张量估算进程峰值。
- batch 变大可能提高吞吐，也增加内存并改变更新频率；不保证质量更好。区分每进程 batch 与全局有效 batch。

本机实际 CPU 对照（48 样本、batch 8、3 轮，毫秒）：

| worker | 保留 worker | 首轮 | 后两轮中位数 |
|---:|---|---:|---:|
| 0 | 否 | 34.41 | 30.31 |
| 2 | 否 | 11212.26 | 11150.24 |
| 2 | 是 | 1177.72 | 20.02 |
| 4 | 是 | 1361.40 | 15.56 |

本地版本组合的退出开销显著；保留进程的最终清理在轮次计时外，不应将后续轮次直接视为整个应用成本。macOS / Python 3.12 / torch 2.2.2 的进程退出兼容处理及上游依据见讲义。结果不代表生产最佳配置，无真实 GPU 重叠验证。

### 分片与缓存

| 手段 | 主要针对什么 | 边界 |
|---|---|---|
| 小文件分片 + 合适的顺序读取 | 文件 / 小请求固定开销 | PNG 原样放进 tar 仍需解码；普通 tar 不等于外层压缩 |
| 缓存原始字节 | 重复源读取 | 仍要解码 |
| 缓存解码像素 | 重复读取与解码 | 容量、淘汰、版本及进程独立性影响命中率 |
| 缓存确定性处理结果 | 重复读取、解码及部分预处理 | 张量可能更大；每次需要变化的随机增强留在缓存之后执行 |

相邻窗口 [0,1,2]、[1,2,3] 可按帧复用。单进程、空缓存、容量足够时，训练一轮 144 次帧访问只涉及 54 张不同帧，理论上解码 54 次、命中 90 次。有限容量会淘汰；shuffle 可能降低局部性，不能只为命中率取消训练所需随机性。普通字典通常每 worker 独立，同帧可能在不同进程重复解码与占内存。OS 文件页缓存不等于解码结果缓存。

### 真正的 GPU 测量与扩容

低 GPU 利用率不能直接证明数据供给不足。先测固定训练设置下预热后的端到端 samples/s 和时间线，再分辨数据等待、CPU 解码预处理、设备传输、GPU 计算、通信 / 慢 worker。GPU 异步执行，CPU 计时可能只覆盖提交开销；使用合适的 profiler / CUDA events 或测量边界同步，避免逐段强制同步破坏正常重叠。独立环节 benchmark 需贴近真实访问和并发条件，并用端到端验证收益。

供给预算示例：每卡 10 batch/s，每 batch 从源读取 20 MB 压缩数据，16 卡需求为 3.2 GB/s；若共享链路持续上限 2 GB/s，增加卡数或预取不能让所有卡长期达到该目标。存储压缩字节与解码张量载荷不同，要分别核算进程、节点、集群的存储 / 网络 / CPU 需求。

成本示例：48 万次样本，8 卡 × 600 秒=4800 GPU·秒；16 卡 × 400 秒=6400 GPU·秒。后者更快但 GPU 时间增加约 33%。在每卡单位时间成本相同的假设下该项成本更高；实际总成本还计存储、网络、预处理等。相同样本次数不保证同等收敛质量，最终比较达到目标质量的总时间、总成本及业务价值。

## 13. 成本模型速查（L10）

### 先统一口径

固定周期、数据与训练工作量、评估质量目标和交付时限，再比较用量、单价与增量开销。以下价格均为教学假设，不代表真实厂商报价；模型所列费用不等于完整平台总账。

单位采用十进制：1 Byte=8 bit，1 GB=1000 MB，1 TB=1000 GB；GiB / TiB 另行标注。Mbps 是每秒百万 bit，MB/s 是每秒百万 Byte。

| 项目 | 核心公式 | 注意事项 |
|---|---|---|
| 采集视频量 | 机器人台数×相机数×平均码率×录制秒数÷8 | bit/s 转 Byte；峰值码率不等于平均值 |
| 上传量 | 采集字节量×实际上传字节比例 | 不用片段数量比例直接替代；另计实际协议 / 重传开销 |
| 所需平均有效带宽 | 上传字节×8÷可用上传秒数 | 还看数据可发送时点、波动、可用性与余量 |
| 稳态逻辑保有量 | 各类每日新增量×各自保留天数，再相加 | 假设稳定新增、到期实际删除；初始月份未必稳态 |
| 副本载荷 | 逻辑量×总副本份数 | 三副本总共 3 份；不等于最终裸盘采购容量 |
| 月容量费 | 当月平均计费容量 GB×元/(GB·月) | 查明冗余是否已含，避免重复乘副本 |
| GPU 消耗 | 各次任务的卡数×占用小时数之和 | 等数据也占卡，不能再乘实际利用率扣除 |
| 重算增量 | 中断次数×卡数×每次重复计算小时数 | 基线若已含同一重算，不能重复加 |
| 月净节省 | 减少的费用−全部新增月费用 | 含保存、筛选、存储写入等连带开销 |
| 简化回本月数 | 一次性投入÷稳定月净节省 | 净节省须为正，收益须可兑现，结合预计使用期 |

### 本课计算链

单相机平均 4 Mbps、每天录制 8 小时：0.5 MB/s×28800 s=14.4 GB/天。100 台机器人、每台 2 相机：每天采集 2880 GB；上传字节占 25%：720 GB/天。8 小时传完需理想平均 200 Mbps，4 小时需 400 Mbps，均为群体合计有效载荷需求，不是采购线路规格。

原视频每天 720 GB、保留 30 天：21.6 TB；保留 90 天：64.8 TB。回到 30 天场景，三副本视频载荷为 64.8 TB，还需其他占用和恢复余量。另假设派生图像每天 1440 GB、保留 7 天：10.08 TB；两类共 31.68 TB 逻辑量。派生量 2 倍仅为假设，实际依格式与处理方案而定。

训练每次 8 卡×6 小时、每月 30 次：1440 GPU·小时；单价假设 5 元/(GPU·小时)：7200 元。每月 6 次中断，各需重算 20 分钟：额外 16 GPU·小时、80 元，合计 7280 元。此处每次 6 小时明确不含额外重算。

### 月度汇总示例与净收益

| 纳入项 | 假设计费口径 | 月费用 |
|---|---|---:|
| 上传 | 720 GB/天×30 天×0.02 元/GB | 432 元 |
| 视频与派生数据 | 稳态平均 31680 GB×0.10 元/(GB·月)，已含冗余 | 3168 元 |
| GPU 训练含原方案重算 | 1456 GPU·小时×5 元 | 7280 元 |
| 已纳入项合计 | 其他未覆盖项须另行确认 | 10880 元 |

单项比较：上传费降低 50% 省 216 元，GPU 费降低 10% 省 728 元。优化百分比不能代替实际节省金额，也不能代替实施难度与风险评估。

联动例子：筛选后上传量减半，若派生新增量也减半、保留周期和单价不变，稳态上传及存储合计省 1800 元/月。仅改变视频压缩率不保证派生数据减半；上传字节减半也不保证训练 GPU 费减半。旧数据需逐步到期，稳态收益不等于上线首月收益。若新增运行费 600 元/月、投入 6000 元，则净省 1200 元/月、简化 5 个月回本。

checkpoint 例子：重算从每次 20 分钟降至 5 分钟，月重算费从 80 降至 20 元，节省 60 元。若新增保存 GPU 占用费 40 元、存储写入费 30 元，则最终反而多花 10 元/月。不能只看重算减少。面试追问：省重算 300 元，新增保存 120 元、存储写入 80 元，月净省 100 元；投入 1000 元，简化 10 个月回本。

### 决策约束与常见误区

- 固定专线月费不一定随传输字节减少；已有磁盘释放空间也不意味着采购款退回。区分实际新增支出、固定资源分摊和延缓扩容的收益。
- 按逻辑容量收费且已含底层保护，不额外乘三副本；自建物理容量则按实际冗余布局计算。副本不等同独立备份。
- 减少不必要重复数据与减少可靠性副本是不同方案。副本策略要满足可靠性和恢复要求，不能只靠模型质量评估判断。
- 缩短保留周期要验证历史重训、复现与长尾场景需求；数据筛选须保持观测 / 动作对齐及关键场景覆盖。
- 先确认方案满足质量和交付时限，再比较净收益、投入回本和业务价值。95% 成功率为硬要求时，92% 的方案不能因更省钱而直接通过；具体质量指标由任务决定。
- 核算 GPU 开销时，卡数已包含在 GPU·小时中，不重复计入同一成本。相同样本次数也不保证相同质量，最终比较达到目标质量的时间与总成本。

完整推导与课堂问答见 [L10 成本模型讲义](lessons/L10-robot-data-cost-model.md)，口述参考见面试笔记题 4。L10 完成的是手算与场景分析，未编写成本估算器，未使用真实账单或进行报价验证。后续进入系统设计综合练习；估算器可作为可选练习。

## 14. 系统设计速查（L11）

### 设计顺序与产物

先问训练目标 / 监督信号、质量标准、上传 / 训练 / 发布各自时限、可靠性 / 留存和资源预算。本题是动作策略训练，视频之外还需要约定的动作、状态和指令及时间对齐。完整链路：

```text
采集与轻量筛选 → 可靠上传 → 文件 / 数据质量检查 → ready episode
→ 样本构建与固定数据集版本 → 排队准入 → 训练与持久 checkpoint
→ 候选模型与发布前评估 → 代表性小批灰度 → 观察后扩大
                                        ↓
                          失败证据回流、质检 / 标注 / 补采
                                        ↓
                                后续新数据集与训练
```

原视频、派生数据、训练 run、checkpoint、模型和发布批次分别标识。模型能追溯到数据集和训练配置，失败事件能追溯到当时实际运行版本。部署后评估不能替代部署前质量门槛。

### 上传与数据集

- 分块续传记录已完成部分；超时重试用稳定标识和服务端幂等约束，进程重启后也能恢复。hash 去重解决内容重复，不能替代 episode / 文件关系的幂等。
- episode 清单声明必需文件和校验信息，全部满足约定检查再发布 ready；多对象先后上传不代表天然原子完成，下游不能读取半套数据。
- 时间范围只是选数据的规则；不可变版本清单还需固定实际对象、处理版本和划分。先按 episode 等独立组划分，再切重叠窗口，避免共享帧泄漏。
- 数据对象生命周期与版本引用相协调，保护在用依赖，并明确长期复现保留策略。保存清单不等于保存了实际数据。

### 集群与训练：三个数字和两道检查

示例：甲队列名义 8 GPU，任务 3 Pod×4 GPU=12 GPU。每 Pod 的 4 是资源请求，整体 12 用于准入，8 是队列份额。甲 LocalQueue → 甲 ClusterQueue，乙亦然；ClusterQueue 加入同一 Cohort，在策略内借入 / 借出。

Kueue 基础配置看资源配额及队列策略，并非直接数物理空闲卡；不只支持 GPU。准入后 Job 控制器创建 Pod，scheduler 再放置。如果四台 4 卡节点各占 1 卡，总空闲 12，但每台只空闲 3，则任何一个 4 卡 Pod 都放不下。已获配额但 Pending 的任务仍可能占配额。额外拓扑感知等能力须另配置，不将基础实验边界泛化为全部能力。

调度器不必自己写。既有实验三个文件：`robot-k8s-lab/step6/scheduler-config.yaml` 定义 GPU MostAllocated，`scheduler.yaml` 启动原生 kube-scheduler 并通过 ConfigMap / --config 读取，`auto-small.yaml` 的 Pod 模板用 schedulerName=l08-binpack 选择它。过滤硬约束后才评分，按请求量而非实际计算利用率；不自动整理旧 Pod。

checkpoint 由训练程序保存与恢复，绑定本 run、数据 / 模型 / 配置及完整兼容状态，存持久位置。Kueue 重新准入不等于业务续训。扩卡用独立可比训练验证，检查数据供给与通信；每进程 batch×数据并行进程数×梯度累积步数决定全局有效 batch，即使没有在跑任务，改卡数也可能改变新任务训练行为。

### 发布与系统指标

先通过离线及约定受控验证，再小批灰度，按代表性场景与对照观察；退化时先暂停扩大并按预案回滚到已验证兼容版本，再定位和修复。失败可能来自模型或输入 / 动作配置、运行环境，不一律归因数据不足。记录机器人 / episode / 任务 / 时间 / 指令、视频与对齐动作状态、失败结果、模型 / 处理配置及发布批次。失败数据不一定带有正确示范动作，需检查标签来源，且不能同时当独立未见测试。

| 环节 | 重点指标 |
|---|---|
| 接入 | 上传积压量 / 年龄、采集到 ready 延迟、完整与对齐合格率 |
| 调度 | 按团队 / 优先级看排队、准入到就绪、Pending 原因 |
| 训练恢复 | 端到端吞吐与时间线、目标质量完成时间、保存 / 加载与重算 GPU 时间 |
| 发布 | 分场景成功 / 失败、关键事件、推理延迟与稳定性、实际版本及回滚结果 |
| 经济性 | 达到同等质量的总时间与总成本、净节省、一次投入与回本周期 |

完整问答见 [L11 系统设计讲义](lessons/L11-robot-data-system-design.md)，完整面试口述见面试笔记题 5。本课仅方案设计与配置复习。计划更新：后续按视频压缩 / 过滤 → 小型训练 / checkpoint → 成本估算器进行，三个实操均已确认必修，替代前文历史“可选”安排。

## 15. 视频压缩与端侧过滤实操速查（L12）

### 工具、容器和编码

imageio-ffmpeg==0.6.0 安装于 backend/.venv，macOS ARM64 包内置 FFmpeg 7.1，路径通过 imageio_ffmpeg.get_ffmpeg_exe() 取得；支持 libx264，不包含 ffprobe。依赖已加入 scratch 可选依赖组。

MP4 / MKV 是容器，组织视频轨、可选音频轨、时间戳等；H.264 / FFV1 是编码方式，libx264 是 H.264 的具体编码器。重新封装可复制编码流，重编码需要解码再编码；只改后缀不会完成任何转换。H.264 的 CRF 数值提高通常减少体积、增加损失，不保证固定码率；preset 调整编码速度与压缩效率取舍，不是直接指定画质等级。

### 固定源、单因素对照

无损源由 testsrc2 生成，640×360、30 fps、8 秒、240 帧，以 FFV1 / MKV 保存；文件 4108055 Byte。完整解码与生成源逐帧哈希一致。各有损输出均从同一无损源生成，不串联有损转码；固定 libx264 / medium / yuv420p / 单编码线程 / 无音轨，逐项改参数。

| 输出条件 | 字节数 | MB（十进制） | 完整解码帧数 | 相对源 PSNR |
|---|---:|---:|---:|---:|
| 640×360 / 30fps / CRF18 | 1166283 | 1.166283 | 240 | 49.118780 dB |
| 640×360 / 30fps / CRF28 | 423107 | 0.423107 | 240 | 39.337538 dB |
| 320×180 / 30fps / CRF18 | 246506 | 0.246506 | 240 | 未比较 |
| 640×360 / 15fps / CRF18 | 738218 | 0.738218 | 120 | 未比较 |

所有输出都实际解码验证为 8 秒。CRF28 比 CRF18 小约 63.72%；宽高减半时像素数为 1/4，文件减少约 78.86%；帧率减半时文件减少约 36.70%。这些比例只属于该素材与设置，不能推广成通用压缩规律。

PSNR 比较对应帧像素，须核验分辨率、像素格式和时间对齐；单位 dB，不是任务成功率。整体平均可能掩盖小物体和短暂事件。实际同帧同区域放大观察中，CRF28 的细纹更模糊；最近邻放大仅放大像素，不恢复细节。跨尺寸或帧率结果未经定义的重采样 / 对齐不能直接比较前述指标。

缩小分辨率减少空间信息；减少帧率稀疏时间采样，30 → 15 fps 的间隔约 33 → 67 ms。真实训练要按时间戳维持动作对应。模型本身的预处理 / 采样需求也影响最终结果，压缩质量评估不能只看视频参数。

### 本机处理时间与边界

预热一次、重复 3 次取中位数，固定线程；编码输出临时文件、解码到 null：

| 条件 | 生成输出视频（ms） | 完整解码输出视频（ms） |
|---|---:|---:|
| CRF18 基线 | 1094.58 | 142.55 |
| CRF28 | 907.23 | 93.30 |
| 320×180 | 375.88 | 47.16 |
| 15fps | 665.35 | 94.04 |

这是墙钟时间，含进程启动、读取、处理及相应输出开销，不是纯编码器时间或 CPU 使用率。生成链路先解码源，再执行 fps 滤镜；输出帧减半不代表源解码工作也减半。短素材、缓存及固定运行次序限制了推论，不能拿此表直接做生产容量估算。

### 完整片段过滤实验

脚本 `backend/scratch/robot_video_filter.py` 生成三段 100×100、12 帧、6fps 的 FFV1 / MKV 视频，再实际解码评分。相邻帧先转 float32 再相减，避免 uint8 溢出；全图平均绝对差按 0～255 尺度，片段取最大相邻差，阈值假设为 1。

| 片段 | 分数 | 仅变化规则 | 加已知事件保护 |
|---|---:|---|---|
| 静止 | 0 | 不选 | 不选 |
| 明显运动 | 约 4.08 | 保留 | 保留 |
| 2×2 局部变化 | 约 0.102 | 漏掉 | 保留（人工模拟 contact） |

这不是视觉接触识别器。第二规则依赖外部已知事件，缺标记的重要事件仍可能漏掉；静止也未必无价值。输入 4133 Byte，两规则分别选择 1576、2864 Byte，只展示玩具片段的选择结果，不是实际网络账单。保留完整片段内所有帧，不删原文件；重跑同名输出拒绝覆盖。

### 怎样决定真实上线

与原数据对照按失败 / 长尾类型统计保留比例，而非只看有没有失败样本；抽查排除数据并为未知事件保留探索样本。计入端侧解码 / 评分 / 重编码、能耗、延迟和实施运维，减去实际上传 / 存储等收益，保持训练质量与时序对齐。先影子记录且保留原数据，再代表性小范围启用、逐步扩大；逐条改规则便于归因。关闭规则不能恢复已永久丢弃数据。

## 16. 视频与状态训练、checkpoint 速查（L13）

可视化入口：[离线交互版](visuals/robot-training-flow.html) · [静态流程图](visuals/robot-training-flow.svg) · [图片预览](visuals/robot-training-flow-preview.png)。可逐步回放真实参数更新记录、查看完整31条训练 / 验证记录，并切换checkpoint恢复对照；页面本身不执行训练。

### 用简单话解释整个训练

给模型过去的视频和当前状态，让它猜下一步动作；用已经记录的示范动作检查差距，计算梯度并调整内部参数，反复练习后用未参与更新的数据检验，再保存参数与续训状态。

| 内容 | 本实验 | 角色 |
|---|---|---|
| 视频窗口 | 连续 3 帧、每帧 RGB 32×32 | 模型输入 |
| 当前模拟本体状态 | 窗口末帧同时间的二维位置，除以31归一化 | 模型输入 |
| 示范动作 | 下一采样间隔水平位移 −2 / −1 / +1 / +2 像素 | 监督标签，不输入模型 |
| 模型参数 | 网络层的权重 / 偏置 | 初始化后通过训练调整，无预先给定正确值 |

动作由示范控制器生成并记录，不是模型自己生成真值。真实系统可来自遥操作或专家控制记录，仍需检查示范质量及时间对齐；示范命令与实际执行结果不是同一个概念。失败视频也不自动提供正确示范。训练产出调整后的参数及评估结果；模型运行时只用视频与状态输出动作，不要求示范标签。

### 函数与数据流

| 函数 / 类 | 做什么 |
|---|---|
| robot_video_data.make_fixture | 生成视频与动作 / 模拟状态清单，拒绝覆盖 |
| decode_rgb | 实际解码，返回 uint8 [帧,高,宽,通道] 与元信息 |
| VideoActionDataset | 按 episode 分组、检查同步、构建图像 / 当前状态 / 标签 |
| VideoStateModel.forward | 图像展平并提取特征，拼接状态，预测动作 |
| train_step | 预测、MSE、清梯度、backward、optimizer.step |
| train_epoch | 遍历全部 batch 更新一次，尾批按样本数计损失 |
| evaluate | 固定权重计算整集误差，无梯度更新 |
| fit | 记录未训练基线并重复整轮训练 / 验证 |
| save_checkpoint / load_checkpoint | 保存 / 恢复完整训练状态 |
| robot_video_resume_demo.main | 三种独立进程模式做续训对照 |

核心伪代码：

```python
for epoch in range(1, epochs + 1):
    model.train()
    for batch in train_loader:
        optimizer.zero_grad()
        prediction = model(batch["images"], batch["state"])
        loss = MSE(prediction, batch["action"])
        loss.backward()
        optimizer.step()
    validation = evaluate(model, val_loader)
    if epoch % 5 == 0:
        save_checkpoint(...)
```

这是把各函数展开的概念流程，实际 fit 不自动定期保存，演示入口在指定边界调用保存。model.train() 只切模式；backward 计算梯度；step 才更新权重；zero_grad 清梯度不清权重。MSE 是预测减标签、平方、再平均，不是错误率或百分比。

### 本课数据与模型的边界

16 段 FFV1 无损视频，每段 8 帧 / 8 fps / 32×32，先按 episode 分为训练 12、验证 4，再切 3 帧窗口；末帧后无动作记录，故每 episode 5 窗口，共 60 / 20 样本。输入 [0,1,2] 的状态取帧2，标签对应帧2→3，未来位置不能用于输入。

单样本 images=[3,3,32,32]、state=[2]、action=[1]，batch8 后分别为 [8,3,3,32,32]、[8,2]、[8,1]。模型将每样本图像展平为9216，Linear / ReLU 得32特征，与2状态拼成34，再得到1动作；是教学 MLP，不是生产视频策略架构。

当前小数据在 Dataset 初始化时全部解码缓存，不是生产大视频方案。1080p / 30fps RGB uint8 1分钟约11.2 GB，float32约44.8 GB；实际大数据应按窗口 / 顺序块读取、有限缓存与预取。每10帧处理可控制缓冲，但解码器内部和转换仍占内存；3帧窗口跨块须保留末尾2帧。压缩视频随机访问还可能从前面关键帧开始解码。

### 实测训练结果：拟合与泛化分开看

每轮 60 样本、batch8，7×8+4 共8次更新；30轮为240次。单步同 batch MSE 从3.1226降至2.9147，参数确实变化；完整曲线示例：

| 轮次 | 训练轨迹 MSE | 验证 MSE |
|---:|---:|---:|
| 0 | — | 2.5624 |
| 1 | 2.3981 | 2.8382 |
| 5 | 0.6525 | 4.3447 |
| 10 | 0.0876 | 4.1917 |
| 30 | 0.0008 | 3.8373 |

训练指标来自逐批变化的模型，验证指标来自轮末固定模型，计量时点不同。结果呈明显过拟合 / 泛化不足迹象，不宣称质量改善；观察范围内最佳验证值仍是未训练基线，更多训练不保证更好。数据量 / 覆盖、结构容量与训练设置等需另作对照诊断，不能把验证集混入训练来修饰结果。

### checkpoint 保存什么、实测恢复什么

本课限定 CPU / num_workers=0 / 整轮完成边界，保存模型 state_dict、Adam 状态与参数组、completed_epoch / global_step、配置、清单 SHA256，以及 Python / NumPy / torch CPU / 两个 loader generator 状态。没有梯度累积中途状态；其他自建 RNG / CUDA / 分布式状态不是自动全覆盖。数据清单指纹也不代替源文件生命周期与对象版本管理。

保存先写临时文件再发布完整文件，不覆盖旧版本；恢复先核验配置 / 数据 / 参数结构，再装回状态，最后恢复 RNG，避免新建模型消耗已恢复序列。只读取自己生成的可信本地产物。第5轮 / 40步 checkpoint 约3.58 MB；新进程恢复后验证 MSE 与保存时完全一致，下一轮从6开始。

三命令模式依次执行 prepare、resume、without-adam，使用同一 manifest 和新的 output-dir：

```bash
backend/.venv/bin/python -m backend.scratch.robot_video_resume_demo \
  --manifest backend/scratch/robot-video-lab/training-demo-state/manifest.json \
  --output-dir backend/scratch/robot-video-lab/training-demo-state/resume-comparison \
  --mode prepare
# 后续两次保持路径不变，将 mode 分别改为 resume、without-adam。
```

| 路径 | 总更新数 | Adam计数 | 最终权重相对连续训练 | 验证MSE |
|---|---:|---:|---|---:|
| 连续10轮 | 80 | 80 | 参考 | 4.1917 |
| 5轮保存，新进程完整恢复再5轮 | 80 | 80 | 逐项完全一致 | 4.1917 |
| 同权重与RNG，仅不恢复Adam再5轮 | 80 | 40 | 最大绝对差约0.0294 | 4.3428 |

完整恢复的 Adam、五类随机状态和后续曲线也严格一致，限本例固定CPU条件。跳过 Adam 丢的是 m / v 历史与计数，不是不能重新计算当前梯度；学到的权重保留，后续更新行为改变。重置不必然让质量更差，但不等于沿原过程精确续训。边界后未保存的进度仍可能重算；这次在已保存边界退出，没有模拟任意时刻故障。

### 关键单位与计费口径

- 十进制GB/TB：Mbps×一百万×秒数÷8÷十亿，得到GB。720GB允许4小时上传为400Mbps，允许8小时则为200Mbps；按GB计费的上传费用不会因窗口变长自动减半。
- 保留期积累满后的稳定逻辑容量=每日新增GB×保留天数。三副本物理占用再乘3；按逻辑GB且单价包含冗余时，月费不再乘3。副本物理占用未含元数据与空间余量，不直接当裸盘采购容量。
- 训练资源量=GPU数×占用小时×运行次数，不按GPU利用率打折。8卡×6小时为48GPU小时；16卡×4小时为64GPU小时，更快不一定更便宜。
- 8卡每月6次重复训练10分钟，是480GPU分钟=8GPU小时，不是480GPU小时。保存/加载实际占用GPU的时间和存储读写金额分开算，不把无GPU的排队时间计为GPU时间。
- 月净节省=原月费−新月费，可为负；只有为正时，简单回本月数=一次投入÷月净节省，否则输出null（Python None）。月净节省固定、未折现；内部资源折算费用下降也不一定代表可回收投入的现金节省。
