## 题目

### 题 1 · "我们每月 GPU 账单很高，你入职第一个月会怎么做？"（L07 第 6 步）

**答题框架**：量化 → 找最大头 → 按类出方案（等价 → 近似等价 → 有损）→ 红线验证 → 灰度上线 + 看板。

**参考回答**（约 1 分钟）：
1. **先量化**：拿账单按团队 / 任务拆开，同时接上利用率指标——GPU 分配率 vs 实际使用（DCGM）、MFU、排队时长、失败重跑次数。账单说明钱花在哪，指标说明浪费在哪。
2. **找最大头**：通常是三类——GPU **在等数据**（视频解码打满 CPU）、**占着不用**（闲置 notebook、调试任务独占整卡）、**白算**（失败后从头重跑、重复实验）；再加上**碎片**导致大任务排不上、被迫扩容。
3. **先做等价优化**：GPU 解码 / 离线预处理 / 预计算冻结特征 / 本地缓存；回收闲置、小任务用 MIG 共享；checkpoint + 断点恢复；装箱调度防碎片；可中断任务用低价资源。**再做近似等价**：BF16 等，需验证。降分辨率、换小模型这类**有损**方案只提出数据，和算法团队一起决定。
4. **质量红线不变**：沿用现有评估标准（离线指标 → 仿真 → 真机），A/B 只改一项、多随机种子。
5. **灰度上线**：先在部分队列 / 任务开启，看成本看板和质量指标，没问题再全量；随时可回滚。目标用**单位成本**汇报：每有效训练小时成本、MFU 提升多少。

### 题 2 · 共享 GPU 集群的调度优化（L08 综合口述，已完成）

场景：私有云有 4 台 GPU worker，每台 4 卡，共 16 卡，暂不加机器、不改模型与训练数据。训练任务可能需多个 worker 同时到齐，多个团队共用集群。观察到部分训练 worker 占卡等同伴、总空闲卡不少但整机任务 Pending，以及紧急训练到来时缺少可控的资源交接机制。

请口述：怎样安排整体准入、团队资源份额与空闲借用、紧急任务处理、减少节点碎片，并说明如何减少训练中断的损失；上线后用哪些指标验证改善？

**我的第一轮回答**：

1. 使用 Kueue 配置整体准入，避免多个任务各拿到部分 GPU、达不到运行所需数量而互相等待。
2. 配置自定义 kube-scheduler，使任务尽量放在 GPU 已分配比例高的节点，减少碎片。
3. 使用 withinClusterQueue=LowerPriority，让低优先级任务退出让出资源，并保存 checkpoint。

**点评**：三点方向正确。更准确地说，Kueue 按整体需求准入但不保证所有 Pod 原子启动或物理节点可放下；MostAllocated 在先满足资源、污点等硬约束的节点中评分，可配置原生调度器，不要求开发新算法；LowerPriority 还需任务优先级配置，并只描述队列内部抢占，跨团队份额回收是另一条策略。checkpoint 须持久化且新进程主动加载，光“保存”不足以恢复。

**待补齐**：团队 ClusterQueue 名义份额、Cohort 空闲借用与回收边界，以及验证指标。下一问先补团队资源管理，再补指标。当前不将口述题标为完成，也不把模拟 GPU 调度实验表述为真实训练性能测试。

**团队配额追问的回答**：甲乙各自有独立 LocalQueue，各 8 卡，设置 borrowingLimit / lendingLimit，但共同指向一个 16 卡 ClusterQueue，并让 LocalQueue 关联 Cohort。

**纠正**：入口分开和借入 / 借出含义正确，配额和关联层级需修正。甲 LocalQueue → 甲 ClusterQueue（8 卡及借用上限）；乙 LocalQueue → 乙 ClusterQueue（8 卡及借用上限）；两个 ClusterQueue 的 cohortName 均指向同一 Cohort。LocalQueue 没有本实验中的 nominalQuota / borrowingLimit / lendingLimit 字段，也不直接加入 Cohort；共同指向一个 16 卡 ClusterQueue 不会定义各 8 卡份额。16 是两队名义额度之和，不需要另建 16 卡 ClusterQueue。

继续确认：甲运行 12 卡任务（自身 8、借入 4）时，total=12 / borrowed=4 应出现在哪个 ClusterQueue 的状态里？用户回答“属于甲的状态”，正确；借入额度计入使用方的账本。随后进入最后的指标追问：如何验证调度优化效果，尤其要区分 GPU 分配率和实际计算利用率，并考虑排队 / 完成时间、吞吐与抢占重算成本。等待用户先提出指标，再补充点评。

**指标追问的回答**：

1. 看 Pending Pod，或 GPU 当前使用率。
2. 看 Job 从 suspend=true 到 false 花多久，应该缩短。
3. 统计 Pod 被驱逐时生成的 checkpoint 数量。

**点评**：

- GPU 实际利用率方向正确；还需对比分配率，识别占卡不算的任务。Pending Pod 要看数量、持续时长和原因；未准入 Job 可能没有 Pod，所以必须同时看 Kueue Pending Workload，不能只看 Pending Pod。
- suspend 状态可辅助观察，但重排队 / 抢占会多次改变它。分别量化首次提交到准入的排队时间、准入到所需 Pod 全部就绪的时间、端到端完成时间。按团队 / 优先级看 P50/P95 以及总吞吐，不能要求所有任务等待都下降：紧急任务变快可能以普通任务等待变长为代价。
- 驱逐时 checkpoint 次数不直接衡量损失。应观察保存成功率、耗时、最近完整 checkpoint 到抢占时的未保存进度，以及恢复后的重复计算步数 / GPU 时间、启动加载时间。退出补存成功时损失可能很小，失败时回到定期 checkpoint。checkpoint 太频繁也有 I/O 和存储成本。

成本检查题：8 卡任务最近一次成功 checkpoint 为 10:00，10:06 被抢占且补存失败，之后从 10:00 恢复。重复计算约多少分钟，折合多少 GPU 分钟？暂不计重新启动 / 加载开销。用户回答“需要 6 分钟，8×6=48 GPU 分钟”，正确，相当于 0.8 GPU 小时。

收尾前用户追问 LocalQueue 的意义，已用 dev / eval 两个 namespace 共享一个 8 卡 ClusterQueue 的例子讲解：LocalQueue 是 namespace 内入口、ClusterQueue 是共享账本，两者可多对一；需要 LocalQueue 对象但不要求独立 YAML 文件。用户确认两入口合计仍为 8 卡。继续等待是否还有疑问，尚未进入下一课。

**最终参考回答**（将上述回答与追问整理成口述版）：

我先把 GPU 分配情况、实际利用率、队列等待和节点分布量化，区分配额不足、部分分配和资源碎片。对固定规模分布式训练，用 Kueue 按整个任务的资源需求准入，避免任务各占一部分卡等同伴；同时检查节点容量和拓扑，因为配额够不代表 Pod 一定放得下。

团队之间分别设置 ClusterQueue 名义份额，通过 namespace 内的 LocalQueue 提交任务；将团队队列放入同一 Cohort，在上限内借用空闲额度。紧急任务配置较高的 Workload 优先级，按规则抢占低优先级任务；同队列抢占和跨队列份额回收分别配置，避免无边界地驱逐。

对碎片问题，配置 kube-scheduler 的 GPU MostAllocated 评分，让新小任务倾向集中放置，保留完整空闲节点；这不会自动搬迁现有 Pod，已有碎片需另行安排任务退出 / 重建，并评估中断成本。被抢占的训练任务定期保存持久化 checkpoint，优雅退出时争取补存，新进程启动后加载恢复，避免从头训练。

验证时对比分配率和实际 GPU 利用率，按团队 / 优先级看排队与完成时间 P50/P95、任务吞吐，以及 worker 等待 / 碎片导致的 Pending 时间；同时核算抢占后的重算 GPU 小时、保存和恢复耗时。先在部分任务上灰度，保持训练质量评估标准，验证单位有效训练成本下降，再扩大范围。

**可讲的实操证据**：在本地 kind 4 worker × 4 张模拟 GPU 环境复现了部分分配、Kueue 整体准入、团队借用与份额回收、队列内优先级抢占及重新运行；复现总空闲 12 卡却放不下单个 4 卡 Pod，再通过人工集中与独立 MostAllocated 调度器验证可调度性改善。只证明调度行为，不声称测过真实 GPU 性能或真实训练 checkpoint 恢复。

**最终状态**：用户确认其余问题已解决，可以收尾；本题完成。后续面试题必须先确认上一题无疑问再切换。

### 题 6 · 视频压缩与端侧筛选如何安全降成本（L12，已完成）

**场景**：真实数据上的候选筛选规则令准备上传的字节减少 60%，尚未验证训练质量和完整端侧开销。怎样检查误丢、核算收益并安排上线？60% 为题目假设，不是合成实验的生产结论。

**我的回答**：与原视频集比较，检查筛选后是否保留失败视频；计算筛选的计算量 / 时间和最终训练质量影响；逐条增加规则，一轮验证后再加下一条。

**点评**：方向正确。不能只看“有失败视频”，还要按失败 / 长尾类型统计保留率并抽查被排除数据，必要时人工补标，给未知事件保留探索样本。成本计入端侧解码、评分、重编码、能耗和运行 / 实施开销，云端收益按实际变化算。规则逐条验证便于归因，上线范围也应渐进；影子运行保留原数据，小范围启用后再扩大，关闭规则不能找回已永久丢弃数据。

**参考口述**：

我先固定源素材与其他编码参数，分别对照 CRF、分辨率和帧率，测实际字节和完整处理开销。容器不是编码方式，相同 MP4 或相同 CRF 不保证任务质量相同。像素指标和局部检查可发现压缩损失，但最终要用既定机器人任务评估，并保持观测、时间和动作对齐。

端侧按完整片段选择，避免直接删帧后破坏时序。平均变化小可能掩盖局部关键事件，静止也可能有价值；已知失败 / 任务事件可以保护片段，但事件源漏报仍可能漏选。与原数据对照，按失败和长尾场景统计保留，抽查被排除部分并保留探索样本，验证训练后的质量底线。不能把少传 60% 等同总成本下降 60%。

最后核算上传、后续存储与处理的真实收益，减去端侧和运维增量。先影子运行记录候选决策且保留原数据，再在代表性小范围启用，一次改变一条规则便于归因；监测质量、积压、处理延迟与资源，配关闭开关和留存策略，通过门槛再扩大。

**可讲实操证据**：在 FFmpeg 7.1 上，同一 8 秒合成无损源，H.264 CRF18 / CRF28 文件约 1.166 / 0.423 MB，PSNR 约 49.12 / 39.34 dB；降低分辨率 / 帧率也实测大小与完整解码。另一组真实编解码玩具视频中，2×2 局部事件平均差约 0.102，被阈值 1 漏掉，加人工模拟 contact 标记后保留。10 项新测试和完整 240 项回归通过。没有真实机器人质量评估，不声称这些比例可直接用于生产。

### 题 7 · 解释视频与状态训练，以及如何正确续训（L13，已完成）

**场景**：用本地 CPU 真正读取合成视频与对齐的模拟状态，预测示范动作，训练并演练跨进程恢复。请说明输入 / 标签来源、参数怎样更新、质量怎样判断，以及为什么只保留权重不足以精确续训。

**主要课堂回答与点评**：

- 单帧无法确定运动趋势，需要连续帧；但趋势不是任意真实任务的正确动作，标签仍由示范记录提供。
- 把未来状态用于当前输入会泄漏信息；本例在 0.25 秒只使用截至当时视频与位置，预测随后动作。
- 训练损失接近 0 不代表新 episode 表现好，还要看验证；数据可能影响泛化，但曲线不单独锁定原因。
- 仅恢复权重后“梯度信息丢失”的方向正确，更准确是 Adam 的 m / v 和计数丢失，当前梯度仍重新计算。
- 用户要求逐函数细读，已依次讲数据生成、解码、Dataset、入口、模型结构与前向、MSE、单步 / 单轮 / 多轮训练、评估和 checkpoint。特别解释 reshape 不理解图像语义、batch 维与图像维、全量缓存仅用于小实验。

**参考口述**：

输入是过去几帧视频和当前本体状态，训练数据另外提供示范动作标签。模型先预测动作，用 MSE 衡量预测与示范的差距；反向传播计算各参数对误差的影响，Adam 根据当前梯度及历史状态修改权重。按 batch 更新、遍历样本构成一轮，重复多轮后用独立 episode 验证，不能把训练拟合当泛化达标。

我们并不知道正确参数是多少，已知的是示范者在相应观测下做过什么。标签要有可靠来源并对齐；本课是合成脚本与模拟位置，不是实际传感器噪声、异步采集或真实机器人策略。模型前向输出动作，训练主要产出调整后的参数与评估结果；保存完整 checkpoint 还包括优化器、进度、配置、数据版本和随机状态。

恢复时先创建相同结构模型和优化器，检查数据 / 配置，装回权重与 Adam，再恢复随机状态，从已完成轮的下一轮继续。我们比较连续 10 轮与保存 5 轮后新进程完整续训，最终权重、Adam、随机状态和曲线完全一致；若只重置 Adam，其他条件相同，续训后仍会分歧。这是当前固定 CPU 条件的实证，不是所有 GPU / 分布式场景逐位一致的保证。

**实操结果与质量边界**：16 段真实编解码合成视频，训练 12 episode / 60 窗口，验证 4 / 20。30 轮训练 MSE≈0.0008，但验证≈3.8373，高于未训练≈2.5624，呈过拟合迹象。完整续训到第 10 轮验证≈4.1917；不恢复 Adam 则≈4.3428，最大权重差≈0.0294。没有真实机器人评估，不声称质量达标；checkpoint 与模型质量分别验证。
