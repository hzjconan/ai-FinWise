## RAG（检索增强生成）

**RAG = Retrieval-Augmented Generation**。解决大模型两个硬伤：① 不知道你的私有数据；② 装不下太多数据（context 有上限、按 token 计费）。

思路很朴素：**别让模型硬记，临时查给它看**。用户提问 → 先从你的数据里**检索**出最相关的几条 → **塞进 prompt** → 模型**基于这几条**回答。

> 类比：**开卷考试**。模型不用背，你把相关那几页翻开摆它面前。

对应 FinWise：产品库模型没见过，用 RAG 让它能回答"有没有适合养老、波动小的产品"这类自然语言需求。

## Embedding / 向量

**embedding = 一个函数：把一段文本 → 一串固定长度的数字（向量）。** 例如 `multilingual-e5-small` 输出 384 个浮点数。

```
"养老储备"      → [0.02, -0.11, 0.34, …]   # 384 维
"退休后的钱"    → [0.03, -0.09, 0.31, …]   # 跟上面很接近
"科技股高波动"  → [-0.20, 0.15, -0.05, …]  # 跟上面差很远
```

关键：这个函数是**专门训练**出来的，目标是 **意思相近的文本 → 向量也相近；意思无关 → 向量差很远**。

- 向量长度（维度数，如 384）由模型设计时定；维度越高一般表达越细，但更慢更占空间。
- 单个维度人看不懂，是模型学到的某种"语义特征"；**整体位置**才编码意思。

## 为什么"语义近 → 向量近"（对比学习）

疑问：为什么两个语义相近的字符串，转出来的向量**恰好**相似度也高？

**不是"恰好"，是训练特意训出来的。** 破除错觉：模型不"理解"养老，它只是台函数（吃 token 吐数）。凭什么这些数和意思对齐？——因为训练时有个目标函数逼它这么做。

**对比学习（contrastive learning）**：喂海量**配对**——正样本对（该近，如"适合养老的基金"↔"为退休储备设计的产品"）、负样本对（该远，如"养老基金"↔"科技股高波动"）。损失函数一句话：**正样本对余弦要大（拉近）、负样本对余弦要小（推远）**。反复微调那 1.18 亿参数，直到"人类觉得相关的配对，算出来余弦都大"。于是语义关系被**压进了向量的几何位置**——"养老"和"退休储备"向量近，是被无数类似相关对反复"拉近"的结果，不是巧合。

**关键：没见过的新句子为什么也对？——泛化**。模型不是背下某一对，而是学会了"把语义映射成坐标"的**通用规则**（藏在参数里，作用在词/字层面）。新句子进来，按这套规则组装成向量，自然落到语义邻居附近。类比：没背过 1234×5678，但学会乘法规则照样算。

**余弦的角色**：它**不产生语义**，只是把"向量方向多一致"读成一个数。因果是——**先有训练让向量有意义，余弦才有意义**。拿没训练的随机模型 encode，"养老"和"退休储备"余弦就是随机的。

> 反证（正好接 s4_03）：**TF-IDF 向量不是训练出来的**，是机械数词频，每维死板对应一个字面词，从没有机制把"养老"和"退休储备"关联起来——所以同一把余弦尺子，量 embedding 高分、量 TF-IDF 低分。**差别不在尺子，在向量有没有被训练赋予语义。**

## 训练数据哪来的（自监督 / 自动造对）

疑问：海量语义对不可能人工一条条标注吧？**对，根本没这么干。** 数据绝大部分**自动从现成文本造出来**——叫**自监督（self-supervised）**，是现代 AI 能 scale 的根本。

**核心：让数据自己标注自己**。利用文本自带结构自动生成"相关对"，不用人判断：
- **天然共现**：同一篇文章里相邻两段 → 自动当正样本对（同源相邻=大概率相关）。
- **天然配对**：互联网现成的 标题↔正文、FAQ 问↔答、维基标题↔摘要——爬下来直接用。（e5 大量用"query-passage"对训练，这也是它要 `query:`/`passage:` 前缀的原因。）
- **负样本几乎白送**：正样本的 query 配一段随机抽的文本 → 大概率无关 → 天然负样本，要多少有多少。

**怎么喂**：不是一条条，是成批自动流水线——① 爬海量文本自动切成"对" → ② 一批几千对，模型各自 encode → ③ 损失函数自动算正/负样本余弦对不对 → ④ 反向传播自动调参 → ⑤ 换下一批，重复几十亿步。**全程无人在环**，人只做两件事：设计"自动造对的规则" + 写损失函数。所以能 scale（瓶颈是算力/数据，不是人力）。

**批内负样本（in-batch negatives）**：一批 N 个正样本对，对第 1 对的 query 而言，其余 N-1 对的 passage 全当它的负样本 → 一批自动产生 N×(N-1) 个负样本，一份数据榨出海量对比信号，几乎零成本。

**人工标注还有吗？** 有但占比极小：**预训练**（学通用语义）几乎全自监督（海量、免费、脏但管用）；**微调/对齐**（冲精度）用少量高质量人工标注精修。规律：**海量脏数据（自动）打底 + 少量精标（人工）提纯**，绝大多数能力来自前者——正因为它不靠人、能 scale。

## 文本长度 → 向量维度（定长输出 / 池化 / 截断 / chunk）

疑问：一个字 vs 一篇文章，都转成 384 维吗？**是——输出永远固定 384 维，与输入长度无关。** 但有三层要点：

**① 为什么必须定长**：余弦只能比同维度向量。embedding 的使命就是把任意长度文本压成统一大小，才能互相比较。

**② 怎么做到长度无关——池化（pooling）**：内部是"每个 token 一个 384 维向量"，长文本 token 更多、中间向量更多；再用**池化**（常见 mean pooling=取平均）把 N 个向量压成 **1 个**。N 多少无所谓，平均完永远 1 个 384 维。
```
"养老储备"→3 token→[v1,v2,v3]  ；一段话→60 token→[v1…v60]   （每个 384 维）
                    │ 池化（取平均，N→1）
                    ▼   一个 384 维句向量
```

**③ 硬上限：最大 token 数（截断）⚠️**：模型有最大输入长度（e5-small≈512 token），**超出部分被悄悄截断丢弃**。一篇 2000 token 的文章，只有前 ~512 token 参与编码——"整篇进去了"是错觉。

**④ 即使没超限，长文压一个向量会"糊"**：一篇多主题长文压成一个向量 = 所有意思被平均成一团，检索变模糊。**这正是 RAG 要 chunking（分块）的原因**：长文档切成小段、每段单独 embedding，每个向量代表聚焦片段，检索才精准。（chunking 是阶段四后续主题。）

| 输入 | 输出 | 说明 |
|---|---|---|
| 一个字 / 一句话 / 一段（≤512 token） | 384 维 | 池化后定长、完整表达 |
| 一篇长文（>512 token） | 384 维 | **超出被截断丢弃** |

一句话：**输出定长（靠池化）、输入有上限（超了截断）、长文压一个向量会糊 → 长文档先 chunk 再逐段 embedding。**

## 向量空间与语义

把每段文本想成 **N 维空间里的一个点**（N=向量维度）。embedding 训练的结果就是：

> **意思近 = 空间里位置近。**

"养老储备"和"退休后的钱"会挤在一块，"科技股"在很远的另一片区域。于是"找意思相近的文本"就变成了"找空间里离得近的点"——一个纯几何问题。

## 点积与模长（余弦公式的两块积木）

### 模长 ‖a‖ —— 向量的"长度"

**每个分量平方、求和、开根号**，本质是勾股定理推广到 N 维：

```
2D:  a=[3,4]         ‖a‖ = √(3²+4²) = 5           （就是勾股定理）
N维: a=[a₁,…,aₙ]     ‖a‖ = √(a₁² + … + aₙ²)
```
numpy：`np.linalg.norm(a)`（= `np.sqrt(np.sum(a**2))`）。

### 点积 a·b —— 逐位相乘再相加，得到一个数

对应位置相乘再全部加起来，结果是**一个标量**：
```
a·b = a₁b₁ + a₂b₂ + … + aₙbₙ
[1,0]·[1,1]=1    [1,0]·[0,1]=0（垂直）    [1,0]·[-1,0]=-1（反向）
```
它衡量两向量**方向多一致（对齐程度）**——因为 `a·b = ‖a‖‖b‖cosθ`：一致→大正数，垂直→0，相反→负。

**为什么"逐位乘加"= 对齐？** 单看一项 `aᵢbᵢ`：同号→正（这个轴上一致）、异号→负（相反）；把所有轴的一致/相反加总，就是整体对齐度。

numpy：`np.dot(a, b)`。

### 隐藏联系：`a·a = ‖a‖²`

向量和自己点积 = 模长平方（自己跟自己夹角 0、cos=1）：`a·a = a₁²+…+aₙ² = ‖a‖²`。所以 `‖a‖ = √(a·a)`——点积是更基础的积木，模长是它的特例。

### 拼回余弦
```
cos(a,b) = (a·b) / (‖a‖·‖b‖)
         =  对齐程度(含长度) ÷ 各自长度 = 纯方向的一致性
```

## 余弦相似度

有了向量，要一个**数值**衡量两个点多"像"。最常用的是**余弦相似度（cosine similarity）**：看两向量的**夹角**。

```
夹角小 → 方向几乎一致 → 很像 → cos ≈ 1
垂直   → 不相关          → cos = 0
反向   → 相反            → cos = -1
```

范围 `[-1, 1]`。公式：

```
cos(a, b) = (a · b) / (‖a‖ · ‖b‖)
```

- **`a · b`（点积）** = `a[0]*b[0] + a[1]*b[1] + …`，衡量两向量"对齐"程度；
- **`‖a‖`（模长/范数）** = `sqrt(a[0]² + a[1]² + …)`，箭头长度；
- 除以两个模长 = **把长度归一化掉，只留方向（夹角）**。

**为什么只看方向、不看长度？** 向量长度往往反映文本长短等无关因素，**方向**才编码意思。两段话意思相同、一长一短，仍应算"很像"——除掉模长正好做到。

小例子：
```
a = [1, 0];  b = [1, 1]
a·b = 1;  ‖a‖ = 1;  ‖b‖ = √2 ≈ 1.414
cos = 1 / (1 × 1.414) ≈ 0.707    # 夹角 45°，中等相似
```

> 若向量已**归一化**成单位长度（模长=1），则 `cos = a·b`（分母为 1，省了）。

## 余弦公式怎么来的（和直角三角形 cos 的关系）

疑问：直角三角形里学的是 `cos θ = 邻边 / 斜边`，跟 `cos(a,b) = (a·b)/(‖a‖‖b‖)` 什么关系？

**答：是同一个 cos θ，只是一个"用角度算"、一个"用坐标算"。**

**① 直角三角形的 `cos=邻/斜` 定义的是角 θ。** 把向量 `a` 当斜边（长 `‖a‖`），向 `b` 方向作垂线，落在 b 上的影子就是邻边：

```
        a
       /|
 ‖a‖ /  |     θ = a、b 夹角；斜边=a（长 ‖a‖）
     /θ__|__→ b   邻边 = a 在 b 方向的投影 = ‖a‖·cosθ
```

**② 点积正好打包了 `‖a‖‖b‖cosθ`**：`a·b` = "a 在 b 方向的影子长度 `‖a‖cosθ`" × "b 的长度 `‖b‖`" = `‖a‖‖b‖cosθ`。两边除以 `‖a‖‖b‖`，就把角度单独解出来：`cosθ = (a·b)/(‖a‖‖b‖)`。**这就是余弦相似度——不是新定义，是用坐标反算那个 cosθ。**

**③ 为什么 `a·b = ‖a‖‖b‖cosθ`（用余弦定理证）**：对 a、b 张成的三角形，第三边是 `a−b`：
```
余弦定理： ‖a−b‖² = ‖a‖² + ‖b‖² − 2‖a‖‖b‖cosθ
坐标展开： ‖a−b‖² = (a−b)·(a−b) = ‖a‖² + ‖b‖² − 2(a·b)
两式相等 ⇒ a·b = ‖a‖‖b‖cosθ    ∎
```

**④ 为什么非用公式**：2D 能画图量角，但 embedding 是 384 维，"看"不到角。公式的价值 = **纯靠坐标（点积+模长）算出夹角的 cos，把"邻边/斜边"推广到任意维度**——这才能用在语义检索上。

## 关键词匹配 vs 语义检索

| | 怎么比 | 软肋 |
|---|---|---|
| 关键词匹配（`LIKE '%养老%'`） | **字面**词是否重合 | 问"养老"、文档写"退休储备"→ 一字不重合 → **漏掉**，尽管意思一样 |
| 语义检索（embedding + 余弦） | **意思**（向量空间位置）是否接近 | 需要模型编码，成本略高；但能跨字面匹配意思 |

这就是 RAG 用 embedding 而不用关键词的根本原因。（TF-IDF 是"高级一点的关键词匹配"——仍是字面词频，见 s4_03 的对照实验。）

### 真机对照实证（s4_03：同一 query、同一检索核心，只换 encoder）

| query | embedding | TF-IDF |
|---|---|---|
| 养老、能放很多年 | 养老2040 **0.89** | 养老2040 **0.17** |
| 能随时取、基本不亏 | 货币A 0.89 | 货币A 0.36、养老2040 **0.00** |
| 大波动博高收益 | 科技股 0.92 | 科技股 0.27、纯债 0.06 |

三个直击本质的观察：
1. **分数量级天差地别**（embedding ~0.9 vs TF-IDF ~0.0–0.3）：TF-IDF 向量没经对比训练，余弦读不出语义，只靠字面偶尔重合，202 维里绝大多数是 0 → 分数天生低。
2. **出现 `0.00`——字面零重合铁证**："随时取/不亏" vs 养老文档没有一个共同 bigram → 向量正交、余弦精确为 0。关键词匹配的死穴：**没共同的字＝毫无关系**，哪怕意思沾边也看不到；embedding 对同一对给了非零分。
3. **TF-IDF 命中也靠字面巧合**："养老"这条 TF-IDF 竟也命中养老2040，但只 0.17——因为文档恰好也含"养老"这个词；若文档只写"退休储备"，TF-IDF 就会像第 2 条那样掉到 0.00。**embedding 不依赖巧合，它认意思。**

一句话：**同一把余弦尺子、同一套检索核心，只换"怎么造向量"——差别不在检索，在向量有没有被训练赋予语义。**（呼应 [[为什么语义近-向量近对比学习]]。）

## embedding 打分特性（分数压缩 / 话题 vs 极性 / 为什么 top-K）

真机跑 s4_01 后观察到的"能用但不完美"特性——很实用的认知，别把语义检索神化：

**① 分数压缩在高窄带**：e5 余弦分数常挤在 0.7~0.95。**绝对值没意义，只有同一个 query 内部的相对排名有意义**。别拿"cos>0.9"当"很相关"的绝对阈值。

**② 抓"话题相似"强，抓"立场/极性对立"弱**：同领域文本（都在讲基金/投资/收益/风险）话题高度重叠 → 彼此都"挺像"，所以语义**相反**的也可能排很高（query"博高收益"检出"稳健纯债"）。embedding 抓 aboutness 好、抓细微极性差弱——小模型、短 query 更明显。

**③ 有时 top-1 都不对**：表层结构相似可能压过语义内容（"养老长期"query 命中"活钱短期"货基）。

**启示**：
- **取 top-K 不取 top-1**：#1 不总对，检索给若干候选、交给后面的 LLM 甄别（RAG 的"生成"半段）。
- 提升精度靠 **re-rank / 更大模型 / chunking**；small 模型"够学不够精"。
- "检索到底多好"该用 **eval 量化**（如 top-K 命中率），不是凭感觉。

## 完整 RAG 管线

```
【离线，只做一次】
  所有文档 ──encode──▶ 一堆文档向量，存起来（doc_vecs）

【用户每次提问】
  query ──encode──▶ query 向量
                      │
     对每个 doc_vec 算 cosine_similarity(query_vec, doc_vec)
                      │
            按分数降序，取前 k 个（top-k 检索）
                      │
   把这 k 篇文档塞进 prompt ──▶ 模型基于它们作答（生成）
```

对应 `scratch/s4_01_rag_embedding.py`：`CORPUS`（文档）→ `encode_docs`（向量化）→ `cosine_similarity` + `retrieve_top_k`（检索）。生成那步在 s4_02。

## 向量数据库：手搓检索的「生产化升级」（s4_05）

s4_01 是**内存 list + numpy 手算余弦 + for 循环逐条比**（O(N) 暴力）。向量数据库（Chroma/FAISS/pgvector…）把这套**同样的**「文本→向量→比距离→top-K」做成了能落盘、能过滤、能扛量的产品——**本质没变，只是工程化**。三大增值：

| | s4_01 手搓 | 向量数据库 |
|---|---|---|
| **持久化** | 进程内 list，一停就没、每次重算 | 落盘，建一次索引反复用（进程重启不丢） |
| **检索速度** | O(N) 逐条暴力扫 | **ANN 近似最近邻索引**（HNSW：多层"小世界"导航图，亚线性，百万级毫秒返回） |
| **元数据过滤** | 没有 | `where={...}`：**先按结构化条件筛，再在子集里算相似度** |

- **ANN 的取舍**：为了快，它**不保证**每次都返回严格 top-K（可能漏个别真最近的）——"**速度换召回**"，上索引要用 Hit@K/MRR 复核（接回 eval）。
- **距离度量**：文本检索要显式用 **cosine**（`distance = 1 - 余弦相似度`，越小越近）；默认 L2（欧氏）会因长度差异排出怪结果。
- **运行形态**：`PersistentClient` = **嵌入式**（像 SQLite，无服务、无启停、数据即文件、**单进程独占、无事务**）；多进程并发要升 **服务端**（`chroma run`+`HttpClient`，像 Postgres）；要真 ACID 事务选 **pgvector**。
- **真机彩蛋（s4_05）**：query「基本不会亏的」把"科技股票"排进前列——**embedding 话题>极性**（[[embedding-打分特性分数压缩--话题-vs-极性--为什么-top-k]]）的复现；而加 `where={"risk_level":"C3"}` 后它就被挡在外——**印证"关键场景不能只信向量分数、要靠元数据/业务规则兜底"**（过滤值从哪来见下节 Agentic RAG）。

> API / 部署 / 并发 / 事务的**细节**在单独的工具讲义 `chroma-primer.md`（本文只讲概念）。

## Agent 怎么决定「何时检索 / 从哪个库检索」（Agentic RAG）

上面的完整管线默认了"就是要检索、且从这个库检索"。但**通用 agent**（比如客服 agent）事先不知道用户会问什么、目的是什么、该查哪个库（产品库？合规库？FAQ？）。"**何时检索、从哪检索**"这个决策本身，就是可以交给模型的判断。按"你对用户意图的确定程度"分三种模式：

### 模式 1：静态 RAG——你**已知**意图

agent 目的单一（如 FinWise 产品匹配：用户来就是找产品）→ **每次都从那个已知的库检索**，无需判断。简单、确定、可控。**只要 agent 干一件明确的事，就用这个，别过度设计。**

### 模式 2：检索即工具（Agentic RAG）——通用 agent 的主答案

把**每个知识源做成一个独立工具**，靠工具的 **name + description** 告诉模型"什么时候该用我"：

```
search_products    "当用户想了解、比较、咨询理财产品时使用"
search_compliance  "当用户问到监管、合规、资质、风险披露相关问题时使用"
search_faq         "当用户问账户操作、使用流程等常见问题时使用"
（没有工具匹配 → 模型直接回答 / 转人工）
```

然后就是熟悉的 agent loop：模型读用户输入 →**匹配到哪个工具描述就调哪个**（可多源组合，如"这产品合规吗"→ 同时调 products + compliance）→ 结果回喂 → 生成。**"何时检索、检索哪个"的逻辑全写在工具描述里**——所以工具描述质量是关键（见 [[reference_field_order_affects_output]]「schema 即 prompt」）。

### 模式 3：路由器（Router / 意图分类）——更可控、更省的变体

先用一个**轻量分类步骤**（一次小 LLM 调用，或基于 embedding 的"语义路由"）判断"这问题属于哪个域"，再**硬路由**到对应检索器（或不检索）。LangGraph 里就是一条**按意图分流的条件边**。

| | 谁决定检索 | 特点 |
|---|---|---|
| **Agentic（模式2）** | 模型在 loop 里自己调工具 | 灵活、能多源组合；多一次往返、可控性弱 |
| **Router（模式3）** | 先分类再硬路由 | 快、便宜、可控、可 eval；分类错则路由错 |

### 两道必须补的护栏（通用 agent 尤其重要）

1. **必须有"不检索"这条路**：用户问的东西哪个库都不覆盖（闲聊、投诉、转人工），强行 RAG 只会灌噪声、烧 token。模型/路由要能选"都不匹配 → 直接答 / 转人工"。
2. **检索到 ≠ 相关，要有「相关性闸门」**：开放问题容易检索出"最不烂但其实不相关"的一堆（embedding 分数压缩，它总能排个序）。**卡相似度阈值**：top1 低于阈值就当"无相关资料"，走 grounding 的"资料不足就说不知道"，别硬编。

### 关键路径去模型化（接 [[reference_pricing_agent_orchestration]]）

对**有财务/合规后果**的问路，"选哪个源"本身也可能**不该完全交给模型自由裁量**——如**合规类问题硬路由到合规库**（甚至强制走确定性流程），而非赌模型每次挑对工具。这是"关键路径去模型化"往检索路由上的延伸。而"模型选工具/路由准不准"**也可 eval**：备一批 `(用户问题 → 该触发哪个工具)` 的 golden set，量"工具选择准确率"——又接回 eval。

### 元数据过滤的「过滤值」从哪来（关键：不是从 query 文本猜的）
向量库给你 `where={"risk_level":"C3"}` 这个**过滤机制**，但"这次该填 C3 还是 C5"这个**值**是 harness/编排层的决策，**不来自解析用户那句话**。三个正当来源，按重要性：
1. **用户画像/状态（最主要）**——值是**你早就算好、存着的**。FinWise 里"这人是 C3"是**风险评估（确定性定级 B#7）的输出**，存进画像；推荐时**编排代码从画像取出注入**，不是从"攻守兼备"反推。→ 即 [[reference_pricing_agent_orchestration]]「关键值别信模型」往检索上的延伸：**风险等级是权威状态，不是从当前句子解析的**。
2. **query 里明说的软偏好**——用户主动说"只看债券/要低风险"，可用 LLM **slot-filling（槽位抽取）** 解析成过滤条件。但两条铁律：**抽出的值必须校验白名单**（模型可能吐库里没有的枚举）；**软偏好服从下面的硬规则**。
3. **合规/适当性硬规则**——代码强制的护栏。C2 用户**不管嘴上要什么**都不该被推 C5（适当性管理）；真正约束常是 `risk_level ≤ 用户可承受上限`，由代码按画像+合规策略算出，**用户和模型都改不了**。硬约束永远赢。

**已在 FinWise 落地**：`search_products` 的 `MATCH_RULES`（C→R 映射）就是这个 `where` 的"规则表版本"——按等级圈定可推产品；等级值取自 `conclude` 的确定性定级，编排代码注入。所以"过滤值来自权威状态"这条你早已在做。
**通用 agent（无预知用户态）**：有用户态用用户态 → query 明说的抽取+校验 → 合规硬加 → **都没有就不加 filter**（别硬凑）。

**一句话**：已知意图 → 静态 RAG；开放意图 → 把库做成工具让模型选（Agentic）或先分类再路由（Router），加"可以不检索"+"相关性闸门"两道护栏，关键路径再考虑硬路由去模型化。**过滤值来自认证过的用户状态 + 代码算的业务/合规规则，不是模型从原文猜的。**

## Chunking（分块）：为什么切 / 怎么切 / 没有最优切法

### 为什么要切
真实文档是**多主题长文**（一份产品说明讲收益/风险/赎回/费用）。整篇压成**一个**向量有两个问题（承接 [[文本长度--向量维度定长输出--池化--截断--chunk]]）：① 超 512 token 被截断丢弃；② 就算没超，多主题被平均成一团"糊"，检索某个细节时被别的主题**稀释**。解法：切成小段、**每段单独 embedding**，每个向量代表一个**聚焦**片段。

真机（s4_04）：问"养老赎回限制"，整篇只能定位到"哪篇"（0.868，被稀释）；分块直接把"最短持有期一年"那段捞出来（0.913）——**分块能定位到"哪一段"、分数还更高**。

### 三种切法（s4_04 的 A/B/C）
- **A 整篇**：不切，一篇一向量。基线。
- **B 按句 + 定长硬切**：每句成块，超长句按 max_len 硬切。隐患：把一句话**拦腰截断**成无头碎片、短句碎成一堆。
- **C 按句 + 贪心合并**：句子是原子（绝不从句中切），短句攒进一块直到接近 max_len。代价：**单句超长时块会超 max_len**（贪心的取舍——保完整 vs 保长度，鱼与熊掌）。

### ★ 关键教训：没有普适最优的切法
s4_04 加"对抗性文档"（超长句 + 极短句串）让 B/C 差异显现，结果**反直觉**：
- query「全球分散对冲」：**B 硬切的碎片反而赢**（0.932 > C 0.907）——碎片恰好只含"全球分散对冲"、更聚焦；C 的完整长句掺了别的内容、被稀释。
- query「起投+定投」：**C 合并的完整块反而赢**（0.926 > B 0.919）——短句合成一个语义单元、信息更全。

→ **B/C 各赢一局**。这是 chunking 的核心张力：**块越小越聚焦（和精准 query 更对齐）但易丢上下文；块越大越完整但易被无关内容稀释。碎片有时是坏事、有时反是好事——取决于 query**。

**结论**：chunk 大小/切法是**需要 tune 的超参数**，最优值取决于文档结构 + query 粒度 + 用途。"更聪明的算法"不等于"检索分更高"——**怎么切好要用 eval 在真实 query 上量，不能凭直觉**（呼应 [[embedding-打分特性分数压缩--话题-vs-极性--为什么-top-k]] 和阶段五）。

### 真实系统还会考虑（本练习未做）
- **重叠 overlap**：相邻块留一点重叠，防一句话/一个语义被切在边界上丢失上下文。
- **按 token 而非字符**计数（对齐模型的真实上限）。
- **按结构切**：按标题/段落/markdown 层级切，比纯长度更贴合语义边界。
- 工程实现避免拼接 bug：用 `"。".join(句子列表)` 而非手动 `+= "。"`（否则易出 `。。`/句子粘连）。

### 切完怎么存：chunk 的 id 与出处（metadata）
一篇文档 chunk 成 N 段落进向量库（如 Chroma），就是 N 行：`embeddings`/`documents` 各 N 个，一一对应。每行还要配 **id** 和 **metadata**——这俩不是随便填：

- **id 用"可推导的确定性 id"**，别用纯随机：`{文档id}#chunk{序号}`（如 `P-TECH#c0`）或内容哈希。原因：① **幂等**——文档更新后重新入库能 `upsert` 覆盖同一批，随机 id 会每次多插 N 条重复；② **能整篇删/更新**——按 id 前缀或 `metadata` 里的 `source` 删掉这篇的所有 chunk。
- **metadata = 父文档属性（继承）+ 本块位置**，而不是"这段的语义摘要"（语义已由 embedding+document 负责）。典型字段：
  - 继承自父文档：`source`/`doc_id`、`product_code`、`risk_level`、`category`…→ 让你**先按业务条件过滤再语义检索**（`where={"risk_level":"C3"}` 只在 C3 产品的块里找）。
  - 本块位置：`chunk_index`（第几块，可用来取**相邻块**补上下文，治"切太小丢上下文"）、`page`/`section`（出处）。
- **出处（页码等）必须在"提取"时保留，事后无法从纯文本反推**。做法：解析器（如 `pymupdf`）**按页**给你文本+页号，chunking 时**带着页号切**、钉进 metadata——不是把整篇拍平再盲切。很多框架的 PDF loader 会自动给每块附 `page`。
  - **一个 chunk 跨两页**很常见（块边界按 token 定、不管页边界）。处理：记范围 `page_start/page_end`（最诚实）、或记起始页（够引用用）、或按页边界切（出处最干净但可能切碎跨页内容）。
- **为什么这套重要**：`source`/`page` 就是 grounding 里的 **citation**——命中后能告诉用户/模型"答案来自《XX说明书》第3页"，让回答**可核对**（呼应 [[grounding接地与分层防御]]）。metadata 是把"语义检索"和"可追溯引用"接起来的那根线。

## Grounding（接地）与分层防御

**Grounding = 强制模型"只根据给定的资料回答，没有就说没有"**，不许用自己的先验瞎编。这是 RAG 防幻觉的核心——检索只负责"找资料"，grounding 负责"逼模型只用这些资料说话"。没有它，模型会拿检索结果当参考再掺私货，RAG 就白做了。

**检索召回 vs 生成精选（两段分工）**：真机 s4_02 观察到——检索返回的 top-K 里常混入不相关候选（embedding 分数不完美），但**生成阶段的 LLM 会二次甄别、挑真正匹配的**。所以检索负责**召回**（把对的捞进候选池），生成负责**精选 + grounding**。这就是"为什么取 top-K 不取 top-1"。

### ⚠️ 关键：grounding 靠 system prompt 是「软约束」，不是硬保证

跟"prompt 让模型输出 JSON""工具在 schema≠模型会用"是同一条铁律：**prompt 是恳求模型自律，不是机制保证**。这次答对不代表下次一定——换模型、换刁钻问法、检索结果更像时，模型仍可能张冠李戴或编一个产品。**所以关键系统要分层加固**，越往下越硬：

| 层 | 手段 | 硬度 |
|---|---|---|
| 1. prompt grounding | "只用清单作答、没有就说没有" | 软（靠自律）——性价比最高的第一道防线 |
| 2. 结构化 + 引用约束 | 让模型必须标注每句来自哪个产品（product_code / doc_id） | 中 |
| 3. **服务端校验（硬）** | 模型答案里提到的产品/数字，**代码去检索结果里核对**，查无此项就拦下/重生成 | 硬（机制保证） |
| 4. 兜底 | 校验不过 → 返回安全话术（"暂无"），不把可疑答案给用户 | 硬 |

**第 3 层才是真正的硬保证**，正是 [[03-agent-loop-lessons]] 那套"别信模型"在 RAG 的迁移：不信模型"answer 里的产品真来自清单"，用代码核对。生产做法——强制引用（只准输出候选集里的 product_code，服务端校验在不在集内）、provenance 核对（关键数字和检索数据比对）、NLI 校验（另一个模型判"答案是否被上下文支持"）。

一句话：**prompt grounding 让它"大概率照做"，服务端校验保证"照不做也拦得住"。有后果的系统永远要有第 3 层。**

## 工具库：numpy / sentence-transformers

s4_01 的两半：**sentence-transformers 造向量，numpy 拿向量算。**

### numpy —— Python 数值计算地基
- **是什么**：核心是 `ndarray`（N 维数组，连续内存+定类型）+ 一整套**向量化**运算，底层 C/SIMD，比 Python for 循环快几十上百倍。几乎所有 ML/数据库都建在它上。
- **embedding 就是 float 数组**，所以点积/模长/矩阵乘都靠它。
- 常用：`np.dot(a,b)`（点积）、`np.linalg.norm(a)`（模长）、`np.asarray(x)`、`x.shape`（如 `(7,384)`=7 篇×384 维）。
- **向量化** = 对整个数组一次运算而非逐元素循环：`a*2`、`np.sum(a**2)`——又快又好读。

### sentence-transformers —— 一行把文本变向量
- **是什么**：把 transformer 包装成"文本 → embedding"，`model.encode(texts)` 直接出向量。
- **建在** PyTorch + Hugging Face transformers 上，把「分词→过模型→池化成句向量→(可选)归一化」藏在 `.encode()` 后面。
- **模型**首次加载从 Hugging Face Hub 下载权重（几百 MB），缓存到 `~/.cache`，之后离线可用。
- `encode()` 默认**返回 numpy 数组**，正好交给 numpy 算余弦。

### 接力关系
```
model.encode(文本)  ──▶  ndarray 向量  ──▶  np.dot / np.linalg.norm 算余弦 → top-k
（造向量，黑箱）           （数据载体）        （检索核心，你的 TODO）
```
一句话：**sentence-transformers 把语义压进向量，numpy 在向量上算几何。**

---

## multilingual-e5-small（我们用的 embedding 模型）

拆名字：**multilingual**（多语言 100+，中英都行）+ **e5**（Microsoft 的 E5 家族，专为**检索**训练）+ **small**（尺寸档，还有 base/large）。HF id：`intfloat/multilingual-e5-small`。

**关键规格**：
- 输出 **384 维**；最大输入 ~**512 token**（超了截断）；权重 ~470MB，CPU 可跑。
- **encoder-only**（类似 BERT）：活是"文本 → 向量"，**不生成文字**。和 Claude（decoder，生成文字）是两类不同的模型。

**为什么要 `query:` / `passage:` 前缀**：E5 用**对比学习**训练——喂大量"查询-文档"配对，学会"匹配的 query 与 passage 向量靠近"。训练时两者就带不同前缀，用时必须照做，否则和训练分布不一致、检索质量掉。**前缀是模型"从小被这么教"的，不是随便加。**

**尺寸档取舍**：

| 档 | 参数/维度 | 取舍 |
|---|---|---|
| small | ~118M / 384 | 快、省、够用（学习期选它） |
| base | ~278M / 768 | 中等 |
| large | ~560M / 1024 | 质量最好，但慢、占内存 |

一句话：E5 家族的**多语言、小号、专为检索训练**的 embedding 模型，输出 384 维、encoder-only，因对比训练需 `query:`/`passage:` 前缀。

## 生成模型 vs embedding 模型（输出不同）

"模型的输出"是什么？**取决于哪类模型**——你接触的两类模型输出**完全不同**（容易混，因为一直用的 Claude 输出是文字）：

**① 生成模型（Claude，decoder）——输出是文字**
```
输入 "适合养老的产品有哪些?" → 输出 "根据您的情况，推荐养老目标基金……"   ← 文字，给人读
```

**② embedding 模型（e5，encoder）——输出是向量**
```
输入 "适合养老的产品" → 输出 [0.02, -0.11, …]   ← 384 个数，给机器算相似度
```
它**不会说话、不回答问题**，只把文本压成一串数。所以"e5 输出 384 维"说的是 ② 的输出，**跟"回答用户的文字"无关**——e5 压根不产生文字。

| 模型 | 类型 | 输入 | 输出 | 给谁用 |
|---|---|---|---|---|
| Claude | 生成（decoder） | 文本 | **文字** | 人读 |
| e5 | embedding（encoder） | 文本 | **向量（384 个数）** | 机器算余弦 |

**RAG = 两类接力**：embedding 模型负责**检索**（把文档/query 变向量、找最像的），生成模型负责**作答**（基于检索到的文档输出文字）。s4_01 练前半段（检索），s4_02 接后半段（生成）。

## Temperature：随机性/创造性旋钮

模型每步生成时，先算出"下一个词的**概率分布**"（"今天天气"后："真好"35% / "不错"25% / "晴朗"15% …），**temperature 控制从这个分布里怎么挑**（范围通常 0~1，有的到 2）：

- **temperature = 0**：永远挑概率最高的（贪心）→ **确定性**，同输入几乎同输出（保守、可复现、单调）。
- **temperature = 1**：按原始概率**随机抽** → 有随机性，同输入多次运行**不同**（多样、有惊喜、但会跑偏）。
- **越高越发散**（把低概率词也捞上来、分布拉平）；**越低越保守**（集中在高概率词）。过高（≈2）会语无伦次。
- （机制：softmax 前 logits 除以 T——T 小→差距放大赢家通吃、T 大→差距缩小人人有机会。记"低=确定、高=随机"即可。）

**取舍（工程判断）**：
| 场景 | 该用 | 为什么 |
|---|---|---|
| 结构化输出/工具调用、分类、抽取、有后果的定级 | **低(0~0.3)** | 要稳定、可预测、格式不跑偏、可复现 |
| eval / 要复现对比 | **低(0)** | 同输入同输出才好比 |
| 创意写作、头脑风暴、要多个不同候选 | **高(0.7~1)** | 要多样（低了 5 个候选几乎一样） |

**与 FinWise 的联系**：风险评估这种"要稳定、可校验、有财务后果"的场景**该用低 temperature**——正好治你见过的 **C4/C3 定级抖动**（B#7）；若用高 temperature 抖动会更严重。⚠️ 本学习环境的 bridge **忽略 temperature**（见 memory），所以真机实验控制不了它——真 API 上评估链路应显式 `temperature=0`，这其实是一条生产化优化项（降低不确定性）。

## 参数 vs 维度

结论：**参数是"模型内部有多少个学出来的数"，维度是"输出向量有多长"——一个说模型多大，一个说输出多宽。**

- **参数（parameters）**：模型内部**学出来的权重**，训练就是调这些数。它们**就是模型本身**（知识编码在里面）。数量 = 容量/大小，越多越强但越慢越占内存。e5-small ≈ **1.18 亿**。类比：工厂里所有**旋钮**的总数。
- **维度（dimension）**：embedding 语境里 = **输出向量长度**（e5-small=384）。是产出**表示的规格**，不是内部权重数。类比：工厂产出的**产品规格**。（对 e5 这类 encoder，384 也是其内部每层宽度 hidden size。）

### 参数长什么样（从 2 个到 1.18 亿个）

最简单的模型就是**一条直线** `y = w·x + b`——`w`、`b` 是参数，**这个模型就 2 个参数**。训练学到 `w=2, b=1` 后：输入 x=3 → 输出 7；x=10 → 输出 21。"训练"就是拿一堆数据点不断调 w、b 让线拟合好，调好就写死。

**10 个参数** = 9 个特征的线性模型：`y = w1·x1 + … + w9·x9 + b`（9 权重 + 1 偏置）。这 10 个学出来的数就是模型的全部"知识"。

e5-small 完全同理，只是参数从 10 个变 **1.18 亿个**、堆成很多层、输入是文本、输出是 384 维向量。

> **关键区分**：**参数固定**（训练完写死，对任何输入都一样那一堆数）；**输出随输入变**（不同文本 → 不同向量）。类比函数：参数 = 函数体里写死的系数，输出 = 传入具体输入后算出的返回值。同一公式（参数不变）喂不同输入得不同输出。

| | 参数 | 维度 |
|---|---|---|
| 衡量 | 内部有多少学出来的数 | 输出向量多长 |
| 关于 | 模型大小/容量（内部） | 输出规格（外部） |
| 随输入变？ | 不变（固定） | 长度不变，值随输入变 |
| e5-small | ~118M | 384 |

**联系（关键）**：两者相关但不同。E5 阶梯 small(118M/384) → base(278M/768) → large(560M/1024)，参数和维度**一起变大**。机制：transformer 每层权重矩阵约 `维度×维度`，所以
```
参数量 ≈ 维度² × 层数 × 常数（+ 词表相关）
```
**维度是参数量的一个来源**（维度翻倍那部分参数约×4）。所以"大模型往往也高维"，但一个描述**模型规模**、一个描述**输出宽度**，不是同一回事。

## Eval：给不确定输出打分（Hit@K / MRR / 召回·精确 / golden set）

**为什么需要 eval**：LLM 同输入可能不同输出，没有唯一正确答案——`assert 相等` 那种单测测不了"回答好不好/检索准不准"。**单测防"代码逻辑错"，eval 防"模型质量降"**。AI 功能的"测试"主要靠 eval。

**eval 三件套**：
1. **golden set**：一批 (输入, 期望) 的标准答案——你定义"什么叫对"，eval 的地基。
2. **指标 metric**：把"对不对"聚合成一个数。
3. **可回归**：同一 golden set + 指标，换方案（模型/prompt/chunk 策略）分数直接可比 → 改动是变好还是变坏，一眼看出。

**打分器三种（由硬到软）**：① 规则断言（代码能判的：命中吗、code 合法吗、数字对吗）② golden set 比对（人工备"输入+期望要点"）③ LLM-as-judge（主观质量用另一个 LLM 打分）。**原则：能用规则测的先用规则（便宜、确定），主观质量才上 LLM-judge。**

### 召回 vs 精确（一对基础概念）
- **召回 recall** = 找回来的 ÷ **本应找回的总数** → 关心**漏不漏**。
- **精确 precision** = 找对的 ÷ **你一共返回的** → 关心**混不混**。
- 常此消彼长：网撒大召回高但精确低，反之亦然。**RAG 检索这步优先保召回**（对的没进候选池，后面 LLM 再强也救不回来；杂质靠 LLM 精选过滤）——所以检索保召回、生成保精确，分工。

### 两个检索指标（s5_01）
- **Hit@K**：期望结果**出现在 top-K 里就算命中**（1/0），聚合成命中率。**只看在不在前 K、不管排第几**——召回视角，粗但直观。
- **MRR**（Mean Reciprocal Rank）：单条 RR = **1/名次**（排第1→1.0、第2→0.5、第3→0.33、没进→0），MRR = 所有 query 的 RR 平均。**在乎排名**，能区分"排第1"和"勉强排第3"——排序视角，更细。用倒数是想"排越前分越高"，且下降快（第1→第2直接砍半，符合"从第1掉到第2是大损失"）。
- **为什么两个都要**：Hit@K 一样时 MRR 能拉开（全排第1 vs 全排第3，Hit 都=1，MRR=1.0 vs 0.33）。合看才知是"又准又靠前 / 能找到但排不准 / 排得准但常找不到"。

> **误区：高 MRR ≠ 高命中率**。MRR 是**全部 query** 的平均（没命中的按 0 算进分母），少数命中排很前就能把它拉高、**掩盖大量没命中的**。单条 RR>0 才等于该条命中；聚合后的 MRR>0 只说明"有些命中"。（典型：TF-IDF 两极分化——字面重合的精准命中排第1、不重合的直接 0。）

### ★ 最核心的一课：eval 结论完全取决于 golden set
s5_01 真机演示——**同一对检索器（embedding / TF-IDF），只换 golden set，结论翻转**：

| golden set | Embedding | TF-IDF |
|---|---|---|
| A 送分（query 字面≈文档措辞） | Hit 1.00 / MRR 1.000 | Hit 1.00 / MRR **1.000** |
| B 真实（query 跨字面、贴近口语） | Hit 1.00 / MRR 0.722 | Hit **0.67** / MRR 0.556 |

A 里 TF-IDF 靠字面重合被喂满分（送分题）、看着和 embedding 一样好；B 里字面优势没了，掉到 Hit 0.67，embedding 完胜。**检索器一个字没变，变的只有题。**

教训：**数字看着客观，其实被 golden set 操纵**。有偏的题（如无意中用了文档原词）会得出错误结论。**要先质疑题（公不公平、像不像真实用户、有没有替某方送分）、再信分**——这和 [[03-agent-loop-lessons]]「测试数据与 bug 合谋假绿」是同一个幽灵。指标怎么算是技术（5 分钟学会），**golden set 出得公不公平才是 eval 的灵魂**（靠判断力，没有标准答案）。

### 别只质疑题，还要质疑样本量与噪声（s5_02 / B#8）
s5_02 用真机 A/B eval 测"conclude 字段顺序改动值不值"（A 结论在前 / B dimensions 打头），结果 A=4/4=1.00、B=3/4=0.75。**看着 A 更好，但这个结论不可靠**：
- **n 太小**：golden set 只有 4 条，一个 case 就是 25%。B 只错 1 个（边界人设 C5→C4），准确率就掉 25 个百分点——是分辨率太粗，不是真的更差。
- **模型有噪声 + 边界 case**：那个错的人设正好卡在 C4/C5 边界（维度均值≈边界阈值，本就抖，见 B#7 的 3.6→C4/C3 抖动）。A 判 C5、B 判 C4 很可能纯是这一次采样的随机。
- **单轮跑**：要区分"B 真更差"还是"这次运气差"，必须**同一 golden set 多跑几轮取平均**。跑一次的 0.75 vs 1.00 统计上没意义。

→ **结论：这个 eval 的分辨率不足以判断字段顺序有没有用。** 想真回答，需要扩 golden set（20+）、每人设多跑取多数、专盯边界 case（非边界 case 两种顺序都轻松判对、区分不出好坏）。**质疑 eval 要三层：质疑题（偏不偏）+ 质疑样本量（够不够）+ 质疑噪声（可不可复现）**。

### "数据不足以支持改动 → 不改" 也是有效结论
字段顺序在当前能测到的范围内**没显现明确收益**（A 已 1.00、B 没更好）。理性决定：**不改**。这正是把这类"质量改动"放到 eval 阶段的意义——**用数据（哪怕是"数据不足"这种结论）取代"理论上应该更好就改"**。工程上，"证明某改动无效/不值得"和"证明有效"一样有价值。

### eval 工程：批量真机调用必须容错
真机 eval 跑几十次 LLM 调用，**必然遇到偶发失败**（s5_02 里 claude CLI 偶发返回 1）。脚本若"单点失败就整轮崩"，你永远跑不完一轮——A 组运气好跑完、B 组第一个就挂。修法：`try` 兜住单次运行、记为 ERR 继续，别让一个失败毁掉整个 eval。

## ReAct：推理+行动交替（agent loop 的正式名字）

**ReAct = Reasoning + Acting**（2022 论文提出）：让模型"想一步、做一步、根据工具结果再想下一步"——推理和行动**交替循环**，而非一口气想完/做完。一个回合：
```
Thought（想）      : 我需要知道 C4 等级有哪些产品
Action（做）        : 调 search_products("C4")
Observation（看结果）: [P-R4 成长精选混合]        ← 工具返回
Thought（想）      : 有产品了，可以推荐
Action（做）        : 给出最终推荐
```
关键：**每次行动后拿到真实观察（工具结果），喂回去让模型基于事实继续推理**。对比——纯 Reasoning（闷头想不查）易幻觉；纯 Acting（机械执行）不灵活；ReAct 交织两者：既接地、又能随结果调整。

**你早就手写实现过 ReAct**：B#3–B#7 的 `for _step in range(MAX_STEPS)` loop——"模型调工具(Act)→执行返回结果(Observe)→回喂→模型继续(Reason)→再调或收尾"——**就是一个 ReAct loop**，只是当时没用这个名字。所以：

- **ReAct = agent loop 的正式名字**（推理与行动交替）；
- **`create_react_agent`（LangGraph 预制件）/ `tool_runner`** = 把这个 loop 预制成一行，内部就是 `agent(想/调工具) ⇄ tools(执行/返回观察)` 的循环图——和你手写的是同一个东西。它靠"模型不再调工具（返回纯文本 end_turn）"来收尾（见 [[agent-框架本质是手写-loop-的封装]]）。

一句话：**ReAct = 让模型"想一步做一步、看工具结果再决定"的范式，就是你手写过的那个 agent loop。**

## Agent 框架：本质是"手写 loop 的封装"

前面（B#3–B#7）**亲手**写过 agent loop：`for _ in range(MAX_STEPS)`、判断 tool_use、执行工具、成对回喂 tool_use+tool_result、配 id、终止判断。**框架（如 Anthropic SDK 的 `tool_runner`）做的就是把这套整个包掉**——不是魔法，是"你写过的那个 for 循环的官方版"。

**手写 vs 框架逐条对照（s6_01，以 `tool_runner` 为例）**：

| 你手写的 | 框架替你做的 |
|---|---|
| `for _ in range(MAX_STEPS)` | 内部循环 + `max_iterations` 参数 |
| `if block.type=='tool_use'` | 自动识别 tool_use |
| `_execute_tool` 按名分发 | 按 name 自动调用你的工具函数 |
| 手拼 tool_use+tool_result、配 id | 自动拼、自动配 `tool_use_id` |
| `messages.append(...)` + continue | `append_messages` + 自动续调 |
| 终态判断 / break | 模型不再调工具 = 迭代耗尽 = 自动停 |
| 工具 = schema dict + 执行函数（两块） | `@beta_tool`：**一个函数 = schema + 实现**（装饰器从签名+docstring 自动生成 schema） |

**核心认知**：
1. **框架不是黑箱——因为你裸手写过一遍**。别人看框架只觉得"有个神奇东西自动跑了"，出问题两眼一抹黑；你能一眼定位"这是 id 没配对""这是撞了 max_iterations"。**裸调五个阶段的回报，就是框架对你透明**。这也是"先裸调建直觉、再学框架"路线的意义。
2. **runner 是迭代器：遍历它 = 驱动 loop**（`for message in runner` 每摇一步 = agent 走一轮，框架在幕后执行工具+回喂+续调；模型不再调工具→迭代耗尽→自动停）。见 [[python-syntax-notes]] 迭代器。
3. **框架高级封装依赖更完整的 API**：`tool_runner` 内部用 beta `messages.parse`，本地 bridge（简化 shim）撑不起 → 崩。**手写 loop 反而更 portable**（只用最基础的 messages 接口）。生产里换框架，"底层依赖不匹配"是常见坑。
4. **什么时候上框架**：样板代码（loop/schema/回喂）重复且稳定时，框架省事、少出错。但要能**看穿**它，否则调试成本更高。工程判断，不是越框架越好。

## Agent loop 的两种终止模式（"谁宣告结束"）

面试易混、也容易被追的点：**loop 到底靠什么停？** 有两种截然不同的模式，别糊在一起。

### 模式 A：默认——"模型这轮不再要工具"就停（框架自带）

`tool_runner`（Anthropic SDK helper）和 `create_react_agent`（LangGraph 预制图）**默认都用这个**。它们**不认识"哪个 tool 是终态"**，判断结束只看一件事：**模型这轮回复里还有没有 tool_use**。

- **`tool_runner`**：每轮看 `stop_reason`——
  - `== "tool_use"`（有 tool_use 块）→ 执行工具、append tool_result、再调；
  - `== "end_turn"`（无 tool_use，纯文本终答）→ 停，返回最终 message。
- **`create_react_agent`**：agent(模型)节点后挂一条**条件边** `tools_condition`——看最后一条 AIMessage：有 `tool_calls` → 去 ToolNode → **回边**转回 agent；没有 → 走到 `END`。
- 两者本质一样，只是一个读 `stop_reason`、一个读 `.tool_calls`（LangChain 把 `stop_reason:tool_use` 映射成了 AIMessage 上的 `tool_calls`）。

**要点：终态由「模型」发出（它不再调工具），框架只负责「检测」这个信号。没有"某个 tool_use 是最终态"这回事。** 上表里"终态判断 = 模型不再调工具 = 自动停"说的就是这个模式。

### 模式 B：结构化终态工具——"调了那个约定的工具"就停（应用层自己判）

FinWise 手写 loop（`is_terminal_tool`）用的是这个。因为我们把**最终答案本身也做成了一个工具调用**（如结构化的 `conclude`/输出评估结果的 tool）——模型的"最后一步"是**调那个终态工具**，而不是"停下来说人话"。这时：

- **框架默认不会替你判**——你的 loop 得拿 `tool_name in TERMINAL_TOOLS` 自己比对，命中就 break。
- 在 LangGraph 里要实现"调了某 tool 就结束"，得**自己改那条条件边**：发现是该 tool 就 route 到 `END`，而不是回边。

### 对照

| | 谁宣告"结束" | 怎么判断 | 谁来判 |
|---|---|---|---|
| **模式 A（默认）** | 模型**不再调工具**、返回纯文本 | 看 `stop_reason` / `.tool_calls` | 框架自动 |
| **模式 B（结构化终态）** | 模型**调用约定的终态工具** | `tool_name` 比对终态白名单 | **你的代码 / 自定义条件边** |

**为什么值得懂**：只会用框架默认值的人默认"模型不调工具=结束"；而当你需要**最终产物是结构化输出**（如定级结果、必须走 schema 的结论）时，就得用模式 B——终答通过工具走，你自己接终止逻辑。这正是 [[reference_pricing_agent_orchestration]] 里"定级去模型化"能落地的前提之一：结论是一个**受控的终态工具**，不是模型随口说的文本。

## Tracing（可观测性）：看进一次运行内部

**Tracing = 把一次运行的详细执行过程逐步记录下来，让你"看进"内部到底发生了什么。** 对普通程序用断点/日志调试；但 LLM agent 是**多步 + 不确定**的（多次 LLM 调用、多次工具调用、多节点流转），出问题时需要看清每一步的**输入/输出/耗时/token**。tracing 就是自动全程录下来。

**一次 trace = 一棵带层级的步骤树（span/trace）**（以 s6_02 多 agent 为例）：
```
trace: supervisor("我炒股5年…")                    ← 一次完整运行
├─ span: assessment_agent
│   └─ LLM call: assess  in={desc} out={dims} 0.8s 120tok
├─ span: retrieve_products  in="C4" out=[P-R4]
└─ span: recommendation_agent
    └─ LLM call: recommend  in={等级+候选} out={P-R4,理由} 0.9s 200tok
```
每个 span 记：输入/输出/耗时/token·成本/模型/嵌套关系 → 一眼看清数据怎么流、哪步慢/贵/错。

**为什么 LLM/agent 特别需要**：① 多步+不确定 → 结论错了是评估打错分？检索没召回？还是推荐幻觉？**逐 span 看直接定位到出错那步**（print 调试在 10 节点的图里抓瞎）；② 成本/延迟可见（每次调用 token+耗时）；③ 可复盘/回放。

**你其实手搓过 tracing**：a2 的 `ToolLoggingLLM`（包在 LLM 外、打印每次工具调用）就是手搓探针。专业工具（**LangSmith / Langfuse**）做的是同一件事，只是**自动 + 结构化（span 树/耗时/token）+ 有 UI（时间线、调用树、点开看 prompt/response、回放）**。

**tracing vs eval（可观测性的两半，别混）**：

| | 问什么 |
|---|---|
| **eval** | 结果**好不好**（质量、打分：Hit@K/MRR…） |
| **tracing** | 过程里**发生了什么**（可见性：哪步慢/贵/错） |

eval 告诉你"变差了"，tracing 告诉你"**为什么**变差、卡在哪步"。生产里两个都要。（阶段六 lg_06 会把手搓的 ToolLoggingLLM 换成 LangSmith，看 LangGraph 图每步轨迹——补上阶段五留的可观测性坑。）

## Harness Engineering：给模型造脚手架（统领全局）

> 不是严格教科书术语，是 agent 工程圈（尤其 Anthropic / Claude Code 语境）的常用说法，但含义清晰。

把一个 AI 系统拆两半：
- **model（模型）**：吃 token 吐 token 的"引擎"，你基本不训练/不改，拿来就用。
- **harness（脚手架/挽具）**：**把引擎套起来、让它真正干活的一切外围代码**——agent loop、工具定义与执行、上下文/prompt 构造、记忆/状态、重试/容错、多 agent 编排、防幻觉校验、输出解析……

**harness engineering = 设计打磨这套脚手架的工程**。名字来自"挽具"：马（模型）力气大，但要靠挽具才能拉车干活。

**核心洞察——你的杠杆几乎全在 harness 上**：模型是给定的、你改不了，所以一个 agent 产品好不好**大部分取决于 harness 而非模型**。同一个 Claude，套烂 harness vs 好 harness 天差地别。（Claude Code 本身就是一个 harness——同一模型，能力很大程度来自它的 harness 工程。）

**这个概念统一了本文档几乎所有零散知识**——它们不是一堆技巧，是"造 harness"这一件事的不同侧面：

| 学过的 | harness 的哪一块 |
|---|---|
| 手写 agent loop（B#3–B#7） | harness 的心脏（loop） |
| 工具定义 + 执行器 | 工具层 |
| 上下文/messages 构造 | 上下文工程（context engineering） |
| 重试/容错 | 健壮性 |
| grounding 硬校验 / 定级去模型化 | 护栏（guardrails） |
| RAG 检索 + chunking | 上下文供给 |
| supervisor 多 agent / LangGraph | 编排 |
| eval / tracing | 衡量与观测"模型+harness"这套系统 |

**框架的定位**：tool_runner / LangGraph 本质是 **harness 框架**——给你现成的 harness 组件（loop、编排）。你**亲手造过 harness**，才能看穿它们（见"Agent 框架"节）。

一句话：**harness engineering = 工程模型外围那套脚手架，把"一个语言模型"变成"一个能干活的 agent 系统"。模型给定，harness 才是你真正施力、决定产品质量的地方——这正是整趟学习在做的事。**

## 常见追问

- **384 维哪来的**？模型设计时定的（e5-small=384）。维度越高表达越细，但更慢更占空间。
- **为什么用余弦、不用欧氏距离（直线距离）**？文本检索里方向比长度更代表意思，余弦对长度不敏感；归一化后两者其实等价。入门默认"文本语义检索用余弦"。
- **向量库（Chroma / FAISS 等）干嘛的**？把"存一堆向量 + 快速找最近的"工程化。几百万条时不能像 s4_01 那样 for 循环全算一遍，需要专门的近邻索引。我们先用 numpy 手算，看清它内部在干嘛。
- **e5 的 `query:` / `passage:` 前缀**？e5 系列约定：文档编码加 `"passage: "`、查询加 `"query: "`。不加检索质量明显下降——真实且非直觉的坑。
