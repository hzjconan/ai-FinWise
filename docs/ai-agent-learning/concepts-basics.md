## RAG（检索增强生成）

**RAG = Retrieval-Augmented Generation**。解决大模型两个硬伤：① 不知道你的私有数据；② 装不下太多数据（context 有上限、按 token 计费）。

思路很朴素：**别让模型硬记，临时查给它看**。用户提问 → 先从你的数据里**检索**出最相关的几条 → **塞进 prompt** → 模型**基于这几条**回答。

> 类比：**开卷考试**。模型不用背，你把相关那几页翻开摆它面前。

对应 FinWise：产品库模型没见过，用 RAG 让它能回答"有没有适合养老、波动小的产品"这类自然语言需求。

## Embedding / 向量

**embedding = 一个函数：把一段文本 → 一串固定长度的数字（向量）。** 例如 `multilingual-e5-small` 输出 384 个浮点数。

```
"养老储备"      → [0.02, -0.11, 0.34, …]   # 384 维
"退休后的钱"    → [0.03, -0.09, 0.31, …]   # 跟上面很接近
"科技股高波动"  → [-0.20, 0.15, -0.05, …]  # 跟上面差很远
```

关键：这个函数是**专门训练**出来的，目标是 **意思相近的文本 → 向量也相近；意思无关 → 向量差很远**。

- 向量长度（维度数，如 384）由模型设计时定；维度越高一般表达越细，但更慢更占空间。
- 单个维度人看不懂，是模型学到的某种"语义特征"；**整体位置**才编码意思。

## 文本长度 → 向量维度（定长输出 / 池化 / 截断 / chunk）

疑问：一个字 vs 一篇文章，都转成 384 维吗？**是——输出永远固定 384 维，与输入长度无关。** 但有三层要点：

**① 为什么必须定长**：余弦只能比同维度向量。embedding 的使命就是把任意长度文本压成统一大小，才能互相比较。

**② 怎么做到长度无关——池化（pooling）**：内部是"每个 token 一个 384 维向量"，长文本 token 更多、中间向量更多；再用**池化**（常见 mean pooling=取平均）把 N 个向量压成 **1 个**。N 多少无所谓，平均完永远 1 个 384 维。
```
"养老储备"→3 token→[v1,v2,v3]  ；一段话→60 token→[v1…v60]   （每个 384 维）
                    │ 池化（取平均，N→1）
                    ▼   一个 384 维句向量
```

**③ 硬上限：最大 token 数（截断）⚠️**：模型有最大输入长度（e5-small≈512 token），**超出部分被悄悄截断丢弃**。一篇 2000 token 的文章，只有前 ~512 token 参与编码——"整篇进去了"是错觉。

**④ 即使没超限，长文压一个向量会"糊"**：一篇多主题长文压成一个向量 = 所有意思被平均成一团，检索变模糊。**这正是 RAG 要 chunking（分块）的原因**：长文档切成小段、每段单独 embedding，每个向量代表聚焦片段，检索才精准。（chunking 是阶段四后续主题。）

| 输入 | 输出 | 说明 |
|---|---|---|
| 一个字 / 一句话 / 一段（≤512 token） | 384 维 | 池化后定长、完整表达 |
| 一篇长文（>512 token） | 384 维 | **超出被截断丢弃** |

一句话：**输出定长（靠池化）、输入有上限（超了截断）、长文压一个向量会糊 → 长文档先 chunk 再逐段 embedding。**

## 向量空间与语义

把每段文本想成 **N 维空间里的一个点**（N=向量维度）。embedding 训练的结果就是：

> **意思近 = 空间里位置近。**

"养老储备"和"退休后的钱"会挤在一块，"科技股"在很远的另一片区域。于是"找意思相近的文本"就变成了"找空间里离得近的点"——一个纯几何问题。

## 点积与模长（余弦公式的两块积木）

### 模长 ‖a‖ —— 向量的"长度"

**每个分量平方、求和、开根号**，本质是勾股定理推广到 N 维：

```
2D:  a=[3,4]         ‖a‖ = √(3²+4²) = 5           （就是勾股定理）
N维: a=[a₁,…,aₙ]     ‖a‖ = √(a₁² + … + aₙ²)
```
numpy：`np.linalg.norm(a)`（= `np.sqrt(np.sum(a**2))`）。

### 点积 a·b —— 逐位相乘再相加，得到一个数

对应位置相乘再全部加起来，结果是**一个标量**：
```
a·b = a₁b₁ + a₂b₂ + … + aₙbₙ
[1,0]·[1,1]=1    [1,0]·[0,1]=0（垂直）    [1,0]·[-1,0]=-1（反向）
```
它衡量两向量**方向多一致（对齐程度）**——因为 `a·b = ‖a‖‖b‖cosθ`：一致→大正数，垂直→0，相反→负。

**为什么"逐位乘加"= 对齐？** 单看一项 `aᵢbᵢ`：同号→正（这个轴上一致）、异号→负（相反）；把所有轴的一致/相反加总，就是整体对齐度。

numpy：`np.dot(a, b)`。

### 隐藏联系：`a·a = ‖a‖²`

向量和自己点积 = 模长平方（自己跟自己夹角 0、cos=1）：`a·a = a₁²+…+aₙ² = ‖a‖²`。所以 `‖a‖ = √(a·a)`——点积是更基础的积木，模长是它的特例。

### 拼回余弦
```
cos(a,b) = (a·b) / (‖a‖·‖b‖)
         =  对齐程度(含长度) ÷ 各自长度 = 纯方向的一致性
```

## 余弦相似度

有了向量，要一个**数值**衡量两个点多"像"。最常用的是**余弦相似度（cosine similarity）**：看两向量的**夹角**。

```
夹角小 → 方向几乎一致 → 很像 → cos ≈ 1
垂直   → 不相关          → cos = 0
反向   → 相反            → cos = -1
```

范围 `[-1, 1]`。公式：

```
cos(a, b) = (a · b) / (‖a‖ · ‖b‖)
```

- **`a · b`（点积）** = `a[0]*b[0] + a[1]*b[1] + …`，衡量两向量"对齐"程度；
- **`‖a‖`（模长/范数）** = `sqrt(a[0]² + a[1]² + …)`，箭头长度；
- 除以两个模长 = **把长度归一化掉，只留方向（夹角）**。

**为什么只看方向、不看长度？** 向量长度往往反映文本长短等无关因素，**方向**才编码意思。两段话意思相同、一长一短，仍应算"很像"——除掉模长正好做到。

小例子：
```
a = [1, 0];  b = [1, 1]
a·b = 1;  ‖a‖ = 1;  ‖b‖ = √2 ≈ 1.414
cos = 1 / (1 × 1.414) ≈ 0.707    # 夹角 45°，中等相似
```

> 若向量已**归一化**成单位长度（模长=1），则 `cos = a·b`（分母为 1，省了）。

## 余弦公式怎么来的（和直角三角形 cos 的关系）

疑问：直角三角形里学的是 `cos θ = 邻边 / 斜边`，跟 `cos(a,b) = (a·b)/(‖a‖‖b‖)` 什么关系？

**答：是同一个 cos θ，只是一个"用角度算"、一个"用坐标算"。**

**① 直角三角形的 `cos=邻/斜` 定义的是角 θ。** 把向量 `a` 当斜边（长 `‖a‖`），向 `b` 方向作垂线，落在 b 上的影子就是邻边：

```
        a
       /|
 ‖a‖ /  |     θ = a、b 夹角；斜边=a（长 ‖a‖）
     /θ__|__→ b   邻边 = a 在 b 方向的投影 = ‖a‖·cosθ
```

**② 点积正好打包了 `‖a‖‖b‖cosθ`**：`a·b` = "a 在 b 方向的影子长度 `‖a‖cosθ`" × "b 的长度 `‖b‖`" = `‖a‖‖b‖cosθ`。两边除以 `‖a‖‖b‖`，就把角度单独解出来：`cosθ = (a·b)/(‖a‖‖b‖)`。**这就是余弦相似度——不是新定义，是用坐标反算那个 cosθ。**

**③ 为什么 `a·b = ‖a‖‖b‖cosθ`（用余弦定理证）**：对 a、b 张成的三角形，第三边是 `a−b`：
```
余弦定理： ‖a−b‖² = ‖a‖² + ‖b‖² − 2‖a‖‖b‖cosθ
坐标展开： ‖a−b‖² = (a−b)·(a−b) = ‖a‖² + ‖b‖² − 2(a·b)
两式相等 ⇒ a·b = ‖a‖‖b‖cosθ    ∎
```

**④ 为什么非用公式**：2D 能画图量角，但 embedding 是 384 维，"看"不到角。公式的价值 = **纯靠坐标（点积+模长）算出夹角的 cos，把"邻边/斜边"推广到任意维度**——这才能用在语义检索上。

## 关键词匹配 vs 语义检索

| | 怎么比 | 软肋 |
|---|---|---|
| 关键词匹配（`LIKE '%养老%'`） | **字面**词是否重合 | 问"养老"、文档写"退休储备"→ 一字不重合 → **漏掉**，尽管意思一样 |
| 语义检索（embedding + 余弦） | **意思**（向量空间位置）是否接近 | 需要模型编码，成本略高；但能跨字面匹配意思 |

这就是 RAG 用 embedding 而不用关键词的根本原因。（TF-IDF 是"高级一点的关键词匹配"——仍是字面词频，见 s4_03 的对照实验。）

## 完整 RAG 管线

```
【离线，只做一次】
  所有文档 ──encode──▶ 一堆文档向量，存起来（doc_vecs）

【用户每次提问】
  query ──encode──▶ query 向量
                      │
     对每个 doc_vec 算 cosine_similarity(query_vec, doc_vec)
                      │
            按分数降序，取前 k 个（top-k 检索）
                      │
   把这 k 篇文档塞进 prompt ──▶ 模型基于它们作答（生成）
```

对应 `scratch/s4_01_rag_embedding.py`：`CORPUS`（文档）→ `encode_docs`（向量化）→ `cosine_similarity` + `retrieve_top_k`（检索）。生成那步在 s4_02。

## 工具库：numpy / sentence-transformers

s4_01 的两半：**sentence-transformers 造向量，numpy 拿向量算。**

### numpy —— Python 数值计算地基
- **是什么**：核心是 `ndarray`（N 维数组，连续内存+定类型）+ 一整套**向量化**运算，底层 C/SIMD，比 Python for 循环快几十上百倍。几乎所有 ML/数据库都建在它上。
- **embedding 就是 float 数组**，所以点积/模长/矩阵乘都靠它。
- 常用：`np.dot(a,b)`（点积）、`np.linalg.norm(a)`（模长）、`np.asarray(x)`、`x.shape`（如 `(7,384)`=7 篇×384 维）。
- **向量化** = 对整个数组一次运算而非逐元素循环：`a*2`、`np.sum(a**2)`——又快又好读。

### sentence-transformers —— 一行把文本变向量
- **是什么**：把 transformer 包装成"文本 → embedding"，`model.encode(texts)` 直接出向量。
- **建在** PyTorch + Hugging Face transformers 上，把「分词→过模型→池化成句向量→(可选)归一化」藏在 `.encode()` 后面。
- **模型**首次加载从 Hugging Face Hub 下载权重（几百 MB），缓存到 `~/.cache`，之后离线可用。
- `encode()` 默认**返回 numpy 数组**，正好交给 numpy 算余弦。

### 接力关系
```
model.encode(文本)  ──▶  ndarray 向量  ──▶  np.dot / np.linalg.norm 算余弦 → top-k
（造向量，黑箱）           （数据载体）        （检索核心，你的 TODO）
```
一句话：**sentence-transformers 把语义压进向量，numpy 在向量上算几何。**

## multilingual-e5-small（我们用的 embedding 模型）

拆名字：**multilingual**（多语言 100+，中英都行）+ **e5**（Microsoft 的 E5 家族，专为**检索**训练）+ **small**（尺寸档，还有 base/large）。HF id：`intfloat/multilingual-e5-small`。

**关键规格**：
- 输出 **384 维**；最大输入 ~**512 token**（超了截断）；权重 ~470MB，CPU 可跑。
- **encoder-only**（类似 BERT）：活是"文本 → 向量"，**不生成文字**。和 Claude（decoder，生成文字）是两类不同的模型。

**为什么要 `query:` / `passage:` 前缀**：E5 用**对比学习**训练——喂大量"查询-文档"配对，学会"匹配的 query 与 passage 向量靠近"。训练时两者就带不同前缀，用时必须照做，否则和训练分布不一致、检索质量掉。**前缀是模型"从小被这么教"的，不是随便加。**

**尺寸档取舍**：

| 档 | 参数/维度 | 取舍 |
|---|---|---|
| small | ~118M / 384 | 快、省、够用（学习期选它） |
| base | ~278M / 768 | 中等 |
| large | ~560M / 1024 | 质量最好，但慢、占内存 |

一句话：E5 家族的**多语言、小号、专为检索训练**的 embedding 模型，输出 384 维、encoder-only，因对比训练需 `query:`/`passage:` 前缀。

## 常见追问

- **384 维哪来的**？模型设计时定的（e5-small=384）。维度越高表达越细，但更慢更占空间。
- **为什么用余弦、不用欧氏距离（直线距离）**？文本检索里方向比长度更代表意思，余弦对长度不敏感；归一化后两者其实等价。入门默认"文本语义检索用余弦"。
- **向量库（Chroma / FAISS 等）干嘛的**？把"存一堆向量 + 快速找最近的"工程化。几百万条时不能像 s4_01 那样 for 循环全算一遍，需要专门的近邻索引。我们先用 numpy 手算，看清它内部在干嘛。
- **e5 的 `query:` / `passage:` 前缀**？e5 系列约定：文档编码加 `"passage: "`、查询加 `"query: "`。不加检索质量明显下降——真实且非直觉的坑。
