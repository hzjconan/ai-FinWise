## RAG（检索增强生成）

**RAG = Retrieval-Augmented Generation**。解决大模型两个硬伤：① 不知道你的私有数据；② 装不下太多数据（context 有上限、按 token 计费）。

思路很朴素：**别让模型硬记，临时查给它看**。用户提问 → 先从你的数据里**检索**出最相关的几条 → **塞进 prompt** → 模型**基于这几条**回答。

> 类比：**开卷考试**。模型不用背，你把相关那几页翻开摆它面前。

对应 FinWise：产品库模型没见过，用 RAG 让它能回答"有没有适合养老、波动小的产品"这类自然语言需求。

## Embedding / 向量

**embedding = 一个函数：把一段文本 → 一串固定长度的数字（向量）。** 例如 `multilingual-e5-small` 输出 384 个浮点数。

```
"养老储备"      → [0.02, -0.11, 0.34, …]   # 384 维
"退休后的钱"    → [0.03, -0.09, 0.31, …]   # 跟上面很接近
"科技股高波动"  → [-0.20, 0.15, -0.05, …]  # 跟上面差很远
```

关键：这个函数是**专门训练**出来的，目标是 **意思相近的文本 → 向量也相近；意思无关 → 向量差很远**。

- 向量长度（维度数，如 384）由模型设计时定；维度越高一般表达越细，但更慢更占空间。
- 单个维度人看不懂，是模型学到的某种"语义特征"；**整体位置**才编码意思。

## 为什么"语义近 → 向量近"（对比学习）

疑问：为什么两个语义相近的字符串，转出来的向量**恰好**相似度也高？

**不是"恰好"，是训练特意训出来的。** 破除错觉：模型不"理解"养老，它只是台函数（吃 token 吐数）。凭什么这些数和意思对齐？——因为训练时有个目标函数逼它这么做。

**对比学习（contrastive learning）**：喂海量**配对**——正样本对（该近，如"适合养老的基金"↔"为退休储备设计的产品"）、负样本对（该远，如"养老基金"↔"科技股高波动"）。损失函数一句话：**正样本对余弦要大（拉近）、负样本对余弦要小（推远）**。反复微调那 1.18 亿参数，直到"人类觉得相关的配对，算出来余弦都大"。于是语义关系被**压进了向量的几何位置**——"养老"和"退休储备"向量近，是被无数类似相关对反复"拉近"的结果，不是巧合。

**关键：没见过的新句子为什么也对？——泛化**。模型不是背下某一对，而是学会了"把语义映射成坐标"的**通用规则**（藏在参数里，作用在词/字层面）。新句子进来，按这套规则组装成向量，自然落到语义邻居附近。类比：没背过 1234×5678，但学会乘法规则照样算。

**余弦的角色**：它**不产生语义**，只是把"向量方向多一致"读成一个数。因果是——**先有训练让向量有意义，余弦才有意义**。拿没训练的随机模型 encode，"养老"和"退休储备"余弦就是随机的。

> 反证（正好接 s4_03）：**TF-IDF 向量不是训练出来的**，是机械数词频，每维死板对应一个字面词，从没有机制把"养老"和"退休储备"关联起来——所以同一把余弦尺子，量 embedding 高分、量 TF-IDF 低分。**差别不在尺子，在向量有没有被训练赋予语义。**

## 训练数据哪来的（自监督 / 自动造对）

疑问：海量语义对不可能人工一条条标注吧？**对，根本没这么干。** 数据绝大部分**自动从现成文本造出来**——叫**自监督（self-supervised）**，是现代 AI 能 scale 的根本。

**核心：让数据自己标注自己**。利用文本自带结构自动生成"相关对"，不用人判断：
- **天然共现**：同一篇文章里相邻两段 → 自动当正样本对（同源相邻=大概率相关）。
- **天然配对**：互联网现成的 标题↔正文、FAQ 问↔答、维基标题↔摘要——爬下来直接用。（e5 大量用"query-passage"对训练，这也是它要 `query:`/`passage:` 前缀的原因。）
- **负样本几乎白送**：正样本的 query 配一段随机抽的文本 → 大概率无关 → 天然负样本，要多少有多少。

**怎么喂**：不是一条条，是成批自动流水线——① 爬海量文本自动切成"对" → ② 一批几千对，模型各自 encode → ③ 损失函数自动算正/负样本余弦对不对 → ④ 反向传播自动调参 → ⑤ 换下一批，重复几十亿步。**全程无人在环**，人只做两件事：设计"自动造对的规则" + 写损失函数。所以能 scale（瓶颈是算力/数据，不是人力）。

**批内负样本（in-batch negatives）**：一批 N 个正样本对，对第 1 对的 query 而言，其余 N-1 对的 passage 全当它的负样本 → 一批自动产生 N×(N-1) 个负样本，一份数据榨出海量对比信号，几乎零成本。

**人工标注还有吗？** 有但占比极小：**预训练**（学通用语义）几乎全自监督（海量、免费、脏但管用）；**微调/对齐**（冲精度）用少量高质量人工标注精修。规律：**海量脏数据（自动）打底 + 少量精标（人工）提纯**，绝大多数能力来自前者——正因为它不靠人、能 scale。

## 文本长度 → 向量维度（定长输出 / 池化 / 截断 / chunk）

疑问：一个字 vs 一篇文章，都转成 384 维吗？**是——输出永远固定 384 维，与输入长度无关。** 但有三层要点：

**① 为什么必须定长**：余弦只能比同维度向量。embedding 的使命就是把任意长度文本压成统一大小，才能互相比较。

**② 怎么做到长度无关——池化（pooling）**：内部是"每个 token 一个 384 维向量"，长文本 token 更多、中间向量更多；再用**池化**（常见 mean pooling=取平均）把 N 个向量压成 **1 个**。N 多少无所谓，平均完永远 1 个 384 维。
```
"养老储备"→3 token→[v1,v2,v3]  ；一段话→60 token→[v1…v60]   （每个 384 维）
                    │ 池化（取平均，N→1）
                    ▼   一个 384 维句向量
```

**③ 硬上限：最大 token 数（截断）⚠️**：模型有最大输入长度（e5-small≈512 token），**超出部分被悄悄截断丢弃**。一篇 2000 token 的文章，只有前 ~512 token 参与编码——"整篇进去了"是错觉。

**④ 即使没超限，长文压一个向量会"糊"**：一篇多主题长文压成一个向量 = 所有意思被平均成一团，检索变模糊。**这正是 RAG 要 chunking（分块）的原因**：长文档切成小段、每段单独 embedding，每个向量代表聚焦片段，检索才精准。（chunking 是阶段四后续主题。）

| 输入 | 输出 | 说明 |
|---|---|---|
| 一个字 / 一句话 / 一段（≤512 token） | 384 维 | 池化后定长、完整表达 |
| 一篇长文（>512 token） | 384 维 | **超出被截断丢弃** |

一句话：**输出定长（靠池化）、输入有上限（超了截断）、长文压一个向量会糊 → 长文档先 chunk 再逐段 embedding。**

## 向量空间与语义

把每段文本想成 **N 维空间里的一个点**（N=向量维度）。embedding 训练的结果就是：

> **意思近 = 空间里位置近。**

"养老储备"和"退休后的钱"会挤在一块，"科技股"在很远的另一片区域。于是"找意思相近的文本"就变成了"找空间里离得近的点"——一个纯几何问题。

## 点积与模长（余弦公式的两块积木）

### 模长 ‖a‖ —— 向量的"长度"

**每个分量平方、求和、开根号**，本质是勾股定理推广到 N 维：

```
2D:  a=[3,4]         ‖a‖ = √(3²+4²) = 5           （就是勾股定理）
N维: a=[a₁,…,aₙ]     ‖a‖ = √(a₁² + … + aₙ²)
```
numpy：`np.linalg.norm(a)`（= `np.sqrt(np.sum(a**2))`）。

### 点积 a·b —— 逐位相乘再相加，得到一个数

对应位置相乘再全部加起来，结果是**一个标量**：
```
a·b = a₁b₁ + a₂b₂ + … + aₙbₙ
[1,0]·[1,1]=1    [1,0]·[0,1]=0（垂直）    [1,0]·[-1,0]=-1（反向）
```
它衡量两向量**方向多一致（对齐程度）**——因为 `a·b = ‖a‖‖b‖cosθ`：一致→大正数，垂直→0，相反→负。

**为什么"逐位乘加"= 对齐？** 单看一项 `aᵢbᵢ`：同号→正（这个轴上一致）、异号→负（相反）；把所有轴的一致/相反加总，就是整体对齐度。

numpy：`np.dot(a, b)`。

### 隐藏联系：`a·a = ‖a‖²`

向量和自己点积 = 模长平方（自己跟自己夹角 0、cos=1）：`a·a = a₁²+…+aₙ² = ‖a‖²`。所以 `‖a‖ = √(a·a)`——点积是更基础的积木，模长是它的特例。

### 拼回余弦
```
cos(a,b) = (a·b) / (‖a‖·‖b‖)
         =  对齐程度(含长度) ÷ 各自长度 = 纯方向的一致性
```

## 余弦相似度

有了向量，要一个**数值**衡量两个点多"像"。最常用的是**余弦相似度（cosine similarity）**：看两向量的**夹角**。

```
夹角小 → 方向几乎一致 → 很像 → cos ≈ 1
垂直   → 不相关          → cos = 0
反向   → 相反            → cos = -1
```

范围 `[-1, 1]`。公式：

```
cos(a, b) = (a · b) / (‖a‖ · ‖b‖)
```

- **`a · b`（点积）** = `a[0]*b[0] + a[1]*b[1] + …`，衡量两向量"对齐"程度；
- **`‖a‖`（模长/范数）** = `sqrt(a[0]² + a[1]² + …)`，箭头长度；
- 除以两个模长 = **把长度归一化掉，只留方向（夹角）**。

**为什么只看方向、不看长度？** 向量长度往往反映文本长短等无关因素，**方向**才编码意思。两段话意思相同、一长一短，仍应算"很像"——除掉模长正好做到。

小例子：
```
a = [1, 0];  b = [1, 1]
a·b = 1;  ‖a‖ = 1;  ‖b‖ = √2 ≈ 1.414
cos = 1 / (1 × 1.414) ≈ 0.707    # 夹角 45°，中等相似
```

> 若向量已**归一化**成单位长度（模长=1），则 `cos = a·b`（分母为 1，省了）。

## 余弦公式怎么来的（和直角三角形 cos 的关系）

疑问：直角三角形里学的是 `cos θ = 邻边 / 斜边`，跟 `cos(a,b) = (a·b)/(‖a‖‖b‖)` 什么关系？

**答：是同一个 cos θ，只是一个"用角度算"、一个"用坐标算"。**

**① 直角三角形的 `cos=邻/斜` 定义的是角 θ。** 把向量 `a` 当斜边（长 `‖a‖`），向 `b` 方向作垂线，落在 b 上的影子就是邻边：

```
        a
       /|
 ‖a‖ /  |     θ = a、b 夹角；斜边=a（长 ‖a‖）
     /θ__|__→ b   邻边 = a 在 b 方向的投影 = ‖a‖·cosθ
```

**② 点积正好打包了 `‖a‖‖b‖cosθ`**：`a·b` = "a 在 b 方向的影子长度 `‖a‖cosθ`" × "b 的长度 `‖b‖`" = `‖a‖‖b‖cosθ`。两边除以 `‖a‖‖b‖`，就把角度单独解出来：`cosθ = (a·b)/(‖a‖‖b‖)`。**这就是余弦相似度——不是新定义，是用坐标反算那个 cosθ。**

**③ 为什么 `a·b = ‖a‖‖b‖cosθ`（用余弦定理证）**：对 a、b 张成的三角形，第三边是 `a−b`：
```
余弦定理： ‖a−b‖² = ‖a‖² + ‖b‖² − 2‖a‖‖b‖cosθ
坐标展开： ‖a−b‖² = (a−b)·(a−b) = ‖a‖² + ‖b‖² − 2(a·b)
两式相等 ⇒ a·b = ‖a‖‖b‖cosθ    ∎
```

**④ 为什么非用公式**：2D 能画图量角，但 embedding 是 384 维，"看"不到角。公式的价值 = **纯靠坐标（点积+模长）算出夹角的 cos，把"邻边/斜边"推广到任意维度**——这才能用在语义检索上。

## 关键词匹配 vs 语义检索

| | 怎么比 | 软肋 |
|---|---|---|
| 关键词匹配（`LIKE '%养老%'`） | **字面**词是否重合 | 问"养老"、文档写"退休储备"→ 一字不重合 → **漏掉**，尽管意思一样 |
| 语义检索（embedding + 余弦） | **意思**（向量空间位置）是否接近 | 需要模型编码，成本略高；但能跨字面匹配意思 |

这就是 RAG 用 embedding 而不用关键词的根本原因。（TF-IDF 是"高级一点的关键词匹配"——仍是字面词频，见 s4_03 的对照实验。）

### 真机对照实证（s4_03：同一 query、同一检索核心，只换 encoder）

| query | embedding | TF-IDF |
|---|---|---|
| 养老、能放很多年 | 养老2040 **0.89** | 养老2040 **0.17** |
| 能随时取、基本不亏 | 货币A 0.89 | 货币A 0.36、养老2040 **0.00** |
| 大波动博高收益 | 科技股 0.92 | 科技股 0.27、纯债 0.06 |

三个直击本质的观察：
1. **分数量级天差地别**（embedding ~0.9 vs TF-IDF ~0.0–0.3）：TF-IDF 向量没经对比训练，余弦读不出语义，只靠字面偶尔重合，202 维里绝大多数是 0 → 分数天生低。
2. **出现 `0.00`——字面零重合铁证**："随时取/不亏" vs 养老文档没有一个共同 bigram → 向量正交、余弦精确为 0。关键词匹配的死穴：**没共同的字＝毫无关系**，哪怕意思沾边也看不到；embedding 对同一对给了非零分。
3. **TF-IDF 命中也靠字面巧合**："养老"这条 TF-IDF 竟也命中养老2040，但只 0.17——因为文档恰好也含"养老"这个词；若文档只写"退休储备"，TF-IDF 就会像第 2 条那样掉到 0.00。**embedding 不依赖巧合，它认意思。**

一句话：**同一把余弦尺子、同一套检索核心，只换"怎么造向量"——差别不在检索，在向量有没有被训练赋予语义。**（呼应 [[为什么语义近-向量近对比学习]]。）

## embedding 打分特性（分数压缩 / 话题 vs 极性 / 为什么 top-K）

真机跑 s4_01 后观察到的"能用但不完美"特性——很实用的认知，别把语义检索神化：

**① 分数压缩在高窄带**：e5 余弦分数常挤在 0.7~0.95。**绝对值没意义，只有同一个 query 内部的相对排名有意义**。别拿"cos>0.9"当"很相关"的绝对阈值。

**② 抓"话题相似"强，抓"立场/极性对立"弱**：同领域文本（都在讲基金/投资/收益/风险）话题高度重叠 → 彼此都"挺像"，所以语义**相反**的也可能排很高（query"博高收益"检出"稳健纯债"）。embedding 抓 aboutness 好、抓细微极性差弱——小模型、短 query 更明显。

**③ 有时 top-1 都不对**：表层结构相似可能压过语义内容（"养老长期"query 命中"活钱短期"货基）。

**启示**：
- **取 top-K 不取 top-1**：#1 不总对，检索给若干候选、交给后面的 LLM 甄别（RAG 的"生成"半段）。
- 提升精度靠 **re-rank / 更大模型 / chunking**；small 模型"够学不够精"。
- "检索到底多好"该用 **eval 量化**（如 top-K 命中率），不是凭感觉。

## 完整 RAG 管线

```
【离线，只做一次】
  所有文档 ──encode──▶ 一堆文档向量，存起来（doc_vecs）

【用户每次提问】
  query ──encode──▶ query 向量
                      │
     对每个 doc_vec 算 cosine_similarity(query_vec, doc_vec)
                      │
            按分数降序，取前 k 个（top-k 检索）
                      │
   把这 k 篇文档塞进 prompt ──▶ 模型基于它们作答（生成）
```

对应 `scratch/s4_01_rag_embedding.py`：`CORPUS`（文档）→ `encode_docs`（向量化）→ `cosine_similarity` + `retrieve_top_k`（检索）。生成那步在 s4_02。

## Grounding（接地）与分层防御

**Grounding = 强制模型"只根据给定的资料回答，没有就说没有"**，不许用自己的先验瞎编。这是 RAG 防幻觉的核心——检索只负责"找资料"，grounding 负责"逼模型只用这些资料说话"。没有它，模型会拿检索结果当参考再掺私货，RAG 就白做了。

**检索召回 vs 生成精选（两段分工）**：真机 s4_02 观察到——检索返回的 top-K 里常混入不相关候选（embedding 分数不完美），但**生成阶段的 LLM 会二次甄别、挑真正匹配的**。所以检索负责**召回**（把对的捞进候选池），生成负责**精选 + grounding**。这就是"为什么取 top-K 不取 top-1"。

### ⚠️ 关键：grounding 靠 system prompt 是「软约束」，不是硬保证

跟"prompt 让模型输出 JSON""工具在 schema≠模型会用"是同一条铁律：**prompt 是恳求模型自律，不是机制保证**。这次答对不代表下次一定——换模型、换刁钻问法、检索结果更像时，模型仍可能张冠李戴或编一个产品。**所以关键系统要分层加固**，越往下越硬：

| 层 | 手段 | 硬度 |
|---|---|---|
| 1. prompt grounding | "只用清单作答、没有就说没有" | 软（靠自律）——性价比最高的第一道防线 |
| 2. 结构化 + 引用约束 | 让模型必须标注每句来自哪个产品（product_code / doc_id） | 中 |
| 3. **服务端校验（硬）** | 模型答案里提到的产品/数字，**代码去检索结果里核对**，查无此项就拦下/重生成 | 硬（机制保证） |
| 4. 兜底 | 校验不过 → 返回安全话术（"暂无"），不把可疑答案给用户 | 硬 |

**第 3 层才是真正的硬保证**，正是 [[03-agent-loop-lessons]] 那套"别信模型"在 RAG 的迁移：不信模型"answer 里的产品真来自清单"，用代码核对。生产做法——强制引用（只准输出候选集里的 product_code，服务端校验在不在集内）、provenance 核对（关键数字和检索数据比对）、NLI 校验（另一个模型判"答案是否被上下文支持"）。

一句话：**prompt grounding 让它"大概率照做"，服务端校验保证"照不做也拦得住"。有后果的系统永远要有第 3 层。**

## 工具库：numpy / sentence-transformers

s4_01 的两半：**sentence-transformers 造向量，numpy 拿向量算。**

### numpy —— Python 数值计算地基
- **是什么**：核心是 `ndarray`（N 维数组，连续内存+定类型）+ 一整套**向量化**运算，底层 C/SIMD，比 Python for 循环快几十上百倍。几乎所有 ML/数据库都建在它上。
- **embedding 就是 float 数组**，所以点积/模长/矩阵乘都靠它。
- 常用：`np.dot(a,b)`（点积）、`np.linalg.norm(a)`（模长）、`np.asarray(x)`、`x.shape`（如 `(7,384)`=7 篇×384 维）。
- **向量化** = 对整个数组一次运算而非逐元素循环：`a*2`、`np.sum(a**2)`——又快又好读。

### sentence-transformers —— 一行把文本变向量
- **是什么**：把 transformer 包装成"文本 → embedding"，`model.encode(texts)` 直接出向量。
- **建在** PyTorch + Hugging Face transformers 上，把「分词→过模型→池化成句向量→(可选)归一化」藏在 `.encode()` 后面。
- **模型**首次加载从 Hugging Face Hub 下载权重（几百 MB），缓存到 `~/.cache`，之后离线可用。
- `encode()` 默认**返回 numpy 数组**，正好交给 numpy 算余弦。

### 接力关系
```
model.encode(文本)  ──▶  ndarray 向量  ──▶  np.dot / np.linalg.norm 算余弦 → top-k
（造向量，黑箱）           （数据载体）        （检索核心，你的 TODO）
```
一句话：**sentence-transformers 把语义压进向量，numpy 在向量上算几何。**

## multilingual-e5-small（我们用的 embedding 模型）

拆名字：**multilingual**（多语言 100+，中英都行）+ **e5**（Microsoft 的 E5 家族，专为**检索**训练）+ **small**（尺寸档，还有 base/large）。HF id：`intfloat/multilingual-e5-small`。

**关键规格**：
- 输出 **384 维**；最大输入 ~**512 token**（超了截断）；权重 ~470MB，CPU 可跑。
- **encoder-only**（类似 BERT）：活是"文本 → 向量"，**不生成文字**。和 Claude（decoder，生成文字）是两类不同的模型。

**为什么要 `query:` / `passage:` 前缀**：E5 用**对比学习**训练——喂大量"查询-文档"配对，学会"匹配的 query 与 passage 向量靠近"。训练时两者就带不同前缀，用时必须照做，否则和训练分布不一致、检索质量掉。**前缀是模型"从小被这么教"的，不是随便加。**

**尺寸档取舍**：

| 档 | 参数/维度 | 取舍 |
|---|---|---|
| small | ~118M / 384 | 快、省、够用（学习期选它） |
| base | ~278M / 768 | 中等 |
| large | ~560M / 1024 | 质量最好，但慢、占内存 |

一句话：E5 家族的**多语言、小号、专为检索训练**的 embedding 模型，输出 384 维、encoder-only，因对比训练需 `query:`/`passage:` 前缀。

## 生成模型 vs embedding 模型（输出不同）

"模型的输出"是什么？**取决于哪类模型**——你接触的两类模型输出**完全不同**（容易混，因为一直用的 Claude 输出是文字）：

**① 生成模型（Claude，decoder）——输出是文字**
```
输入 "适合养老的产品有哪些?" → 输出 "根据您的情况，推荐养老目标基金……"   ← 文字，给人读
```

**② embedding 模型（e5，encoder）——输出是向量**
```
输入 "适合养老的产品" → 输出 [0.02, -0.11, …]   ← 384 个数，给机器算相似度
```
它**不会说话、不回答问题**，只把文本压成一串数。所以"e5 输出 384 维"说的是 ② 的输出，**跟"回答用户的文字"无关**——e5 压根不产生文字。

| 模型 | 类型 | 输入 | 输出 | 给谁用 |
|---|---|---|---|---|
| Claude | 生成（decoder） | 文本 | **文字** | 人读 |
| e5 | embedding（encoder） | 文本 | **向量（384 个数）** | 机器算余弦 |

**RAG = 两类接力**：embedding 模型负责**检索**（把文档/query 变向量、找最像的），生成模型负责**作答**（基于检索到的文档输出文字）。s4_01 练前半段（检索），s4_02 接后半段（生成）。

## 参数 vs 维度

结论：**参数是"模型内部有多少个学出来的数"，维度是"输出向量有多长"——一个说模型多大，一个说输出多宽。**

- **参数（parameters）**：模型内部**学出来的权重**，训练就是调这些数。它们**就是模型本身**（知识编码在里面）。数量 = 容量/大小，越多越强但越慢越占内存。e5-small ≈ **1.18 亿**。类比：工厂里所有**旋钮**的总数。
- **维度（dimension）**：embedding 语境里 = **输出向量长度**（e5-small=384）。是产出**表示的规格**，不是内部权重数。类比：工厂产出的**产品规格**。（对 e5 这类 encoder，384 也是其内部每层宽度 hidden size。）

### 参数长什么样（从 2 个到 1.18 亿个）

最简单的模型就是**一条直线** `y = w·x + b`——`w`、`b` 是参数，**这个模型就 2 个参数**。训练学到 `w=2, b=1` 后：输入 x=3 → 输出 7；x=10 → 输出 21。"训练"就是拿一堆数据点不断调 w、b 让线拟合好，调好就写死。

**10 个参数** = 9 个特征的线性模型：`y = w1·x1 + … + w9·x9 + b`（9 权重 + 1 偏置）。这 10 个学出来的数就是模型的全部"知识"。

e5-small 完全同理，只是参数从 10 个变 **1.18 亿个**、堆成很多层、输入是文本、输出是 384 维向量。

> **关键区分**：**参数固定**（训练完写死，对任何输入都一样那一堆数）；**输出随输入变**（不同文本 → 不同向量）。类比函数：参数 = 函数体里写死的系数，输出 = 传入具体输入后算出的返回值。同一公式（参数不变）喂不同输入得不同输出。

| | 参数 | 维度 |
|---|---|---|
| 衡量 | 内部有多少学出来的数 | 输出向量多长 |
| 关于 | 模型大小/容量（内部） | 输出规格（外部） |
| 随输入变？ | 不变（固定） | 长度不变，值随输入变 |
| e5-small | ~118M | 384 |

**联系（关键）**：两者相关但不同。E5 阶梯 small(118M/384) → base(278M/768) → large(560M/1024)，参数和维度**一起变大**。机制：transformer 每层权重矩阵约 `维度×维度`，所以
```
参数量 ≈ 维度² × 层数 × 常数（+ 词表相关）
```
**维度是参数量的一个来源**（维度翻倍那部分参数约×4）。所以"大模型往往也高维"，但一个描述**模型规模**、一个描述**输出宽度**，不是同一回事。

## 常见追问

- **384 维哪来的**？模型设计时定的（e5-small=384）。维度越高表达越细，但更慢更占空间。
- **为什么用余弦、不用欧氏距离（直线距离）**？文本检索里方向比长度更代表意思，余弦对长度不敏感；归一化后两者其实等价。入门默认"文本语义检索用余弦"。
- **向量库（Chroma / FAISS 等）干嘛的**？把"存一堆向量 + 快速找最近的"工程化。几百万条时不能像 s4_01 那样 for 循环全算一遍，需要专门的近邻索引。我们先用 numpy 手算，看清它内部在干嘛。
- **e5 的 `query:` / `passage:` 前缀**？e5 系列约定：文档编码加 `"passage: "`、查询加 `"query: "`。不加检索质量明显下降——真实且非直觉的坑。
